# The core-application blueprint (T93)

One application on the lean base (LVGL, Freeze only) that every core without Gideon's Ultimate application runs. This
build serves every core whose `core.toml` says `app = "blueprint"`: the A500 and the A1200 (Amiga), atari800, nes, apple2, zx, zxnext, cpc, vc20, c264, c128, pet, snes, neogeo, c64scpu, diag and the two DDT demos. Only the C64 reference core (`trx64g.cor`) runs Gideon's Ultimate application; `trx64u.cor` runs our own application (the VC-20 and the C16/Plus/4 left Gideon's application on 2026-10-22, Alex; the A500 uses the blueprint since T93).

- `src/` the shared services: start and identity (`start.cc`), the hand-over (`host-app/software/hostapp/handover.*`), settings
  and the `.cfg` format (`settings.cc`, `cfgfile.cc`), the ROM manager (`romfind.cc`, `boot.cc`), the whitelist menu (`menutree.cc`,
  `menuctl.cc`), the video service and Freeze (`video.cc`, `freeze.cc`), the board glue (`hw.cc`, `fm_fs.cc`, `ui.cc`, `run.cc`) and
  `coreapp.cc` (the program).
- where the rows the application adds stand (T239.3 D32): `base_ui.toml` holds, for every such row, its route (area, tab, heading), its setting group and its order; `tools/gen_base_ui.py` compiles it into `src/base_ui.inc`, which `menutree.cc` includes, and `src/base_rows.inc`, which `menubuild.cc` includes. A core's UI TOML places a base row elsewhere with `[[place]]` (and its own blocks with `[[group_route]]`); `menubuild.cc` and `bundle.cc` give the rows their groups, `menutree.cc` routes and orders them. The rows themselves (label, key, kind, values, default, and the provider of a list that changes at run time) are in `base_ui.toml` too; the extend functions of `picture.cc`, `volume.cc`, `tone.cc`, `mediamounts.cc`, `home.cc`, `hotkeys.cc` and `baseset.cc` take them from `menu_base_row` and keep what a row cannot say (whether a core gets it, a default the core's map sets, a provider's values, the operations).
- the service layer (T104.1): `ops.*` the registry of operations, state and events, `exec.*` the executor and the core lock, `service.*` a
  contributor's poll task, `ops_glue.*` how the descriptor, the menu and the boot code call by name. The descriptor holds operation names,
  not functions; each core registers its own as a built-in contributor.
- USB gamepads (T156): `hidpad.*` the HID report descriptor parser and report decoder, `pad.*` the pad service (two pads in plug order, the map per core button, the register pair per player, the capture of "Map buttons"), `pad_ops.cc` its operations and states. A descriptor's `pad` record (`PadSpec`) opts a core in (NES, SNES); the USB driver's hook is `usb_hid_set_pad_sink` (host-app/software/io/usb/usb_hid.*), registered in `run.cc`.
- the loader (T104.1 D10-D12): `libfmt.h` the .u2a format 3, `libapi.h` what a library sees and returns (`lib_register`), `libload.*` the
  loader (checks, placement, relocation, registration, rollback). Libraries are built with `app/lib/lib.mk` and packed by `tools/u2a_pack.py`;
  `tests/loader/run.sh` runs the loader against a model of the heap. Wired to the board: `libboard.cc` loads the libraries of `<root>/trx/lib` and of the `.cor` at every start (`lib_board_load`, called from `run.cc`).
- the drive library (T104.1 D15, built 2026-10-22): `app/lib/cbm1541/` (`d1541_gcr` the disk in memory, `d1541_wd` the 1581's controller, `d1541_drive` the drive, `d1541_fs` a .d64 / .d81 as a read only folder) is portable and pure; `cores/cbm1541.cc` is its contributor (`drive.*` operations, states `drive.drive_a.*`), `cores/cbm1541_desc.h` the descriptor pieces a core with the capability `drive_a` splices in (VC-20, C264, C64). `CoreIo` has the drive window (`drv_rd/drv_wr`, `ddr_abs_*`, `drv_buffer`). Built in, not loaded; spec T104.1 5.7.
- new disk images (T122): `newfile.*` where a new file goes and under what name (the folder the menu is on, a free name, never over a file; the 1541 drive uses it too), `newdisk.*` the builders for a blank Apple II DOS 3.3 `.dsk`, Amiga OFS `.adf`, Atari DOS 2.0S `.atr` and CPC `.dsk` and the operation `disk.create` (the 1541's own are in `app/lib/cbm1541`).
- the write-back service (T154): `writeback.*` what a game writes to its cartridge or battery RAM goes back to the user's file - Off / Ask / Auto, quiet time, flush before reset / eject / core change / power-off / menu open, NAME.tmp and NAME.bak; `writeback_crt.*` the .crt writer. A core registers its medium and reports changes with `wb_mark()`; the C64's flash and EEPROM path is `cores/c64_cart.cc`.
- `cores/` one translation unit per core: its descriptor and hooks, next to that core's register constants. Media code a core owns sits beside
  it: `tape_pulses.*` (a .tap/.tzx/.cdt as the pulse stream of the Spectrum's and the CPC's tape engine) and `tape_deck.*` (insert, play, blocks,
  eject: shared by `zx.cc` and `cpc.cc`), `zx_snap.*` (.sna/.z80), `cpc_disk.*` (the two DSK drives with write-back), `cbm_run.*` (Run PRG and
  Load PRG of the VIC-20 and the 264: the job around the PRG library, shared by the VIC-20's library `cores/vc20/app/lib/vc20.cc` and `c264.cc`).
- `tools/build_coreapp.sh` builds it (`--dist` copies the image to `dist/coreapps/atari800.app`, `nes.app`, `apple2.app`, `zx.app`, `cpc.app`, `zxnext.app` and `c264.app`: one image, D14 (the VIC-20 has an app of its own since V-4, `tools/sdk_core_app.sh`), the core
  is chosen at run time from the ID block; the Amiga names stay untouched).
- `tests/coreapp/run.sh` runs the logic natively with a negative control per test.
- `libs/shared.toml` is the TOML B of the shared app (T239.3 D31, P3-1): the libraries the app is linked with (sources, headers, the entries each hands the generic application). `tools/libtab.py` makes the library table
  (`libtab_table.cc`, walked by `src/libtab.cc`) and the list of library sources the core app Makefile compiles from it; `libtab.py lint` (ci/lint.sh) and `libtab.py symcheck` (ci/trxapps.sh) check that
  no generic source or object names a library. The generic application calls `libtab_*` and no function of a library.
  A library whose code a generic source needs too gives its table to that source with its `bind` entry, and the generic source calls the table only: the sector engine (`sectors.cc`) mounts a folder through `folderhd_api.h`, the
  file manager's CoreFs (`fm_fs.cc`) seeks through `fastseek_api.h`, the network file system (`netfs.cc`) reaches FTP through `ftp_api.h`. Without the library the call is refused with a reason (or, for the fast seek, the file seeks the normal way).
  The two string helpers of `newfile.h` that menus and cores use (`nf_base`, `nf_copy`) are `textcopy.h`, generic; the media engines `sectors.cc` and `winslot.cc` are the base's own (engines, mounts and descriptors use them) and stay generic.
  Besides the entries that run at a point of the start, a library gives the generic application its call table (`table`, found by `libtab_table(name)` with no loader; its header `*_api.h` is the seam), and a library that has to follow the core's
  description has `core` (run.cc calls `libtab_core` before and after the bundle is read). The USB mouse ("mouse", `mouse_api.h`), the gamepads ("pad", `pad_api.h`, with `hidpad`, the mapping wizard, XInput and its USB driver),
  pad as keys ("padkeys", `padkeys_api.h`) and the C64U's audio resampling ("resample", `u64_resample.h`, called by `u64cfg.cc`) are libraries of it (T239.3 L-1); the native builds give the tables in `tests/coreapp/libtab_native.cc`.
