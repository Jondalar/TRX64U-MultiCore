## §1 The problem

**Who.** A user with a C64U or U64 Elite II and our host. A core maintainer who wants his core found. The release process of this repository.

**What they try to do.** The user wants to pick a core in the host menu, have it installed into `<medium>/cores/<core>/`, and start it. The user wants the same for a host update. A maintainer wants to publish a core by a pull request, without a build in our CI (T239 D4, D5).

**What happens today.**

- The host has no TLS client. The host app builds against Gideon's lwIP (`vendor/gideon/software/lwip`); `host-app/software/network/config/lwipopts.h` has no `LWIP_ALTCP` define. No mbedTLS source is in the tree (a find over the repository for `*mbedtls*` returns nothing). The lwIP tree has the altcp TLS glue (`altcp_tls.h`, `altcp_tls_mbedtls_opts.h`) but not the library.
- The host has no outbound HTTP client. `vendor/gideon/software/lwip/src/apps/http/http_client.c` exists in the tree. No host app source calls it. The network sources under `vendor/gideon/software/network` hold an FTP client (`ftp_client.cc`) and a server (`httpd.cc`), no HTTPS.
- GitHub serves release assets over HTTPS only, and answers with a redirect to another host.
- Certificate validity needs a wall clock. `host-app/software/network/sntp_time.cc` sets the RTC from NTP; the NTP setting can be turned off (`CFG_NETWORK_NTP_EN`).
- The host has no entropy source. The upstream issue GideonZ/1541ultimate#952 says the main CPU has none and that lwIP's `LWIP_RAND()` is an unseeded `rand()` (read 2026-11-19 with `gh issue view 952`). The null core's register block (`cores/null/null_regs.v`) holds ID, CAPS, CAPS2, BUILD, IRQ_EN, IRQ_CAUSE and the pixel page 6; every other address reads 0.
- The release package carries trx64u and trx64g through `release/imports/*.pin` (`ci/package.sh:208` loops over the pins, `tools/pack_import_cor.sh` packs them). `release/imports/` holds `trx64g.pin` and `trx64u.pin`.
- A core reaches a user today by the release package or by hand onto the SD card. No list of cores exists outside the package.

**Facts of the host that bound the design (read from the code).**

- The host app is RISC-V `rv32im` with `-mno-div` (`host-app/target/u64ii/riscv/hostapp/Makefile:9,230`), built with `-DCLOCK_FREQ=100000000` (line 231): 100 MHz.
- The app image goes into the flash slot at 0x220000, at most 0x1E0000 - 12 = 1,966,068 bytes (`tools/check_app_size.py:15-17`; `host/bootrom/bootrom.c:74`). The last size recorded in a spec: `hostapp.app` 902,416 bytes, 1,063,652 bytes of the slot not used by that image (`docs/specs/done/T184-wifi-in-host.md:140`). The image is a figure of that day, to be measured again.
- The app runs from RAM at 0x30000 with a region of 0xE60000 bytes (`host-app/target/u64ii/riscv/hostapp/linker.x:7`); the heap ends at the top of that region (lines 172-174, 255). lwIP's own heap is `MEM_SIZE` 16384 (`lwipopts.h:113`), `TCP_WND` 5 x 1460, `TCP_SND_BUF` 16384.
- A DFX core fits one host build only. The host refuses a manifest `host_key` of another build with `COR_ERR_HOST` (`host-app/software/hostapp/cor.cc:285`, T84 D5b). A large core has neither `contract` nor `host_key` (`cor.cc:232`).
- A `.cor` manifest already holds `id`, `name`, `version`, `fpga`, and the per-part SHA values (`cor.cc:152,225-267`).
- The host starts a core from the menu on the trust of its entry, with the SHA-256 of the bitstream checked once at import (`docs/specs/done/T115-full-bitstream-cores.md`, D10, Alex 2026-10-28).
- Applications are loaded without a signature check (`docs/specs/done/T104.3-applications.md`, Q3, Alex 2026-10-26).

**Why it matters.** Without the registry every core stays in our package and in our CI (T239 D1, D4). Without TLS in the host the registry cannot be read from the board (T239 D6). Without entropy a TLS handshake is not safe: an unseeded generator makes the client random, the key exchange and any signature nonce predictable.

**Parts (MECE).**

- **P1 The registry form.** What the repository is, what an entry holds, how an entry gets in, where the files are hosted.
- **P2 The trust model.** What the host checks before it writes and before it starts. Reported from the earlier decisions; the open points are questions.
- **P3 The host transport.** A TLS client in the host app: library, size, CPU time, CA roots, redirects, wall clock.
- **P4 The entropy.** A true random generator in the null core and its use as the seed of the DRBG.
- **P5 The host menu flow.** Browse, install into `<medium>/cores/<core>/`, update, the red state of a DFX core that does not fit.
- **P6 The release package.** TRX64 leaves the package once P1-P5 work; the package is then host and our cores.
- **P7 The refusal paths.** What the host does when TLS, entropy, network, clock or a check is missing: it says so and writes nothing.

## §3 Decision

Epic decisions that apply (no new decision here):

- **T239 D3:** a DFX core that does not fit the installed host stays visible, marked red.
- **T239 D5:** a core in its own repository is resolved through the core registry, not pinned, built or shipped by us.
- **T239 D6:** the host reads the registry itself, from the host menu; the host needs a TLS client.
- **T239 D7:** the hardware TLS needs goes into the null core: a true random generator (ring oscillators with health tests) seeds mbedTLS's DRBG; AES/SHA only if a measurement asks for them; the static routing and the host key stay.
- **T239 D8:** one central registry first: a GitHub repository with an index file, entries by pull request that the maintainers review. Several registries later, if a community forms.
- **T239 D9:** TRX64 comes from the registry; the package stops carrying trx64u/trx64g. Until the host reads the registry, the pins stay.
- **T239 D13:** this spec is step C, after A, D and B.
- **T192 D24 and T213 D4:** no per-core code in `coreapp/` or `uicore/`; `tools/check_d24.py` and `tools/d24_ledger.txt` stay green. The registry flow is in the host app (`host-app/software/hostapp/`), not in the core app, and holds no per-core name.

Facts for the questions below (reported, not decided):

- The trust model of the earlier decisions: T115 D10 trusts a menu start after the SHA-256 at import; T104.3 Q3 has no signature check for applications. The registry adds one new step: the index and the file arrive over TLS, and the index holds the SHA-256.
- The host key of the running host is `cor_host_key` (`cor.cc:285`); the null core reads it as `build` (`null_regs.v`).

- **T239.4 D1 (Alex, 2026-11-19): the SHA-256 in the index, read over TLS, is the whole trust model.** The anchor is our review of
  the pull requests into the registry repository (T239 D8); TLS protects the way; no signatures (as T115 D10 and T104.3 Q3). A
  signature on the index can be added later. Asked against "we sign the index" and "every maintainer signs his entries"; Alex:
  "1".

- **T239.4 D2 (Alex, 2026-11-19): host updates come from the same index, as a kind of their own.** An entry of the kind `host` (the
  host's own update file `.txu`) may be added by the host team only (CODEOWNERS on the host entries); the host menu says when a
  host update is there. Asked against a separate index for host updates and "no host updates through the registry"; Alex: "1
  unbedingt" (1, definitely). Narrowed the same day (D3): no `.cfw` or `.ue2` in the registry.

- **T239.4 D3 (Alex, 2026-11-19): the board downloads only from GitHub, and the registry holds no `.cfw` or `.ue2`.** An entry's
  file is a GitHub release asset (and its redirect target), so the host needs only the roots of the GitHub chains. The installer
  files `.cfw` and `.ue2` (installing from a stock firmware) stay on the GitHub release page only. Asked "only GitHub" against
  "any HTTPS server" (then the full Mozilla store); Alex (translated): "then 1 for now, but please: no .cfw/.ue2 in the registry.
  That is only on the release page on GitHub for download."
