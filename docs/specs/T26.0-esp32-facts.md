## 0. Headline

1. The C64U/UE2 firmware is ESP-IDF 5.3.1 for **ESP32-S3**, 8 MB flash configured, no PSRAM enabled, **no OTA partitions, rollback compiled out of the bootloader**. One image set only (bootloader + partition table + u64ctrl.bin).
2. **There is no standalone, ready recovery path today.** The code that can flash the ESP32 (`Esp32::Download/Flash`) exists, but (a) it is compiled out of the application (`-DFLASH_EXTRA_PROTECTION`), (b) it is in Gideon's updater only as the tail of a full update that first rewrites the FPGA flash, (c) our `update_trx` has `NO_ESP`, and (d) our TRX64 bitstream does not wire `WIFI_BOOT`/`WIFI_DIS` at all, so even the code could not reset the ESP into its ROM loader on our core.
3. `jtag.c` can already do PROGRAM / CFG_IN / START (`jtag_configure_fpga`) but it is dead code: no caller, no RPC, the bitstream embed line is commented out in CMake. Bit-banged with `gpio_set_level`, so slow (est. ~1 MHz TCK, to be measured).
4. The decisive unknown is the **external default of the two regulator-enable lines** while the ESP sits in its ROM loader / has no valid app. Everything else is solvable in software.

## 2. Partition table and images

* `APP/software/u64ctrl/partitions.csv`: `nvs 0x9000/0x6000`, `phy_init 0xf000/0x1000`, `factory app 0x10000/3M`. Prebuilt `partition-table.bin` matches (factory size 0x300000).
* **No `otadata`, no `ota_0/1`.** `grep` for `esp_ota`/`esp_partition`/`app_desc`/`mark_app` in `u64ctrl/main`: no hits. `sdkconfig:415` `# CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE is not set`, `:409` factory-reset GPIO not set, `:410` app-test not set. Bootloader WDT 9000 ms only guards the bootloader phase (`:412-414`); task WDT 30 s, no panic (`:1116-1119`).
* **Consequence for the concept:** rollback needs a *new bootloader* (flashed at offset 0) and a new partition table. The bootloader is the one part of the ESP flash whose corruption leaves only the ROM loader; the ROM loader still works, but then the FPGA must be alive to use it (see 4). Alternative without a new bootloader: `factory` stays, our image goes to a new `ota_0` plus `otadata`; without rollback support recovery means erasing `otadata` over the ROM loader (selects factory again). Either way the partition table changes, so the table write is a brick-relevant step.
* Images actually on the module: **one set**, written by `APP/software/application/update_u2p/update_u64ii.cc:55-60`: `bootloader.bin@0x0`, `partition-table.bin@0x8000`, `u64ctrl.bin@0x10000`. Not written: `phy_init` (0xf000) and `nvs` (0x9000). NVS therefore survives updates and holds power mode / wake-on-WiFi / recent APs (`power_state.c:14-17`, `wifi_modem.c:331`). `u64ctrl.bin` = 845,072 bytes.
* Version identity: `IDENT_STRING "ESP32 WiFi Bridge V1.14"` (`rpc_dispatch.h:29-37`). The updater flashes only if the module's version differs (`update_u64ii.cc:75-98`).
* Shipped originals (string search in the files, not decoded): Gideon `update_v3.14.ue2` = V1.8; Commodore `c64u_v1.1.0.ue2` and `update_v3.14d.ue2` = V1.11; our current build = V1.14. Which one is on the board: read via `CMD_IDENTIFY` (read-only, `wifi_detect`).
* The updater's flash params tell the ROM loader **2 MB** (`esp32.cc:339-344`, `0x200000`), not 8 MB. Fine for offsets below 0x200000 (all of today's writes end below 0x100000). Writing to offsets above 2 MB through this routine may be refused by the ROM; not determinable from code, needs a test (matters if ota_1 sits high).

## 3. How the ESP32 is flashed today

All in `APP/software/io/wifi/esp32.cc` (our tree) with the `ModuleCtrl` register in `software/io/uart/dma_uart.cc:107-112`.

Sequence (`Esp32::Download`, lines 234-350, via `Boot()` 157-169 and `Disable()` 83-91):
1. `ModuleCtrl(ESP_MODE_OFF)` (`esp32.h:19`: U64==2 value 3), wait 150 ticks, UART 115200 8N1, no flow control, SLIP off, `ModuleCtrl(ESP_MODE_BOOT)` (value 1). Register bits: `uart_dma.vhd:314-320` (`flowctrl` bit4 = boot, bit5 = enable, bit6 = route); the app writes `mode << 4` (`dma_uart.cc:110`). Reset values `uart_dma.vhd:414-416` (boot=1, enable=0, route=0).
2. Waits 100 ticks and reads the boot text; looks for the string `DOWNLOAD` in the first 100 bytes; up to 3 tries, else error -7 (`esp32.cc:249-280`).
3. SLIP on; sends the 44-byte `SYNC` frame (`0x08`, `07 07 12 20` + 32x `0x55`) up to 10 times, expects the 12-byte reply (`:286-301`).
4. `SPI_ATTACH` (0x0D) default flash (`:318-322`).
5. `CHANGE_BAUDRATE` (0x0F) to **2,000,000** at 100 MHz clock (666,666 at 66.7 MHz) (`:325-336`), UART divisor switched after the ACK.
6. `SPI_SET_PARAMS` (0x0B): 2 MB, 64 KB block, 4 KB sector, 256 B page (`:339-348`).
7. Per image `Esp32::Flash` (`:352-415`): `FLASH_BEGIN` (0x02, S3 variant with the 5th zero word, `:363-368`), then `FLASH_DATA` (0x03) in **1 KiB blocks** padded with 0xFF, checksum 0xEF-xor, ACK per block with 1 s timeout. `FLASH_END` is **commented out** (`:407-411`), so the loader stays in the ROM; the updater then calls `EnableRunMode()` (`update_u64ii.cc:69`, `esp32.cc:139-155`) which resets the module into the app.
8. **No verification.** No `SPI_FLASH_MD5` (0x13), no readback. The only check is the per-block ACK. Erase is implicit in `FLASH_BEGIN`.
9. Protocol = ESP ROM bootloader protocol directly (no esptool stub is uploaded). Baud 115200 -> 2 Mbit/s. Files/offsets: see 2.

Entry points that exist:
* Updater `update_u64ii.cc:49-72` (embedded images, only after rewriting the FPGA flash, `:177-179`, `:190-191`). Our `update_trx.cc` / `target/u64ii/riscv/update_trx/Makefile:134` has `-DNO_ESP=1` and never touches the ESP.
* File-browser entry **"Flash into ESP32"** for `*.ESP` files (`software/filetypes/filetype_esp.cc:48-51`, `execute` 82-169; file = repeated `{signature 0x4d474553 "SEGM", length, address}` + data, `:116-133`). It is compiled only without `FLASH_EXTRA_PROTECTION` (`:46-52`, `:79`). The C64U/U64-II application sets `-DFLASH_EXTRA_PROTECTION=1` (`target/u64ii/riscv/ultimate/Makefile:278`; SPEC-06 R3 `APP/doc/specs/SPEC-06-robustness.md:30-31`), so **the shipped application has no ESP flash code and no menu entry**. `Esp32::Download/Flash` are excluded at `esp32.h:64-67`.
* Upstream branch `tools/esp-probe` (UP) adds `esp_loader` ABI op 0/1/2 (`UP/software/app_loader/app_api_impl.cc`, `esp32.cc EnterLoader/LoaderCommand`) so a `.u2a` app can drive the raw ROM loader; only with `-DESP_LOADER_TOOL`. Not present in INTEG (grep: no hits). `UP/apps/esp_probe` uses it to load a RAM-only stub that bit-bangs JTAG and reads the FPGA IDCODE (no flash write; `Nutzungs.md`). **No hardware log of a run exists in either repo** (searched `*probe*.log`): treat the JTAG-via-ESP path as unproven on the board.

**Answer to "can the FPGA re-flash the original ESP firmware from a USB file with nothing else?"** Not with what ships. Missing pieces, all software/FPGA-side: (1) a small updater/app that takes a segment file (the `.esp` SEGM format or a `.ue2`-extracted trio) and calls Download/Flash, built with the ESP code in; (2) our bitstream must drive `WIFI_BOOT` / `WIFI_DIS` (see 7); (3) the image to restore, taken from Commodore's `.ue2` (V1.11) or our V1.14 build. The ROM-loader flash-write sequence is small (steps 1-7 above) and already written in `esp32.cc`.

## 4. Power control

* `pinout.h`: `IO_ENABLE_MOD 21`, `IO_ENABLE_V50 37`, `IO_5V_GOOD 12` (input), buttons UP 13 / DOWN 14, UART1 TXD 43 / RXD 44 / RTS 15 / CTS 16.
* Neither 21 nor 37 is an ESP32-S3 strapping pin (S3 straps: GPIO0, 3, 45, 46). After an ESP reset both float as inputs in the ROM loader unless the board has external pulls. **The external pull/default of both enable lines is not determinable from code.**
* u64ctrl boot (`control_main.c:184-198`, `button_handler.c:101-121`, `power_state.c`):
  1. `check_fpga()` (`control_main.c:167-182`): UART RXD input with pull-down, 100 ms, read level; high = "FPGA already running".
  2. `jtag_disable_io()` (all four JTAG GPIOs to high-Z inputs, no pulls, `jtag.c:121-132`), LED, ADC, `setup_modem()`.
  3. `power_initial_state(fpga_running)` (`power_state.c:130-159`): FPGA running -> machine stays on (1). Cold start: NVS `mode` (default **OFF**, `power_state.c:74`); ON / LAST_STATE otherwise.
  4. Button task: writes the output *level first*, then sets direction to output (`button_handler.c:114-117`, glitch-free handover), then `regulator_enable()`: on = V50 high, optional delay, MOD high, 100 ms, UART pins attached; off = MOD low, V50 low, UART pins to pull-down inputs (`:25-61`).
  So a cold start with the default mode leaves the machine **off** until a rocker press; the order on is V50 then MOD.
* Is the board powered while the ESP sits in its ROM loader? **INFERENCE (strong):** the updater runs on the RISC-V in the FPGA and calls `Boot()` (ESP reset via `WIFI_DIS`, then GPIO0 low) in the middle of its run (`update_u64ii.cc:49-51`, `esp32.cc:157-169`) and goes on to flash and prints results afterwards. That only works if the regulators stay on while the ESP is reset / in the ROM loader, i.e. the enable lines are held on externally, or the ROM leaves them as they were. `recovery/u64ii/README.md:109` also says parts of the board stay powered with the PSU connected (ESP32 listed). This does **not** answer the cold-start case: ESP powered, no valid app, FPGA never configured. If the external default is "off", a bad ESP image = dead board without loose wires. That is the exact risk in docs/boot-chain-concept.md and it is still open.
* Also: `uart_set_pin(UART_NUM_0, 0, ...)` (`wifi_modem.c:1047`) puts the ESP console TX on GPIO0 = the boot-strap net that goes to the FPGA's `WIFI_BOOT` side (`pinout.h:5` `IO_BOOT 0`). Worth knowing when probing that net.

## 5. JTAG

* ESP GPIOs: TMS 8, TDI 9, TDO 10, TCK 11 (`pinout.h:11-14`). FPGA balls per `UP/apps/esp_probe/Nutzungs.md`: TMS T13, TDI R13, TDO U13, TCK V12 (that table cites `pinout.h`, `jtag.c`, `recovery/u64ii/README.md`; the ball numbers are not in any constraint file, because dedicated JTAG pins are not constrained; they are the device's fixed JTAG balls: from the device pinout, not from code here).
* Header P5 (`recovery/u64ii/README.md:95-100`): TCK 1, TDO 3, TMS 5, TDI 9. That the P5 header and the ESP are on the same nets without a series switch/buffer: documented by that README plus the esp_probe notes, **not verifiable from code; needs a continuity check or the esp_probe IDCODE run**.
* `jtag.c` functions: `jtag_reset_to_idle`, `jtag_instruction`, `jtag_go_to_shift_dr`, `jtag_send_dr_data(+readback)`, `jtag_send_dr_data_rev` (MSB first, for configuration data), `jtag_get_id_code`, USER4 virtual-JTAG helpers (`vji_*`), `jtag_start/stop/disable_io`, `jtag_configure_fpga` (`jtag.c:363-376`): `reset_to_idle`, `PROGRAM (0x0B)`, 10,000 idle TCKs (fixed wait, **no INIT_B/DONE polling**), `CFG_IN (0x05)`, shifts `8 * (fpga_end - fpga_start)` bits raw (so the embedded file must be a header-less stream, not a `.bit`), `START (0x0C)`, 32 TCKs. `SHUTDOWN`, `IDCODE`, `EXTEST`, `CFG_OUT` are defined but unused.
* **Nothing calls it.** `jtag_start`, `jtag_stop`, `jtag_configure_fpga`, `vji_*`, `jtag_get_id_code` have no caller outside `jtag.c` (grep of `u64ctrl/main`); `rpc_dispatch.c:426-496` has no JTAG command (full command list `rpc_calls.h:185-209`, 0x01-0x19). `CMakeLists.txt:7` has the bitstream embed commented out. Whether the shipped binary even links `jtag_configure_fpga`: not needed to know.
* Speed: every TCK edge is `gpio_set_level()` (IDF function calls, 160 MHz CPU, `jtag.c:173-176`), three calls per bit. Expect order ~1 MHz TCK (INFERENCE; the concept's "2-10 MHz" is not supported by this code). 2.2 MB = 17.6 Mbit -> ~18 s at 1 MHz; direct register writes (`GPIO.out_w1ts`) would be several times faster. **Measure.**
* Power-on: `app_main` calls only `jtag_disable_io()` (`control_main.c:191`); no code drives JTAG at boot. (The note that JTAG activity at power-on stops the FPGA from configuring is from our memory notes, not from this code.)
* Sharing with the USB-Blaster/FT232H at P5: only by the ESP releasing its pins (`jtag_disable_io`, no pulls). Nothing in u64ctrl arbitrates; a guest-load RPC must switch the pins itself and restore them (as `Pinout-Plan.md` says: "Restore" and "Locking" are missing).

## 6. UART link FPGA <-> ESP32

* ESP side: UART1, `UART_BAUDRATE_INIT 5000000`, `UART_HW_FLOWCTRL_CTS_RTS`, rx flow threshold 122 (`my_uart.h:14-15`, `my_uart.c:403-408`); custom ISR driver with SLIP; rx FIFO full threshold 120.
* FPGA side (app): `wifi_command_init()` sets **5,000,000 baud** at 100 MHz (6,666,666 at 66.7 MHz) and flow control on (`io/wifi/wifi_cmd.cc:33-39`). `CMD_SET_BAUD (0x03)` can change both ends (`wifi_cmd.cc:44-70`, ESP `cmd_setbaud`); `WiFi::RequestEcho` tests up to 6.67 Mbit (`wifi.cc:121-160`). Before that 115200 for ROM boot/detect.
* Framing: SLIP in hardware (`slip_encoder`/`slip_decoder` instantiated in `cores/gideon/fpga/io/uart_lite/vhdl_source/uart_dma.vhd:145,211`, enabled by flowctrl bit 2). RTS/CTS active low, `uart_dma.vhd:267-273`; RTS = "RX FIFO not almost full".
* RPC header 4 bytes `{command, thread, sequence}` (`rpc_calls.h:17-21`). Packet buffers: payload **1536** bytes (+16 header) (`io/uart/cmd_buffer.h:12-14`), **12 TX + 12 RX** buffers (`:17-23`), same count on both ends.
* Throughput: wire limit 500 kB/s at 5 Mbit/s 8N1; SLIP escapes cost ~1% on random data. 2.2 MB -> ~4.6 s minimum, ~5 s realistic if the ESP consumer keeps up; with a 1.5 KB packet and a per-packet reply it will be slower (round trip). The ESP cannot buffer the file: 512 KB internal SRAM, no PSRAM. So either stream straight into the JTAG shifter under CTS/RTS flow control (then the JTAG speed in 5 is the real limit) or stage in ESP flash (unpartitioned space 0x310000-0x7FFFFF exists with the current table, but that is a flash write per guest load, rejected: wear and risk). No throughput measurement exists in the repo; the echo test exists but needs a run.

## 7. What our TRX64 bitstream wires for the ESP32

* `INTEG/designs/c64_basic/top.v:84-90`: ports `WIFI_TXD, WIFI_RTS` (out), `WIFI_RXD, WIFI_CTS` (in) only. `WIFI_BOOT`, `WIFI_DIS` are **not ports**. `pins.xdc:213-220`: only the four UART pins, RXD/CTS pull-ups; explicit comment says boot/dis stay unused (comment only; the code agrees: `ultimate_sys.vhd:~543-545` `boot => open, enable => open, route => open`, i.e. `ModuleCtrl()` has no effect). No `BITSTREAM.CONFIG.UNUSEDPIN` anywhere in `designs/c64_basic/*.xdc|build.tcl`, so L13/M13 get the tool default (weak pull-down; Vivado default, not set by us).
* Pin constraints exist in `INTEG/constraints/c64u.xdc:430-435`: `WIFI_BOOT L13`, `WIFI_CTS L14`, `WIFI_DIS M13`, `WIFI_RXD N13`, `WIFI_RTS N14`, `WIFI_TXD P14`, LVCMOS33 (`:150`). Same in `1541ultimate-tools/pinmap/c64u_gideon_issue615.xdc:430-435`.
* Gideon's U64-II top is binary only here. The only VHDL that maps `boot/enable/route` to pins is the U2+ top (`ultimate_logic_32.vhd:1311-1317`: `WIFI_BOOT`, `WIFI_ENABLE`, route muxes UART_TXD/WIFI_TXD). **Polarity and open-drain behaviour of `WIFI_BOOT`/`WIFI_DIS` on the C64U are not determinable from code**: the register values (BOOT=1, OFF=3, RUN=0, `esp32.h:19-22`) imply `boot_i=1` must mean GPIO0 low (BOOT) and `enable_i=1` means disabled; so the pin is either inverted or open-drain on the board side. Measure on Gideon's own core (boundary-scan SAMPLE with the existing tool while a diagnostic firmware calls `ModuleCtrl` modes), then wire ours.
* What our core is missing for Gideon's updater / ESP recovery: the two ports + XDC lines + `boot`/`enable` outputs in `ultimate_sys.vhd` with the right polarity (3-bit register already exists in the unmodified `uart_dma.vhd`). `route` is probably not needed for flashing (it swaps the UART to the other UART on U2+; C64U meaning unknown). Everything else (UART, 5 Mbit/s, RTS/CTS, SLIP, DMA) is present and used by the rocker events (`ultimate_sys.vhd:801-816`).
* Not in our core for T26 either: any JTAG master toward the ESP (ESP is the master; nothing needed).

## 9. Proposed recovery-proof procedure

Principle: **prove the way back before the first write**, and prove it first without touching ESP flash. Steps marked **[WRITES ESP FLASH]** are the only ones that do. Nothing below touches the FPGA flash (use the USB-Blaster/softboot SRAM path as today).

* R0 (offline, no board): extract the three original images from Commodore's `c64u_v1.1.0.ue2` (V1.11) and Gideon's V1.14 (our `UP/u64ii/*.bin`) and record SHA-256. Build the "restore" file in SEGM format for `filetype_esp.cc`. Also record what version the board reports (M1).
* R1 **[read-only]** Run the ROM-loader probe on Gideon's core: reset into the ROM loader through the app, read security info, chip id, strap/UART_DATE registers, flash size via register read. Confirms chip (M1), power survival in the warm case (M2), and that `EnterLoader` works on this board. Needs the `esp_loader` hook build (UP branch) loaded via softboot or the existing developer path, no flash write. The esp_probe RAM stub also gives M5 here; the stub is RAM only, a power cycle clears it.
* R2 **[read-only]** Measure M3/M4 with a multimeter and the existing boundary-scan tool. This decides whether a dead ESP app can be recovered with the FPGA at all. If the cold-case default is "regulators off", the recovery trigger must come from elsewhere, and the plan must change before any ESP write: options are (a) keep the Gideon bootloader and factory image untouched and add ours only as OTA with `otadata` (a bad OTA image falls back to factory via the bootloader's invalid-image path even without rollback), or (b) leave ESP flash alone entirely and use the RAM-only stub route (below).
* R3 **[read-only]** Wire `WIFI_BOOT`/`WIFI_DIS` in the TRX64 bitstream with the polarity from R2; check on the board with the stock V1.14/V1.11 ESP image that `ModuleCtrl(BOOT)` reaches the ROM loader (`DOWNLOAD` string, SYNC reply) and `ModuleCtrl(RUN)` returns to the app. Still no flash write.
* R4 **[read-only]** Build the standalone restore app/updater (with the ESP code compiled in; not in the normal application, SPEC-06 R3 stays intact). Dry-run mode: do everything up to `FLASH_BEGIN`, then `SPI_FLASH_MD5` (0x13) over the three regions and compare with the expected hashes. This also gives the missing verify step Gideon does not have.
* R5 **[WRITES ESP FLASH]** Restore test with the **original image over itself**: write bootloader, partition table, u64ctrl.bin (exactly what `update_u64ii.cc:55-60` writes), read back with `SPI_FLASH_MD5`, power cycle, confirm the ESP boots, `CMD_IDENTIFY` matches, power on/off and rocker events work. This proves the re-flash path end to end with known-good bytes (same content, so a failure mode is only the transfer, and the ROM loader can repeat it).
* R6 **[WRITES ESP FLASH]** Deliberately damage a *non-bootloader* region (e.g. write 4 KB of 0xFF over the start of `u64ctrl.bin` at 0x10000 through the same app), power cycle, observe the bootloader's failure behaviour (no valid app -> loop; does the board power up? M3 cold case), then run the restore app. This is the real proof; skip it only if R2 shows the cold case is safe by hardware (regulators held on).
* R7 Only after R5 (and R6): flash our firmware. Layout choice follows R2. Keep factory = Gideon's original, our image as OTA with rollback bootloader (this is the one extra write to offset 0x0, with R5/R6 proof already behind us), `confirm` timing short, power/rocker code untouched.

Alternative that avoids flash writes for the bring-up of "ESP loads bitstream into FPGA": a RAM stub (like esp_probe's) that receives the bitstream over the ROM-loader UART and shifts it via GPIO8-11, run from the ROM loader each time; nothing persistent changes, a power cycle always returns to Gideon's firmware. Caveats: the stub replaces u64ctrl while it runs (no rocker/power handling, no flow-control hardware in the ROM UART path unless the stub drives it), and the ROM UART runs at the baud set by `CHANGE_BAUDRATE` (2 Mbit/s in Gideon's code; ~1.1 s/MB at best => ~10 s for 2.2 MB before JTAG limits). Useful as the first end-to-end guest-load demo, and it makes R5-R7 unnecessary until we want the real OTA image.
