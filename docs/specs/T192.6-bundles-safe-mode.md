## §1 The problem

- **Who:** a tester or Alex at the TV with a C64 keyboard or a USB keyboard; a tester who wants the keys of the C64U or their own.
- **What they want:** pick another key set and colour scheme (and text mode) without rebuilding anything, and never be locked out by a
  wrong choice.
- **What happens today** (read from the code, not from comments): the key maps are code. Host: view switches F1/F3/F5/F7/F8 and V in
  `on_key`, per-view `if (k == ...)` chains, no table, no TOML, no remap (`hostapp.md` section 4; `hostui.cc`). Core app: the menu
  keymap is hard-coded in `MenuCtl::key` (`menuctl.cc` 2988-3258). Only the runtime hotkeys while a core runs are data (`HkMap`,
  `hotkeys.h:20-33`, `.cfg`), and those are a C64-matrix modifier map, not the menu's keys. The colour scheme is data (seven schemes,
  `trxview.cc` `k_schemes[7][11]`, `ui_set_look`). The record is TRXD v3 and has no bundle table (`coreapp.md` section 4). Nothing
  reads a key at host start except `menukeys.cc` (C= and port-1 fire, latched, for T135).
- **Why it matters:** C64U users carry muscle memory (C=+F3/F5 paging; D33, MC#34 on GitHub); testers should finish the "C64U classic" set
  themselves (D9); a remappable UI without a way back is a way to brick the menu.

Parts (MECE):
- **P1 Bundle content.** What a bundle holds: key set, colour scheme, text mode (no density, D10), and nothing else (no code, D9).
- **P2 File format and place.** The TOML shape and where the files live (SD/USB), for the two shipped bundles.
- **P3 Selection.** Host default plus per-core override (D5); where the choice is stored.
- **P4 Load and validation.** Edit on a computer, copy, restart (D9); a broken file falls back to the built-in bundle and says so.
- **P5 Protected keys.** What no bundle may remap, enforced at load.
- **P6 Safe mode.** C=+S held at host start (D7): how the host reads it before any UI and what it resets.
- **P7 Tester workflow.** How the testers finish "C64U classic" in the tester discussion.

## §3 Decision

Applying epic decisions (quoted):
- **D2 (Alex, 2026-11-07, translated: "Mine, TRX.")**: the default key set is the TRX64 grammar; "C64U classic" may be a selectable set.
- **D5 (Alex, 2026-11-07: "C")**: the interface choice is set in the host as the default; each core may override it for itself.
- **D7 (Alex, 2026-11-07, translated: "D: with T+R+X the host starts with the TRX key set .. or we think of something like C=+S, i.e. safe
  mode"; "make it C=+S")**: a key chord held while the host starts gives the built-in TRX interface; it does not clash with T177.
- **D9 (Alex, 2026-11-07, translated: "B, where we prepare B and then the testers in the tester discussion may work it out themselves ...
  it has to be testable: edit your TOML in an editor, copy it to the board, restart, see the result")**: TRX64 plus a prepared "C64U
  classic"; plain TOML; no build, no tool; a broken file must not lock anyone out.
- **D10 (Alex, 2026-11-07: "A")**: no density choice; a bundle is key set, colour scheme, text mode.

- **D11 (Alex, 2026-11-09, T192.3 D27, translated)**: there is one shared default key table for all cores (the left arrow in the Library goes one folder up everywhere); anyone who wants it different changes that line per context/core in the bundle. The per-context override is the bundle's job.

Design (this spec's choices, to be confirmed by Alex where §6 asks):

### Design

**B1 Bundle = data, three fields plus a key table.** A bundle file holds: `[bundle]` (name, version, title), `scheme` (index 0..6 of the
existing colour schemes), `text_mode` (`off` | `on`, only effective where T192.5 exists), and key tables mapping a key to an intent id of
T192.1. No density, no layout, no code, no widget (D10, D9, T104.3 D0). Layout stays the built-in templates. Where a bundle omits an
intent, the built-in TRX64 binding of that intent applies (so a short file is valid and "C64U classic" can ship unfinished).

**B2 Key tables are contexts.** The key map is a table per context, because both apps have per-context chains today: `global` (area and
page keys), `list` (rows, paging, +/-), `dialog` (confirm), `core` (keys of the core app that are not runtime hotkeys). Runtime hotkeys
while a core runs stay `HkMap` / `.cfg` (`hotkeys.h`); a bundle does not touch them (they are a matrix modifier map, a different
mechanism; see §4).

**B3 TOML format.** Key names: `F1`..`F8`, `RETURN`, `LEFT_ARROW`, `UP`, `DOWN`, `LEFT`, `RIGHT`, `DEL`, `ESC`, a single character, with
a prefix `C=+` (Commodore), `SHIFT+`, `CTRL+`. Intent ids are the stable ids of T192.1 (the ids below are placeholders until T192.1 fixes
them; the example shows the shape, not the final names).

TRX64 (the default; also compiled in as the built-in bundle):

```toml
[bundle]
name    = "TRX64"
version = 1            # format version of this file, not of the content
title   = "TRX64 (default)"

[look]
scheme    = 0          # 0..6, the seven existing colour schemes
text_mode = "off"      # off | on

[keys.global]          # host and core app, outside dialogs
"F1" = "nav.area.1"
"F2" = "nav.area.2"
"F3" = "nav.area.3"
"F4" = "nav.area.4"
"F5" = "nav.area.5"
"F6" = "nav.area.6"
"F7" = "nav.area.7"
"F8" = "nav.area.system"
"1"  = "nav.tab.1"
"2"  = "nav.tab.2"
"3"  = "nav.tab.3"
"4"  = "nav.tab.4"
"5"  = "nav.tab.5"
"6"  = "nav.tab.6"
"7"  = "nav.tab.7"
"8"  = "nav.tab.8"
"9"  = "nav.tab.9"
"LEFT_ARROW" = "nav.back"
"C=+SPACE"   = "search.open"        # T192.4, D3

[keys.list]
"UP"     = "list.prev"
"DOWN"   = "list.next"
"+"      = "list.page.down"
"-"      = "list.page.up"
"RETURN" = "list.activate"
"DEL"    = "list.delete"

[keys.dialog]
"RETURN"     = "confirm.yes"
"LEFT_ARROW" = "confirm.no"
```

"C64U classic" (prepared skeleton for the testers; it loads and binds only what the C64U menu is known to do, the rest stays TRX64 per B1):

```toml
[bundle]
name    = "C64U classic"
version = 1
title   = "C64U classic (skeleton, testers finish it)"

[look]
scheme    = 0
text_mode = "off"

[keys.global]
"C=+F3" = "list.page.up"      # C64U muscle memory, D33 / MC#34
"C=+F5" = "list.page.down"
"F5"    = "action.menu"       # C64U: F5 opens the action menu; in TRX64 F5 is area 5
# TODO(testers): F1/F3/F7 as paging or as areas? F2/F4/F6? where do the TRX areas go?

[keys.list]
# nothing bound here yet: the TRX64 list keys stay
```

A key bound twice in one table is an error. An intent bound to two keys is fine. A key in one context shadows the same key in `global`
(most specific wins), as the code's per-view chains do today.

**B4 Where the files live, and the choice is stored.** Bundle files: folder `trx/bundles/` on the SD card; the same folder on a USB
stick is read when the SD card does not hold that bundle name (SD wins). File name = the bundle name with spaces as `_` plus `.toml`
(`C64U_classic.toml`); the `name` inside is what counts. Built-in: `TRX64` is compiled in and also written as an example file by the
shipped package (so a tester can copy it); "C64U classic" skeleton likewise ships as a file and is compiled in as a fallback so that
the selector lists it without a card. The host default is a setting `ui_bundle` in `host.cfg` (D5); a core's override is a setting
`ui_bundle` in that core's settings, value `host` (default, follows the host) or a bundle name. Both are chosen in a menu row
System > Interface (host) and in the core's settings; the row lists the built-ins plus every `*.toml` found. Exact folder is Q3.

**B5 Load and validation.** Load points: the host default at host start, after the safe-mode check (B7); the core's bundle when the core
app starts (it reads the override, else the host default). Never re-read while the menu runs (S9). The parser: strict, whole file or
nothing. It rejects: syntax error, unknown table or key (so `density` is an error), unknown intent id, unknown key name, a key twice in
one table, `version` newer than the build knows, a protected key remapped or unbound (B6), file over a size limit (value fixed in the
build; the limit protects the RISC-V heap, measure it). A reject means: the built-in TRX64 bundle is active, one toast "Bundle <file>:
<line>: <reason>", and the same line on System > Interface until restart. The stored name is kept (S18). The parser reads values; it
never uses a comment (the file's comments are for the editor's reader only).

**B6 Keys no bundle may remap.** RUN/STOP, Freeze, the reset chord, and C=+S itself. Enforced by the validator (reject whole file, S10)
and by the key router, which handles them before the bundle table is consulted (so even a table bug cannot take them away). The
confirm answers (RETURN yes, LEFT_ARROW no) are not protected by this list; they are in the built-in `dialog` table and a bundle may
rebind them as long as both a yes key and a no key remain (Q4).

**B7 Safe mode C=+S.** The host reads the keyboard matrix at start the way `menukeys.cc` samples C= and port-1 fire, before the bundle
load, before the UI exists and without a picture (the T177 situation: no pixel layer must still work). C= and S are both read from the
matrix registers the T135 sampler already uses; the sampler gets S as a third latched input (the build checks that the
register read for S exists; T177 Q2 shows the same kind of check for RESTORE). With both held: the host sets a session flag `safe`,
does not open any bundle file, and runs the built-in TRX64 key set, the built-in colour scheme, text mode off. Nothing is written
(S15): `host.cfg` keeps the user's choice, the next normal start uses it again. The flag is passed to the core app; while it is set the
core app ignores its override and the host default (S16). System > Interface shows "Safe mode active" and offers the way out: a row that
saves the built-in interface as the host default (that is the permanent reset). Order at power-on: T177 recovery (RESTORE+F1) first,
then the safe-mode sample, then the T135 direct-boot decision, then the bundle load. Chord conflicts: F1 and S are different keys, so
RESTORE+F1 and C=+S cannot be confused; C= is shared with T135, see Q2.

**B8 Tester workflow (D9).** The package ships both files and a short read-me text in the same folder. A tester edits "C64U classic"
in any editor, copies it to the SD card (FTP or USB stick), restarts the host, selects the bundle in System > Interface, and uses it. If
the file is wrong the menu says why (B5) and C=+S is the way back (B7). The tester discussion carries the finished bindings back; the
finished file replaces the skeleton in the repository.

## §4 Out

- Density or a "Large" size (D10).
- Code, a renderer, layout templates, fonts or free pixel values in a bundle (D9, T104.3 D0). A `.u2a` may carry a bundle only as the same
  data; no app-carried bundle format is added here.
- Runtime hotkeys while a core runs (`HkMap`, `hotkeys.h`): different mechanism (C64-matrix modifier pair, read by the host logic), stays as is.
- A bundle editor in the menu or on the web; no tool (D9).
- A third shipped bundle ("a C64 layout", D9 option C): only TRX64 and the C64U classic skeleton.
- Re-reading bundle files while the menu runs; a hot reload.
- A keep-or-revert timer for a key-set change (D7 chose the start chord instead).
- Safe mode from a running menu, or a second rescue chord; a power-cycle by software (never).
- Recovering from a broken host app or bitstream (T177 §4).
- Search-overlay keys inside bundles beyond the one binding of `search.open` (D3: C= SPACE only); the overlay owns every key while open.

## §6 Open questions

- **Q1 Safe mode: session only or saved?** D7 says the host "starts with the built-in TRX interface". This spec makes it session-only
  (B7) plus a row to save the reset permanently. Alternative: C=+S rewrites `host.cfg` to the built-in. Which one?
- **Q2 C= is also the T135 direct-boot key.** C=+S holds C=. Should C=+S then also act as the T135 "C= held" (skip direct boot, show the
  menu), or must safe mode swallow C= so direct boot runs as without it? (Proposal: it counts as T135 C=, because safe mode needs the
  menu.)
- **Q3 Folder and name.** `trx/bundles/` on SD (USB the same, SD wins). Any other place you want (next to `/SD/cores`)?
- **Q4 Confirm keys.** Protected list is exactly yours (RUN/STOP, Freeze, reset chord, C=+S). The UX analysis also wanted F8 (System) and
  the confirm answers unremappable. Add them, or keep the list as you gave it?
- **Q5 Scheme by number or by name.** The schemes have no names in the code today (index 0..6). Name them in the TOML (needs names
  from you) or keep the number?
