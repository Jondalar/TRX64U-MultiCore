## 3. Register map (derived, per voice, base `SAMPLER_BASE + 32 v`; C64: `$DF20 + 32 v`, v = 0..6)

Multi-byte values are **big endian** (byte at the lowest address is the most significant), as the players
write them. Reads: +0 status, +1 version, everything else reads 0 (write-only registers, as the manual says).

| Offset | W | Meaning |
|---|---|---|
| +0 | 1 | CONTROL: b0 enable, b1 repeat, b2 IRQ enable, b4 16 bit samples (else 8 bit). **0 -> 1 on b0 starts the voice from START** (a write that keeps b0 = 1 only changes repeat / IRQ: Heartbeat "loop with release" writes 0x11 over 0x13 and expects the voice to continue). b0 = 0 stops it and silences it |
| +0 (R) | | STATUS: b0 = IRQ pending (set when the voice ends, or wraps a loop, with IRQ enabled); no other bit |
| +1 | 1 | VOLUME, bits 5:0 (0..63) |
| +1 (R) | | VERSION = 0x01 (ours; the app never reads it, the players only print it) |
| +2 | 1 | PAN, bits 3:0 (0 left, 8 centre, 15 right; the app's player writes 8 by default, Xander writes nibble x 17) |
| +4 | 4 | START: byte address in DDR2 (bits 26:0; the REU is 0x01000000), MSB first |
| +9 | 3 | LENGTH in bytes (+8 ignored) |
| +E | 2 | RATE n: one sample every n x 160 ns (6.25 MHz / n) |
| +11 | 3 | REPEAT_A: byte offset from START where a loop restarts (+10 ignored) |
| +15 | 3 | REPEAT_B: byte offset from START where a loop ends (+14 ignored) |
| +1F | 1 | write: clear the voice's IRQ pending flag |

Voice 7 (SAMPLER_BASE + 0xE0) is reachable from the app only (the C64 window $DF20-$DFFF is 7 voices).
8 bit samples are signed (MOD data goes in untouched), 16 bit are signed little endian (Heartbeat).
Detection (Xander's `audio_detect`, and the app's cart does the same): ctrl 0 on all voices, write `$DF3F`, read `$DF20` 256 x = 0,
start a 256 byte sample, rate 1, ctrl 5 (enable + IRQ), the status turns 1 within 128 reads and stays 1; this is
what the engine does (rate 1 runs at the engine's speed limit, 1 sample per C64 cycle).

Semantics chosen where the sources do not say (all open for a board comparison, 8):
- A voice stops when `rel == LENGTH` (rel = byte offset from START of the next sample), IRQ if enabled. With
  repeat: at `rel == REPEAT_B` (B != 0) or at LENGTH the voice goes to REPEAT_A and sets the IRQ flag. Clearing
  repeat while playing lets it run on to LENGTH.
- 16 bit: addresses and lengths are bytes, the step is 2, bit 0 of START/LENGTH/A/B is ignored for 16 bit.
- Pan (Gideon's law, measured 2026-10-08): nibble p; p <= 7: L = T[p], R = 166; p >= 8: L = 166, R = T[15 - p];
  T = 0 24 47 71 95 119 142 166 (= 166 x p / 7). Both sides full at the centre ($7 and $8 alike), only the far side
  falls; pan 0 is the RIGHT lane loud (L lane silent), the app's mixer bytes then put it where Gideon's core does.
  Volume x pan x sample / 2^11, summed over the voices into a 23 bit signed value (SID scale: one voice at full scale = full scale, 2^19;
  8 voices can reach 8 x that). The mixer applies the app's "Vol/Pan Sampler L/R" bytes and saturates at 24 bit
  once. Not measured against a board.
- A rate below 7 behaves as 7 (the engine makes at most one step per C64 cycle = 6.34 ticks); 0 as 7; above 32767
  as 32767. The first sample of a started voice is fetched at once, the next one `rate` ticks later.
- Time base: the engine counts C64 cycles, 6.25 MHz ticks per cycle by System Mode: PAL 6.34375 (1624/256), NTSC
  6.1133 (1565/256), PAL-60 6.1055 (1563/256), NTSC-50 6.332 (1621/256), derived from the same clock ratios as
  trx_audio. The sampler therefore stops while the machine is stopped (freeze menu) and keeps its voices; the
  app can still write registers then.

## 4. Design (`cores/trx_sid/rtl/trx_sampler.v`)

One datapath for all 8 voices, in `clk2x` (= 64 clocks per C64 cycle, the frame), voice state in a distributed
RAM: 64 words x 32 bit (4 byte lanes with their own write enable), 8 words per voice. Words 0..5 hold the app's
register bytes exactly where the app writes them (CONTROL/VOL/PAN, START, LENGTH, RATE, REPEAT_A, REPEAT_B; the
bus never writes words 6 and 7, so the app's "clear" of +18..+1F cannot hit the state), word 6 is the phase
counter (ticks x 256, signed, less 1) and the low byte of the current sample, word 7 is `rel` (the offset of the
next sample from START) and its high byte. `run`, `chg` (started / stopped) and IRQ pending are 8 FFs each (the C64
reads the status in the cycle after the address, so it cannot wait for a RAM slot).

Frame schedule (clk2x clock t of 64, free running; a C64 cycle sets `adv`, so the voices only advance while the C64
runs, but the register file stays reachable; the voice the frame starts with goes round, so the one step per frame
is shared fairly):

| t | what |
|---|---|
| 0..39 | per voice 5 clocks: read the counter, read the rate, write the counter (- T per C64 cycle; when it turns negative a step is due and `+ rate`; at most one step per frame is accepted, the others wait a frame, nothing is lost), read the sample's high byte, read control / volume / pan; a multiplier pipeline (the one DSP, busy 4 clocks of 5): the sub-cycle blend of the sample (below), x volume, x L factor, x R factor (pan table above), accumulated in 23 bit. **Sub-cycle blend:** the counter holds the step instant to 1/256 of a 6.25 MHz tick, the output changes once per frame (6.34 ticks). The weight w (0..128) of the new sample in the step's cycle is `(-E-1) / T x 128` (shifts, +-0.4 %), taken when the step is accepted; it travels with the fetch (`sv_w`, `f_w`), when the sample lands the old sample and w go to `sold_m` / `sw_m`, and the next visit outputs `old + (new - old) x w / 128` (the time average of the cycle; w = 128 = no blend, also for a step that was already late when it was accepted) |
| 40, 41 | the pending register write from the C64 and from the app (one entry each; the app is acknowledged here) |
| 42, 43 | the sample that came back from DDR2 is written into its voice |
| 44..51 | the handler, one job per frame: a started / stopped voice (3 clocks: counter = -1, `rel` = 0, sample = 0) or a due step (read control, `rel`, LENGTH, B, A, START; decide wrap / stop / next address = START + rel; write `rel`; issue the DDR2 read) |
| 48 | the 23 bit L/R sums go to the mixer |
| 60, 61 | second chance for the two register writes |

DDR2: no new port. The sampler is one more client of the REU's port in `top.v` (`ddr2_port`, one 32 bit read
about 0.4 us); the REU keeps absolute priority (its command is taken "the clock it is offered"), the sampler is
served before the JTAG window. The word read comes back through a toggle handshake; one read in flight, so one
step per frame at most (about 1 M samples/s over all voices; 8 voices at 44 kHz use a third of it).

Mixer (`trx_audio.v`): inputs 2 and 3 (sampler L / R, 23 bit, signed) and a second 32 bit gain word (bytes 8..11),
the four products per side run one after the other through **one** multiplier instead of four in parallel (the
T25.3 mixer used four DSPs for two sources); the sums are the same arithmetic, bit exact with the old mixer when
the sampler is silent.

Bus: C64 side in `top.v`/`c64_core.v` next to the UCI (the slot-side outputs `io_ev*`, `bus_addr`, `io_oe`,
`io_dout`, `io_irq` are or-ed with the UCI's); app side `trx_io.v` page 8 (0x10048000..0x100480FF, aliased at
0x101A8000), a toggle handshake into the sampler; `ultimate_sys.vhd`: region decode for 0x10048000, the register
at cart page +0x0E (`C64_SAMPLER_ENABLE`), mixer bytes 8..11, capability bit 21.

- `tb_sm_io`: the app's path through the real `trx_io` page 8 with three unrelated clocks: version, status, the

## 8. Risks / board test

- Loop points: Xander's `modplay.c` hands **absolute** REU addresses to REPEAT_A/B (start + loop offset); the
  app's cart and Heartbeat write **offsets from START**. This design follows the two that agree. In Xander's MOD
  loops would not loop (the voice would run to LENGTH and stop) - first thing to compare on the board with
  UltimateDemo2026 music.
- Pan: 4 bit nibble (cart, Heartbeat, Xander x 17); Xander's "centre" 0x80 then reads as 0 = left.
- Absolute loudness and pan law are ours.
- Jitter: the step instant is exact to 160 ns / 256 and the step's cycle carries the time-weighted blend (SMP-KR fix,
  `spur.py`), so a single voice is within -94 dB of the ideal. A second voice due in the same cycle still waits one
  cycle for the handler (one job per frame) and then steps a whole cycle late (1 us, w = 128): with 3..7 other voices
  running the error is back at -67..-70 dB (`spur.py` INFO lines). The original works from a 6.25 MHz clock.
- 16 bit sample rate at the limit: max about 62 kHz per voice with 8 voices busy.
- Capability bit 21 turns on app paths that were dead before (menus, REST, MOD player); the audio output
  routing registers (`AUDIO_SEL`) go nowhere in our core, which is right for the U64 family.

- **2026-10-08, fix SMP-KR (agent, bench only; Alex hear-tests the CI package):** two races in `trx_sampler.v` fixed, found by `tb_stress`. (1) 16 bit low byte: the sample back from DDR2 is written in two slots, the low byte at t == 42 and the high byte at t == 43, both gated by `fret`. If the done event lands while t == 42, `fret` is only seen at t == 43, the low-byte slot is skipped and the sample keeps the previous low byte (old bench: 2.7 % of 16 bit samples wrong with a random latency of 8-80 clk). Fix: `fq` samples `fret` at t == 42; the high byte, the clear of `fret`/`fbusy` and the handler's "fetch is back" test use `fq`, so a late `fret` is taken whole (both bytes) in the next frame. (2) Retrigger with a fetch in flight: a control write that stops or restarts a voice (`op_ctl`) did nothing to a fetch already requested for it; the old note's sample landed after the start handler had cleared the sample words and was played as the first sample of the new note (bench: 3400+ wrong sample slots per 400 directed retriggers). Fix: `fkill` is set when such a write hits `fv` while `fbusy`; the landing sample is dropped (no byte written) and `fkill` is cleared with the fetch. Cost: 3 FFs (`fq`, `fkill`, no new RAM) and a few LUTs. Bench: `tb_stress` now checks rule R (after a restart the voice puts out 0 until the first fetch of the new note is back; a directed phase retriggers voice 0 with a 150-400 clk DDR2 400 times) and F by the engine's own previous fetch (+2) instead of the model's; S ignores a voice that was restarted or ran out between sample and visit. Old RTL: S low-byte fails about 4700-5500 per 1.5 M cycles, R fails about 3400; new RTL: 0 over 12 runs (latencies 1-8 up to 200-600). Also seen, not changed: a queued step can fetch for a voice that was just stopped (run bit 0, sample forced to 0, dropped by `fkill` if it is restarted meanwhile); `tb_sampler` at DDR2 latency 60 or 77 fails 2 of 307 checks with the old and the new RTL alike (throughput check).
