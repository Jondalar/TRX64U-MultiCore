## §1 The problem

**Who:** Alex at the C64U running TRX64 Ultimate; TRX64-FW, who builds the replacement; the coordinator, who has to
keep one application for every core.

**What he wants:** switch on the C64U with the TRX64 Ultimate bitstream and get our application, not Gideon's: a C64
that comes up with its ROMs, resets from the menu, starts a `.prg` from the browser, and freezes into our menu.

**What happens today.** The monolith runs Gideon's application from the flash slot at 0x220000 (TRX64-Ultimate
`software/ultimate-app/software/io/flash/w25q_flash.cc:51-56`, app 0x220000 length 0x1E0000). The generic
application has never run on that bitstream. It was written for the MultiCore host, and it assumes that host in five
places.

**The measured fact that makes this small: the two bitstreams have the same CPU-side register map.** Both decoders are
our `ultimate_sys.vhd` (TRX64-Ultimate `designs/c64_basic/ultimate_sys.vhd:846-899`, MultiCore
`host/ultimate_sys.vhd:896-951`). `pix_layer.v`, `overlay.v`, `trx_sys.v`, `trx_engine.v`, `dma_win.v`, `cart_fill.v`
and `jtag_dbg.v` are byte-identical between the two trees; `trx_io.v` differs in one comment. The monolith's ID block
reads "TRX2" (`designs/c64_basic/trx_io.v:328-331`), which is also what the MultiCore `trx64` core answers
(`cores/trx64/` uses the same `trx_io.v`). The build flags are the same: `rv32im`, `-mno-div`, `IOBASE=0x10000000`,
`U2P_IO_BASE=0x10100000`, `CLOCK_FREQ=100000000` (TRX64-Ultimate `software/ultimate-app/target/u64ii/riscv/ultimate/Makefile:6,273-274`,
here `host-app/target/u64ii/riscv/coreapp/Makefile:8,157-158`), and so are the memory map and the heap: `ORIGIN =
0x00030000, LENGTH = 0xE60000` and `configTOTAL_HEAP_SIZE=0x7A0000` in both (`ultimate/linker.x:7`, `ultimate/Makefile:284`;
`coreapp/linker.x:7`, `coreapp/Makefile:161`).

**P1 — Start.** On MultiCore the host application stages the core application, writes a hand-over page at
`HANDOVER_ADDR` 0x03EFF000 and jumps (`host-app/software/hostapp/coreboot.cc:217-245`, `handover.h:11`). On the monolith
nothing writes that page: the boot ROM in the FPGA copies the record at 0x220000 (`{dest, length, run}` little endian,
then the data, no magic, no checksum) to its `dest` and jumps, and only when the bitstream in flash carries the running
bitstream's build stamp (TRX64-Ultimate `software/bootrom/bootrom.c:74-75, 416-424`); a JTAG load
(`[0xFFFC]=0x1571BABE`, entry at 0xFFF8) always wins (`bootrom.c:371-378`). So `coreapp.cc:47` reads DDR2 noise or a
stale block, `handover_valid()` refuses it (`handover.h:33-35`), and `start_paths()` leaves `cfg_path` empty
(`start.cc:51-62`). On the monolith that page is also inside Gideon's cartridge ROM area `__cart_rom_start` 0x03C00000 ..
0x04000000 (`ultimate/linker.x`, same lines in `coreapp/linker.x`).

**P2 — Identity and capabilities.** `start_identify()` picks the descriptor by the four ID bytes (`start.cc:31-49`).
There is no "TRX2" descriptor in `core_table` (only `atari800.cc`, `nes.cc`), so today the monolith ends at "This core
cannot be started" (`coreapp.cc:52-58`). And a descriptor's capability list is a constant (`desc.h:135`,
`atari800.cc:193`), while the C64 differs per bitstream: the monolith has the T37 SID sockets, the MultiCore `trx64` core
does not (`c64_core.v` is the one file that really differs, the sockets at `ultimate_sys.vhd:1139-1158` there and
not in `host/ultimate_sys.vhd:1193`); UCI is optional on MultiCore (`host/top.v:634-636`).

**P3 — Board services.** What `hw.cc` and `run.cc` need, item by item, and what the monolith has:

| `coreapp` uses | file:line | monolith |
|---|---|---|
| core register window `TRX_IO_BASE` + reg | `hw.cc:23-24`, `trx_io.h:14` | same address, `trx_io` in `top.v` |
| DDR2 window 0x01000000 (frame buffers) | `hw.cc:17, 27-35` | there, but it is the REU's 16 MB (`reu_ddr_map.v:1-3`; `__reu_ram_start` 0x01000000) |
| ROM aperture `U64_ROMS_BASE` | `hw.cc:36-51`, `io.h:18` ("16 KB") | 32 KB: BASIC +0, KERNAL +0x2000, CHAR +0x4000, colour RAM +0x7000 (`ultimate_sys.vhd:892-893, 1004-1019`) |
| RAM window `C64_MEMORY_BASE` | `hw.cc:52-67` | same, `dma_win` (`ultimate_sys.vhd:858`) |
| `C64_STOP` = CARTREGS+1, `C64_MODE` reset 0x04 / unreset 0x08 | `hw.cc:13-16, 68-69` | same bits (`ultimate_sys.vhd:1058-1070`); STOPPED reads back at once (`:1300-1303`) |
| ITU button 1, ESP32 link at `WIFI_UART_BASE` | `hw.cc:236-278` | same: rocker events become ITU buttons (`ultimate_sys.vhd:827-837`), `uart_dma` at 0x10060900 |
| ICAP at 0x10060600, ID 0x7A | `hw.cc:280-311`, `run.cc:217` | **not decoded, reads 0** (`ultimate_sys.vhd:1343`) |
| pixel layer, page 6, `PX_*` | `video.h:11-18`, `run.cc:76-79` | identical `pix_layer.v`; the C64's own picture is **not** on it |
| `trx_io_alt_id` | `coreapp.cc:45`, `trx_io.cc:36-41` | not needed: "TRX2" is the primary ID |

**P4 — The picture.** The video service assumes the core draws into frame buffers that the application flips onto the
pixel layer (`video.cc:53-104`). The C64 does not: its picture goes through Gideon's video path, and the pixel layer
is only the menu's. A C64 `VideoDesc` of zeros is not "none": `Video::init()` would still write `FB_BASE` and
`FB_STRIDE` to register offsets `reg_fb_base + i` = 0..3, the ID bytes (`video.cc:67-70`), and `show()` would switch
the layer on with size 0 (`video.cc:83-86`).

**P5 — The C64 machine.** Gideon's application does the four things of step (2) like this (TRX64-Ultimate
`software/ultimate-app/software/`):
- *Reset* `C64::reset()`: `C64_MODE=0`, `=RESET`, a short busy wait, pokes $00=$2F, $01=$37, `=UNRESET`
  (`io/c64/c64.cc:815-843`). A plain register sequence.
- *ROMs* `init_system_roms()`: KERNAL from `/flash/roms/<cfg name>` (exactly 8192 bytes, else a built-in default),
  BASIC straight into `U64_BASIC_BASE`, CHAR into `U64_CHARROM_BASE`, `KERNAL_ENABLE=0` (`c64.cc:1614-1649`). A plain
  copy; the built-in defaults and the fast-reset patch at KERNAL+0x1D6C are policy.
- *PRG run* `dma_load()`: an 8K boot cartridge built from `6502/bootcrt.tas`, a handshake at $02 and $0172-$0185,
  60 polls of 25 ms, the copy into `C64_MEMORY_BASE`, the BASIC pointers, then RUN through $A533/$A659/$A7AE
  (`io/c64/c64_subsys.cc:993-1145`, `6502/bootcrt.tas:531-601`). C64 logic, not a register sequence.
- *Freeze* `freeze_slim()`: `C64_STOP_MODE=FORCE`, `C64_STOP=1`, wait for `HAS_STOPPED`, then poll `TRX_IO+0x100`
  bit 8 (the gate shut), then save $0800, colour RAM and screen for his C64-screen menu (`c64.cc:1440-1498`). Our
  `ultimate_sys.vhd` decodes no `C64_STOP_MODE` at +2 (the write case has 0, 1, 5, 6, 8, 9, 14 only,
  `ultimate_sys.vhd:1058-1080`), so that write does nothing here.

`coreapp` already has the pieces that fit: `boot_start()` (hold, ROMs by `put_op`, settings, release; `boot.cc:65-108`),
`Freeze` (stop, wait for a status bit, layer to the menu; `freeze.cc:4-39`) and the CBM program loader as a library
(`app/loaders/cbm_prg.h:20-57`: place, relink, type `RUN`/`SYS` into the keyboard buffer).

**P6 — Settings and the flash.** Without a hand-over there is no `.cor` and so no `.cfg`: settings live "in memory
only" (`run.cc` log line after `ctx.settings->load()`). The generic application never writes the flash: `fm_fs.cc:111,
127` refuse `/flash` paths, `tests/coreapp/test_noflash.cc` scans for flash writes (T93 S14). On the monolith the
user's ROMs are files in `/flash/roms` (`io/c64/c64.h:13`) and Gideon's settings are the last 16 sectors 0xFF0000..
(`w25q_flash.h:8`, `w25q_flash.cc:261-283`).

**P7 — Getting it onto the board and back off.** The image must fit the slot: at most 0x1E0000 - 12 bytes
(`bootrom.c:75`); the generic application's size has not been measured on this branch. The way back is Gideon's
original firmware (ADR-0057, consequences). Today a `.cfw` is run by "Run Update", which loads the record to 0x03000000
and jumps into Gideon's updater (`filetypes/filetype_u2p.cc:76-166`); that updater writes `/flash/roms`, `/flash/html`,
0x0 and 0x220000, the ESP32, and offers a config reset (`application/update_u2p/update_u64ii.cc:164-195`). The generic
application has no "run an updater" path.

## §3 Decision

**D1 — One source tree, one image, one link.** The monolith and the MultiCore host have the same ISA, clock, IO
bases, origin and heap (§1). A second link target would differ in nothing. The image stays `coreapp.app` from
`host-app/target/u64ii/riscv/coreapp/` (the `.app` already carries the 12-byte `{0x30000, length, 0x30000}` record the
boot ROM reads). Lost: a separate `TRX_MONOLITH` build - it would bring back the `#ifdef` forks T104 §1 P2 removes.

**D2 — A board profile, chosen at run time.** New `coreapp/src/board.{h,cc}`, pure, read once before the descriptor:

```c++
enum BoardKind { BOARD_MULTICORE, BOARD_MONOLITH };
struct BoardProfile {
    BoardKind kind;
    bool has_handover;      // MultiCore: handover_valid() of the page; monolith: never read
    bool can_return_host;   // ICAP loader present (ID byte 0x7A at 0x10060600)
    const char *cfg_dir;    // where a descriptor's <store>.cfg lives without a .cor (D7)
    uint32_t probes;        // what the hardware answered (D3)
};
BoardProfile board_detect(BoardProbe *p);   // BoardProbe: icap_id(), trx_caps(), caps3(), uci_present(), ...
```

The rule: ICAP ID 0x7A is the MultiCore host, anything else the monolith. On the monolith the hand-over page is not
read at all (it lies in the cartridge ROM area there, §1 P1). `run.cc`'s `BoardMenuHost::return_to_host` and the menu
item it serves exist only when `can_return_host`. `coreapp.cc:45` (`trx_io_alt_id`) stays: on "TRX2" it is not needed
and does no harm.

**D3 — Capabilities: the descriptor names what the machine may have, the profile strikes what this board lacks.**
The C64 descriptor lists `iec`, `drive_a`, `cartridge`, `reu`, `ring`, `uci`, `sid_sockets`. `board_detect()` probes
and the effective list (in the merged descriptor, as `picture_extend()` already merges, `run.cc` start of
`coreapp_run`) keeps a name only when its probe holds:

| capability | probe (read, never written) | monolith | MC `trx64` |
|---|---|---|---|
| `drive_a` | the ITU capability word's `CAPAB_DRIVE_1541_1` (Gideon's own test; a read of the drive block cannot tell a register that is 0 from nothing) | yes | yes (`drive_l2`) |
| `drive_b` | not in the list: `DRIVE_B_BASE` is decoded by neither design | - | - |
| `iec` | the IEC stub answers version 0x25 (`ultimate_sys.vhd:1347-1349`) | stub | stub |
| `cartridge` | CAPS b4 (`TRX_CAPS_CART`) | yes | yes |
| `reu` | always on the C64 core, refused while a cart forbids it (ADR-0053) | yes | yes |
| `ring` | CAPS b0, b1 and b2 (gate, state bus, engine); CAPS2 b5 is only the engine's faster walk | yes | yes |
| `uci` | the ITU capability word's `CAPAB_COMMAND_INTF` (both designs set it; an MC build with `UCI_EN` = 0 is not told apart, §5) | yes | build-dependent |
| `sid_sockets` | none: the T37 registers are write only (`ultimate_sys.vhd:1152-1158`), so the profile answers (monolith yes) | yes | no |

The probe values are in §5 once measured; a probe that cannot tell is a question, not a guess. A library whose
capability is struck is refused as T104.1 Q10 says.

**D4 — The C64 descriptor is data** (`coreapp/cores/c64.cc`, `id = "TRX2"`, `cor_name` "TRX64 (C64)" as
`cores/trx64/core.toml`). The same descriptor serves the monolith and the MultiCore `trx64` core:

- `roms`: BASIC (8192, `put_op` `c64.rom_basic`), KERNAL (8192, `c64.rom_kernal`), CHAR (4096, `c64.rom_char`), all
  required, names the ones Gideon's flash holds (measured in §5) plus `basic.901226-01`, `kernal.901227-03`,
  `characters.901225-01` (`cores/trx64/core.toml`). Folder: `/flash/roms` itself on the monolith (D8). No built-in
  ROM: none may ship (CLAUDE.md, licences); a missing ROM is told on screen as for every core (`boot.cc:77-92`).
- `init`/`release`: `C64_MODE` = 0x04 / 0x08 through `CoreIo::mode_reset` (`hw.cc:69`). `reset_ms`: 50, as
  Gideon's `start_cartridge` waits (`c64.cc:1766-1768`). The $00/$01 pokes are not made: the KERNAL's reset sets
  them; §5 records whether the board disagrees.
- `freeze`: `reg_status` 0x101, `mask` 0x01 (the gate bit Gideon polls, `TRX_IO`+0x100 b8), `timeout_ms` 200.
  `C64_STOP_MODE` is not written (not decoded, §1 P5).
- `video`: `w = 0` (D5).
- `tasks`: Reset (`machine.cold_reset`), Reload ROMs (`machine.reload_roms`) - both exist (`boot.cc:156-161`).
- `filetypes`: `.prg` / `.p00` Run and Load, through the `cbm_prg` library (D6).
- `caps`: D3's list.

The three `put_op`s are the C64's only operations of step 2. They are three `rom_write` calls at aperture offsets 0,
0x2000, 0x4000, registered by the descriptor's `register_ops`. Gideon also writes `KERNAL_ENABLE` = 0 (CARTREGS+7,
`c64.cc:1614`); our `ultimate_sys.vhd` does not decode +7 (write case `:1058-1080`), so it is left out. The operations belong in a `c64` machine library only if a second consumer appears (the C128 mode, a C64 in
another core). Lost: putting reset and ROMs into a `c64` library now - it would be a library with one user and no
behaviour beyond three writes.

**D5 — "The core draws its own picture" is a descriptor value: `video.w == 0`.** `Video` then writes no core register,
`show()` only switches the pixel layer off, `poll()` returns false, `wanted_hdmi()` answers the profile's default, and
the Picture item (T107) still sets the HDMI mode through `video_apply()` (`picture.cc:63-76`), the scaler being
Gideon's video path. `desc_check` accepts `w == 0` only with `fb_base == 0`. Lost: a `has_video` flag - two fields
would have to agree.

**D6 — PRG start through `cbm_prg`, not Gideon's boot cartridge.** The C64's `CbmPrgParams`: BASIC start $0801,
`txttab` $2B, window $0801..$9FFF, `vartab` $2D, `arytab` $2F, `strend` $31, keyboard buffer $0277, count $C6,
`ready_ms` measured (§5), `.P00` header 0x1A, size 3..0xFFFF - Gideon's addresses (`c64_subsys.cc:1080-1145`,
`bootcrt.tas:164-170`). Sequence: cold reset, wait `ready_ms`, `cbm_prg_place` through the RAM's second port, `cbm_prg_type_start`.
**Large PRGs (Alex, 2026-10-18: "klappt das auch mit large PRGs, weil wir per DMA unter Basic und ROM schreiben können bis
fff7?" - "does it also work with large PRGs, since we can write by DMA under BASIC and ROM up to $FFF7?"):** yes, if the
bytes never become bus cycles. `dma_win.v` sends a byte to the C64 RAM's second port while the machine runs (dma_bus = 0),
which reaches all 64 KB regardless of $01, under BASIC and KERNAL; **$D000-$DFFF is a bus cycle whether the machine runs or is
stopped, unless `C64_DMA_MEMONLY` is set** (`ultimate_sys.vhd` r_dma branch, G06: `dma_bus <= not dma_memonly` for $Dxxx), and while the
machine is stopped by `C64_STOP` every other byte is one too. So the place step sets MEMONLY around the write and runs with the machine
running (or held by the debug block, where `C64_STOP` is 0), never as stopped bus cycles; the first draft of this paragraph said the
second port reaches the I/O area with the machine running and no MEMONLY, which the decoder does not do (§5); the C64 parameters allow an image from $0801 to
$FFFF (`max_size`); a BASIC program past $A000 leaves the pointers above MEMSIZ, and RUN still executes its SYS line at
once (VICE's inject autostart does the same). Proved by S15.
**Two file actions for a `.prg` (Alex, 2026-10-18: "RUN PRG / LOAD PRG and start from:"):** (1) *Run PRG*: a BASIC
program gets `RUN`, a machine-language file `SYS <load address>`. (2) *Load PRG and start from: $____*: loads the file
at its own load address (any range $0000-$FFFF) and asks for the start address, default the load address. Starting
by a typed `SYS` needs zero page, stack, $0277 and the KERNAL intact; a file that overwrites $0000-$03FF cannot be
started that way. So the start is an operation `machine.go(addr)` that sets the CPU's PC directly (the path the
Timewarp/ring restore uses to set the CPU registers, T20); whether `machine.go` is always used or only when the file
covers $0000-$03FF is decided while building (§5). The address prompt is a text-input widget (T104.1 D7) bound to the
file action's argument. Proved by S16. What
loses: Gideon's DMA handshake (boot cart, $02, 60 polls), because it needs a 6502 image, the cartridge slot and his
KERNAL entry points; ours needs RAM writes only and is already benched for two machines. What it cannot do: a program
that loads over $0277 or needs the drive number in $BA before `RUN` - §5 records the first such program found.

**D7 — Settings without a `.cor`.** The profile gives the directory; the file is `<cfg_dir>/<store>.cfg` in the same
`cfgfile` format (`cfgfile.cc`). Where `cfg_dir` points is Q1. Until Q1 is answered the build uses the first
writable stick (`/usb0/trx/`), which `fm_fs` already allows, so S11 can run.

**D8 — ROM roots on the monolith.** `rom_roots` stays (`romfind.cc:6`); the monolith profile searches
`/flash/roms` first (the files the user has there, Gideon's layout) and then `<root>/roms/c64` of `/flash`, the sticks and the
card; the first file found wins, so a file in the flash beats a stick (as built, 5). Where a `.cor` exists, its folder's `roms/` comes
before all of this (T112 D1, Alex 2026-10-19; point 8). DECIDED (Alex, 2026-10-20): "/flash/roms wins" (translated) on the monolith, as built. Reading `/flash` is allowed;
writing stays refused (T93 S14), except what Q1 decided for the settings file.

**D9 — What step 3 and the rest of day 1 get from this spec (interfaces only).**

1. *`cbm1541` (T104.1 D15).* `CoreIo` gains `drv_rd/drv_wr(page, reg, v)` for `DRIVE_A_BASE` (0x10020000) and
   `GCR_CODER_BASE` (0x10060500), the same addresses on both designs (monolith `ultimate_sys.vhd:850, 864`; MC
   `host/ultimate_sys.vhd:900`, routed to `drive_l2`). The drive's 32 KB ROM and RAM image is DDR2 at
   `__drive_a_area` 0x00EE0000 (Gideon `drive/c1541.cc:96-98`, both linker scripts), outside the application's
   range 0x30000..0xE90000, so the library writes it through a new `CoreIo::ddr_abs_write(addr, ...)` restricted to
   the fixed areas of `linker.x` (0x00EA8000..0x00F00000). The capability is `drive_a`; `drive_b` is never offered.
2. *Cartridge start (`.crt`, T33).* Needs: `C64_CARTRIDGE_TYPE` (CARTREGS+5), `KILL` (+6), `TRX_ROM_SEL`
   (`TRX_IO`+0x4030) and the 37-byte descriptor at `TRX_IO`+0x4040 (Gideon `trx_cart.cc:128-135, 237-286`) - all
   through `CoreIo::wr`/`rd`, plus the image area (`TRX_XPORT_BLOCK` 0x01000000 or 0x03C00000, `c64.h:525-541`) via
   D9.1's absolute DDR2 write. The `.crt` parser and the type table are a `c64cart` library (`cartridge` capability).
3. *Firmware update.* The profile names the slot: monolith 0x220000, length 0x1E0000 (`w25q_flash.cc:51-56`). The base
   needs one operation `update.run_record(path)`: load a `.cfw`/`.ue2` record to its address and jump, as
   `filetype_u2p.cc:145-163` does; that one operation is also the safety net (S13). Writing the flash itself stays in
   the updaters (T49 `update_trx.cc`), not in the application.
4. *Network and REST.* No difference: RMII at 0x10060800 on both. The Gideon-path alias table (T104.1 Q2) needs from
   this spec only that `machine.cold_reset`, `prg.run` and a RAM write exist as operations - D4, D6, `CoreIo::ram_write`.
5. *Timewarp and the monitor.* The ring's pages are `trx_sys` / `trx_engine`, identical on both designs; they need
   `CoreIo::rd/wr` beyond page 0 (32-bit through `trx_io_read32/write32`) and the `ring` capability. The ring's
   interrupt stays firmware (T104.1 §3 F).
6. *Freeze for Timewarp.* Gideon's resume after a rewind is `trx_ring_unfreeze()` (`c64.cc:1666-1729`); our `Freeze`
   needs a hook `on_leave` that a library can register, so the `timewarp` library lands before `C64_STOP` = 0.

## §5 Implementation Log: decisions taken while building (dated; where it differs from the Current Contract, the contract holds)

Built 2026-10-18 on `t104-generic-app` by an agent of TRX64U-MultiCore (commits bcf63261, e028ecd4, 042b2da1). Every line is from the code
unless it says "measured"; nothing here was measured on a board or on RISC-V.

**Profile and probes (D2, D3).** `board_detect()` takes a `BoardProbe` of five reads: ICAP byte, ITU capability word, `TRX_CAPS`, `IEC_BASE`+0,
and "the page at `HANDOVER_ADDR` holds a block". The probes as built: `drive_a` = `CAPAB_DRIVE_1541_1`; `iec` = the IEC stub's version byte 0x25;
`cartridge` = CAPS b4; `ring` = CAPS b0 and b1 and b2 (not CAPS2 b5: that is the engine's `APPLY`, an accelerator the software walk does without);
`reu` always; `uci` = `CAPAB_COMMAND_INTF`; `sid_sockets` = the profile (monolith yes, MultiCore no). Two of these are guesses I could not
turn into reads, and they are for Alex: (1) the T37 socket registers are write only, so nothing readable tells the monolith from the `trx64`
core - the profile stands in; (2) `host/ultimate_sys.vhd` with `g_uci` = 0 answers its UCI window with 0 but still advertises
`CAPAB_COMMAND_INTF`, so an MC build without UCI keeps `uci`. A descriptor opts in with `board_caps`; the Atari and the NES list what they have.
The effective list replaces `caps` in the merged descriptor (`run.cc`), which is what the loader refuses libraries against (Q10), and the log
says `[core] capabilities: ...; struck by the board: ...`.

**The monolith never reads the hand-over page** (`has_handover` is false there whatever the page holds). Noted, not touched: `HANDOVER_ADDR`
0x03EFF000 lies inside the monolith's cartridge ROM area (0x03C00000-0x04000000); on the MultiCore host nothing changes.

**Menu.** `menu_build(d, t, return_host)`: "Return to host menu" is absent when the profile cannot return (the ICAP loader is not there).
A context with no profile is the MultiCore host of before.

**ROM files (D4, D8).** Names: `basic.bin`, `kernal.bin`, `chars.bin` first - the strings Gideon's firmware defaults to (`c64.cc` CFG_C64_*FILE) -
then `basic.901226-01`, `kernal.901227-03`, `characters.901225-01`, then `*.rom`. **The FTP listing of the board's `/flash/roms` is not measured**
(no board access); if the files there are called otherwise the list needs the names. Order: `/flash/roms` itself, then `<root>/roms/c64` of
`/flash`, the sticks and the card - the first file found wins, so a file in the flash beats a stick (D8 said "a stick can override"; with
first-found-wins that is not so, and it is the order every other board has). The put is three copies without read-back (the KERNAL array is
write only on Gideon's boards).

**Aperture offsets verified against the decoder (D4).** `ultimate_sys.vhd` r_rom: address bit 14:12 = 111 colour RAM (+0x7000, 1 KB), bit 14 CHAR
(+0x4000, 4 KB, mirrored at +0x5000 and +0x6000), bit 13 KERNAL (+0x2000), else BASIC (+0). The file's comment ("char 0x0000, KERNAL 0x2000, BASIC
0x4000") numbers the internal `dma_addr`, not the aperture. `io.h` said "16 KB": it is 32 KB, fixed.

**`C64_DMA_MEMONLY` (D6 correction, S15).** In `ultimate_sys.vhd` (both designs) a byte to $D000-$DFFF is a bus cycle through the PLA unless
MEMONLY, running or stopped; a write of $0000/$0001 is one while `C64_STOP` is set even with MEMONLY; every other byte is one only with
`C64_STOP` set and MEMONLY off. `CoreIo::ram_memonly()` (hw.cc: `C64_IO_BASE`+3) is set around every placement; MEMONLY is off again afterwards
(Gideon's own freeze restores it the same way, `freeze_slim`). A held-by-debugger machine has `C64_STOP` = 0, so a $0000/$0001 write is then RAM
too: the control of S15 and the first half of S16 both rest on it.

**PRG start is two steps (D6).** The menu holds the machine with `C64_STOP` while an operation of it runs (`open_menu`), and a held machine never
reaches READY, so an operation that waited for READY would time out. `c64.run_prg` / `c64.load_prg` check the file (nothing is touched when it is no
program, wraps past $FFFF or is outside the size window), cold-reset the machine and queue the job; `c64.service` (the descriptor's poll,
`poll_when_frozen` false, every 50 ms) counts only the time the machine runs, waits for `ready_ms` (1000, **not measured**) and then for
$2B/$2C = $0801 (at most 4 s more, then a notice "did not reach READY"), plus 300 ms for the banner and the editor loop, then places and types.
A reset (task, reload, a second PRG) clears the queued job. Failures of the second step are told through `CoreCtx::notice`, which the next
menu shows. `max_size` is $0801-$FFFF for Run PRG (+ the .P00 header), $0000-$FFFF for Load PRG; a BASIC program above $A000 leaves its
pointers beyond MEMSIZ and RUN still executes the SYS line, as D6 said.

**`machine.go` (the answer to "can the coreapp set the PC").** Yes, on this gateware, and built: `coreapp/cores/c64_go.cc`. The path is the one
TRX64-Ultimate's trxmon app takes for `r pc=` and `g <addr>` (`software/ultimate-app/apps/trxmon/src/hw_trx.c` `hw_cpu_write`, T21 5.1.1,
`c64_core.v` chip 1 w4/w5/w8-w14): `OWNER` = 1, `CMD` PAUSE_IB (page 3) until STATUS has b0 (gate shut) and b2 (at an instruction boundary), read the
settled registers (w4, w5) and $01 as read (w2), stage the CPU's 209 flip-flops (w8-w14: A X Y S P, PC at bit 40, IR at 80, state flags at 102+,
din_r at 130) with the registers kept, IR = NOP and the pending write-back's three enables off, PC = the address and din_r = the opcode there, `SB_LOAD`
b1, `IPC_SET`, `CMD` RUN; the CPU takes the staged words at the next edge the gate lets through, and OWNER goes back to 0 so `C64_STOP` is the
menu's again (what `trx_dbg_yield()` does). Needs CAPS b1, b3 and CAPS2 b2; both designs carry `trx_io.v`, `trx_sys.v`, `trx_dbg.v` and
`c64_core.v` unchanged. Decided while building: **machine.go is always used when the bitstream has it**, not only for a file over
$0000-$03FF - the start address is then exact whatever BASIC state the machine is in, and the file is written while the debugger holds the
machine, so nothing races it. Registers A X Y S are kept; P gets I and D cleared (the machine may have stopped inside an interrupt handler);
the opcode at the start is read as the CPU sees it ($01's LORAM/HIRAM/CHAREN): RAM, or a ROM through the aperture; in the I/O area the start is
refused (a read there is a bus cycle with side effects); a cartridge's ROML/ROMH is not looked at. Without the CPU write path the start is a typed
SYS and a file over $0000-$03FF is refused with the reason. The pieces I could not test: the real timing of PAUSE_IB (landing on an IB while an
interrupt handler runs), the load at the opening edge, and whether OWNER = 1 changes what the window's D page does; the model reads all of it from
`trx_dbg.v`/`trx_sys.v`, not from a run.

**Freeze (D4).** The status is `GATE_CTRL` b8 ("halted"), read as a 32 bit word: `trx_sys.v` latches a word on a read of byte 0 and serves bytes
1-3 from the latch, so Gideon's `trx_io_read32(0x100) & 0x100` works and a single byte read of 0x101 sees whatever was left. `FreezeDesc::word` makes
`freeze_status()` read byte 0 first; the bench shows the byte read alone never changing. Whether b8 rises after `C64_STOP` = 1 alone or only

### D9.1 built: the drive pages of `CoreIo` (branch `t104-cbm1541`, Claude, 2026-10-22; merged into `main` since: `git branch --contains` shows it, the TODO text "drive pages on branch" was stale)

### 2026-10-26, later: `update.run_record` built (Q4 = a), S13 (Claude, branch `t104-2-trx64`)

**What it does (`coreapp/src/update.{h,cc}`).** The operation `update.run_record` (argument `path`), registered in the base (`ops_glue.cc`); the C64 descriptor has the file action "Run Update" on `.cfw` (`c64.cc`, filetype `.cfw`). It is Gideon's "Run Update" of `filetype_u2p.cc` with his format 1 checks done first, in this order, and nothing is written to DDR2 before they all pass:
1. The board profile must be the monolith (on the MultiCore host the host's menu updates: "Updates run from the host's menu on this board."), the name must end in `.cfw`.
2. Pre-header (36 bytes): fingerprint DE AD 15 41 (read as the word 0x4115ADDE), a named product family must equal `getProductFamily()` ("U64MK2" on this board), a named product name `getProductString()` (his messages: "Invalid Update Image", "Wrong Product Family", "Update for Wrong Product").
3. Records `{load, length, start}` (at most 8): each lies inside the file, inside the updaters' window `[0x03000000, 0x03C00000)` (so it can never overwrite the application at 0x30000-0xE90000, the REU window or the cartridge ROM area), a start address lies inside its own record, at least one start exists. Measured on the four `.cfw` at hand (Gideon's `update.cfw` 8927132 bytes, `vanilla-3.15a` 8813436, `softboot.cfw` 1475796, our `trx64_update_b151154b` 3475612): family "U64MK2", no product name, one record each at 0x03000000 with start 0x03000000.
4. The records go to DDR2 in 32 KB chunks, are read back and compared (a stage that does not hold never gets the jump), the clock is handed over in the four words at 0x03F00000 as `trx_time_handover.h` defines them (all zero when the app has no valid time), the video layer is yielded, the WiFi UART of the rocker link is stopped (`hw_rocker_quiesce`), interrupts are switched off and the CPU jumps (`CoreIo::run_at`, `hw.cc`).
