### Core move: c128 (2026-11-25)

Moved with `tools/core_move.py` and the core-move skill (T239.5 D16, lane B, fifth core). Branch `t239.5-cores-b`. The Commodore 128 is a large core (`cores/c128/mono/core.toml`, delivery `cfw`, experimental). It is the first moved core with the drive window of the C64U's own drive (`c64u_drive_l2`: Gideon's `mm_drive`, a 1541 or a 1581), so its TOML A carries the blocks `drive_a` and `drive_wd`.

- **Commits by phase.** `788e106fc` SDK gaps (`rtl_check.py`, `maps/wd177x.map.toml`, `core_move.py gates`); `503ece0c7` SDK gap (`descrec.py`, `api.md` 6.14.20); `c4c1530f4` library (`c128.cc`, `c128_keys.h`, `c128_prg.h`, `c128_regs.h` moved; copies of `hk_defaults.h` and `drive_rom_pick.h`), TOML A, TOML B, `desc.toml` by name, removal from the shared app (`table.cc`, `cores.h`, the board Makefile, D24 ledger and targets, `tests/coreapp/cores.txt`, `check_core_id.py`, `release_notes_mc.py`, `cores/c128/mono/core.toml`, the two `run_prgrun.sh` benches that build `tools/cbm_prg_sim.cc`); `020e2c06d` tests (the `c128app` units, shared builds without the core, keywalk goldens, rtl_check case, TOML B `tests`); `590026113` `test_cor_pack`; this note is its own commit.
- **TOML A numbers.** The emitter's first form (full scan of the 64 KiB window, 16 minutes on this Mac, `apply`): 1 block with 4 registers (the standard block), the rest "NOT EMITTED": +0x10..+0xBFFF (16170 registers) and +0xE000..+0xFFFF (2058 registers) as dense regions of more than 256, 8192 bytes the decode does not follow (`t_io_resp` at +0xC000..+0xC002). The dry run (`--pages first`) showed 4 blocks, 79 registers, 42 of them unnamed, and the drive as the shipped map. By hand: 17 blocks, 86 properties (57 written out, 29 of the maps `cbm1541` and `wd177x`), all named, no `# TODO` left; `rtl_check check` with the second bus for the drive window: "17 block(s), 86 properties agree". Blocks of the core window: `ident` (id "C128" from `layer2_c128.v`, caps, caps2, caps3, build from `c64u_io.v`), `irq`, `ddr_cal`, `core_caps`, `tape` (`pin_ctrl`, 078), `pixel` (the host's pixel layer: the two registers of the VIC capture, 0x6064 `still_base` and 0x6068 `still_status`), and the C128's own page E from `c128_regs.v` and `c128_act.v`: `page_id`, `page_irq`, `machine` (mon_sel, d4080, capslk, boot64, joy_swap, `xkeys` as a run of 3, xspecial, status with its five bits as fields), `rom`, `video` (fb_base and fb_stride with their reset values, vdc_ctrl), `cold`, `chr`, `perf` (the 20 bit frame lengths as a 16 bit and an 8 bit property, the five RAM counters), `act`. `[identity] id = "C128"`. Not described: the C64U window's pages the core's code does not use (cartridge page 4, expansion port 7, streams, UCI, tape streamer and recorder, reSID8 and socket controls, sampler) and page 6 beyond the two capture registers.
- **rtl_check source list.** `core_sources.tcl` writes Gideon's VHDL list as `foreach n $g_names { lappend g_files $gdir/$n }`; the checker reads file names as text and cannot run the loop, so `mm_drive`, `drive_registers` and `mem_bus_pkg` were no part of the design (first symptom: `an RTL pattern I do not know: the type t_mem_req_32`). `cores/c128/app/rtl_check_sources.tcl` is `core_sources.tcl` with that list written out as names.
- **Registers by number.** `c128_regs.h` names every register through `drvtab.h` (`C128_OFS(DRV_<block>_<prop>_ADDR)`, `C128_ST_HELD` = `DRV_machine_status_held_MASK`, the picture's reset values `DRV_video_fb_base_reset` and `DRV_video_fb_stride_reset`); `C128_STILL_BASE` and `C128_STILL_STATUS`, literals 0x6064 and 0x6068 inside `c128.cc`, are in the header now (`pixel`). `desc.toml` names its registers as `"video.fb_latest"`, `"video.frame_seq"`, `"video.fb_base"`, `"video.fb_stride"`, `"machine.status"` and the reset values `"video.fb_base.reset"`, `"video.fb_stride.reset"`. The compiled record is byte for byte the old one (6703 bytes, `descrec.py compile` of `git show c4c1530f4~1:cores/c128/app/desc.toml` against the new file). `rtl_check.py lint-src` over the four library files: "no literal I/O address in 4 file(s)". A throwaway program (not committed) built `c128_regs.h` against the driver table made from `gateware.toml` and compared with the numbers of the old header (`git show c4c1530f4~1:coreapp/cores/c128_regs.h`): "compared 47 registers, 0 differ"; the two new names print 0x6064 and 0x6068.
- **SDK gaps.** (1) `rtl_check.py` did not parse a port-map actual of the form `m(1).step` (mm_drive_cpu.vhd:404: "expected ')'") and refused a record signal assigned from an expression (`mm <= m(1) when ... else m(0)`, "a record assigned from an expression"): the first is a node `field` that no evaluator follows (as an output target it names the signal and the field), the second gives every field unknown where a module reads it (an input of an instance that is no part of the request's path). That second change relaxes a refusal into "unknown"; the rest of the checker treats unknown as not certain, and all other cases of `tests/rtl_check/test_rtl_check.py` pass unchanged. (2) `app/sdkpkg/maps/wd177x.map.toml`: `dma_addr` was a 32 bit write, the RTL (`wd177x.vhd`) keeps bytes +8, +9 and +0xA only; it is `dma_addr` (16 bit) and `dma_addr_hi` (8 bit) now, the driver's `drv_wr32` at the address of `dma_addr` is unchanged. No test or TOML read the old width. (3) `core_move.py gates` checked only the core window; a core with its own block `drive_a` gets the drive window as a second bus (`drv_io_*`, `0x10020000:0x4000:full`), as `test_rtl_check.py` does for the VIC-20. (4) `descrec.py`: `toml_a_names` read the TOML A without the module maps, so a TOML A with a block `map = "cbm1541"` made every `desc.toml` that names a register fail ("unknown key 'map'"); it reads them with the maps given to the compile, else with `app/sdkpkg/maps` (api.md 6.14.20). `core_move.py sdkgaps` reports the same 2 breaks as for the cores before (`cart_regs`, and all blocks together: `hw.cc:90 DRV_cart_regs_ADDR`), a block every app has, not caused by this move.
