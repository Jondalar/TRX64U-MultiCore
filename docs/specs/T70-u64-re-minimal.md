# T70 — TRX64 RE core for the old U64 (Cyclone V), minimal scope

**Status:** scope complete (2026-10-08, Q1-Q7 answered), nothing built. Basis: the T27 trial synthesis ([T27](T27-u64-cyclone-port.md)): the full TRX64 Ultimate does not fit the 5CEBA4 (120 % ALM, no 1080p). This is a new, smaller design for the old Ultimate 64, not a port.

## 1. Goal

Alex (2026-10-08): "Damit kann ich die Hardware nutzen in meinem C64RE Prozess." The old U64 becomes a real-hardware target for the C64RE workflow: a real C64 with Timewarp, the TRX64 monitor and debug, cartridges and the C64RE connection.

## 2. Scope IN (Alex, 2026-10-08, verbatim list)

- C64
- 1x 1541
- reSID, 2 SIDs
- Cartridges from TRX64, complete ("vollumfänglich")
- Timewarp
- Monitor and all trx_debug functions
- C64RE support
- Keyboard
- Joystick
- HDMI at the resolution that works (T27: 480p/576p, as Gideon's U64 firmware)

Added by the answers below (§4): menu with apps (Ultimate app derivative on the RISC-V), real cartridges on the port, USB host (stick), Ethernet, WiFi (ESP32 UART), UDP video/audio streams (C64RE live tab).

## 3. Scope OUT (confirmed by Alex, §4)

LVGL UI, real 1541 on the IEC port, turbo (T29), 8 SIDs, sampler (T25.6), mixer extras, REU, UCI, palettes, LED effects, T44 flash gate, JTAG debug (jtag_dbg, con_ring, rv_dbg, drv_dbg), 1080p, real SID sockets, tape/user port.

- **2026-10-08 (fourth run): the Timewarp engine's table in block RAM; T70 without the DDR2 interface: 15,758 ALM (85 %), 1,798 of 1,848 LABs (97 %) on the 5CEBA4F23C8.** CI run 551 (flow, package `trx64-t27` `0f9f47a5-551`), run 550 (benches; the first synthesis in 550 did not apply the patch and is void: `git apply` inside the checkout skipped it without a message, fixed to apply in a temp directory and to fail if absent). Branch `t70-synth`; our C64U build is untouched (the change is `tools/t27/t70/trx_engine.patch`, applied to the scratch copy only).
  - *Where the data is needed (code):* `trx_engine.v` held `tab[0:63]` (19 bits, `{count 7, sb address 12}`) and read it combinationally, `q_tab = tab[tab_a]`, with `tab_a = q == Q_IDLE ? tab_idx : q_ent[5:0]`. `q_tab` is used only by the capture sequencer outside `Q_IDLE`: `Q_ENT` (zero count? next state), `Q_RD` (`sb_addr <= q_tab[11:0] + q_cnt`), `Q_W2` (last word of the entry?). `q_ent` changes in three places only: to 0 on the clock that leaves `Q_IDLE`, +1 in `Q_ENT` on a zero-count entry, +1 in `Q_W2` on the last word. The table is written only in `Q_IDLE` (register 0x19, at `tab_idx`).
  - *The solution:* a synchronous-read RAM whose address is the value `q_ent` will have in the next clock (`ent_nx`, the same three conditions), so `q_tab` (now a register) holds in each clock exactly the entry the original read combinationally in that clock. **No cycle changes anywhere: the sequencer's state-bus reads, `seq_busy`, the register read-back and the DDR2 commands are identical clock by clock.** A write in the last clock before the sequencer leaves `Q_IDLE` is covered because `Q_HEAD` lasts at least one clock and the entry is read again in it. The boot contents (9 entries, `initial` block) stay.
  - *Equivalence (cycle-exact, not only functional):* `tools/t27/t70/tb_eng_seq.v` runs the original `trx_engine` and the patched one side by side on the same stimulus: 120 captures, random tables (0-64 entries, zero-count entries, rewrites between and during captures), random state-bus grants: 28,308 state-bus reads, 148,384 clocks, **0 differences** (PASS in CI run 550 and on the Mac with iverilog). A mutation (the `Q_W2` increment removed) is caught at once (1.8 million differences), so the bench does see this path. The two existing engine benches `tb_eng_f4` (drain) and `tb_eng_trace` (trace former) also PASS on the patched engine. They do not touch the sequencer; the full-machine Verilator ring bench (tier 2, `ring_trace_core`) was not run.

  - *The change (`tools/t27/t70/drive_mem.vhd`, used only by the T70 variant; the original in `designs/c64_basic` and Gideon's sources are untouched).* The original reads `lines(idx)` and `tags(idx)` combinationally from `drv_req.address` in the same clock in which it decides hit or miss (`line := lines(idx)`, `hit := valid(idx)... tags(idx) = a(15 downto 9)`), which is an asynchronous read: no M10K. The variant takes the same decision one clock later: the RAMs are read with the address of the request on the port (`line_q`, `tag_q`, synchronous), the request is held in `rq`, and the decision runs on `rq`. A write in the clock of the read is not in the RAM data; it is the registered `wb_*` (line, tag, index) and the decision takes it from there, so it sees exactly what the original saw. A request the drive still shows after it was taken is hidden by `r_rack` and `r_rack_d` (the original needs only `r_rack`). Lines are M10K (4 blocks), tags MLAB. Cost: 128 + 7 + 26 registers and a few muxes.
  - *Timing change:* every answer of the drive memory comes **one clock later** (a cache hit in 3 instead of 2 clocks of the system clock; a miss 1 clock more of 40+). The drive's 1 MHz CPU cycle is about 60 clocks of the 66.67 MHz clock; nothing else changes. The write path (CPU writes straight to DDR2, line updated if cached), the snoop/poison rule and the DDR2 handshake are untouched.

Not a formal proof: no random access/snoop stress against the original was run.
