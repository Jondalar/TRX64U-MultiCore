## §1 The problem

- **Who:** (1) the maintainer of a core that is built outside this repository (first: TRX64-Ultimate with trx64u); (2) the maintainer of a core in this repository, whose per-core code sits inside the shared app image; (3) a person on the board moving the cursor in the trx64u menu.
- **What they try to do:** (1) build a core's app part against a published SDK, with no source of ours in the core's repository; (2) add or fix a core without touching the one image every core runs; (3) use the menu without waiting.

**What exists today (read from the code, 2026-11-19):**

- **One app image for the blueprint cores.** `coreapp/` builds one image for the cores whose `core.toml` says `app = "blueprint"`; the core is chosen at run time from the ID block (`coreapp/README.md`, `tools/build_coreapp.sh`). Only cores with a descriptor in `coreapp/src/table.cc` are built into it (`tools/build_coreapp.sh:38`). Per-core code is part of that image: every core's descriptor, hooks and media code are in `coreapp/cores/` and are linked into every image.
- **The service layer.** `ops.*` (registry of operations, state values, events), `exec.*` (executor, core lock), `service.*` (contributor poll task), `ops_glue.*`, `contrib.*` (menu merge), `bundle.*` (the `.cor` carries a menu record, record 6, and a library record, record 7). The descriptor holds operation names, not functions.
- **The loader.** `.u2a` format 3 (`coreapp/src/libfmt.h`: 104-byte header, up to `U2A3_NEEDS_MAX` = 4 needs, image at most `U2A3_IMAGE_MAX` = 1 MiB, residence transient or resident, kind lib or app, a `capability` the core has to have). `libapi.h` gives `lib_register(const LibApi *, LibRecord *)` and `app_main(const LibApi *, AppCtx *)`. `libload.*` checks, places, relocates, registers and rolls back; `libboard.cc` loads `<root>/trx/lib` and the libraries of the `.cor` at every start. Build: `app/lib/lib.mk` (rv32im, no compressed instructions, position independent) and `tools/u2a_pack.py`. Test: `tests/loader/run.sh` against a model of the heap.
- **The API a sub-app sees.** `LibApi` holds `log`, `abi_major/minor` and the call tables `sys`, `mem`, `ops`, `fs`, `dlg`, `job`, `trx`, `net`, `c64`, `lib` (`libapi.h`, `svctab.h`). A group the core does not have is a null pointer. The ABI is major 3, base minor 1 (`U2A_ABI_MAJOR`, `U2A_BASE_MINOR` in `libfmt.h`). An application brings a declarative UI description and no LVGL (T104.3 D0); `app/sdk/u2p_app.h` and `u2p_compat.c` carry the older ABI 2 calls of the four applications over the tables of ABI 3. The registry takes operations, state values and events; menu nodes, file actions and settings are merged by `contrib.h`; the poll of a library "is declared and kept, and not served yet" (`libapi.h` header).
- **No heap of its own for a library.** A library gets memory from `api->mem` (`SvcMem`: malloc, free, realloc) and its image from the board heap (FreeRTOS heap_4, `coreapp/src/libboard.cc:35`). The loader counts `resident_bytes()` (`libload.h:139`), but the budget of T104.1 Q7 is "deferred until measured" (T104.1 §6: 5,700,064 B free at UI start, Atari, 2026-10-18). The tables are static arrays: `OPS_MAX` 400 and `STATES_MAX` 320 in `coreapp/src/ops.h:151-152`, raised on 2026-11-18 for trx64u and TREX CRT (T228 §5: 200 to 320 and 300 to 400, 4.4 KB static RAM). A library that registers past them is refused with "no room" (`ops.cc:77,99`).
- **Per-core code in the app.** The D24 ledger (`tools/d24_ledger.txt`, built by T213 D4) holds 145 files and 44,132 code lines of per-core code; the lint only stops it growing. The trx64u exceptions of T228-R20 add `coreapp/src/u64cfg.cc` +1033, `coreapp/cores/trx64u/menu.toml` +1313, `menu_rec.inc` +2530, `coreapp/src/trx64u_ops.cc` +927 (+22), `u64cfg.h` +4, `trx64u_ops.h` +5: about 5,830 lines. The ring and monitor code (`ring*.cc`, `monitor.cc`, `monsrv.cc`, `trxmon/*`) is on the ledger as per-core too. Only trx64u has a TOML menu; the other cores are C descriptors.
- **The drive library.** `app/lib/cbm1541/` (`d1541_gcr`, `d1541_wd`, `d1541_drive`, `d1541_fs`) is pure and portable. Its contributor is `coreapp/cores/cbm1541.cc`, its descriptor pieces `cbm1541_desc.h`. The VIC-20 uses it as source linked into the image (`coreapp/cores/vc20.cc:14-15,226`); it is built in, not loaded (T104.1 D15).
- **Menu speed on the board.** Alex, 2026-11-18 (T228 §5, translated): "trx64u is dead slow in the UI", "the A1200 is incredibly fast in comparison", "the app re-renders the whole UI on every key press .. I think the emulator just does not show it". The board reads the compiled record (322 entries), it parses no TOML. Nothing is measured yet. T231 records the same symptom for the diag core: each cursor move redraws the whole screen (board test 2026-11-16).
- **SDK.** T131 (App API description and SDK for outside developers, planned 2026-10-26) is not written. T153 wrote the UI contract (widgets, layouts, TOML content, BDD suite in ue2emu; DONE 2026-11-14). Tools to test without a board: `tools/menusim/` (`hostsim.cc`, `menusim.cc`, `run.sh`), ue2emu, `tests/ui`, `tests/coreapp`, `tests/loader`.
- **Versioning.** T221 gives the generic core app its own `version.toml` and SemVer (D6, D18). The `.u2a` carries the ABI major/minor and `needs base >= x.y`; nothing says which API versions an outside core may rely on, or how a break is announced.

**Why it matters.** TRX64-Ultimate cannot own trx64u's menu, code and limits (T239 D9) until the app has a clean boundary they can sit behind. Every per-core line in the shared image is built, flashed and heap-counted for all cores. An outside core maintainer has no written contract.

**Parts (MECE):**

- **P1 The app core boundary:** what the app core owns (ops, states, events, menu merge, media, settings, saves, drive window, jobs, UI rendering) and what a sub-app or library may call, as one written API.
- **P2 Versioning of that API:** how its version is counted, checked at load, and changed (T221).
- **P3 Per-core code:** the sort of today's per-core code into data (TOML), generic module, or a core's own library; the order of moving it.
- **P4 trx64u leaves the image:** its menu, ops and config code (the T228-R20 exceptions) load as `trx64u.u2a` from its `.cor`; the
  image holds none of it. Whether the ring, monitor and trxmon code goes with it is open (question 5).
- **P5 Shared libraries with source:** the cbm1541 drive library (and 1581/1571 pieces) as a loadable library with source in the SDK; the VIC-20 builds its app with it.
- **P6 Limits and memory:** table sizes, per-library budget, the heap a library gets, refusal with a message.
- **P7 Menu speed:** measure on the board, find what is drawn per key press, fix in the generic drawing path (T231).
- **P8 The SDK, app side:** headers, ABI description, build template, packer, test tools, a worked example, per release.
- **P9 Relation to T213:** whether its child specs are replaced or used.

## §3 Decision

Only decisions of the epic apply; nothing here is invented.

- **T239 D9:** "TRX64 comes from the registry; our release package stops carrying trx64u/trx64g." Its menu TOML and its code in `coreapp/cores/trx64u/` (the D24 exceptions of T228-R20) and its table and memory limits belong to TRX64-Ultimate, built against the SDK. Applies to P4 and P6.
- **T239 D10:** data by default, a core's own library where no generic module fits, one app core with an API for sub-apps and libraries; "TRX64U gives it back into the central repo as a library with source. The VIC-20 then uses it to build its app." Applies to P1, P3, P4, P5.
- **T239 D13:** the order is A, D, B, C; this is B. It starts after the GitHub home and the platform checkpoint.
- **T192 D24 and T213 D4:** no per-core code in `coreapp/` or `uicore/`; the ledger only shrinks (`tools/check_d24.py`, `tools/d24_ledger.txt`). Every build agent brief for this spec cites it.
- **T213 D1:** format and machine logic are C modules in the service, chosen and parametrised by the API TOML; the TOML is no programming language. Applies to the "generic module" target of P3.
- **T213 D2 and D5:** one child per core, same pictures and tests before and after; tests split into one generic set and a set per core. Applies to S7.
- **T104.1 D10-D12 and D15:** the `.u2a` format 3, the loader, the drive library as source. Applies to P1, P5, P6.
- **T104.3 D0:** an application brings a UI description and never calls LVGL. Applies to P1 and P8.
- **T221 D6, D7, D18:** each deliverable has its own `version.toml`; the generic core app counts its own SemVer. Applies to P2.
- **T228-R20 and T228 §5 (menu speed note):** the trx64u exceptions are removed only when the code has moved; "Measure on the board first (time per key press, what is drawn again), then the concept". Applies to P4 and P7.
- **Project rules:** the SDK work follows "Generic app, no per-core code" (CLAUDE.md); no `tools/dev.sh` per step; UI is checked in the menu simulator and ue2emu with the `ux-review` skill before it goes to a person.

- **T239.3 D1 (Alex, 2026-11-19): a library declares its budget, sub-apps take the free heap.** A library declares in its header
  the heap bytes and the table slots (operations, states) it needs; the loader checks them against what is free before it loads
  the library and refuses with a message when they do not fit. Libraries load with the core app (they are part of it for that
  core); sub-apps load dynamically, on demand, into the free part of the heap. Alex (translated): "1 yes, but apps go into the
  free part of the heap. That is also the difference: libs with the core app, sub-apps load dynamically." Asked against a fixed
  share per library and the shared pool of today (OPS_MAX 400, STATES_MAX 320, `ops.h:206`; no heap of its own,
  `libboard.cc:35`).

- **T239.3 D2 (Alex, 2026-11-19): monitor, monitor server and ring move with trx64u into its library.** `monitor.cc` with
  `trxmon/` (the F4 machine code monitor, 6502 assembler and disassembler), `monsrv.cc` (the TRX64 runtime contract on TCP 4312) and
  `ring*.cc` (the Timewarp ring, T20) leave the app core with trx64u. Asked against "the monitor becomes a shared library for the
  6502 family, ring and server go with trx64u" and "everything stays in the app core"; Alex: "1, die anderen Cores haben das
  nicht" (1, the other cores do not have that).

- **T239.3 D3 (Alex, 2026-11-19): T213 D2 stays: one child spec per core, the A1200 first.** T239.3 uses those children for the
  migration of the per-core data (P3) instead of grouping cores. Alex: "Ja".
