## §1 The problem

Alex designs and reviews menus: the generic core menu, the trx64u rework (T228, decisions R1-R8), the host app. He wants to change a
menu and see it at once, and to drive it with the keys the way the board is driven.

Today there are two ways to see a menu, and neither is that:
- **The board image in ue2emu:** `tools/dev.sh riscv` builds coreapp.app on the builder (CLAUDE.md: warm about 13 s, plus the trip of the
  image back), then ue2emu boots the host app, starts the core, and the menu is reached by keys. Every change pays the whole chain, and
  the builder is shared with Vivado (`appslot.sh` waits).
- **The render benches:** `tests/coreapp/render/run.sh` builds the real `ui.cc`, MenuCtl and LVGL natively with the board stubbed and
  writes PNGs of scripted states (goldens, `mock_shots()` on `t228-mock`). Fast and exact, but not interactive: one state per scripted
  case, every source compiled again on each run (one `c++` call, `-O1`), and a menu TOML change needs the record regenerated by hand.

The parts:
- **P1 Build:** the real UI code built natively on the Mac, a change rebuilt in seconds (only what changed).
- **P2 Picture:** a window shows what the board's HDMI output shows: the canvas the app sets, placed and scaled in the output frame of
  the chosen video mode (1080p, 720p, 480p) as the MultiCore host does it (PX_POS, PX_SIZE, PX_OSIZE; ue2emu S45).
- **P3 Keys:** the Mac keyboard drives the menu through the same entry the board uses (`MenuCtl::key`, coreapp/src/run.cc:783).
- **P4 Menu TOML at run time:** a core whose menu is a TOML description (today trx64u: coreapp/cores/trx64u/menu.toml) shows an edit of
  that file without a C rebuild.
- **P5 One build with the benches:** the simulator and tests/coreapp/render compile the same sources against the same stubs and the same
  LVGL objects, so the two cannot drift; the bench's result does not change.
- **P6 Another tree:** a proposal on another branch (T228 `t228-mock` in its own worktree) runs in the simulator without the tool being
  merged into that branch.
- **P7 The host app:** the host app's menu (core selection, settings) runs the same way.
- **P8 Platforms:** what is built and proven on which machine (Mac arm64, Mac x86_64, Windows).

## §3 Decision

- **D1 A tool, not a test.** `tools/menusim/run.sh` (build and start), `tools/menusim/menusim.cc` (main: window, keys, loop, reload),
  `tools/menusim/keys.h` (the key table). Not in `ci/`, not in any pipeline stage, not in `ci/fundamental.txt`, not in an image.
- **D2 One source list.** The list the render bench derives from the core app's Makefile (`SRCS_CC` of
  host-app/target/u64ii/riscv/coreapp/Makefile, the application directories, `NOT_HERE`, the test-only sources) moves into
  `tests/coreapp/srclist.sh`, sourced by tests/coreapp/render/run.sh and by the simulator. Not copied.
- **D3 One rig.** The pieces of render.cc the simulator needs (the native pixel-layer port `trx_lv_*`, `Built`/`board_desc`, `Host`,
  `Rig`) move into `tests/coreapp/menu_rig.h`, included by render.cc and menusim.cc. The port gets one hook: a function called with each
  finished frame (the bench leaves it empty). The stubs stay where they are (`tests/coreapp/board_stubs.cc`, `fakes.h`,
  `video_stub.cc`); LVGL's objects come from `tests/lvgl_objs.sh` with host-app/software/hostapp/lv_conf.h, the same objects the bench links.
- **D4 Incremental build.** run.sh writes a Makefile into `.ci/menusim/<tree key>/` (`.ci/` is ignored) with one object per source and
  `-MMD` dependencies; `nice -n 15 make -j4`. Flags as the bench (`-std=gnu++14 -DVIDEOMODE_NO_BOARD=1 -DLV_CONF_INCLUDE_SIMPLE`, its
  include path), `-O0 -g` for compile speed. The build line of S1 is printed every time.
- **D5 The picture without LVGL's SDL driver.** LVGL's own driver (`lv_sdl_window`) needs `LV_USE_SDL` in lv_conf.h, which is the board's
  configuration (or a second LVGL build with other objects than the bench). Lost for that reason. Instead the bench's display stays (direct
  mode, RGB565, two buffers), and the frame hook (D3) copies the finished canvas into an SDL texture. The output frame is built as the
  MultiCore host builds it (ue2emu S45): the mode's active area black, the canvas at PX_POS with the size PX_OSIZE (nearest, or bilinear
  when the app sets smoothing), read from the PX_* values the app's own Video wrote into the rig's `PxRec`. The window shows that frame,
  scaled down to fit the screen when it is larger.
- **D6 SDL2.** Found with `pkg-config sdl2` (brew: `sdl2`, or `sdl2-compat` over SDL3 — this Mac has sdl2-compat 2.32.74), else
  `sdl2-config`; missing: run.sh stops with "menusim: SDL2 not found - brew install sdl2". SDL2's API, so the same code builds against
  MSYS2's `mingw-w64-x86_64-SDL2` on Windows.
- **D7 Keys.** A table from SDL keys to keyboard.h codes (cursor keys, RETURN, ESC, BACKSPACE, TAB, HOME, SPACE, letters and digits,
  F1-F8, shift+F1-F8), fed to `MenuCtl::key` as run.cc:783 does; `R_CLOSE` closes the menu, the key that opens it on the board (as run.cc
  takes it; named in §5) opens it again. Window commands with Cmd (Ctrl on Windows): Cmd+R reload, Cmd+S screenshot, Cmd+Q quit. On a Mac keyboard F1-F8 need
  fn or the system setting "use F1, F2 as standard keys"; the run prints that once.
- **D8 The menu.** `run.sh <core>` takes the core's descriptor from the board's core table (coreapp/src/table.cc, as the bench). A core
  with a menu TOML (default `coreapp/cores/<id>/menu.toml` when it exists, or `--toml FILE`) has it compiled at start with
  `tools/descrec.py compile --ops <ops file>` (the ops file gen_menu_rec.py checks against), and the record goes through
  `descrec_parse` + `descrec_apply` + `menu_build`, the way the board reads record 6. The file's mtime is polled every 250 ms; a change or
  Cmd+R compiles again and rebuilds the rig on the same page; a refused record keeps the last menu and shows the sentence. A core without
  a TOML (vc20, amiga1200 today) has its menu in C: an edit there is an incremental rebuild (S1).
- **D9 Headless mode.** `--keys LIST --shot FILE [--mode M]` runs the keys, writes the PNG and ends, without opening a window. It is
  the evidence path of §2 and lets an agent check a menu without a person.
- **D10 The stick.** The bench's fake filesystem; `--stick FILE` (one line per file: path and size) fills it, so a run shows the same
  files as a bench job (S6).
- **D11 Another tree.** `--tree DIR` builds that tree's application with this tool's scripts; the build directory is keyed by the tree's
  path. The tree must have the shared pieces of D2/D3 or the tool says so; for `t228-mock` (older than D2/D3) run.sh falls back to the
  bench's inline list of that tree (its run.sh is read, not changed).
- **D12 The host app.** `run.sh --host` builds the host app's UI with tests/hostapp/render's stubs and source handling the same way
  (shared, not copied), its canvas through the same frame hook and output frame, its keys through the host UI's entry.
- **D13 Platforms.** Built and proven on the Mac (arm64). The script and sources stay portable (no Mac-only API); x86_64 Mac and Windows
  are §4.

## §4 Out

- Everything behind the stubs: no core runs, no real stick, SD or network, no WiFi, no hand-over, no mode switch by a core, no frame
  timing. The simulator shows the menu; what the menu does to a machine stays with ue2emu and the board.
- Mac x86_64: not built or run here (no such Mac). **For Alex to decide** whether it stays untested.
- Windows (MSYS2 MinGW64 with SDL2): the build path is written (D6), never built or run here (no Windows machine). **For Alex to decide**
  whether it stays untested or someone with Windows tries it.
- No CI stage, no golden pictures of its own (the benches keep the goldens).
