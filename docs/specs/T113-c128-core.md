## §1 The problem

**Who:** Alex, who wants a Commodore 128 as one more swappable core on the C64 Ultimate board.

**What he wants:** pick "C128" in the core selector; the machine boots in C128 mode (BASIC 7.0, 40 or 80 columns), `GO64` gives the C64,
a disk from the stick loads, the C64U's keyboard types, the picture is on HDMI.

**What is there today.**

- **One FPGA C128 exists, and only one:** `MiSTer-devel/C128_MiSTer` (GitHub search 2026-10-18 for "c128", "commodore 128 fpga", "8563 vdc":
  the only other hits are forks of it for DE10-Standard and SoCKit boards, keyboard adapters and emulators/software). MiSTle-Dev (Till Harbaum) has
  17 repositories and no C128 (API listing, 2026-10-18). Nothing exists for a VDC outside this repository.
- **It is written for a different machine class.** All RAM and all ROMs live in one SDRAM (`c128.sv:1194-1213`, `fpga64_buslogic.vhd:23`
  "moved ROM images to SRAM"), the clocks are three PLL outputs of 47.29, 63.06 and 31.53 MHz plus a 32 MHz one for the VDC
  (`rtl/pll/pll_0002.v:36-42`, `rtl/pll_vdc/pll_vdc_0002.v:24`), the VDC RAM is an Intel `altsyncram` (`rtl/vdc856x/vdcram.v`), and the drives are its
  own 1541/1571/1581 (`rtl/iec_drive/`).
- **The partition is nearly full for a C64 already.** `pb_l2` has 18,000 LUT, 36,000 FF, 50 RAMB36 tiles, 80 DSP. The c64u core
  (T103) routes at **14,039 LUT (77.99 %), 11,795 FF, 34.5 BRAM tiles, 30 DSP**
  (`core-c64u-07b63882623b29f2/c64u.utilization_pb_l2.rpt`, builder cache, 2026-10-18 17:55, pr_verify passed); the highest density that ever routed is
  pipeline tim6 with 14,472 LUT (80.40 %, T103 spec, "Timing without drive B"); the 17,286-LUT build (96 %) did not route (same section). The brief for this
  analysis gives ~14,250 LUT (opt) as the measured threshold for cores.
- **The host's picture path offers a 16-entry palette raster and an RGB565 layer.** `pix_color[3:0]`, `pix_x[9:0]`, `pix_y[8:0]` is the only video output
  of the partition (`contract/layer2_ports.txt:234,247-248`); the pixel layer reads RGB565 from DDR2, source width up to 960, scale 1-3, over the C64
  picture (`host/pix_layer.v:1-12`).
- **The host's keyboard is the C64 matrix:** `c64_keys[63:0]` (`contract/layer2_ports.txt:121`, `host/app_input.v:10-29`).

**Why it matters:** the C128 is a Commodore machine on Alex's list and the nearest relative of what the board already is. It is also the first core
that wants more than the partition holds in **both** LUT and block RAM (§3 D4, D9), so what is learnt here decides how big a core can be.

**Break the problem into parts, MECE** (§2 is checked against this list):

- **P1 Source and licence.** What is taken, under which terms, what is not.
- **P2 Shape.** Our C64 core plus the C128's chips, or the MiSTer core ported.
- **P3 CPUs and clocks.** 8502 at 1 and 2 MHz, the Z80 and the boot hand-over.
- **P4 Memory and ROMs.** MMU banking, 128 KB RAM, 72 KB ROM, VDC RAM, and where each lives.
- **P5 The 40-column picture** (VIC-IIe).
- **P6 The 80-column picture** (VDC) and how both reach HDMI.
- **P7 Drives and media.**
- **P8 Input.** The C128's extra keys.
- **P9 Application, identity, ROM files, Freeze.**
- **P10 Size and timing** against `pb_l2`.

**F6 Memory (P4).**

- A 4 KiB RAMB36 holds 4 KiB at 8 bits (measured: the VDC with 16 KiB reports 4 tiles, with 64 KiB 16, F3).
- RAM: 128 KiB = **32 tiles**. The VIC-IIe reads one of two 64 KiB blocks every cycle (hardware fact: the MMU selects the VIC bank), so both blocks must be at line rate: BRAM.
- ROM: the MiSTer image `boot0.rom` is `0x12000` = **72 KiB** (`c128.sv:729`; README: C64 BASIC + KERNAL 16, C128 editor + Z80 BIOS + KERNAL 16, C128 BASIC 32, character ROM 8) = **18 tiles**.
- The c64u core's 34.5 tiles contain RAM 64 KiB (16) and ROM 32 KiB (8) (`cores/c64u/c64_mem_c64u.v:1-8`); the remaining **10.5 tiles** (SID, FIFOs, colour RAM, drive; by difference, computed) stay.
- C128 in BRAM only: 10.5 + 32 + 18 + 4 = **64.5 tiles** (VDC 16 KiB) or 76.5 (VDC 64 KiB) against **50**. With the ROMs in DDR2: **46.5** (58.5 with VDC 64 KiB). What is left for ROM in BRAM
  after RAM and the 16 KiB VDC is 3.5 tiles (14 KiB): not one of the four images fits. The c264 core already uses 43 tiles for a 64 KiB machine (F4).
- DDR2 as a ROM source: a 32-bit client read takes "about 0.4 us" (`host/ddr2_port.v:5`, measured with the MIG; the T85 and T91 specs quote it). A 1 MHz cycle is 1.015 us (PAL, computed: 31.5278 MHz / 32 = 0.985 MHz),
  a 2 MHz cycle 0.51 us: a ROM byte from DDR2 fits one 1 MHz cycle with margin and a 2 MHz cycle only without queueing. The NES core already puts its cartridge behind DDR2 line caches that hold the machine on a miss (T95
  history, 2026-10-15); that is the precedent for a stall-on-miss ROM. The VDC's display fetch needs its RAM at line rate; the CPU's access is by register with a busy flag (hardware fact, `vdc_top.sv:419` shows the status bit).

**F7 Video (P5, P6).**

- *40 columns.* The only picture the partition can carry is the palette raster (`pix_color[3:0]`, `pix_x`, `pix_y`); the host scaler shows a 400-dot x 270-line window of it (T91 D6, `vic_scaler.v`).
  Our VIC is Kawari's. The VIC-IIe adds `$D02F` (extra keyboard lines K0-K2) and `$D030` (bit 0: 2 MHz, display blanked while set) (hardware fact; MiSTer: `video_vicII_656x.vhd:283-300` "VIC-IIe registers and state / turbo mode and test mode").
  Kawari uses `$D02F`/`$D030` only when its extra registers are activated by its magic key (`registers_scaled.v:1078-1092,1225-1235`); the turbo block already decodes `$D030`/`$D031` (`vendor/icepi/c64_turbo.v:195-217`), so the two meanings have to be arbitrated.
- *80 columns.* The VDC delivers 4-bit RGBI at 16 MHz (`vdc_video.sv:59` `rgbi`), 640 x 200 (80 characters of 8 pixels), interlace up to 400 lines. It does not fit the 400-dot window. The pixel layer takes RGB565 from DDR2, width up to 960, scale 1-3, position free, over the C64 picture and
  under the menu (`host/pix_layer.v:1-12`): 640 x 400 (lines doubled) x 2 B = 512 KiB per buffer, three buffers 1.5 MiB (computed, the Amiga's scheme, T85 D5), shown at scale 2 = 1280 x 800 (16:10; a 4:3 image would need
  1067 x 800, which scale 1-3 cannot give).
- *Both.* The layer can be switched on, off or moved by the application, so "40/80" is a layer switch and a "side by side" like MiSTer's is possible in principle; its geometry is not proved.
- *Clock.* MiSTer runs the VDC on its own 32 MHz (`pll_vdc_0002.v:24`); on `sys_clk` (31.5278 MHz, `fpga64` and the VC-20, C264 cores use it, contract C1) it would run at 98.5 % of its speed (computed). Nothing is locked to the VDC's frame, because the layer shows whole buffers.

**F8 CPUs (P3).** The 8502 is a 6502 with the 1/2 MHz switch (hardware fact); our `cpu6510` is 853 LUT (F4) and there is a turbo CPU (`cores/c64u/c64_turbo_c64u.v`, 517 lines) whose `$D030` bit-0 logic is a related mechanism. The MMU's `$D505` reads
`d4080 & reg_os & exrom & game & fsdir & "11" & reg_cpu` (`mmu8722.vhd:261`): bit 7 is the 40/80 key line, bit 0 the CPU. The Z80 starts first on a real C128 (hardware fact; the BIOS lives in the second 16 KiB ROM). The MiSTer MMU takes its starting CPU from an input, `cpumode` ("0" Z80, "1" 8502,
`mmu8722.vhd:16-17,111`), which `fpga64_sid_iec.vhd:627-628` ties to `force64` only; with `cpumode` = 1 the MMU also sets the C64-mode pins (`reg_fsdir/exrom/game/d4080`, `:112-115`), so "start on the 8502 in C128 mode"
is not a flag but a state the Z80 BIOS would otherwise have produced: unproven. T80 would be the first Z80 in the repository: T91 and T92 are specified and not built (`TODO.md:63-64`, no `cores/zx*`).

**F9 Drives (P7).** The contract has the IEC lines ATN, CLOCK, DATA and no SRQ (`contract/layer2_ports.txt:5-7,139-141`); the C128's fast serial and the 1571/1581 burst mode use SRQ (hardware fact), so they cannot exist without a contract bump
(every published core invalidated, `contract/README.md`). The c64u core carries 1541 and 1581 on one drive A; the 1571 bundle (decode, parallel cable, fast serial, side, 2 MHz) was removed on Alex's word, "We drop the 1571" (2026-10-17, translated;
`cores/c64u/gideon/PROVENANCE.md:41`, T103 §"The 1571 is removed"); both drive instances together saved 20 LUT (pipeline 881 -> 882, T103). A C128 on the 1541 loads at C64 speed (the kernal falls back to the slow serial; S11). CP/M
boots from a CP/M-formatted disk in a 1571 or 1581 (hardware fact); a 1541 cannot read it.

**F10 Keyboard (P8).** The C64U's own keys are the C64 matrix and the host passes 64 bits (`host/app_input.v:10-29`, `contract/layer2_ports.txt:121`). The C128's extra keys — ESC, TAB, ALT, HELP, LINE FEED, NO SCROLL, the 17-key numeric pad, four separate cursor keys,
CAPS LOCK and the 40/80 DISPLAY switch (hardware fact) — read through three extra matrix columns on `$D02F`, CAPS LOCK on its own sense line and 40/80 on `$D505` bit 7. MiSTer maps them from a PS/2 keyboard and, for the C64-shaped keys, with a "FN" layer
(F1 = ESC, F2 = ALT, F3 = TAB, F4 = CAPS LOCK, F5 = HELP, F7 = 40/80; `fpga64_keyboard.vhd:226,242,401-403,437`). A USB keyboard reaches the core through the application, which can write core registers in the 17-bit `cw_*` window (`contract/layer2_ports.txt:93,126`):
no contract change is needed for extra keys, but the application (T104) needs a descriptor for them.

**F11 Application (P9).** T104 D9 (2026-10-18): "Gideon's application is replaced for every core"; the generic application plus libraries (1541/IEC/GCR named for the C64, VC-20 and C16), the C64U vanilla core keeps Gideon's application longest (T104 D10). T93's blueprint is superseded by T104
(`TODO.md:65,75`). `core.toml` knows `app = "ultimate" | "blueprint"`, `app_ref`, `app_make` (`cores/c64u/core.toml`, `cores/atari800/core.toml`). Nothing in this spec decides it (Q10).

  after it (VICE `vdc.c`: the pointers are reset after an odd frame only), changed in the VDC's `vdc_signals_v.sv` (5.9). Open with Alex: the 7-pixel left

### Effort verdict

**Not easy.** Main risk first: **no variant that keeps the drive, the VDC and the Z80 fits `pb_l2`, in LUT or in block RAM, with what is measured** (F5: 97-102 % with the Z80, 88-94 % without it, against 80.4 % as the densest layout that ever routed;
F6: 64.5 tiles in BRAM against 50). The BRAM problem has a known answer (ROMs behind a DDR2 cache, as the NES) and still adds risk at 2 MHz; the LUT problem has none yet (the VDC as it is costs 2,472 LUT and 3,245 FF, the Z80 1,512, and the drive stays).
Second: the work is a surgery on our C64 core's address decode (MMU, `c64_pla.v`, `c64_top_c64u.v` 1,913 lines), the VIC-IIe registers and the 8502 clock, plus a new frame writer for the VDC, a key path for 25 extra keys, a Z80 that does not exist in the repository yet, and
sources that Vivado rejects as they are (F2). Nothing of that is a copy; "build it right away" is not available before Q1 and Q2 are answered.
What would turn the verdict: Z80 and CP/M out (Q4) *and* an accepted density above what has routed *or* a smaller VDC; a measurement build of the c64u tree with MMU and VDC and no glue would show the real routing limit before anything else is written.

### §5.4 The ROM in the DDR2 behind a line cache, built (2026-10-22, branch `t113-mono`, asked by Alex: "Yes, the C128's ROM in DDR2 then please, give it a try", Q3 (a))

**What is built** (`-DROM_CACHE`; the 16-byte ROM stub of §5.3 is gone):
- `cores/c128/c128_romc.v` (core clock): a direct-mapped cache of 512 lines of 16 bytes (8 KiB), one block RAM word per line = 128 bit data + 4 bit tag + valid, **2 RAMB36**. The key is the
  *linear* ROM address (bank * 4096 + offset, 72 KiB = 17 bits; the banks come from the MMU map in `c128_map.v` as before), the index is the 9 line bits xor the top 4 bits of the line
  number, so a bank switch needs no invalidation (another bank is another address) and a fixed bank and a switched one do not fight for the same lines (the scheme of `nes_mem.v`, T95 D13).
  A hit answers in the clock after the command, as the block RAM ROM did. On a miss `cmd_ready` goes low and `rvalid` stays low until the line is in. A flush walker clears the valid bits
  in 512 clocks after a reset of the core; lookups wait for it. Counters `n_hit`, `n_miss` (32 bit).
- `cores/c128/c128_rome.v` (`ui_clk`): one 128-bit read at a time on the host's engine client `e_*` (data on `c_rd_data` with `e_rd_valid`, `mig_arb`'s contract), toggle request in, toggle
  done out, as the NES core's `c_*` client. The image is at byte `0x01C00000` (parameter `ROM_BASE_W`), line n at +16 n: the application fills it through the host's DDR2 access, like the
  cartridge and the REU images.
- `layer2_c128.v`: `e_*` is shared with the VDC frame writer (`c264_pixw`): while a line fetch is open (`rom_owns`) the frame writer's `e_rdy` is held low and it waits.
- **How the machine is held:** by the stall the C64 core already has for slow memory (`c64_top_c128.v`: `mem_rdata_valid_r` is cleared when a read is accepted, `vic_stall = !mem_rdata_valid && a phi2
  edge`): no CPU cycle, VIC cycle or Z80 cycle passes until the word is in, and with `cmd_ready` low the arbiter keeps every other command (RAM too) waiting. No clock gate was added.
  Not held: the drive and the SIDs keep running in real time (a miss is about 0.6 us).

**Bench** `cores/c128/sim/run_romc.sh` (iverilog; `tb_romc.v` with `c128_romc` + `c128_rome` + the NES bench's `ddr2c_model.v`, 293..693 ns per read, `c_rdy` low a quarter of the clocks; sys clock 31.5 MHz, a
C64 cycle = 32 clocks, ui_clk 75 MHz). The machine in the bench presents a word address, takes the word in the clock `rvalid` is up, and starts the next read `period` clocks later. Result:
`PASS tb_romc`, 112,716 reads, 0 errors. Cases: flush then first read (21 clocks); a miss holds 19 clocks (about 0.6 us) and `cmd_ready` is seen low during it; the same line again answers in 1 clock without a DDR2
read; the last word of the line likewise; the same offset in all 18 banks, repeated, and A/B/C reads of lines with the same index and different tags (conflict misses refetch, data right); the app
rewrites the image: a cached line stays old until the flush, after the flush the new bytes are read; a program-like pattern (eight loops of 200-800 bytes in kernal/BASIC/editor banks plus random
character-ROM table reads over 4 KiB, a stress for an 8 KiB cache): at 1 MHz (a ROM read every 32 clocks) the machine is held **4.4-4.9 %** of the time, 93 % hits; at 2 MHz (a read every 16 clocks, a bench-side
stimulus: `$D030` is still not acted on) **9.0 %**. Negative controls (`run_romc.sh` runs them; each must fail and does): `-DROMC_MUT_NOHOLD` (a miss is answered at once: `FAIL: read 00100 got 0000 want 3510`),
`-DROMC_MUT_NOTAG` (the tag is ignored, a bank switch is not seen: `FAIL: read 102a4 got a47f want 5934`), `-DROMC_MUT_NOFLUSH` (`FAIL: read 01230 got e0bb want 2d08`, the stale line after the image changed).

**Still not built:**
- the application side: the register for `ROM_BASE`, the loader that writes the 72 KiB image into the DDR2 (the host's DDR2 access can do it, no core-side window was written), a flush request from the app (the walker runs on the core's reset only; an image rewritten under a running core is not seen until the next reset);
- the 2 MHz mode (`$D030` bit 0 stored, not acted on; the bench's 2 MHz is a stimulus only), so the hold cost at 2 MHz is the bench's 9.0 %, not a measurement of the machine;
- the Z80's behaviour (it is a structural stand-in on the same bus, §5.3); the turbo CPU's second port into the ROM is tied off (`NO_TURBO`);
- **no simulation of the whole core with the cache in it:** the stall (`vic_stall`) is the core's existing mechanism for slow memory, and the bench proves the cache's side of it (valid late, ready low); that the VIC, CPU and
  CIA timing hold exactly across a miss in the real core, and that the frame writer's wait for a line fetch costs no overrun (`c264_pixw` `overruns`), is argued, not shown;
- the drive and the SIDs are not held during a miss (about 0.6 us each); an IEC fast loader that counts cycles could notice;
- the VDC's own DDR2 use (its frame writer) and the ROM fetches share `e_*`; no measurement of the added latency of the frame writer; one placement.

**Task 2, why the machine stays in the C64 mode after a reset (cause found, fixed).** The C128 Z80 BIOS (`$D000` of the editor/KERNAL ROM, seen at `$0000`) writes `$D505 = $B0`, reads it back, then reads
`$DC01` with `$DC00 = $7F` and goes to the C64 mode (`OUT $D505 = $F1`) if bit 5 (the C= key, column 7 row 5) is 0 or if GAME/EXROM read low (disassembled from the ROM file: `0046`-`007A`, branch to `0054`).
The real-ROM simulation with a machine reset at 1.5 s (no key, no cartridge) shows that second start: the Z80 reads `$DC01 = $00` (trace `cy 1480064 ... a=201e R d=00`, then `$D505 W f1` at cycle 1,480,113).
The reason is in the bytes the Z80 fetches before that: at `$005A`-`$0064` it reads `$20` for eleven bus cycles, instead of `0F DC 3E 08 ED 79 0D ED 79 0E 03` - the screen code of a space, the VIC's screen
fetch. **`c64_top_c128.v` `z80_ce` (line 604 before the fix) took no notice of BA**: the 8502 is held by RDY = BA (`cpu_rdy`), the Z80's clock enable was `vic_phi2_n && !vic_stall` only, so in a badline the
Z80 ran on while the VIC had the bus and read the VIC's screen bytes as program and port data. At the first start the VIC's display is off (DEN = 0 at power-on), no badlines; after the KERNAL has run, DEN is on, and
a machine reset does not reset the VIC (its registers are not touched by `rst`: `registers_scaled.v` has the reset of every visible register commented out, as the chip has none; the VIC's own `rst` is the power-on
one, `vic_reset_req` is tied 0), so every later Z80 start runs with badlines. A BIOS fed with garbage ends in the C64 mode with a MMU/RAM set up half by garbage (the torn picture: the VIC reads another RAM block
or bank than the KERNAL fills). "Restart core" does not reset the VIC either, so it had the same fate. Fix: `z80_ce` additionally needs `vic_ba` now and in the cycle before (`z80_ba_q`; BA falls three cycles before
AEC and rises with it). Bench `sim/run_z80ba.sh` (synthetic ROM, tools/gen_c128_test.py `z80ba`): at each start the Z80 adds up 512 bytes of its BIOS window, the 8502 switches the display on, the bench resets
the machine in the idle; start 1 and start 2 give the ROM's sum `0d`; control `C128_MUT_Z80NOBA` (as before): start 2 gives `e5`, FAIL. `sim/run_realrom_reset.sh` (local, real ROMs): C= held at the start gives the C64 mode (screen at 3.0 s: `**** COMMODORE 64 BASIC V2 ****`, `64K RAM SYSTEM  38911 BASIC BYTES FREE`, `READY.` - the board's text), and a 50 ms machine reset at 3.1 s brings

**Task 1, the picture after a reset; the frame phase.** The VIC-IIe is not reset by a machine reset and was not before: `c64_core_c128.v` ties `vic_reset_req` to 0, the VIC's `rst_dot4x` is the power-on `rst`, and

colour RAM and character ROM select all 0 in its half-cycle). The consumers (read): the register block and the `bus` mux (VIC data in `vic_dbi`/`vic_dbh`), the select decode, `ras_locked/cas_locked`
(RAS/CAS of the VIC's own cycle); the MMU (`c128_map` `.rst`) must stay on `cpu_reset` (a machine reset resets the MMU). Now only `vic_reset` (the power-on) resets the arbiter's VIC side and the registers; in the
CPU's half-cycle `cpu_reset` selects nothing, as before. Bench `sim/run_reset.sh` (reset in line 159, held 2 ms = 63 lines): every frame is 628,992 clocks, the one with the reset in it too; the arbiter selects
RAM/colour RAM/character ROM for the VIC in 29,640 of the 63,226 clocks of the reset; control `C128_MUT_ARBRST` (the old wiring): 15 selects, FAIL. **Check 1 (the frame period) passes with the old wiring too:** the
frame counters never came from the arbiter, so the displaced picture of the report is not this; it is evidence that the VIC's timing is not reset, not a control.

*The shift against the scaler's one lock - cause found in the code. **The repayment described in this paragraph (al_hold, the window and the quiet rule, their bench and controls) did not hold on the board and was removed in 5.7: the VIC does not stall any more; `sim/run_phase.sh` is the bench of 5.7.** The analysis of the cause stays.* The host's `vic_scaler` locks once, on the first VIC frame after its reset or after a decoupler release, and
then runs free at the nominal frame period (D16a of the VC-20 core). Everything that makes the VIC's frame longer or shorter in real time afterwards moves the picture. In this core the ROM in the DDR2 does:
a ROM miss holds the whole machine (`vic_stall`, spec 5.4) and, since 5.4, the VIC's dot phase with it (`vicii_c128.v`), so **every miss delays the VIC's raster by the clocks of the fill and the delay is never
paid back**. Measured in the real-ROM boot with the cache (model of the DDR2 port, 293..693 ns per read): the frames of the first second are 110-130 clocks longer than 628,992 each, 2,557 clocks (1.3 lines) of
phase lost by frame 17, on the real DDR2 more (the arbiter of the host has other clients); the board's "moves down shortly after the start" fits. The same hold of the gate paid for pauses in whole frames
(`shut`, resume at `FRAME - 1`) since T12; the stalls were not counted. Fix, in `c64_core_c128.v`: `shut` counts the stalled clocks as well (lost phase modulo one frame); `ph_cnt` is real time modulo one frame
since the power-on release (the phase the scaler locked to); when the loss is more than 2 lines (`AL_TH`, 4,032 clocks) in the first 300 frames after the machine's release (`bwin`, restarted by the application's
reset, so the window opens when the machine starts), or more than 1 line (`AL_MIN`) after three frames without a stall (`qcnt`), the gate holds the machine (`al_hold`, the pause's own mechanism) until the loss
is a whole frame - at most one frame of 20 ms, the picture is not blanked for it (`halted` stays 0, `blank(c64_halted)` is the host's) - and a pause by the user waits for the same `shut` and so ends in phase
too. Cost: up to one frame of hold per repayment (one was seen in the first second of the real-ROM boot, frame 18: phase 2,557 -> -443 clocks), none in a program that does not miss. **Not repaired:** a program that misses permanently (two ROM sets fighting over the same cache
lines) is repaid only when it is quiet for three frames, so its picture creeps by the loss in between; the cure is a stall that holds the CPU only (RDY, as for BA) with the VIC running - the memory port
and the character ROM fetch of the VIC would need a second path - a larger change, not done. Bench `sim/run_phase.sh` (program `romwalk`: after six frames it reads 1,024 ROM lines, every one a miss; phase = frame start
modulo one frame, read from the VIC's raster): window rule - largest drift 2,779 clocks, last frame 1,224 clocks (limit 6,000); quiet rule (build with `C128_SIM_BOOTWIN`, window 4 frames) - largest drift 13,338
during the walk, last frame -46; controls `C128_MUT_NOALIGN` (stalls not counted, no hold): last frame 13,338 in both, FAIL.
Not excluded: a change of the System Mode (`vm != vmode`, `c64_core_c128.v`) restarts the VIC's timing (T40, kawari `reset_req`) and moves the picture as well; nothing in the application writes it during the

### §5.7 The VIC never waits for the ROM (2026-10-24, Alex's decision after the board run of `c128.cfw` c64b45c4...)

mode: stable, but the VIC flickers and shows artefacts while typing and while the screen scrolls (LIST). `trxdbg.sh mode` after the drift settled: PAL, switches 0, VIC 312 lines x 2016 = 628,992 clocks per frame, scaler

**Cause (read from the code, consistent with every observation; the stall counter itself is not readable on the board in that build).** A ROM-cache miss stopped the whole machine, VIC included (`vic_stall`, 5.4), so every
fetch from the DDR2 made the VIC's frame late by the fetch time, for good; the host scaler locks once, so the picture slides down by the sum. 5.6 repaid the loss with a hold - fast only in the first 300 frames (6 s)
after the release, later only after three stall-free frames; the board matches that boundary (cursor 2-5 s, drift 2-3 s later) and the repair's holds delayed the start and tore rows. The ROM cache index is
`line[8:0] ^ {line[12:9], 5'b0}`; computed for the image's 4 KiB banks, **the C128's character ROM (bank 17), editor (bank 4, `$C000`, the IRQ/key scan/cursor code) and KERNAL low half (bank 6) all use slots 0-255 and the
character ROM overlaps the editor in all 256 of them**, while in C64 mode the character ROM (bank 16) uses 256-511 and the IRQ code (KERNAL bank 2) 0-255: no overlap but the `$FF48` IRQ stub. So in C128 mode the editor
and the VIC's glyph fetches evict each other in every frame (a miss each, every frame), in C64 mode only the cold start misses: the drift in C128 mode only, the flicker in C64 mode (the screen editor's own misses
freeze the VIC mid-frame while it runs).

**Decision (Alex, 2026-10-24, on the coordinator's recommendation "the VIC never stalls; the character ROM gets a fixed store the VIC reads directly, only the CPU waits for the ROM cache"):** "ja dann machen wir das mal so"
("yes, then let's do it that way", translated). Built as follows.

**What changed.**
- **Character ROM store** (`c128_chr.v`): the two character sets of the image (bytes `0x10000-0x11FFF`: C64 set, C128 set, 4 KiB each - verified: `rom_char_addr` is 12 bits, the set is `c128_n`) are two block RAMs (2 RAMB36, 4K x 8) written
  by the application (register page E: `CHR_ADDR` `090/091`, `CHR_DATA` `092`: write stores and adds 1, read reads and adds 1; the app writes the 8 KiB with the ROM image and reads them back) and read by the arbiter's
  character-ROM select in the clock after the address, like RAM. The VIC and the CPU's view of the character ROM no longer make a memory command. The bitstream holds no ROM byte (the store starts empty; a simulation preloads it).
- **The ROM line cache never keeps a command waiting** (`c128_romc.v`, `c64_mem_c128.v`): the answer to a ROM lookup is in the clock after the command, as for RAM - the word (`rvalid`) or `rmiss`; a miss starts the DDR2
  fetch (one at a time; a lookup that misses while a fetch is open only reports the miss) and the line is written into the cache when it arrives; `cmd_ready` is always 1. A flush makes lookups miss and drops a fetch in flight.
- **Only the CPU waits** (`c64_top_c128.v`): `rom_miss` (a pulse in the clock after the command, known at ph 7 of the 1 MHz cycle, ph 23 for the 2 MHz mode's second cycle: the moments the 8502 captures its data) and
  `rom_wait_q` (to the end of the cycle) make `rom_hold`; `cpu_rdy` has `&& !rom_hold` (the 8502 repeats the read in its next cycle, as under BA) and the Z80's clock enable `&& !rom_wait_q`. `vic_stall` is constant 0: the
  VIC's phi generator and dots, the CIAs, the SIDs, RAM never stop for the ROM. A missed line costs the CPU one cycle (the fetch is 15-27 clocks in the model, a cycle is 32).
- **The 5.6 repair is removed** (`al_hold`, `bwin`, `qcnt`, the stall counting into `shut`, `C128_MUT_NOALIGN`, `C128_SIM_BOOTWIN`): if the VIC never loses time there is nothing to repay. Kept: `ph_cnt` (the cold start's release
  at the power-on frame phase) and the whole-frame pause (`shut`, as since T12). The pause and the 8502/Z80 still cost the VIC nothing.
- **Debug words** (page E, read-only for the application): `ROM_HITS/ROM_MISSES` (fetches), `ROM_WAITS` (CPU cycles held), `ROM_FILL_MAX` (longest fetch in clocks), `FR_MIN/FR_MAX` (the VIC's frame length measured
  in the core, cleared by `DBG_CLR`, which the release writes). **JTAG cannot read page E**: `host/top.v` answers only pages 0, 1 and 5 of the IO block (`trx_sys.v`); a read of E044 returns the "not answered" word
  `0x81..` that `trxdbg.sh` reports as "is a TRX64 design loaded?". The tool now refuses such offsets with that explanation. The application prints the counters to the console (`[c128] rom: hits, fetches, CPU cycles held,
  longest fetch; VIC frame min..max`) every 2 s when one moved (`trxdbg.sh console follow`). The host's own words still work: `trxdbg.sh mode` shows the measured VIC frame length.

**Block RAM, the numbers (`mono/reports/b_r5/utilization_hier.rpt` of the build before; 75 tiles on the chip).** Before: 74.5 (RAM 128 KiB 32, VDC 16, ROM line cache 2, SID waveforms 4, scaler 4, overlay 3.5, pixel
writer 2, pixel layer 2, console ring 2, boot ROM 2, USB/cartridge/misc 4.5+). The 8 KiB store needs 2 tiles. Freed: **the host's menu overlay (`host/overlay.v`: 3 RAMB36 + 1 RAMB18 = 3.5 tiles)**, replaced in this flat build by the
existing port-compatible stub (`mono/stubs/overlay_stub.v`, `core.toml mono_env` `TRX_STUB=overlay`): the generic core application draws on the pixel layer (`pix_layer`) and never writes the overlay's registers (grep of `coreapp/`);
`host/` is not touched. Not freed: the console ring (the JTAG console Alex reads), the VDC (Q5), the RAM, the cache (its 8 KiB are now only for the CPU's code; narrowing it to one tile would need an 8-byte line or a
two-clock lookup: left). Result: **73 of 75 tiles** (`mono/reports/b_r6/utilization_hier.rpt`: `chr` 2 RAMB36, the overlay gone, the rest as before) - 2 tiles left, not a pool: the next block RAM user has to find its own..

**Open, deliberately (not covered by the CPU hold):** a ROM read by the REU's DMA or the application's DMA window while the line is not in the cache gets the previous word once (they cannot be held by RDY); the REU
transfers from the ROM area are not benched. The Z80 at half speed (5.5) is as before.
