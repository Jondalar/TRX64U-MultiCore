# T192 architecture (arc42): one functional core, many user interfaces

Epic spec: `docs/specs/T192-ui-architecture-epic.md` (requirements R1-R33, tensions C1-C8, questions §6). Status: draft
(2026-11-07; 2026-11-15 sync: §1-§5 describe `main` of 2026-11-07, the as-is. Since then built: token handshake and remote confirm (§6.2, T192.1), destructive REST ops ask (D18/D19a; §8's "REST bypasses them" is no longer true), the shared service in `uicore/`. Not built: search overlay, safe mode, bundle load (§6.2).). Decisions D1-D14 are in the epic §3; text marked "Chosen" follows them, the rest is analysis. Paths: host app `host-app/software/hostapp/`,
core app `coreapp/src/`.

| Goal | Meaning | Requirements |
|---|---|---|
| G1 Separation | functional layer without UI in both apps; views are clients | P1 |
| G2 Contract | written, versioned interface: state, intents, ops, events | P2, R1 |
| G3 Selectable bundles | key map, layout parameters, skin as data | P3, R4, C4 |
| G4 Search | one index over settings, tabs, ops, files | P4, R6, R5 |

## 2. Constraints
- C++ on the board's RISC-V application (rvlite, FreeRTOS), Gideon's drivers (USB host, FatFs, network, SD) (T192 D1).
- LVGL renders into the TRX pixel layer, no framebuffer of its own (canvas 960x540 or the mode's size below 960 wide).
- XC7A50T board, host immutable (contract/host_pin.txt); one host app, one generic core app for every core.
- Single-task ownership: `MenuCtl` is touched only from the menu task (`uiapp.cc`, the service's menu-task handshake); other tasks queue (the service's intent queue).
- Cooperative host UI loop: one task, polling, modal flows block it (`hostui_run`, `hostui.cc:6835-6945`); no queue, no event bus.
- LUT and DDR2 are shared with the cores (#32, C5/C6); the upper DDR2 ring is the TRX64 large core's (`FW_STAGE_*` in DDR2 for staged images).
- Speed comes from pre-rendered pictures and caches (#4, #2, D15), not from rendering faster (C8).
- `app/view` is shared by both apps; LVGL types must not enter an API.
- Ops and REST names are shared (`machine.warm_reset`); T106 host web is single-writer (mailbox + snapshot).

## 4. Solution strategy
- O1 **Chosen (D1, D14).** Headless functional core, views as clients; ONE shared framework for host app and core app (state snapshot, intents with stable ids, event stream, jobs with confirmations, token, WebSocket), domain logic per app. Freedom comes from the boundary, not the language.
- O2 **Chosen (D12, D14).** Host: `host_core` domain in new non-LVGL files on the framework (~3-3.5k lines move out of `hostui.cc`); the host menu is rebuilt declaratively as its client and compared 1:1 in ue2emu (S44) before it replaces `hostui.cc`. Not "flow by flow in place", not chosen.
- O3 **Chosen (D12).** Flows as job state machines `Job{id, kind, state probing|asking|running|result, lines, progress, choices, can_cancel}`; `UpAsk/UpDone/FmPage/FwAsk` already are view-model data.
- O4 **Chosen (D12, D13).** One `start_sequence(entry, mode)` for menu start and direct boot; the T152 lock rule stays (lock for a full image, not for DFX).
- O5 **Chosen (D14).** Core app: leaks leave `MenuCtl` (pad wizard, monitor, timewarp keys, write-back, Wi-Fi, T64, volume, file manager, startup/home), leaving navigation, dialogs and rows.
- O6 **Chosen (D3, D4, D11, D14).** Key/intent route into the menu loop (queued like `uistate_request`), stable item ids, `select/activate/set` through the same confirm/dirty rules; a remote client with the token answers every confirmation; menu key map becomes a table "key -> intent".
- O7 **Chosen (D14).** Versioned event stream and schema (today pull snapshot with `seq`); T153 D7.1 lint is a later check.
- O8 **Chosen (D2, D5, D7, D9, D10).** Bundles are plain TOML data (key set, colour scheme, text mode; no density): TRX64 default, prepared C64U classic, host default plus per-core override, safe mode C=+S at host start. Renderer in a `.u2a` not chosen (T104.3 D0).
- O9 **Chosen (D3, D8).** Search index over settings, pages and actions (`MenuTree`, `Setting`, `OpRegistry`, nodes); no files; activation as intent through the confirm rules; only chord C= SPACE, the overlay owns every key.
- O10 **Chosen (D6).** Text UI as cell-grid view, local on HDMI and remote over `ws://`; estimate ~1000-1500 lines for the core app (estimate, not measured); graphic screens get a text fallback. Telnet/SSH not chosen.
- Not chosen: Rust backend (D1); host-only `host_core` with a separate core-app contract (D14 B); type-to-find (D3); files in search (D8); density choice (D10); encryption (D4).

### 5.3 To-be (D12, D14)
```
 view_lvgl | view_text (local grid) | ws:// terminal client | view_web | remote script
        \        |                      |                     |        /
          shared framework (T192.1): versioned state snapshot, intents + stable ids,
          event stream, jobs/confirmations, token, WebSocket, search index
        host_core (T192.2)                     core-app domain (T192.3)
   start_sequence, flash, update, files     ops, settings, media, write-back, browser
        UI-free modules (host)               OpRegistry / engines (core app)
```
- Views: LVGL (graphic, today's), text grid (HDMI and `ws://`), web (T106, on the same stream), terminal client; every view only draws state and sends intents.
- `host_core` is headless; the host menu is a declarative client of it and replaces `hostui.cc` after ue2emu parity (D12).
- Core app: `MenuCtl` shrinks to navigation, dialogs and rows on the framework; the pad wizard, monitor, timewarp, write-back and file manager sit behind ops.
- Bundles (TOML) feed the key map (key -> intent) and the view parameters; the search overlay is a framework feature drawn by each view.

## 6. Runtime view (as-is)
- Host UI loop (`hostui.cc:6835-6945`): drain up to 24 keys, `apply_updates`, `lv_refr_now`; every 3 s (not within 1.5 s of a key) `refresh_status()` polls media/net; countdown; `lazy_pass`; `web_pump`; `picture_tick`; `vTaskDelay(10)`.
- Modal flow: probe, build text, block in `host_getch` wait; during it no web command is served ("answered busy and dropped", `hostui.cc:3797-3800`).
- Host web: web task writes a command into a one-slot mailbox (`webui.cc:13`), UI task takes it in `web_pump` (`6020`), republishes the `WebSnapshot` when `fingerprint()` changes.
- Core menu task: owns `MenuCtl` (`run.cc:517`), routes keys (`run.cc:837-850`: app dialog and picture confirm first), relists the browser every 2 s (`run.cc:902-904`).
- `uistate_request`: other tasks queue a snapshot request; the menu task fills it; 3 s wait (`uistate.h:20-24`).
- Core start sequence (atomic, one task): stage -> last abort check (`abort_key` after `vTaskDelay(200)`, `hostui.cc:3690-3695`) -> `core_swap` (cuts the old core) -> `core_jump`; `lock_flash` only in `start_full` and the full branch of `direct_run`. A firmware write never runs with a core start (`flashfw.h` staging contract).
- Direct boot (T135) runs before the UI exists (`direct_phase` `6530`, `direct_run` `6486`).

### 6.2 To-be additions (D3, D4, D7, D11)
- Token handshake: the first WebUI login is served without a token and receives it; the token is shown in the menu and kept as a plain file; every later REST/WS/ws:// request carries it (URL parameter, header optional) or is refused.
- Remote confirm: a remote intent that needs a confirmation creates the same question the screen shows (a job in state `asking`); a token holder may answer it, updates and destructive ones included; an unanswered question runs nothing; the screen shows it too.
- Search overlay: C= SPACE (only) opens it; while open it owns every key, nothing reaches the page below; an activated action goes through the normal confirm/dirty rules; it closes on RUN/STOP or after the activation.
- Safe mode: at host start the matrix is read; with C=+S held the host starts with the built-in TRX interface (key set, scheme, text mode) and ignores bundle files; a broken bundle falls back the same way. RESTORE+F1 (T177 recovery boot) is a separate chord.
- Bundle load: host default read at host start, per-core override read when the core app starts.

## 7. Deployment view
- Host app: RISC-V application in its flash slot (0x220000 on the current board image), next to the host gateware at 0x0.
- Core app: carried by the `.cor` of each core (one generic app, descriptor + `menu.toml` -> record per core).
- `.u2a` apps: loaded by the core app's loader (ABI 3), declarative record, no LVGL.
- Cores/`.cor` on `/SD/cores`; settings in `/Flash/trx/host.cfg`, `boot.cfg`.
- A second UI would ship as: part of the host app / core app image (O1-O7), or data bundle (O8); nothing else is planned.

## 8. Cross-cutting concepts
- Confirmations: `ui.confirm` (RETURN yes, Left no), file-delete confirm, write-back question, full-firmware confirm; REST bypasses them (C `rest.cc`, H `web_pump` `ask=false`).
- Live vs at-reset settings (`Setting.when`); changes held until Save when Auto Save Config is Off/Ask; B1 (dirty not cleared after Discard) open.
- Locks: app-tab `lock`, monitor owns keys, flash protect before full handover (read back), T152.
- Jobs / progress: callbacks on the calling task, cancel by polled key; `fw_write` has no cancel; app jobs 4 slots.
- Hot-plug: 3 s media poll (host), 2 s browser relist (core), pad pulled during mapping.
- Picture confirm: 8 s, the first key of any view is consumed (`hv_keep`, `hostui.cc:6165-6171`); a remote/TUI view must forward "any key".
- Write-back of cartridge/battery RAM: Off/Ask/Auto, 2 s quiet / 30 s max / 10 s retry, flush on reset, eject, core change, power-off, menu open.
- Refuse texts come from the producing module; secrets scrubbed in the bug report.
- Single writer for UI state (R30).

- Security concept (D4, D11): one token per app, 128-bit random (width is a build choice for T192.1), shown in the menu and stored as a plain file on the board; plain HTTP/WS, no encryption; the first WebUI login hands it out; a token holder may answer every confirmation. Accepted risk: anyone on the network who sees the URL has the token; FTP port 21 stays without a password (`hostui.cc:1791`).
- Bundle files (D9): plain TOML on the board (key set, colour scheme, text mode); validated at load, a broken file falls back to the built-in bundle; not code, not in a `.u2a`.

## 9. Architecture decisions
- D1 C++ functional core, no Rust (Alex, 2026-11-07).
- D2 default key set TRX64; C64U classic only selectable.
- D3 search only by C= SPACE; overlay owns every key; no type-to-find.
- D4 simple token (menu + file, first WebUI login without, URL parameter), plain HTTP, no encryption.
- D5 interface choice: host default, per-core override.
- D6 text UI local and remote in the first build; remote = `ws://`, no telnet/SSH.
- D7 safe mode: C=+S held at host start.
- D8 search: settings, pages, actions; no files.
- D9 bundles: TRX64 + prepared C64U classic, plain TOML, edit-copy-restart.
- D10 no density choice.
- D11 a token holder answers every confirmation, updates included.
- D12 `host_core` headless; host menu rebuilt declaratively, 1:1 parity in ue2emu, then replaces `hostui.cc`.
- D13 T152 flash lock rule kept in the common start sequence.
- D14 one shared core framework for both apps, domain logic per app.
- Related, as context (not decided here): T104.3 D0 (no UI code in apps), T104.3 ABI 3; T153 Q1 (widget layer internal, outside surface = TOML record D3 + `svc` table), T153 D7.1 (contract lint, not built), T153 D7.2 (host app not on the SDK); T187 D1-D8 (core menu layout, branch not analysed); T152 (flash lock); T135 (direct boot); T164/Q7 (picture confirm); T146 (menu picture); T181 (hotkeys).
- Open: none (epic §6).

## 12. Glossary
| Term | Meaning |
|---|---|
| host app | RISC-V app of layer 1: boot menu, core start, flash, files |
| core app | generic app carried by each `.cor`: menu, ops, settings of that core |
| `MenuCtl` | core-app controller / view-model of the menu |
| `OpRegistry` / op | named, typed function shared by menu and REST |
| `MenuTree` | menu built from the merged descriptor (`menu_build`) |
| record (TRXD v3) | compiled `menu.toml`, <= 0x20000 bytes |
| `.u2a` | application file loaded by the core app (ABI 3) |
| flow | host-app function that probes, shows pages and blocks for keys |
| job | stepped task with progress and cancel |
| intent | UI-neutral request ("activate item X"), as opposed to a raw key |
| bundle | data set of key map, layout parameters, skin |
| view | code that draws state (LVGL, web, TUI) |
| ICAP | internal configuration port used to swap the core |
