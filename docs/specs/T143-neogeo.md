## §1 The problem

**Who / what:** Alex wants the Neo Geo on the C64U/U64E2 as one more core: the upstream is `MiSTer-devel/NeoGeo_MiSTer` (HEAD `ffaab14c`, 2026-09-01), furrtek's chip-level re-implementation of the MVS/AES. It was written for a Cyclone V SoC with 32-128 MB SDRAM and DDR3, and the question is whether it fits the XC7A50T as a large core (flat bitstream, host + core, no partition).

**What the budget is (M, from the routed C128 flat build, `cores/c128/mono/reports/b_r5/utilization_hier.rpt`, Vivado 2024.1 post-route):**

| | total | core (`l2`) | host (rest) |
|---|---|---|---|
| Slice LUT | 28,489 (87.39 %) | 16,717 | **11,772** (`ult` Gideon system 6,459, `dbg` 681, `ovl` 391, HDMI enc 623, DDR2 ctrl 782, ...) |
| FF | 27,436 | 13,560 | **13,876** |
| RAMB36 + RAMB18 | 70 + 9 (74.5 tiles) | 57 + 2 | **13 + 7 = 16.5 tiles** (3.5 of them the overlay, which `c128` r6 stubs out) |
| DSP | 12 | 3 | **9** |

So a core on the XC7A50T has, at the highest proven routing (C128, 87.3-87.4 % LUT, WNS +0.039 ns in r6): **about 16.7k LUT6, 58-62 RAMB36 tiles (75 minus 13-16.5), 111 DSP**. 20.8k LUT is the arithmetic ceiling at 100 %, not reachable (`Slice` 99.96 % already in r5).

**Neo Geo upstream, what it needs:**

- **P1 Logic.** FX68K (68000, SV, GPL-3, 77 KB + 128 KB PLA), T80 (Z80, BSD-style), jt10/jt12 (YM2610, GPL-3), jt49, LSPC2-A2 / NEO-B1 / ZMC2 / PVC / SMA / CMC chip models (furrtek, GPL-2+), memcard, backup RAM, and the CD part (`rtl/cd`: LC8951, CDDA, drive). **E: 11-15k ALM.** Method: no Quartus report is in the repository and none was found online; the number is from the file inventory (137 `.v`, 11 `.vhd`) and typical sizes of FX68K (2.5-3.5k ALM), YM2610 with ADPCM (2.5-3.5k), LSPC/B1 line logic and the glue. Conversion: this repository's own pair `c64_core` 10,793 Vivado LUT6 vs 8,731 Quartus ALM ([T27-u64-cyclone-port.md](https://github.com/Jondalar/TRX64-Ultimate/blob/main/docs/specs/T27-u64-cyclone-port.md):84`) gives LUT6 = 1.24 x ALM, so **E: 13.5-18.5k LUT6** against the 16.7k proven ceiling. Too close to call; CD (about 1k) and PVC/SMA out brings it under. Not measured because the builder was busy (see §5).
- **P2 Block RAM, counted from the instances in the source** (`neogeo.sv:1177-2005`, `rtl/mem/*.v`, `rtl/video/linebuffer.v`, `rtl/io/neo_pvc.v`, `rtl/cd/cd.sv`; one RAMB36 = 4 KB of 8/16/32-bit data): 68k work RAM 64 KB (16 tiles), slow VRAM 64 KB (16), backup RAM 2 x 32 KB (16), `LO` ROM 64 KB (16), palette 16 KB (4), fast VRAM 4 KB, Z80 RAM 2 KB, PVC RAM 8 KB, `XRAM` 8 KB (role not read), memory card 8 KB, CD cache 4 KB, line buffers, FX68K microcode/nanocode, YM2610 tables: **M: about 315 KB of RAM instances = E: 80-85 tiles** against 58-62 available. **It does not fit as it is.** (The `DEV_NOTES.md` table says 385 kB and lists M1 ROM in BRAM; the code reads M1 from DDR3 (`neogeo.sv:1618-1655`), so that table is stale and was not used.)
- **P3 External memory.** `neogeo.sv` has two: **SDRAM** (up to 2 x 64 MB, 96 MHz, 16 bit) for P (68k program, 1 MB + banked P2 up to 4 MB), S (fix, up to 512 KB), C (sprites; `CROM_START` address `0x0800000..`, 24-80+ MB), system ROM; and **DDR3** (HPS, 64-bit Avalon) for V (ADPCM-A/B samples, `V1ROM_MASK` up to 32 MB, `V2ROM_MASK` 16 MB) and M1 (Z80 program, 128 KB). Our board has one memory, the 128 MB DDR2.
- **P4 DDR2 pool and ROM sets.** The `romsets.xml` of the release groups 283 sets by the SDRAM they need: <= 32 MB: 183; <= 64 MB: 37; <= 96 MB: 59; <= 128 MB: 4 (**M**, counted from the file). The SDRAM image keeps an 8 MB lead-in before the C ROM (`DEV_NOTES.md` map, consistent with `CROM_START`) which a packed layout of ours would not need. V and M1 come on top of that (not in the SDRAM figure).
- **P5 Latency.** Sprite (C ROM) reads are timed by LSPC: one 64-bit read per sprite per line, up to 96 per line, one per 1.5 MHz slot (`lspc2_clk.v`: `DIV_CNT` 16 states of 24 MHz = 667 ns; **the exact point by which the data must be there is not derived yet, U**). Rate: 96 x 8 B / 63.6 us = **12 MB/s (E, from the 15.7 kHz line)**. 68k program reads: the core already waits (`PROM_DATA_READY`, per-set `rom_wait`/`p_wait` in `romsets.xml`).
- **P6 Video / audio / input / media.** Native 320 x 224 (visible), 59.19 Hz, palette 15 bit plus the shared dark bit = 6 bit per channel (hence T130's 32-bit pixel list); YM2610 stereo; two players with a 4-button pad plus start/select (coin); ROM sets as zip/folder/`.neo` plus `romsets.xml`, BIOS files, memory card and backup RAM saves.
- **P7 Licence.** Per file group, read from the headers (not the README): see §3 D8.

**What the DDR2 offers (M, code):** 128 MB x16 DDR2-300 behind `ddr2_lean` (`host/ddr2_lean.v:1-12`): BL8, closed page, 8 banks, 128-bit word per command, one command per `ui_clk` (75 MHz), **peak 600 MB/s** ([OPT-ddr2.md](https://github.com/Jondalar/TRX64-Ultimate/blob/main/docs/specs/OPT-ddr2.md) 3.2), read latency about 110 ns plus queue; `mig_arb` (`host/ddr2_port.v:34-80`) serves the layer-2 port `c_*` first (128-bit `c_rd_data`, `c_addr[26:0]`, `contract/layer2_ports.txt:31,86,166,224`) and `e_*` after drive and video; the video client keeps up to 8 reads in flight; sim/lat worst case with full video load: drive read 730 ns, cart line (4 reads) 706 ns (`ddr2_port.v` header comment, quoting the bench; **E for us, not re-run**).
**Where the pool is (Alex, 2026-10-28, two corrections):** in a large core the host application is gone; the only other user is the core application: image at 0x30000 (the C128 `coreapp.bin` is 841,144 bytes), FreeRTOS heap `configTOTAL_HEAP_SIZE 0x7A0000` (7.6 MB) and stack inside the linker region `0x30000 + 0xE60000` = **ends at 0xE90000** (`host-app/target/u64ii/riscv/coreapp/linker.x:MEMORY`, `Makefile:222`; heap and stack lie inside it). Gideon's old zones above that (`0xEA8000-0xFFFFFF` kernal area, drive images, built-in cart, `docs/specs/done/T133-host-dcache.md` F3) belong to the host application and are not read by the generic core application as far as grepped (E). Planning figure: low region **0x0000000-0x0FFFFFF (16 MiB, the real end of use is 0xE90000 = 14.56 MiB)**, pool **0x1000000-0x7FFFFFF = 112 MiB**, no host still capture (`pix_layer` STILL_BASE is host-application business), frame buffers of the core's own `pix_layer` copy: 3 x 320 x 224 x 4 B = 0.86 MB (E). **The RISC-V sees only the bottom 64 MB directly (`T136` D3: "its CPU sees 64 MB")**, so 0x1000000-0x3FFFFFF (48 MiB) can be written by the application with plain stores (`hw.cc` `ddr_write`), 0x4000000-0x7FFFFFF (64 MiB) needs a path through the core (P8).

- **P8 Loading.** MiSTer's ARM does the ROM-set work (`Main_MiSTer/support/neogeo/loader.cpp`, not in this repository): unzip, byte-interleave of C1/C2 pairs, re-order of fix and sprite bit planes, the index scheme of `DEV_NOTES.md` ("C: 64 + odd/even + 1 MB bank x 2"), write by `ioctl`. Our core application has to do the same into DDR2, 40-100 MB per game.
- **P9 Cuts that the budget forces** (follow from P1/P2/P3).

## §3 Decision (proposed; each D waits for Alex's answers in §3a)

- **D1 Large core, flat, like the C128/A1200.** `cores/neogeo/mono/build_mono.tcl` from `cores/c128/mono/build_mono.tcl`; descriptor `cores/neogeo/mono/core.toml` (`delivery = "cfw"`, `roms = ["sp-s2.sp1" (or uni-bios.rom), "000-lo.lo", "sfix.sfix"]`, `experimental = true`). Upstream files vendored unchanged under `cores/neogeo/rtl/` by a script (`tools/vendor_neogeo.sh`, pinned commit `ffaab14c`), with a NOTICE; our glue in `cores/neogeo/trx/`.
- **D2 Clocks.** `clk_sys` 48 MHz with 24 MHz enables as upstream (`neogeo.sv:181-199`); one MMCM from the host's 50 MHz for 48 MHz and 96 MHz is not needed: the ROM ports run in `ui_clk` (75 MHz) with a toggle-handshake crossing into 48 MHz. No other clock in the core.
- **D3 Memory: everything external through `c_*` and `e_*`, with a global stall.** `sdram_mux.sv` is replaced by `neogeo_ddr2_mux.v`: C-ROM (sprites, latency-critical), S-ROM (fix) and P-ROM (68k) on `c_*` (highest priority), V/M1/backup/memory card on `e_*`. One 128-bit read covers two sprite lines (64-bit each) and four fix words, so the port fetches 16 B and the core uses what it needs (prefetch of the neighbour for P ROM/fix). If a read is not back by its deadline the core's clock enables (`CLK_EN_24M_P/N`) are gated for that period (a stall counter exposes it): late data costs a wait, never a wrong picture. The deadline is derived in the bench from the RTL (S2); until then the 667 ns slot is an assumption.
- **D4 Cuts to meet P2 and P1 (all deliberate, proposed):** (a) Neo Geo CD out (`rtl/cd`, `CD` code paths, 1 tile + about 1k LUT); (b) `neo_pvc` and the SMA/CMC chips stay only as far as `romsets.xml` sets need them (KOF2003/SVC need PVC: decision per Q3); (c) backup RAM (64 KB, 16 tiles) and memory card (8 KB) live in DDR2 `e_*` behind a small cache, saved to SD by the application with a dirty log (as the `window_media` engine of `coreapp/src/engines.h`); (d) `LO` ROM (64 KB, 16 tiles) in DDR2 behind a 1 KB line cache, or block RAM if the count allows. Result **E: 82 -> about 44 tiles**.
- **D5 Pool layout.** C ROM packed from 0x1800000 (no 8 MB lead-in), P/S/system ROM in the first MB of the pool, V after C, M1 and saves last; app writes everything below 0x4000000 with stores; above that the core offers a **byte-stream register at the core's `cw_*` page** (`cw_addr[16:0]`, `cw_wdata`) feeding a write command on `e_*` (an 8-byte staging register, the same host-neutral mechanism for any later core with ROMs > 48 MiB). Largest contiguous: 112 MiB, usable for ROM sets: 112 - 0.9 (frame buffers) - 1 (saves/BIOS) = **about 110 MiB (E)**.
- **D6 Video:** the core's own `cores/neogeo/mono/pix_layer.v` (copy with format 2, as the A1200, T136 D1) fed with the 15+1 bit palette expanded to 6 bit per channel; 15 kHz timing is irrelevant (the frame writer stores whole frames, the host scaler does HDMI).
- **D7 Input:** both C64U joystick ports (`c64_joy1/2`, 5 bits each, `contract/layer2_ports.txt:116-117`) give stick + one button; the pot lines (`paddle_cmp_i[3:0]`) give two more only on Competition-Pro style pads; a real 4-button pad needs the USB gamepad path (T141's mechanism, Q4). Coin/start/test from keys on the C64U keyboard.
- **D8 Licence (read from the file headers, 2026-10-28):** top-level `LICENSE` is GPL v2 text. `neogeo.sv` and `rtl/io`, `rtl/cd`, `rtl/mem`, `rtl/video`: "GPL v2 or (at your option) any later version", Copyright 2018 Sean 'Furrtek' Gonsalves (video, cells: GPL v3 or later); `rtl/cpu/FX68K`: GPL v3 or later (Jorge Cwik); `rtl/jt12`, `rtl/jt49`: GPL v3 (own `LICENSE` files); `rtl/cpu/T80`: BSD-style (Daniel Wallner, 7 files, redistribution conditions in the headers); `rtl/mem/ddram.sv`, `sdram.sv`: GPL v3 or later (Sorgelig) - replaced by ours. **Verdict: CLEAR for our GPL-3.0-or-later tree** (every group is v3 or "v2 or later"; T80's BSD notice must stay in the NOTICE); nothing here is "v2 only" or non-commercial. Open: the `.xml` set lists and `loader.cpp` (Main_MiSTer, GPL v3) are read for the layout only, not copied. BIOS (`sp-s2.sp1`, `neo-epo.sp1`, `uni-bios.rom`, `000-lo.lo`, `sfix.sfix`) and games are the user's, never in the repository, a release or a `.cfw`.
- **D9 Media:** the core application reads sets from the SD (zip store or folder, `.neo` as the single-file format first), `romsets.xml` is replaced by an embedded table in the application; decrypted sets only (as upstream: "does not support encrypted ROMs", README).

**Status:** BUILT 2026-10-29 as P1 + P4 (what was built and measured: §5, last entry). Proposal text as written for Alex's decision (asked by Alex, 2026-10-29, after the board run of §5); it described the code before the change. **M** = read in code (file:line), **E** = estimated (method given), **U** = not known (how to find out given). Line numbers are of this branch at `d3e11e10a`; upstream of `rtl/` is NeoGeo_MiSTer `ffaab14c`.

**The problem in four numbers.** The machine needs the sprite word 13 machine clocks = 270 ns after PCK1 falls and the fix word 11 clocks = 229 ns after PCK2 (§5, bench). The DDR2 path answers in 293..693 ns (§5). The address of a sprite word is only known at PCK1: the request is issued when PCK1 falls (`neo_mux.v:162`), the address is `C_LATCH` taken from PBUS at that edge (`neogeo.sv:1331,1392`). Every word is late: 41.7 M stall clocks / 937,560 late sprite words = 44.5 stalled clocks per word on a 32 clock slot (M, §5 figures) = 42 % speed.

### Research result 1: jotego has no Neo Geo core to read
- `jtcores` @ `f848902b8328d48f1d8500cfc119c87f9e83d0f8` (2026-10-28): `cores/` has no Neo Geo (M: directory listing; only `ngp`/`ngpc` = Neo Geo **Pocket**, a different chip set; `modules/jtframe/doc/sdram.md:67` mentions it as a BIOS + cartridge example). `jotego/NeoGeo_MiSTer` is a fork of MiSTer-devel's repo, last push 2020-07-28 (M, `gh api`). So there is no jotego LSPC timing to take over; this answers the premise of the task, not the problem.
- What jotego does for a comparable sprite engine (CPS1, `cores/cps1/hdl`): the engine renders **one line ahead** (`jtcps1_obj.v:17`, `vrender` "1 line ahead of vdump"), `jtcps1_obj_line_table` expands the object table to a per-line tile list, `jtcps1_obj_draw` asks the ROM with `rom_cs`/`rom_ok` and **waits for `rom_ok`** (`jtcps1_obj_draw.v:50,82-83,107`); the line goes into a double line buffer (`jtframe_obj_buffer.v`). So his engines have no fixed ROM deadline at all: they are functional re-writes, tolerant of any latency. Netlist-accurate furrtek RTL is not.
- SDRAM side (jtframe): four banks `ba0..ba3` with a request/ack/rdy handshake each (`jtframe_pocket.v:69,509-512`); clients are slots per bank (`jtframe_ram1_5slots`, `jtframe_rom_1slot`, `jtframe_rom_4slots`); CPS1 puts the 68k program/RAM into bank 0 (5 slots), PCM into bank 1, object gfx, a second gfx slot and the stars into bank 3 (`jtcps1_sdram.v:274,373,444`). Latency in clocks at 96 MHz: min 9, average 11-12, max 30-36 with refresh and writes (`sdram.md:252,259`, a document table, not checked against code). Optional burst/cache client `jtframe_cache.sv` / `JTFRAME_SDRAM_CACHE` (`jtframe_pocket.v:70-81`). Pocket: the ROM lives in the same 64 MB SDRAM (`jtframe_pocket_top.v:192`); the PSRAM `cram0` is the frame buffer (`:85,496-505`), `cram1` tied off (`:341-348`). Nothing in the Pocket target serves ROM from PSRAM.
- MiSTer Neo Geo (the code we derive from), `rtl/mem/sdram_mux.sv` + `sdram.sv` @ `ffaab14c`: **one** SDRAM client in sequence, no prefetch, no line buffer; the sprite read starts when PCK1 falls (`sdram_mux.sv:102`), 4 x 16 bit burst (`sdram.sv:73`), CAS 2 (`sdram.sv:76`), priority 68k > sprites > fix (`:237,261,267`); 68k program and Z80/ADPCM share the SDRAM / DDR3 as plain clients. It works because the access is about 10-12 clocks of 96 MHz = about 100-125 ns (E), under the 270 ns. Our DDR2 is 3-6 times slower in latency, not in bandwidth.

### Research result 2: what the LSPC timing allows (from our RTL)
- Slot: 16 states of the 24 MHz enable = **32 machine clocks = 667 ns** (`lspc2_clk.v:72-73`, 1.5 MHz enables at `DIV_CNT` 7 and 15). One sprite tile per slot; the active list holds at most 96 entries (`fast_cycle.v:356`, `ACTIVE_WR_ADDR[6:5]`), one line is 63.6 us = 95 slots (E, spec P5).
- Sprite list timing: during raster line r the chip parses all sprites (about 382, `fast_cycle.v:245`) against `RASTERC + 2` (`:472`) and writes the active list into bank `FLIP` (`:381`); during line r+1 it reads it from bank `nFLIP` (`:377`), starting at a reload early in the line (`:427`, exact pixel U), and draws into the line buffer that is displayed in line r+2 (`lspc2_a2.v:683`, lookahead +1). **The list of line r+2 is final at the end of line r (E: 382 entries cannot take longer than the 384 pixel line); its entries are 8 bit sprite numbers only.** The C ROM address needs more: tile number (SCB1, slow VRAM), Y/size/chain (SCB2/SCB3, fast VRAM), the vertical shrink line from the LO ROM (`lspc2_a2.v:646`). Those are read at slot time (`CLK_SPR_TILE_EN`/`CLK_SPR_ATTR_EN`, `lspc2_a2.v:345-346`) and come out as `{SPR_TILE[19:16], SPR_LINE, SPR_TILE[15:3], AA}` on PBUS (`:666`). So a whole line of notice exists for **which sprite**, but the **address** can only be had early by reading the same VRAM words early (the 68k may change them in between, e.g. a raster IRQ: the early address must be verified at PCK1).
- Needed lead: latency 693 ns + toggle synchronisers (E: about 100 ns) - 270 ns = **about 520 ns = 16 clocks = less than one slot**. Two to four slots (1.3-2.7 us) of lead is generous (E). A full line of lead (the 768 B per line of the first idea) is not needed for latency; it would only decouple DDR2 bursts.
- Throughput (E): sprites 96 x 16 B command per 63.6 us = 24 MB/s (12 MB/s useful), fix the same 24 MB/s, 68k program up to 3 M reads/s x 16 B = 48 MB/s at full speed: together **<= 96 MB/s = 16 % of the 600 MB/s peak**. One command is already a 16 B line (`neo_mem.v:143-155`); adjacent sprites are unrelated addresses, so "bursts" bring nothing beyond the up to four reads that may be open (`neo_mem.v:124`, tag queue of 4; today each channel has one open, `neo_mux.v:162`).

### The 68k path
The program read has the **lowest** priority at the port (`neo_mem.v:143-155`: sprites, then fix, then 68k) and holds the 68k by DTACK until the line is back (`neo_core.v:354`, `PROM_DATA_READY`). So every ROM fetch costs 293-693 ns against a 4 clock 12 MHz bus cycle of 333 ns (E): the 68k is slow **in addition** to the global stall, and its share is not in the 42 % (the 42 % counts machine clocks, not 68k wait states). Not measured (U): count bus cycles per frame with and without an ideal memory in the p68k bench. The global stall also freezes the 68k (`neo_core.v:135`). Program ROM is read only and addressed by its final DDR2 address, so a **line cache keyed by address** is exact by construction (bank switching changes the address, not the content): 4 lines x 16 B + tags in LUT RAM (E: 40-60 LUT, 0 BRAM), hit rate on straight code up to 7 in 8 (E: 8 words per line).
