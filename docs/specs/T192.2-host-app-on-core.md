## §1 The problem

Read from `hostui.cc` (7628 lines, main `7bef47381`; analysis `scratchpad/t192/hostapp.md`, 2026-11-07).

- **Who:** Alex and the testers at the host menu; any second UI (text UI, web, terminal client) that has to drive the host; the
  T192.4-.6 children, which need a key map as a table and an intent per action.
- **What they do:** pick a core or firmware, start it, manage files, change settings and the picture, update/restore/convert/format.
- **What happens today:** about 90 of 91 host files are UI-free modules with callbacks and bench seams. The mixing sits in
  `hostui.cc`: 181 file-scope statics, 277 functions, 101 `hostui_test_*`, ~25 blocking `while (host_getch() < 0) vTaskDelay(20)` waits
  (e.g. `3651`, `3771`, `5047`), one `on_key` (`6162`, 225 lines) with every key and every business action, key legends as ~20 literals
  (`1114-1146`). The start sequence exists twice: `start_core`/`start_full` (`3657`/`3722`) and `direct_run` (`6486`). The web view-model
  (`fill_snapshot` `5955`, `web_pump` `6020`) re-implements key logic from `on_key` (`6045-6062` vs `6248-6275`).
- **Why it matters:** no second UI can be built against it (T192 P1, P2); every change to a flow touches a 7.6k-line file; the safety
  sequence of a core start (stage, last abort check, `core_swap`, `core_jump`, `lock_flash`) lives in two copies.

Example, worked: `update_run` (`5508-5660`, 152 lines) probes the `.txu` (`txu_probe/check`), checks the flash (`fw_flash_check`), stages,
sizes text, shows the `UpAsk` page, blocks for RETURN, runs the write loop with a progress callback that paints, then loops on a result
page. Probing, view text and blocking input are one function; none of it can run without LVGL or without a key at the board.

**Parts (MECE):**
- **P1 Cut:** what moves into a headless `host_core` and what stays view code.
- **P2 Flows:** modal flows become job state machines; their text and order stay as they are.
- **P3 Start:** one `start_sequence` for the menu and direct boot, with the lock rule of D13.
- **P4 Declarative menu:** pages, rows, key map and footers as data over `host_core`, replacing `hostui.cc`'s layout and `on_key`.
- **P5 Parity:** proof in ue2emu that the new menu equals the old one, screen by screen and flow by flow.
- **P6 Invariants:** requirements the old code enforces that must survive the cut (hostapp.md §8).
- **P7 Transition:** old and new live side by side until parity, then `hostui.cc` goes.

## §3 Decisions

Epic decisions that apply, quoted:

- **D12 (Alex, 2026-11-07, translated: "C: host_core, and with the emulator rebuild the host menu 1:1 until it behaves exactly the
  same, but declaratively, and running as a client of the headless core"):** a headless `host_core` (state, commands, events, flows as
  jobs) is built; the host menu is rebuilt as a declarative client of it, and in ue2emu (S44) the new menu is compared with the old one
  until it behaves exactly the same (same screens, keys, texts, flows); then it replaces `hostui.cc`. Parity is proven in the emulator,
  screen by screen and flow by flow.
- **D13 (Alex, 2026-11-07: "A"):** the T152 flash lock stays as built: `lock_flash()` for a full image (.cfw, large .cor, direct start of
  one), not for a DFX core, which runs under the host; the common start sequence keeps this rule.
- **D14 (Alex, 2026-11-07: "A"):** T192.1 is ONE shared core framework for both apps: state snapshot, intents with stable ids, event
  stream, jobs (progress, confirmations), token and WebSocket, written once; the domain logic stays per app (host: core start, flash,
  update, files; core app: ops, settings, media). The text UI, the search, the terminal client and the bundles are built once on it and
  serve both apps.

This spec adds no decision. Everything below is a proposal; where it needs Alex it is in §6.

### Design (proposal)

Line numbers are `hostui.cc` on `7bef47381` unless a file is named.

**1. The cut (P1).** New files `host-app/software/hostapp/host_core*.{h,cc}` (no LVGL, no key waits), on the T192.1 framework. The ~90
UI-free modules stay untouched and are called from `host_core`. Move map:

| From `hostui.cc` | To `host_core` |
|---|---|
| state: `cfg`, entry states `est[]`, `c_net/c_ip`, media; `try_load_cfg/save_cfg`; `refresh_status` (`333`); `row_view/startable/badge_text`; `lazy_*` | state + snapshot fields |
| `fill_snapshot` (`5955`), `web_pump` (`6020`) | snapshot is the T192.1 snapshot; the web handler becomes an intent client (`webui.cc` keeps the HTTP task and mailbox) |
| `settings_change` logic half (`2471`, `2506`), `picture_set/tick` (`2403/2429`) | settings intents, `hv_*` driven from the core tick |
| add/remove/rename/move/default/countdown logic out of `on_key` and `rename_flow`; `add_bundle/add_full` (`5806/5862`) | commands |
| `start_core/start_full/direct_run/lock_flash` (`3657/3722/6486/3706`) | `start_sequence` (3) |
| `update_run`, `restore_flow`, `convert_flow`, `format_flow`, `inspect_flow`, coremaint flow, file ops flow | jobs (2) |

What stays view: `build_*`, `update_*`, `browse_right_*`, resident panels, `fm_*`, `up_run_page`, `cv_page`, key reading, notes, `snap_save`
(`6674`; the menu picture is a view concern, T146). Size, from the analysis: ~3-3.5k of 7.6k lines move.
`refresh_status` polling (3 s, not within 1.5 s of a key, `hostui.cc:6835-6945`) becomes a `host_core` tick; the view drives it from the
existing loop.

**2. Jobs (P2).** Each blocking flow becomes `step(job, input)` returning page data; the T192.1 job record carries
`kind, state (probing|asking|running|result), lines[] with tone, hint, progress{phase,done,total}, choices, can_cancel`. `UpAsk`
(built at `5575-5617`), `UpDone`, `FmPage`, `FwAsk` already are view-model structs; they move unchanged, text included (the text is the
parity contract, hostapp.md §8 point 7). State machines per flow:
- update: probing (txu probe/check, `fw_flash_check`, stage) -> asking (`UpAsk`) -> running (phases app/host/readback, `fw_write` has no
  cancel: `can_cancel=false`) -> result (retry loop); refuse pages end in `result` from `probing`.
- restore (`5052`, `fw_write` at `5194`) and convert (`4594`, abort `cv_abort_cb` `4458`) the same shape; convert has a cancel.
- format (`4118`): warning/name -> last chance -> running -> result; while it runs the job slot is taken and the web mailbox answers busy
  (`3797-3800`, now by the slot rule, S5).
- start: stage -> running steps -> result (see 3).
Progress callbacks (`up_write_cb`, `fw_write_cb`, `fo_progress`, `FmtProgressCb`) call a progress sink on the calling task; the view paints
from the sink. Mid-work repaints (`trx_lv_handler` at `5809-5812` to show a "checking" note before the SHA read) become a job state
`probing` with a note line that the view paints once before the blocking module call; the job step is split so the paint happens between
steps.

**3. One `start_sequence(entry, mode, hooks)` (P3).** Hooks: progress step, `abort_requested()`, `ovtext` (direct boot overlay), result.
Order unchanged: eligibility (the `6511` "nothing loaded" check) -> `core_stage` / `legacy_stage` -> `vTaskDelay(200)` + last abort check
(`3690-3695`, `3744-3748`) -> `core_swap` -> `core_jump` / `legacy_jump`. The lock rule is data of the entry kind: `lock_flash()` (with
read-back refusal, `3706-3716`) only for `.cfw` and large `.cor`, as `start_full` (`3747`) and the full branch of `direct_run` (`6501`) do
today and `start_core` does not (D13; hostapp.md "not verified: whether `start_core` loads a large `.cor` without `lock_flash`" is checked
by T192.2-S8 before the rule is written as table). Confirm for foreign firmware from the browser only (`3790-3796`) is an `asking` state
of the job that menu-entry starts and network starts skip. A single job slot refuses a second start (S13) and a start during a flash write
(`flashfw.h` staging contract). The sequence runs on the UI/start task; the Job record is the only thing a remote client sees.

**4. Declarative menu description (P4).** Proposed format: constexpr C++ tables in `host-app/software/hostapp/host_menu.inc`, generated
by nothing and parsed at no time (no heap, no parse step, checkable by the compiler and by bench). Schema:
- `Page{id, title_src, tab/area key, regions[]}`; `Row{id, label_src, value_src, tone, enable_src, action_intent}`; `Region` kinds taken
  from `trxview.h` (rows, panel, chips, preview). `*_src` name a `host_core` snapshot field, never a literal that restates state (cf.
  the literal "on, port 21, no password" at `1791`).
- `Keymap{view, key, intent_id[, arg]}` and a footer per view generated from the keymap (replaces `1114-1146`); `nav_name/nav_key`
  (`91`, `1111`) fold into it.
- Dialog/flow pages are not tables: they render the T192.1 job record with the existing `fm_draw`/`up_run_page`/`cv_page` drawers.
Custom drawing that is not rows (browse preview `browse_right_*`, which today probes the file itself at `1321-1331`) reads a cached probe
result from `host_core` (`bci_for`), so the view never probes. The same schema is the later input of T192.6 bundles (key map as TOML);
that file format is T192.6's business, not decided here.

**5. Order of flows (build and parity order).** Safety first, then easy-to-compare, riskiest last; each step ends with its parity walk
green before the next starts:
1. State and read-only pages (home, boot menu, status, help, footers) + settings reads: S1, S9, T192.2-S9/S10.
2. `start_sequence` with menu start and direct boot together (one commit changes both callers): S2, S3, S12, S13.
3. Picture confirm and `V` (S11): small, timer-driven.
4. Boot-menu edits (add, remove, rename, move, default, countdown) and settings writes.
5. File browser and file ops (S8).
6. WiFi (S10; bench plus a board step for the radio).
7. Convert (S6), then format (S7), then restore (S5), then update (S4): ascending in blast radius; update last because it writes the host.
8. Replace: delete `hostui.cc` flows once S1-S13 and T192.2-S1..S16 are green; `webui.cc` consumes intents.

**6. Parity method in ue2emu S44 (P5).** Setup per emu_usage: `ue2emu run --board c64u --trx-io on --icap --cor-dir ... --core-dir ...
--firmware hostapp_emu.elf --roms ... --flash <copy of the same flash.bin> --usb-dir <the same stick> --headless --speed max --script walk.ctl`.
- Two firmwares: `hostapp_old.elf` (tagged `hostui.cc` build) and `hostapp_new.elf`; same flash image copy, same stick contents, same
  `boot.cfg`, same script.
- A walk script is a list of `key`/`hold`/`release`/`restore` lines (the S44 key syntax) with `png <dir>/<nn>_<name>.png` after each
  step. Walks: one per screen group of S1 (home, boot menu, browser with preview of a `.cor` / `.cfw` / `.txu`, status, settings pages,
  help, footers per view, toasts) and one per flow S2-S12 including the refuse and cancel paths (the controls of §2.1).
- Compare tool (host-side script, not board code): pixel diff of the 1920x1080 frames; the board's 480p/720p down-scaling is not modelled
  by the emulator, so parity is on the 1080p frame only. Text/key compare: the new build dumps the snapshot text (rows, footer, job lines)
  per step through the T192.1 state route; the old build needs the same dump to compare text. The pass is the text/key compare: same texts, navigation,
  actions and states (epic D19b). A pixel diff of 0 is required only for the screens the walk file lists as layout-unchanged; elsewhere a
  pixel difference is reported, not a failure.
- Determinism: time-dependent regions (countdown seconds, clock-like chips, IP) are frozen by inputs the walk controls (no network
  address in the emulator profile, default off or countdown value fixed in `boot.cfg`, key sent before the 3 s media poll) and any mask is
  listed in the walk file and has its own control (T192.2-S12). A mask that hides a footer or a label is not allowed.
- Control runs belong to the walk list: old-vs-old with one changed stick file, and old-vs-new with one changed footer literal, must be
  red (S1, T192.2-S11).
- Hardware-only paths (S10 radio, real ICAP, real SPI flash protect) get the bench for logic and a board step for the result; the
  emulator parity proves the screens and key paths.

**7. Transition (P7).** Both menus compile in one tree behind one build switch; until parity is green every change to a host screen lands in
both (arc42 risk 17). After the replacement the old walk stays as a regression script against a stored set of reference pngs taken from the
last old build, so later screen changes are deliberate (reference update in the same commit).

## §4 Out

- The core app side (T192.3), the search overlay (T192.4), the text UI and `ws://` (T192.5), key/interface bundles and safe mode (T192.6):
  each its own child; T192.2 only delivers the key map as a table and an intent per action for them.
- The token, WebSocket and the framework itself (T192.1).
- Any behaviour change of a screen, flow or text: parity is the point (D12). Fixes found on the way are separate commits after the
  replacement, with a spec section.
- New web routes beyond the intents the framework offers; auth is T192.1's.
- Changing a UI-free module (`flashfw`, `txu`, `coreboot`, ...) other than adding a seam; the flash/ICAP sequence is moved, not redesigned.
- Gateware or contract change (the host is immutable).
- A build before the finish plan is closed, unless Alex says so.
- Board-only checks of the ICAP jump and real SPI protect beyond the one S10 radio step and a final start-from-menu board step.

## §5 Decisions taken while building

MVP part (epic D20, D21), branch `t192-mvp-hostapi`, 2026-11-08. The parity build (§3 Design 1-7, S1-S13) is still after the MVP; what is built here is the host's side of the
service with the FULL API (D21) and a key path shared by screen and API. `hostui.cc`'s drawing is untouched.

- **The declaration (D21: "the declaration generates the functions/endpoints"; Q1 answered: constexpr C++ tables compiled in):** `hostdecl.cc` holds the host's capabilities
  once: pages (the five views, the WiFi page and Cores and ROMs over the settings, the colour test), items (the settings rows, the WiFi page, the network page's
  lines), list sources (boot entries, the browser's rows, the cores page's lines), actions (53: navigation, entry edits, the browser's file actions, the flows,
  settings, WiFi, Cores and ROMs) and the keymap (51 key bindings). `hostdomain.cc` is a `UicDomain` that WALKS the tables: ids (`settings.direct`, `entry:<name>`,
  `fs:<name>`, ordinal for equal names), the snapshot, `acts` per row and `ops` per screen, and the routing of select / activate / set / op / key / open / back. No
  handler per function; a new declared row or action is reachable over the API with no further code. `hostmodel.h` is the one interface to the app; `UiModel` at
  the end of `hostui.cc` implements it over the statics and the two ways the board acts anyway: the key path (`on_key`) and `settings_change` / the WiFi page's handler.
  Bound to the declared action means: an action is a key sequence or a field step, queued in order with its navigation key and the focus of its row; the existing
  function runs, not a copy of it.
- **One key path (T192.1-S7):** `host_getch` / `host_getch_nowait` read the queue first; the board's own key enters as a `key` intent (`uic_local`) and comes out of the
  same queue; remote intents fill it. A modal wait calls the service (`hostapi_waiting`), so an answer or a key arrives while a flow waits.
- **Flows:** `FlowScope` makes each flow of `hostui.cc` a job (`start`, `copy`, `move`, `format`, `convert`, `restore`, `update`, `inspect`, `check`) with progress and cancel (the
  abort key the flows poll). A flow's page (`fm_draw`) is told to the service: a page with a bar is progress, a page that waits is a question (its yes key is the page's:
  RETURN, Y for convert's write, U for the ESP32 write); the page that asks over the settings (Cores and ROMs, delete), the replace question of copy / move, the foreign
  firmware confirm and the "any key" failure page are questions too. Text entries (rename, WiFi name / address / password) are an `entry` modal: type by `key` intents
  (`key:"text"`, `value:"..."`), history recall (D19d), or an op that brings its text (`entry.rename` + `value`). A password is masked in the modal and never kept in the history.
  The pick lists (access points, authentication) are items; choosing one moves the cursor and presses RETURN.
- **Confirmation gate (D19a):** an action marked destructive (`entry.remove`, `browse.delete`, `wifi.forget`, `cores.delete`) is asked first over the API; the answer runs the
