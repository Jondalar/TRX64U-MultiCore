## §1 The problem (static analysis of the game, 2026-11-11; nothing measured yet)

- The game: native mode, `$D07B` (20 MHz), optimisation `$D075` (mirror $40-$7F); HUD data written to bank 3 ($FB90/$FC88/$FC18) inside short
  `$D077` (mirror all) windows; raster IRQ chain via the native vector $FFEE; HUD IRQ at line $D1 does ~23 I/O writes ($D011 $6B blank, sprites,
  `$DD00`, `$D016/$D018`, `$D011`); sprite multiplexer writes pointers at $77F8; scroll writes screen $7400 and colour RAM from SuperRAM bank 2.
- The crack's menu ($0801): no SCPU registers; raster IRQ at $F3 acks `$D019` at the very end; designed around 20 MHz.
- P1 (cut sprites, HUD faults while scrolling): candidate 1 — the mirror write queue (`scpu_mem.v` ~356-395) loses or delays bytes under a dense
  stream of mirrored writes; candidate 2 — our I/O write latency in the HUD IRQ is longer than a real SCPU's, so the split runs past the blanking.
- P2 (menu too fast at 20 MHz): candidate 3 — the IRQ handler runs twice per frame (late ack, `cpu65816_c64scpu.v` ~108-111).
- P3 (menu bad at 1 MHz): may be the game's design (a real SCPU at 1 MHz may glitch too), or a DDR2 miss stretching a 1 MHz cycle (`scpu_mem.v` ~360).

### §2a What the trace must contain for Level 1 (read from the 65816 code of Metal Dust, 2026-11-14; `MetalDustUltimate/analysis/dis65816/`, the SuperCPU original, not the 6502 translation)

Files: `G` = `07_game.bin/07_game.bin.asm` (game.bin, `$8000-$B8B9`), `L1` = `level1_code_0810/level1_code_0810.asm`. What the code does, with the event the trace needs for it:
- **SID oscillator poll (game init and level init): `G:471-478` (`$85C0-$85D0`)** - voices 1-3 get frequency `$0004` (`$85AC-$85B2`), control `$21` (sawtooth, `$85B7-$85BD`), then `LDA $D41B / CMP #$54 / BNE` until the OSC3 byte is `$54`, then until it leaves `$54` and is exactly `$55`, else start again. The routine `$8560` runs at the game start (`G:4980`, `$B586`) and at `$ACB1` (`G:4074`, level init). With a SID that answers 0 (the `NO_SID` build) the loop never ends: this is the Level 1 hang of run 1792. Needed: the SID in the build, and every `$D41B` read with its byte and raster position (events: I/O read $D41B).
- **IRQ dispatcher, native vector `$FFEE`: `G:166-186` (`$81A6-$81C4`)** - `LDA $D019`; bit 7 set: acknowledge (`STA $D019`), `CLI`, jump to the raster handler (target patched at `$81BD/$81BE` = self-modifying operand, set by `G:1996-1999` `$9A5E-$9A63`); clear: `BIT $DC0D` (acknowledges CIA 1) and jump to the CIA handler (operand at `$81B6/$81B7`, set to `$8649` by `G:524-526`). The `CLI` before the raster handler lets the CIA 1 timer IRQ nest inside it. Needed: I/O reads `$D019`, `$DC0D` with byte and position (who raised the IRQ, was the flag already gone), IRQ vector pulls and RTI with the interrupt lines (already recorded), code writes into `$8000-$BFFF` (`CODEW`, already recorded: the operand patches at `$81B6/$81BD`).
- **CIA 1 timer A as PCM / music tick: `G:505-528` (`$860E-$8628`)** - `$DC04 = $59`, `$DC05 = 0`, continuous, ICR `$81` = about 11 kHz IRQ (the 218 per frame of the size estimate); the handler `G:529-560` (`$8649-$867B`) writes `$D404/$D40B/$D412` from tables at `$84A0/$84E0/$8520` and ends with RTI (`$867B`); the timer is stopped at `$862D-$8648`. Needed: the timer IRQ vector pulls and RTIs with their raster position (recorded), the three SID writes (recorded), `$DC0D` reads (new).
- **Raster waits: `G:1993-2005` (`$9A6F-$9A79`), `G:2358-2361` (`$9EB9`), `G:2590-2593` (`$A0BB-$A0BE`)** - polls of `$D012` (`CMP $D012`, `BEQ`/`BCS` loops: wait until the raster leaves line N or passes line N+2) with `SEI` at `$9A6E`; also `STA $D012` / `$D011` bit 7 for the next raster IRQ line (`$9A4F-$9A59`, `$9E6E`, `$9EC0`, `$A0A1`, `$A0E7`). Needed: `$D012` reads (folded while the value does not change; the next record carries the count and ends the poll) and the `$D012` / `$D011` writes (recorded).
- **HUD IRQ line `$D1`: `G:1985-1990`, `G:2008-2064`** - the chain of ~23 writes (`$D011 = $6B`, `$D021`, `$D015`, sprite X registers, `$DD00`, `$D016 = $D8`, `$D018`, `$D011`) as in section 1 (recorded, with the clocks the CPU waited and the mirror mode).
- **Random numbers from timers: `L1` `LDA $DD04` (CIA 2 timer A low, ~40 sites, e.g. `L1:216`, `$0AA6`), `G:3088`, `G:3132`, `G:3137`, `G:3154` (`LDA $DC04`)** - used as `AND #mask`. The byte itself decides enemy positions and sprite choices, so a run cannot be replayed without it. Needed: I/O reads `$DC04`, `$DD04` with the byte (new).
- **SuperCPU registers (`MetalDustUltimate/docs/MEMORY_MAP.md` section 2, checked against the code): game.bin writes `$D07B`, `$D07E`, `$D075`, `$D07F` once (`$B564-$B56D`), brackets the HUD table copies with `$D07E / $D077 / $D07F` and back to `$D075` (`$AB13-$ABBF`); nothing reads a `$D07x/$D0Bx` register.** Needed: the register writes (recorded as class `scpu`), the mirror mode in every record (recorded). Reads of the `$D0Bx` area would also be recorded by v2 (none expected).
- **16-bit and long addressing, block move (bank 0 is the C64 RAM; banks `$02+` are SuperRAM and never reach the C64 bus):** level code is copied bank 6 -> `$0810` by `LDA $06C000,X / STA $0810,X` in 16-bit mode (`G:200-211` `$82EF-$8301`, called at `$B5A2`); `MVN $06,$00` copies `$2300` bytes from bank 6 `$8000` to `$5100` (screen / charset area, `G:231`, `$8322`); `L1:2257-2269` stores to `$022520..$02A920,X` (SuperRAM). The `$0810` and `$5100` stores are bank-0 writes (recorded when they reach the bus; `$0810` code is outside the `CODEW` window `$8000-$BFFF`, the earlier SMC bench shows 0 stale bytes). The bank-2 stores are recorded from trace v3 (Alex, 2026-11-14, §3): one record per byte (`STA $022520,X` = 13 stores per call at `L1:1C64-1C94`).
- **Not found in the code:** WAI / COP / BRK, DMA or REU access (the original has none), any read of the CPU port `$01` as a timing source, `PHK`. The speed: `$D07B` once at the game start; the 1 MHz switch `$D07A` only in the intro / boot stub (`BOOT_CHAIN.md`).

What this means for the record set: I/O reads of `$D000-$DFFF` with the byte (VIC `$D011 $D012 $D019 $D01E/F`, SID `$D41B`, CIA `$DC04 $DC0D $DD04 $DD0D`, `$DC00/$DC01` keyboard / joystick) are the one missing class; everything else the code does is a write, a vector pull or an RTI, which v1 already records. A level start with the v2 core is therefore enough to answer: does the SID loop end (`$85C0`), do the timer IRQs nest in the raster handler, are the `$D019` / `$DC0D` flags read as the game expects, are the random bytes the game gets plausible.

## §3 Decision

Findings of the benches (2026-11-11, `cores/c64scpu/sim/run_mdust.sh`, synthetic ROMs of our own from `tools/gen_c64scpu_mdust.py`; the access patterns are those of §1):

- found (S1, candidate 1 negative): the mirror queue holds under the game's dense stream (optimisation mode `$D075`, `$D077` windows, 16-bit stores, `MVN`, eight double-height
  sprites over a bitmap screen). 98,734 mirrored writes: 0 wrong against the VIC's copy, 0 wrong in the DDR2 at the end, `n_wlost` 0, 98,734 accepted by the queue, 98,733 landed
  (one in flight at the end). The same with the HUD IRQ chain running: 174,924 writes, 0 / 0 / 0. The picture faults are not a lost or late mirror byte.
- found (S2, candidate 2 half confirmed, cause is not the arming window): 24 back-to-back `stz $D0xx` at 20 MHz take 23 PHI2 cycles first store to last store when the code is in
  the code cache, exactly the VICE accounting (`scpu64cpu.c` `scpu64_clock_write_stretch_io_start` / `_io`, ported in `check_mdust.py vice_model`: one PHI2 cycle per I/O store); the
  address arming window (`scpu_mem.v` `skip_now`) is not touched by this and was not changed. The first, cold call takes 27: every 16-byte line of code that is not in the cache
  (`scpu_cache.v`, direct mapped, index = address bits 12:4, refill from the DDR2 about 50 clk2x) adds one PHI2 cycle, which VICE does not have (bank-0 fetches never wait there).
  The game's HUD stage (`$9A6E-$9AE4`, 23 writes from `$D011=$6B` to `$D011=$3B`): 23 PHI2 cycles when its code is in the cache, 28 when it is not (first run; every frame when
  the scroll's reads from SuperRAM bank 2 sit on the same cache indexes: the game reads `$02:0000,X`, a sweep over all of them). Whether the game's own layout evicts the stage between
  two frames is not known from the code alone; the board decides (S4). The original Protovision game (`Metal Dust CBM-1581` Disk 1, `game.bin`) has the same bytes at `$9A6E-$9AED` as
  the crack the analysis used (the two differ only at `$8C00-$8CAF`, `$9ED0-$9F1B`, `$B71E`, `$B73F`).
  Decided 2026-11-11 (coordinator, after the board S4 showed the same flicker on the original): option 1, a next-line prefetch on a program-stream miss, built (S5 below); a separate code
  cache and a 2-way cache are not built (their cost is in section 5).
- found (S3, candidate 3 negative): the menu's `$F3` handler (acknowledge `$D019` at the very end) runs once per frame at 20 MHz: 70 entries in 70 frames, none twice, none skipped,
  every entry ends. After the switch to 1 MHz (`$D07A`) the same: 120 entries over both phases, once per frame, none skipped. The menu "too fast at 20 MHz" is the menu's own design
  (it counts frames); it concerns only the crack, its cheat menu is not part of the original game.
- board: `n_wlost` is readable in the core's register page E at `0x101AE0C6` (low) and `0x101AE0C7` (high), 16 bit little endian, `RAM_COUNTERS` word 3 of
  `{vic_miss, cpu_wait, fetch, wlost, blk1}` (`c64scpu_regs.v`); it must stay 0 while the game scrolls. `0x101AE0C0/C2/C4/C8` are `vic_miss`, `cpu_wait`, `fetch`, `blk1`.

Together with it a review finding is fixed: a run of folded identical I/O reads that ended by a recorded write, vector pull, RTI or the stop lost its REP count; now a flush record (type 7 sub-type 5) carries it. ## §4 Out

- CMD FD-2000 / `.d2m` (and `.td0`) images: no FD-2000 drive emulation (Alex, 2026-11-11: "no, we do not want that", translated). Metal Dust runs from its four `.d81` on the 1581 with JiffyDOS.

Decided 2026-11-11 (coordinator, after the board S4): of the three ways to keep the HUD stage's code warm only option 1 (the next-line prefetch, S5) is built.
- Option 2, a separate instruction cache: not built. It needs a second 512 x 141 array that every CPU write must update or invalidate (a second writer; see §5 for the cost). It would make the stage immune
  to data sweeps, which the prefetch does not; the benches (`hudx`: code evicted every frame) show the prefetch already holds writes + 1, so the extra array buys nothing measurable here.
- Option 3, a 2-way data cache of the same 8 KiB: not built. It keeps a code line against one conflicting data line but not against a sweep, so it helps less than option 2 for this game, at +~130 LUT.
- Both come back only if the board (S4) shows a stage that the prefetch does not hold; then as a new decision with Alex.

S5 (2026-11-11, `scpu_cache.v`, `scpu_mem.v`, `cpu65816_c64scpu.v`): next-line prefetch, sequential, program stream only.
- Mechanism: the CPU's `vpa` (opcode or operand fetch) goes into scpu_mem (`b_vpa`). `stream` = the line the program stream is in: set by a program-stream miss (`dgo` with `f_if`), advanced by a
  prefetch. A program-stream read (`rd_if`, the clock after the CPU's enable, with `rd_ln` = its line) in line `stream` sets `pf_pend`; the prefetch of `stream + 1` starts when the fetch engine is idle
  (`!st_wait`, no write open, `quiet == 0`, no demand miss waiting: a demand miss has priority and waits at most for the prefetch in flight) with the same S job, same `s_req_line` / `fill` / write
  port as a demand fill (the block RAM keeps one write port with the same address mux, skill section 3). The first fetch in the prefetched line moves `stream` on, so straight code is always one
  line ahead and a loop over lines that are already in is never refetched. A jump into a line that is in the cache starts nothing.
- Coherence: the CPU runs while the line is on its way (a demand fill never needs this, the CPU is held). A write (`wr_go`) to the line of the open or just finished prefetch (`pf_cur`, the open
  fetch or the 3 clocks after its fill, `rcnt`: `cq` may still show the old line and `wr_byte` would miss) sets `kill_q`: the next clock the line's index is invalidated (`inval`, the same zero word as
  the flush) and a fill still to come is dropped (`drop`, as for a flush). Writes to other lines are untouched: they hit or go through as before. A prefetch fill that meets a `wr_byte` in the same clock
  is lost (the byte write has the port); the line is simply not cached. Review fixes (same day): (a) a prefetch does not start in the clock of a `wr_go` (`pgo` has `!pg_wr`, `pg_wr = wr_go`):
  in that clock `wb` is still 0 and `kill_q` looks at the old `s_req_line` / `st_wait` / `rcnt`, so a write to line `stream + 1` would be missed and the S job (served before the SW byte lands if the two
  toggles reach the engine one ui clock apart) could fill the old bytes; held back one clock the write opens `wb` and the fetch waits for it. The smaller fix of the two (widening `kill_q` with
  `stream_nx` would add a second 21-bit compare). (b) a `kill_q` invalidate no longer takes the port from a byte write to another line (`inval = kill_q && !wr_byte`, `kill_q` stays one more clock):
  before, that byte stayed old in a cached line; the CPU's enables are at least 3 clk2x apart so it was unreachable, now it is by construction. (c) a data miss (`f_if = 0`) leaves `stream` / `pf_pend`
  alone on purpose: `stream + 1` is the next line of code the program is still running in, the fetch is plain DDR2 (the 21-bit line number wraps inside the core's 0x02000000-0x03FFFFFF window, so no
  address outside it is ever read), and what it wastes at the end of SRAM or of the ROM is one line fetch. MVN and mirror writes: MVN's writes are CPU writes through `wr_go`; the mirror queue never touches this cache.
- Proof S5: `hud` and `hudx` (the stage's code is evicted by the data sweep every frame, 10 chains each) and the first, cold chain: 23 writes in 23 PHI2 cycles on every chain (before: 23 in 28 on
  all 9 later chains of `hudx`, 23 in 28 on the cold one; `hud` warm 23). `stz` cold call: 23 PHI2 cycles (before 27; VICE model 23). `smc` (`tools/gen_c64scpu_mdust.py smcbench`): 60 code lines in
  SuperRAM bank 2 that store the pass number into the immediate of the next line, 8 passes, code evicted before every pass (a sweep of bank 3 over the same indexes): all results right. A debug
  print at the guard showed the stores hit every phase of the fetch: 125 of 480 while the prefetch was open, 28 in the 3 clocks after the fill, 334 later (a normal hit write). Negative control
  `SCPU_MUT_NOKILL` (guard off): the same bench FAILS (marker 2, a result of the previous pass); it runs in `run_mdust.sh` as `smc_nokill`. No CPU program of the benches reached the clock of review fix (a)
  (`+PFDBG` `pfcoin|` lines: 0 in `smc`; the enables are at least 3 clk2x apart), so the two races are driven on the ports of `scpu_cache.v` in `cores/c64scpu/sim/tb_scpu_cache.v` against a DDR2 model that
  serves the S job 3 clocks and lands the SW byte 6 clocks after their toggles (the worst order): race_a / race_b / race_c, then a check that whatever the cache holds of the line equals the DDR2.
- Cost (yosys `synth_xilinx -family xc7` of `scpu_cache.v` alone, before -> after): LUT 313 -> 376 (+63; 396 before the review fixes), FF 143 -> 171 (+28), CARRY4 22 -> 29, RAMB36 2 -> 2 (yosys reports no implicitly declared net). scpu_mem.v adds 23 FF (`rd_ln`, `rd_if`,
  `b_vpa`) and no logic of note. The cache read path (`cq`, `hit`, `mem_q`) is unchanged; the new paths are a 21-bit compare from registers into one flip-flop each (`rd_ln == stream`, `w_p[24:4] == s_req_line`)
  and the 21-bit `stream + 1` into `s_req_line`.
- Not built, what it would take: (2) a separate instruction cache: a second 512 x 141 array (2 RAMB36, +~120 LUT for tag compare and the fetch / data steering) that every CPU write must also
  update or invalidate - a second writer into an array that has one, so either a true dual-port inference (two write ports, to be proven in Vivado) or an invalidate-only write port; it makes the stage
  immune to data sweeps, which the prefetch does not (a jump into a stage that the sweep evicted still pays one refill, before its first write in the bench). (3) a 2-way data cache of the same 8 KiB:
  256 sets x 2 ways, the same 2 RAMB36 but a way mux over 128 bits (+~130 LUT), LRU bits, two tag compares in the multicycle path of `hit`; it keeps a code line against a single conflicting data line
  but not against a sweep (both ways are evicted by 8 KiB of data), so it helps less than (2) for this game.

**Record format** (field list in the header of `scpu_trace.v`, decoder `tools/scpu_trace.py`; bit for bit, `--selftest` checks both):
- type 7 sub-type 4 (`[41:38]` = 4), SuperRAM write: `[37:14]` 24 bit CPU address (bank `>= $02`), `[13:6]` data byte, `[5:4]` 0, `[3:2]` mirror mode, `[1]` 20 MHz, `[0]` E flag; raster line / cycle / x mod 8 as in every record. Tap: `scpu_mem.v` `tr_sup` = `b_bus && b_wr && bank in $02..$F7 && d_wk == WK_MEM` (the stores the SuperRAM cache takes; `$F6/$F7` aliases only with hwenable, as the memory map). Control `0x101800` **b5 SUPRAM** (taken at the arm, as b2 / b3 / b4); `tools/trxdbg.py trace arm` sets it by default (`ctl = 1 | 8 | 32`), `nosup` clears it.
- One record per byte: the CPU does one bus cycle per byte, so a 16 bit store is two records (address, address + 1), `MVN` / `MVP` one per byte moved (bank 6 -> bank 2 as well as bank 0 -> bank 2; an `MVN` into bank 0 is a bank-0 write, recorded by the old types when it reaches the bus). A recorded SuperRAM write ends a run of folded I/O reads like any other recorded write.
- type 7 sub-type 5, REP flush: same fields as the read record (`[37:22]` address, `[21:14]` byte, `[13:4]` REP, mode, 20 MHz, E). It stands for REP identical reads of that address / byte that came after the last recorded read of it. It is emitted (own holding register `p`, priority above the CPU record, so it goes out first) when the run ends: a different read, a recorded write / vector pull / RTI / SuperRAM write, or the stop (in `S_END`, before END1). The sub-type 3 read record's REP field is 0 from v3 (reserved): reads of a run = 1 + the REP of its flush records. Its mirror / 20 MHz / E fields describe the event that ended the run (or the live state at the stop), not the folded reads. The decoder prints `R+` lines and adds the REP to the read table of the address.
- Limits: the SuperRAM write oracle in `tb_c64scpu.v` (`trc|s`) is valid for banks `$02..$F5` only; writes to `$F6/$F7` with hwenable print the aliased cell, not the CPU address, and are untested.

**Decision input.** Reference is clear for writes (VICE `:193-203`; electrically a write cannot complete while AEC is low, the 6510's 3 write cycles end at cycle 14). The core's rule `rdy_in = rdy | wr_cyc` (`cpu65816_c64scpu.v:156`, writes never held) is the deviation; the reads are right. Effect on the stars: the sprite X (`$D00C...`) is applied at cycle 13-17 of a badline in the core (this line) and at 55+ on hardware (next line for a sprite at x < 400): every 8th line the star segment moves one line earlier than the original - a 1-line jitter against the neighbouring lines; plus the 3-line steps when the queue holds the first I/O. Minimal RTL (not committed, not run): `scpu_mem.v` gets the BA-derived `rdy` (as the wrapper's `rdy_latched`), counts PHI2 cycles of BA low (`ba_n`), and `arm_go` of a `sync_cyc` **write** additionally needs `ba_n < 3` (writes during the 3-cycle allowance only), i.e. one counter, one term in `arm_go`; the 65816 write is then held like a read (enable withheld). Risk: timing of the 65816 enable path (WNS floor -10 ps), and every bench that counts I/O write spacing on badlines (hud: `$D011 6B -> 3B` in 23 cycles does not hit a badline start; `scroll`, `mirord` do) must be rerun: run_mdust all, run_trace, run_mirror, run_irq, run_map, run_speed.

**HUD / asteroid glitch on fire (code reading, no board).** `game.bin`: the `$FF` stage (`$9AE5-$9B1D`, `G:2060`) is 12 instructions (3 I/O writes, `INC $9A46`, `$D012=$D1`): it cannot be what delays the HUD IRQ at `$D1` ~210 lines later. The HUD stage `$9A6E` (`SEI / LDA $D012 / CMP #$D2 / BCS $9A7B / CMP $D012 / BEQ`): entered at line `$D1` it waits for line `$D2`; entered at or past `$D2` it skips the wait and its 23 writes start at a fixed point after the (late) entry - so any IRQ latency > 1 line at `$D1` puts the HUD writes on the wrong line, the same one every frame while the cause persists. What fire adds are sprite-multiplexer stages (`$9E7A` / `$A0xx` chain, `$D012` set by `$9E6E/$9EC0/$A0E7`, ends via `JMP $9B09` into the HUD IRQ; `CMP #$CF / BCS` ends the chain): each stage is entered with I set, calls `$9D4F` (`STA $77F8,X` = **one** mirrored store in mode `$D075`, 13 I/O stores and 3 reads), and `$A0BB: CMP $D012 / BCS` busy-waits for a raster line with I set. Mirrored stores per stage: 1 (pointer); the stack (`$01xx`) is not in `$40-$7F`, bullet tables `$9Cxx` neither, so the fire path issues about 1 mirrored store per active sprite stage, not tens. That is at most one badline hold (<= 45 cycles) per stage, the same as VICE (its `STA $D027,X` right behind the pointer store waits to cycle 55 on a badline anyway). The numbers do **not** support "mirror queue latency pushes the HUD IRQ past `$D2`" and no core-vs-VICE difference for it comes out of the code; the badline write rule above does change where each stage's 13 sprite-register writes land (cycle 15-17 in the core vs 55+), which shortens a stage in the core, never lengthens it. The HUD fault on fire therefore needs either the game's stage chain running into line `$D1` (a long mux stage / the `$A0BB` wait; identical on VICE) or something the code does not show; not reproduced, not proven. Bench variant with extra mirrored stores in the `$FF` stage: not built - the stage is not on the path.

### 2026-11-14 (evening): BA hold of I/O writes (branch `scpu-ba-hold`, RTL change in `scpu_mem.v`)

**Cause found, bigger than the jitter.** `vendor/icepi/vicii-kawari/hdl/registers_scaled.v:1469` accepts a register write only with `aec && !ce && addr_latch_done && !rw`: a CPU write that arrives while AEC is low is **dropped by the VIC**. The old core never held writes (`rdy_in = rdy | wr_cyc | mem_free`), so on a badline (and in a sprite-DMA window with BA low for 3+ cycles) the writes `$D010/$D02D/$D02E` at cycles 15-17 landed on the bus and were lost in the VIC, the CPU believing them done. That is the stars' flicker and, as the bench shows, a permanent chain stop: in `starsq60` / `starsq90` the `$D012 = next line` write at line 148 cycle 7 (sprite 6/7 DMA, AEC low) is dropped, the compare stays 147, the raster IRQ comes at line 147 once per frame, the handler counts its line variable up by 3 per frame (`$D012` values 96, 99, 9c ... in the log) and the 35-IRQ chain becomes 1 IRQ a frame: 50 IRQs in 200 ms instead of 350. Not a program bug: the same program runs 350 / 350 with the hold; `starsq30` lost 35 of 350 IRQs (315) in the old core, `stars` (16 bit saves, handler starts late) happened to avoid the window.

**Change.** `scpu_mem.v` (`ba_n`, `ba_hold`, `io_wr`, `wr_hold`, `arm_go`, the `a_skip` branch of the arm block): new input `ba` (`vic_ba` through `cpu65816_c64scpu.v` and `c64_top_c64scpu.v`). `ba_n` counts the PHI2 starts (`l_ev`) at which BA was low, saturating at 3, reset by BA high: the same chain as the VIC's `ba1..ba3` that lowers AEC, so `ba_hold = !ba && 3 consecutive low samples` is true exactly in the cycles whose PHI2 half has AEC low (cycle 15 on a badline, VICE's `maincpu_ba_low_start = clk + 3`). An I/O write (bank 0, page `$D0-$DF`, class BUS or INT) at 20 MHz does not arm while `ba_hold`; the CPU's enable is withheld (`bus_go` stays low, as for a MEM wait) until BA is high, then the write takes the next arming point as any I/O cycle. A write armed late in the cycle before (`a_skip`) is disarmed at the `l_ev` that would put it on the bus into a hold. Reads are unchanged (the CPU repeats the cycle on `rdy` low, as before; they already waited from cycle 12). Not changed: CIA writes ("always wait", `scpu64cpu.c:206-217`) - the I/O sync of this bus model (`sync_cyc`, PHI2 rise) already makes every I/O cycle wait for the PHI2 boundary, no BA-independent extra wait was measurable; 1 MHz mode (the 65816 does what the 6510 does there). `SCPU_MUT_NOBAHOLD` switches the hold off (the old core; used for the chain-stop proof above, not a CI control).

**Measured** (`run_mdust.sh`, builder, `+MS=200 +IOW`), median PHI2 cycle of each I/O access of the stars handler:
- before (stars, 72 accesses of 24 badline handlers in the VIC's window): badline `r$D019@10 w$D019@12 w$D00C@13 w$D00E@14 w$D010@15 w$D02D@16 w$D02E@17 w$D012@60 r$D011@61 w$D011@62`; normal `... w$D02E@17 w$D012@24 r$D011@25 w$D011@26`.
- after: badline `r$D019@10 w$D019@12 w$D00C@13 w$D00E@14 w$D010@55 w$D02D@56 w$D02E@57 w$D012@64 r$D011@65 w$D011@66`, normal unchanged; 0 accesses in the window; the three held writes wait to the window's end and the tail keeps its normal distance (7 cycles from `$D02E` to `$D012`): badline = normal + 40 (`check_mdust.py check_stars`, "VICE hand model": accesses before cycle 15 equal on both, later ones +40..43). 350 IRQs of 350 for `starsq30` and `starsq60`.
- Mirror buffer (VICE `wait_buffer`: the next buffered write or I/O waits for `buffer_finish` ~1.5 PHI2, BA-held inside): measured, not changed. The core's queue holds a later I/O until the mirrored write is on the C64 bus: outside a VIC window that is the same ~1.5-1.6 PHI2 (run_mirror S5: 1,024 mirrored stores 1025 PHI2 cycles, VICE model 1025), inside a window both wait to cycle 55 and the queue then drains within the 1-2 cycles VICE's buffer needs (the stars handler's `$D02E` to `$D012` distance is 7 on the badline as on a normal line with 4 mirrored stores in between). A 1-2 cycle difference at most, no longer the 3-5 cycles of the old tail (60-62 vs ~57-58); a rewrite of `arm_go` against the queue would touch the bus-drive collision rules of `go_win` and is not justified by a measured difference.
