# T25.2 — Clean-room Copper (raster-timed VIC register writer)

**Status:** won't do (Alex, 2026-10-02): no user on the C64U, write capture is covered by T20/T21. Keep `CAPAB_COPPER` = 0. Spec kept for reference. Nothing built. **Task:** TODO.md T25 (overview:
`docs/specs/T25-cleanroom-multisid.md`). **Shares with:** T21 (monitor: VIC write capture),
T20 (frame-cycle counter), T16 (the 0x10046000 page is also the cartridge timing buffer).

**One sentence:** the app has a Copper driver, but no current build compiles it and the
C64U app never touches the Copper; for compatibility nothing is needed beyond keeping
`CAPAB_COPPER` off, and a Copper of our own is an optional TRX64 feature whose interface may
follow the old driver.

**Clean-room rule.** Written without opening Gideon's `fpga/io/copper` VHDL, locally or on
the web, and without reading ue2emu's copper model (TODO.md asks first whether that model was
written from Gideon's VHDL, §4 Q1). Sources: the app's driver code (what it writes and
reads), public Copper concepts (Amiga, ZX Spectrum Next), our own design.

All app citations are `path:line` in `software/ultimate-app` at submodule commit `25568658`.

## 1. What the block does for the app and the user

### 1.1 Who uses it: nobody in a current build

- `software/io/copper/copper.cc` is listed with `####` (commented out) in
  `target/u64/nios2/ultimate/Makefile:246`, `target/u2plus/nios/ultimate/Makefile:209` and
  `target/u2/microblaze/mb_ultimate/Makefile:153`, and is **absent** from
  `target/u64ii/riscv/ultimate/Makefile` (the C64U app). It would not compile anyway:
  `copper.cc:223` has `{0]`, and `fetch_task_items` at `copper.cc:41` does not match the
  declaration in `copper.h:52`.
- The driver registers itself only when the FPGA reports `CAPAB_COPPER` (bit 19,
  `software/system/itu.h:68`; `copper.cc:28`). Our ITU reports `g_capabilities = X"25C00222"`
  (`designs/c64_basic/ultimate_sys.vhd:59`): bit 19 is 0.
- The event it listens to, `e_copper_capture` (`copper.cc:80`), is raised nowhere else in the
  app.
- The register page `COPPER_BASE` = `IOBASE + 0x46000` (`software/system/iomap.h:17`) is the
  same address as `CART_TIMING_BASE` (`iomap.h:18`), which `C64::measure_timing` reads as a
  2 KB measurement buffer (`software/io/c64/c64.cc:2136-2160`, triggered by
  `C64_PHI2_EDGE_RECOVER`). In our map this is inside the slot-server window
  0x10040000-0x1005FFFF, today a stub (`docs/ultimate-app-hw-spec.md`, table §6).

**Conclusion for app compatibility:** keep `CAPAB_COPPER` = 0 and let 0x10046000 read as
zero. That is today's state; T25.2 needs no hardware for the C64U app.

### 1.2 The interface the old driver expects (for an optional own Copper)

From `software/io/copper/copper.h:11-35` and the driver code:

| Offset | Name | Dir | Use in `copper.cc` |
|---|---|---|---|
| +0x00 | `COPPER_COMMAND` | W | 1 = PLAY (run the program in RAM), 2 = RECORD (capture) (`:136, :199`) |
| +0x01 | `COPPER_STATUS` | R | bit 0 = busy; the driver polls until 0 (`:138, :173, :201`) |
| +0x02/+0x03 | `COPPER_MEASURE_L/H` | R | 16-bit cycle count from the last CAPTURE (`:141`) |
| +0x04/+0x05 | `COPPER_FRAMELEN_L/H` | W | frame length in cycles, the wrap of the frame timer; written 0xAB.. "far away" before a measurement, then the measured value (`:125, :144-145`) |
| +0x06 | `COPPER_BREAK` | W | stop a running program (`:64, :266, :322, :362`) |
| +0x1000..+0x1FFF | `COPPER_RAM` | R/W | 4 KB program RAM, and the capture buffer in RECORD mode; written while a program runs (`sweep`, `:356-357`), so the engine re-reads it every pass |

Instruction set (`copper.h:24-35`), byte-coded, operand lengths from the lists in
`copper.cc:104-119, 150-159, 228-237, 300-313`:

| Code | Name | Bytes | Meaning (inferred from use) |
|---|---|---|---|
| 0x00-0x3F | WRITE_REG + r | 2 | write the next byte to VIC register `$D000 + r` (`:105-118`, `:232`) |
| 0x40-0x7F | READ_REG + r | 1? | read VIC register r (unused in the driver; length unknown) |
| 0x81 | WAIT_IRQ | 1 | wait for the VIC IRQ line (raster IRQ set up by the list itself) |
| 0x82 | WAIT_SYNC | 1 | wait until the frame timer wraps (start of frame) |
| 0x83 | TIMER_CLR | 1 | clear the frame timer (`measure`, `sync`) |
| 0x84 | CAPTURE | 1 | latch the frame timer into MEASURE |
| 0x85 | WAIT_FOR n | 2 | wait n cycles (`:234`, "two cycles already used" `:305`) |
| 0x86 | WAIT_UNTIL lo hi | 3 | wait until the frame timer equals the 16-bit value (`:231`, `:302`) |
| 0x87 | REPEAT | 1 | jump to the start of the list (loop per frame) |
| 0x88 | END | 1 | stop, clear busy |
| 0x89/0x8A | TRIGGER_1/2 | 1 | pulse a trigger output (scope/debug) |

RECORD format (`capture`, `copper.cc:197-219`): 4-byte records `{t_lo, t_hi, reg, value}` of
CPU writes to the VIC, `t` = frame timer, decoded by the driver as line `1 + t/63`, cycle
`1 + t%63` (PAL, 63 cycles per line); a record with `t_hi` = 0xFF ends the list.

The driver also writes the VIC directly (`VIC_REG`, `C64_POKE`) and saves VIC state plus the
Copper RAM to `image.vic` (`write_state`, `:280-296`).

## 2. What we have today in TRX64-Ultimate

- No Copper. 0x10046000 lies in the slot-server stub (reads 0). `CAPAB_COPPER` = 0.
- Pieces an own Copper would reuse: the VIC's raster position from vicii-kawari
  (`cores/icepi/vicii-kawari`), the app DMA path that already turns a byte write into one C64
  bus cycle while the machine runs or is stopped (`ultimate_sys.vhd` `r_dma`, `top.v`), the
  machine-pause / cycle bookkeeping of T12/T20, the bus trace and write log of T20/T21.

## 3. Required behaviour

### 3.1 Phase 0 (compatibility, the actual requirement)

- `CAPAB_COPPER` stays 0; 0x10046000-0x10047FFF reads 0x00 (RAZ, never 0xFF, as the
  hw-spec requires for stubs), writes ignored. Nothing else.

### 3.2 Phase 1 (optional TRX64 feature): own Copper

Only if a user of it exists (T21 monitor "capture VIC writes with timestamps", demo/debug
tools over REST, our TRX64U menu T32). Behaviour:

- **Frame timer:** counts C64 cycles, wraps at FRAMELEN; cleared by TIMER_CLR; can be locked
  to the VIC frame start instead of being measured (we know the VIC position directly, so
  `measure`/`sync` reduce to reading kawari's raster counters; keep MEASURE for the driver).
- **WRITE_REG** performs one VIC register write as a C64 bus cycle in the cycle it is due,
  through the same path as an app DMA byte (one stolen cycle, the CPU held with RDY like a
  DMA; or, better for demos, a write in the VIC's half-cycle without stealing the CPU's
  cycle, if kawari allows a second write port — design decision, §4 Q3).
- **WAIT_UNTIL / WAIT_FOR / WAIT_SYNC / WAIT_IRQ** with one-cycle resolution against the frame
  timer; a WRITE_REG due at cycle t lands at t (the driver's `sweep` tunes t by ±1 cycle and
  ±63 cycles and expects the effect to move by exactly that).
- **RECORD:** every CPU write to `$D000-$D03F` (and its mirrors) as a 4-byte record with the
  frame timer, until the 4 KB fill or BREAK. This is a subset of T21's bus trace and should
  come from it.
- **Machine pause:** the Copper stops with the machine (no writes, timer frozen) and resumes
  in step, so T20 restore and T21 single-step stay deterministic. Copper state (PC, timer,
  wait state) belongs in the ARCH state rows if it is built.
- **NTSC:** 64/65 cycles per line from the VIC model (the driver hard-codes 63; our software
  would not).

### 3.3 Accuracy targets

- Every WRITE_REG reaches the VIC in exactly the scheduled C64 cycle (checked with T21's bus
  trace: timestamp of the write = scheduled t).
- Colour splits from the `timed_write` list (`copper.cc:228-237`) are stable to the pixel
  across frames.

## 4. Open questions

1. Was ue2emu's copper model written from Gideon's VHDL? Until that is answered by someone who
   may look, nobody on T25 reads it (TODO.md "Clean-room rebuilds").
2. Is there any user for a Copper on TRX64? If not, phase 0 closes T25.2.
3. Write path: steal a CPU cycle (simple, like app DMA) or write in the VIC phase (needs a
   kawari change, invisible to the CPU)? Decides whether demos can use it without timing
   changes.
4. Should our Copper keep the old byte code (familiar, the app driver could be revived) or
   use a cleaner 32-bit format (Amiga-like WAIT/MOVE/SKIP)? Proposal: keep the byte code; it
   is small and documented above from the app.
5. Address: reuse 0x10046000 (clashes with `CART_TIMING_BASE` semantics for U2 cart timing,
   unused on the C64U) or put it in our own TRX64 register page (ARCH §15.3)? Proposal: own
   page, `CAPAB_COPPER` stays 0, so Gideon's app never sees it.

## 5. Resource estimate and fit

| Part | LUT | FF | BRAM tiles | DSP |
|---|---|---|---|---|
| Phase 0 (RAZ inside the existing stub) | 0 | 0 | 0 | 0 |
| Phase 1: 4 KB program/capture RAM (true dual port) | 10 | 0 | 1 | 0 |
| Phase 1: sequencer (PC, decode, 16-bit frame timer, compare, wait states, trigger) | 200 | 120 | 0 | 0 |
| Phase 1: write injection into the DMA path, capture tap from the bus | 80 | 60 | 0 | 0 |
| **Phase 1 total** | **~300** | **~180** | **1** | **0** |

Phase 1 fits the LUT budget (~23.7k → ~24.0k of 32.6k, 74 %), but costs one BRAM tile of
the 3.5 left under 80 % (56.5 → 57.5 tiles; T25.1 frees 3.5). If RECORD comes from T21's
trace, the RAM can be 2 KB (half a tile).
