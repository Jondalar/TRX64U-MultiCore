# T239.5 — a second pipeline next to the old one runs per core: an SDK part and a matrix of the cores that moved to the SDK

**Status:** IN PROGRESS (2026-11-24, D10).
**Repo:** TRX64U-MultiCore — CI (`.github/workflows/`, `ci/`), the app tests (`tests/coreapp/`), each moved core's `cores/<name>/`.
**Number:** T239.5 (the table in `TODO.md`).
**Origin:** Alex, 2026-11-24, after the VIC-20's move to its own app (T239.3 V-4) broke the old pipeline's shared app tests (translated):
"I think we need a 'core' pipeline that works per core ... also an SDK (shared) pipeline only for the app parts ... and then they run
orchestrated. And only the parts that are needed are made and de-diffed ... That is terrible." Basis: the pipeline page of T239.1 (the
maintainer's private site), Alex: "So basically like a further development of this". "When designing it we talked
about these stages having to run PER CORE. Now the SDK comes on top."
**Depends on:** T239.3 (the SDK, the VIC-20 as the first core with its own app), T239.1 D20 (every stage keyed by content).
**Milestone:** M2.

---

## §1 The problem

- The pipeline's stages run once for all cores. T239.1 D20 decided per-core keys for the apps and the `.cor` "once the app is split per
  core (T239.3)"; the app tests were never split.
- `tests/coreapp/run.sh` builds every core into the same test programs, with one driver table on the include path; shared units and
  goldens (`keywalk.txt`, `ids.txt`, the desc goldens) list every core.
- When the VIC-20 moved to its own app (T239.3 V-4), the shared tests broke: its driver table compiled the C64 family's 1581 out, the
  descgen and ROM-table checks still expected it in the shared image. Every move of a core would do the same again.
- A change to one core's files edits shared test files and goldens (T259: keywalk, ids, the bundle count).

## §3 Decisions

- **D1 (Alex, 2026-11-24, translated):** "The old pipeline stays. The new one is built next to it. We migrate core by core: for every core
  that moves to the SDK, its tests etc. come out of the old one, and the new pipeline gets that core in its matrix. Which tests etc.
  follows from TOML A and TOML B."
- **D2 (Alex, 2026-11-24, translated):** "And this pipeline setup can then basically also be 'copied' by the FW session (TRX64-Ultimate)."
  This matches T239 D9 (TRX64-Ultimate builds its `.cor` itself, "maybe with the same pipeline, adapted").
- **D3 (Alex, 2026-11-24, translated):** "Leave the VIC20 as it is and build the 2nd pipeline next to it for the T239 branch, and only THAT
  one runs there ... the rebuild happens in isolation, doesn't it?" The old pipeline keeps running on `main` and `integration`; the
  T239 branch runs only the new one.
- **D4 (Alex, 2026-11-24, translated):** asked whether the pipeline learns the tests of a library from an entry `tests = [...]` of that
  library in the TOML B (recommended) or from a naming rule (`test_<library>.cc`): "Yes. The two TOMLs declare almost everything in the
  build, and so in the tests too." Each library of a TOML B names its tests; the pipeline takes a core's build and tests from its TOML A
  and TOML B.
- **D5 (Alex, 2026-11-24, translated), the target picture:** "A. The SDK must build, so it needs LINT, unit tests, build, test,
  package, deploy (it must be stored somewhere, to build for the cores). B. Core pipeline. Compute the rest from the TOML A: 1) comparison:
  has something changed in the gateware, and is the TOML A complete, or does the app change with it; 2) what must all be in the app ->
  compare the TOML A with the app building blocks or the TOML B; 3) compare the TOML B with the TOML A and the app building blocks -> does
  the app have everything that was defined; 4) what has changed?; 5) tests mock bitstream -> service; 6) tests service -> UI; 7) tests
  service -> API; 8) package with the bitstream -> there is a 'comparison' with the bitstream path ... there we should maybe think about a
  matrix lying across that builds several bitstreams if needed and 'keeps' them for the pipeline lanes; 9) emulator tests; 10) deliver
  .cor + docs. That is roughly how I thought of it." The maintainer's pipeline page shows it as the tab "New pipeline (T239.5)".
- **D6 (Alex, 2026-11-24, translated):** asked whether D5 makes sense or misses something, the answer was: step 4 ("what has changed?")
  goes to the front, because it decides which of the other steps run; missing are the gateware tests (sims), which test the bitstream
  and so belong into the bitstream matrix next to Vivado, the check whether the app fits (size and heap against the limits of the TOML B;
  today only the shared app's size is checked, not vc20.app's) in the step that compares the TOML B, and the sub-apps (.u2a such as
  online.u2a), which A deploys with the SDK from the same build (TRX64-Ultimate lacked the matching online.u2a for SDK 0.4.6). Alex:
  "ok, then adjust it." The picture: A = lint, unit tests, build, test, package, deploy (the SDK and its sub-apps). B, one lane per core,
  the rest computed from the TOML A: 1 what has changed; 2 comparison (gateware changed, TOML A complete, does the app change with it);
  3 what must be in the app (TOML A against the app building blocks or the TOML B); 4 does the app have everything defined, and does it
  fit; 5 tests mock bitstream -> service; 6 tests service -> UI; 7 tests service -> API; 8 package with the bitstream; 9 emulator
  tests; 10 deliver .cor and docs. The bitstream matrix lies across the lanes: it builds the bitstreams, keeps them for step 8 and runs
  the sims of a changed gateware.
- **D7 (Alex, 2026-11-24, translated):** asked where the lint goes, the answer was three places: the tree checks on every push, before A
  and B (the public tree, no ROMs, TODO and specs, the versions; they must run also when only one core changed and A is skipped); A's
  lint (the tool tests descrec, libtab, app_build, u2a_pack, cor_pack, the API document, D24, the shared TOML B); the core's lint in B
  (the core.toml, the core id, the contract ports, the TOML A against the RTL). Alex: "ok, then also for B as step 1 Lint." B has eleven
  steps: 1 lint; 2 what has changed; 3 comparison; 4 what must be in the app; 5 does the app have everything defined, and does it fit;
  6 tests mock bitstream -> service; 7 tests service -> UI; 8 tests service -> API; 9 package with the bitstream; 10 emulator tests;
  11 deliver .cor and docs. The bitstream matrix feeds step 9.
- **D8 (Alex, 2026-11-24, translated), the matrix:** "Now let's think again as a 'matrix'. So the whole thing in lanes, but the steps
  the same ... if the SDK does not have steps, leave them empty .. and then maybe the bitstreams in too? Please the lanes from top to bottom
  and the steps from left to right." Then: "Then there must be a 'unit tests' step before it .. the core has its own libs and apps in
  C++, they need unit tests too .. so between 1 and 2, right?" The steps: 1 lint; 2 unit tests; 3 what has changed; 4 comparison; 5 what
  must be in it; 6 build (added in the discussion: B had no step that builds the app; the SDK builds, a core lane links its app from the
  SDK, a bitstream lane runs Vivado); 7 complete and fits; 8 tests mock bitstream -> service; 9 tests service -> UI; 10 tests service ->
  API; 11 package; 12 emulator tests; 13 deliver. The lanes from top to bottom: the tree checks of every push, the SDK, one lane per
  bitstream (the host, the VIC-20's partial), one lane per core that moved (the VIC-20). The maintainer's pipeline page shows the matrix.
- **D9 (Alex, 2026-11-24, translated):** asked whether one repository for both lines (a monorepo) would be better: it stays two
  repositories (TRX64-Ultimate is on GitHub too, since before this one; its builds still run with Gitea); the matrix removes the hand-over
  by hand once the SDK lane deploys to the registry (T239.4) and TRX64-Ultimate reads it there with the same matrix (D2). Against the
  two gaps found in the matrix (no place that decides which lanes start; the host app, which the emulator step needs, has no lane): "Ok,
  then a kind of 'dispatcher' job that decides what exactly this push has to do. That is fine for now." A dispatcher job at the start
  of each run decides the lanes and steps of the push (the role of `ci/plan.py` today); the host app's lane is open.
- **D10 (Alex, 2026-11-24, translated):** "Good, then I would suggest that this pipeline construct is now built NEXT TO the existing
  ones and wired to T239 as the branch, and you build VIC20 and the host menu with it." The matrix of D8 and D9 is built as a workflow
  of its own beside `pipeline.yml`; it runs on the T239 branch (`t239.3`, `t239.3-*`), where `pipeline.yml` stops running (D3); its
  lanes build the VIC-20 and the host menu (the host app, the lane that D9 left open).
- Later: the registry (T239.4) publishes per core, so the result of a core's run in the matrix is what it publishes.
