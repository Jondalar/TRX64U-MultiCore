## §1 The problem

**Who:** Alex, who plays Wasteland on the Apple IIe core (booted on the board 2026-10-20) and wants the disks and the hard disk the
real machine and the other FPGA Apple cores have.

**What he wants:** (a) mount a `.woz` image (copy-protected games, half-tracks, weak bits) as well as `.dsk/.do/.po/.nib` in either
Disk II drive and write to it; (b) a ProDOS hard disk in slot 7 (`.hdv`, `.po`, `.2mg`, two units, up to 32 MB) that the machine boots
from and writes back to; (c) Wasteland's copy utility (it makes the game disks, 4 new copies) to run without an I/O error.

**Today (code):**
- `drive_ii.vhd` walks a ring of 6,656 pre-nibblized bytes per track, one byte every 64 CLK_2M edges (32 CPU cycles). There is no bit, no
  sync-length, no timing between bytes except that fixed pace. `a2_trk.vhd` raises a request when the head's track number
  (`phase(7:2)`, 0..34) differs from the buffer's; while a request is open `DISK_READY` is 0, the engine stops, the latch is not
  updated and the guest reads `00`.
- The application (`apple2_disk.cc`, `apple2_nib.cc`) nibblizes a `.dsk` track into 16 x 416 bytes with 8-bit `FF` sync (6 before the
  data field, 47 after it), volume 254, and takes a written track back only if all 16 sectors decode with good checksums, else it drops
  the track with a notice.
- Half tracks: `phase` has four values per track, but the track window only knows whole tracks (`TRACK <= phase(7:2)`). Weak bits,
  WOZ: nothing. Slot 7: `io_select(7)`/`device_select(7)` exist in `apple2.vhd` and nothing answers them.
- `CPU_WAIT` of `apple2.vhd` is tied to `'0'` (the Nano used it for its hard disk).

**Wasteland, from the code (no image and no board available to this session):** nothing in the read path is provably wrong for a
standard-format disk; four mechanisms can make a copy program fail intermittently and each is a property of the byte model
(§3 D6 lists them with the counter that will tell them apart on the board).

**Resource situation:** block RAM was the binding resource (T89 D12: 44 of 50 tiles with aux RAM in block RAM). Q4 moved the aux RAM
to the DDR2, so the base is about 28 tiles; the floppy part is 4 tiles (two 8 KB buffers). The tile count is measured at the end of this
work (§5), not estimated here.

**Break the problem into parts, MECE** (§2 is checked against this list):
- **P1 Disk II engine at bit level:** bit cell clock, shift/latch semantics, head position in quarter tracks, rotation, wrap at
  `bit_count`.
- **P2 WOZ features:** WOZ 1 and 2 files, TMAP (half/quarter tracks, empty tracks), weak bits, noise on unformatted tracks, write support
  with write-back into the `.woz` file.
- **P3 Sector and nibble images on the same engine:** `.dsk .do .po .nib` become bit tracks (10-bit sync for sector images), written tracks
  go back.
- **P4 ProDOS hard disk, slot 7:** card ROM, registers, two units, boot, block read/write, write protect, 32 MB, `.hdv .po .2mg`.
- **P5 Application:** mount actions per file type, the unit slots in the menu, service of track and block requests, write-back.
- **P6 Wasteland copy utility:** causes in the read path, fix, instrumentation.
- **P7 Area, timing, licence:** LUT/BRAM/WNS against `pb_l2`; PROVENANCE and NOTICE of every donor file; no Apple ROM content.

## §3 Decision

### What the IIgs core does differently (read from its RTL)

| | IIgs (`rtl/iwm_woz.v`, `iwm_flux.v`, `flux_drive.v`, `woz_floppy_controller.sv`, `hdd.v`) | this core today |
|---|---|---|
| Controller | an IWM chip model (MAME-style), 2,504 lines, driven by flux pulses with a window state machine; 3.5" and SmartPort in the same module | Disk II soft switches + a byte latch (`disk_ii.vhd`) |
| Drive | `flux_drive`: motor with inertia, quarter-track head, bit position, bit timer (56 14M clocks per bit at 5.25"), weak-bit window, LFSR noise for empty tracks, bit write by read-modify-write (1,901 lines, 3.5" and FLUX playback in it) | `drive_ii.vhd`: phase table, byte ring |
| Track data | WOZ parsed **in hardware** (meta RAM 2 KB, TMAP scan, TRKS slots) from the SD block protocol; a 32 KB track RAM per 5.25" drive (supports WOZ 3 FLUX) | 6,656 byte buffer per drive, filled by the app |
| Rotation | continuous; position reset when a track load completes | ring address kept across track changes |
| Sync | the real bit stream (10-bit self sync) | 8-bit `FF` |
| While loading | donor measured on hardware: gating the stream until the track is in made boots fail 0/5 (their comment is a hint only); they play the previous track | `DISK_READY` 0: the guest reads `00` |
| Hard disk | `hdd.v`: AppleWin register set at `$C0F0-$C0FA`, 512 B sector buffer, **bus DMA into RAM** by the card, per-unit mount/protect/size, slot ROM visible only with a unit mounted; ROM = `hdd.a65` (AppleWin firmware, GPL) | none |

**Swap whole modules or port pieces — pieces.** Whole modules would bring about 6,500 lines of Verilog (IWM, IWM wrapper, flux drive,
WOZ controller) that are 3.5"/SmartPort/FLUX-heavy, written for a simulator-driven bring-up (the sources carry many debug and
Verilator-ordering workarounds), a 32 KB track RAM per drive (8 tiles each, against our 2), an SD block protocol we do not have, and
the WOZ parser in gateware where our app (RISC-V, C++) is the cheaper place and testable natively. They share nothing with the
NanoApple2 machine around them (`disk_ii.vhd` is the Disk II card on the machine's own `DEVICE_SELECT`, which stays). What is taken
from the donor, and how, is in D1.

- **D1 Donor and licence.** `rtl/roms/hdd.a65` copied verbatim into `cores/apple2/rtl/roms/` (AppleWin firmware, GPL-2.0+, in a GPL-3.0+
  repository; header kept); assembled with ACME (donor source dialect 0.97; the two diagnostic `!warn` and the `@` label lines are
  dropped in the build script because ACME 0.94 on this Mac and the builder cannot parse them; the result is byte-identical to the
  donor's `hdd.hex`, checked 2026-10-29) into a generated `cores/apple2/app/lib/hdd_rom.h` (256 bytes) that the descriptor
  embeds, with a script that regenerates and compares. `hdd.v` is **not** copied: its register semantics (read of `C0F0` executes, status
  codes `00/01/2B`, unit = bit 7 of the unit byte, sizes at `C0F9/A`, ROM visible only with a unit mounted) are re-implemented in
  VHDL (`a2_hdd.vhd`) because the card's own bus DMA and sector buffer are replaced by the app (D4). `flux_drive.v` is not copied: the
  behaviours (quarter-track head, 56-clock cell, 4-bit-window weak bits, LFSR noise, read-modify-write of bits) are re-implemented in
  `drive_ii.vhd` in this repository's style (one `CE_14M` enable, signals start at 0). Every file that carries donor text or a
  re-implementation of a donor behaviour gets a `PROVENANCE:` line (repo, commit, path, what was taken) and `cores/apple2/rtl/NOTICE`
  lists it. No Apple ROM content is added: the Disk II boot ROM stays `diskii.rom` from the stick.
- **D2 Disk II engine at bit level (P1).** `drive_ii.vhd` is rewritten: per drive a 17-bit position, a 6-bit cell timer (56 enables per
  cell = 8 x 7 of the 14M, the cell of a 4 us bit at the machine's clock; one byte = 448 enables = 32 CPU cycles exactly), the
  existing stepper table (phase 0..139 = quarter tracks, 35 tracks), the shift register, the latch. Read: every cell shifts the bit in;
  when bit 7 of the shifter is set the byte moves to the latch and the shifter clears (zeros between bytes shift through the empty
  shifter, which is how 10-bit sync works); a read of `$C08C` clears the latch (as the byte-consumed semantics of the Nano and of the
  donor's `m_data_read`). Write: `STA $C080+13/15` loads the shifter at the next cell boundary when idle (effective Q7 includes the
  current access); a cell with an empty shifter writes a zero. Position wraps at `bit_count`; on a track change the position is kept and
  wrapped (Open question 4). Motor: the existing 1 s spin-down is kept (the donor's is 300 ms; no software depends on either).
  The buffer is the existing `a2_ram` (13 address bits, 2 tiles per drive), port A bit-RMW for writes (the engine owns the cell: 56
  enables leave room for read, modify, write), port B the app's window. **Where the data lives:** the track bits in block RAM (6,656 bytes
  is the largest WOZ 5.25" track, 53,248 bits), the image in the file, converted by the app per request; the DDR2 holds nothing of the
  disk (a DDR2 read per 32 us would need a third client on the aux/frame-buffer ports for no gain: the latency that matters is the
  app's, D6).
- **D3 Weak bits and noise (P2).** The donor's rule (MC3470): a run of four zero bits makes the following zero bit random; our rule: a
  zero counter, when it is 3 or more and the stored bit is 0 the cell is a random bit with p = 1/4 from a 16-bit LFSR that runs on
  every cell (so two reads differ); data with at most two consecutive zeros (all GCR) is never touched. A track with the noise flag
  (TMAP entry `FF`, or no track served) outputs a random bit per cell (p = 1/2), which RWTS reads as no header. While a
  request is open the engine plays noise (default) or keeps playing the old track (register `DISK_CFG b0`, a board experiment that
  needs no rebuild, because the donor measured both ways differently from its simulation).
- **D4 Slot 7 card (P4).** `a2_hdd.vhd`: ROM 256 bytes at `$C700-$C7FF` (an `a2_ram` filled by the app through a new window array, loaded only
  while a unit is mounted: a zero array has no card signature, the Autostart scan skips the slot — the same trick as slot 6),
  registers at `$C0F0-$C0FA` as in D1. Reading `$C0F0` with command READ or WRITE raises a request (command, unit, block, memory
  address), drives `CPU_WAIT` (the machine keeps running, video, timers, the 14M enable; only the 65C02 step is withheld) until the
  app answers with a status, then the read completes with the final status; the app copies the 512 bytes between the file and
  main RAM through the existing base-RAM window (`ram_write/ram_read`). No sector buffer and no DMA engine in gateware. Target buffers
  are main RAM `$0000-$FFFF` as the window sees it (ProDOS buffers lie in `$0800-$BFFF`; language-card RAM is addressed as the
  window addresses it, not bank-translated: out, §4). STATUS answers from the app's unit table (mounted, size, protect), so a ROM that
  is not in the core costs nothing.
- **D5 Window protocol (P5).** Per drive: `REQ` carries the quarter track (8 bits, was 6) in the stepper's own count: magnet 0 holds the head at
  2, so whole track N is 4N + 2, a half track 4N + 4 (read from the table of `drive_ii.vhd`, confirmed by the bench; it is the offset the donor's
  `flux_drive` subtracts). The app maps it to the image: WOZ `TMAP[q - 2]`, a sector or nibble image track `(q - 2 + 1) / 4` unless `(q - 2) mod 4 = 2`
  (unformatted); positions 0 and 1 (the stop below track 0) read track 0. The app writes `BITS[15:0]` and the flag
  (`b0` noise) before `ACK`; `HEAD` is the quarter track. New window array 8 = slot 7 ROM. Slot 7: `HDD_STATUS` (request open,
  command, unit), `HDD_BLOCK` (2), `HDD_MEM` (2), `HDD_RESULT`, `HDD_ACK`, `HDD_SIZE/PROT/MOUNT` per unit. The register vector `sysv`
  grows from 16 to 32 fields (same sampling rule). `A2_ID` capability bit for the new engine so an old app fails clearly.
- **D6 Wasteland (P6), from the code.** The read path for a standard disk is right: the nibbles, checksums and fields are verified
  by the native test against an independent decoder, the engine pace is exact. What can still produce a read I/O error in a copy
  utility, in order of how well the code supports it: (1) **track-load latency with a silent drive**: every track change opens a
  request, `DISK_READY` = 0 and the guest reads `00` until the app has read, nibblized and written 6,656 bytes (serviced every
  `service_period_ms`, then a USB read plus a 6,656 byte aperture write); a copy utility that steps quickly and reads at once can
  time out where the boot code, which waits, does not. (2) **8-bit sync / short gaps**: a nibble copier that measures sync or
  re-times the track sees no 10-bit self sync; (3) **the write drop rule**: a track the guest formatted or partly wrote that does not
  decode to 16 good sectors is dropped, and the destination disk then reads `FF` there; (4) **volume 254 fixed**: a copier that
  checks the volume. This work removes (2) and (3) by construction (real bit stream with 10-bit sync; a written track is kept as the
  bits the guest wrote, a sector image decodes what it can and says what it dropped) and shrinks (1): same-track quarter positions
  are acknowledged without a copy, noise instead of silence while loading (a header-less stream, as a settling head reads), the
  service period is cut to 1 ms and the service loop spins while a request is open. It cannot prove the cause: the counters of S10
  (largest request latency, guest reads while no track, requests, stale ticks) are read out and printed on the console, so the next
  board run of the copy utility says which mechanism it was. If the mechanism is (4) or something in the image, the counters stay
  zero and the next step is a trace of the guest's `$C08x` accesses, which is outside this spec.
- **D7 Application (P5).** File types: `.dsk .do .po .nib .woz` mount to D1/D2 (actions as today: "Mount D1: and cold start", "Mount D1:",
  "Mount D2:"); `.hdv .2mg .po` (by size, a `.po` of 143,360 bytes is a floppy) mount to "Mount S7 unit 1 and cold start", "Mount S7 unit
  1", "Mount S7 unit 2"; media slots "D1:", "D2:", "S7.1:", "S7.2:" with eject. `.2mg`: 64-byte header, `2IMG`, data offset at `0x18`,
  length at `0x1C`, format at `0x0C` (ProDOS order for a hard disk; DOS order or nibble for a floppy). The image stays open; blocks are
  read and written on request; `sync` on eject/reset/Freeze exit as for floppies. WOZ: 1,536-byte header cache (INFO, TMAP, TRKS),
  track slots resolved per request; write-back of the bits in place; header CRC set to 0 on the first write (the format allows
  "not computed"). Conversions live in `apple2_nib.cc` (sector <-> nibbles <-> bits) and a new `apple2_woz.cc`. A mounted unit puts the
  card ROM (`hdd_rom.h`) into the core; the last unmounted unit zeroes it. Menu strings are in English.
- **D8 Cost (P7), estimated, replaced by §5.** Floppy part: +0 tiles (the two 8 KB buffers stay); engine +300..500 LUT (two drives);
  slot 7 card +150..250 LUT and +1 RAMB18 (256 byte ROM); counters +60 LUT; `sysv` widening +30 LUT. No DDR2 traffic for disks.

### §3a Open questions (recommendation first)

1. **WOZ 3 FLUX and 3.5" images** - answered 2026-10-29 (Alex: "then a", translated): 3.5" ProDOS block images (800 KB
   `.po`/`.2mg`) mount as a further slot 7 unit (read, write, boot), no new gateware; WOZ FLUX and 3.5" images that are not
   block images are refused with a message. A real 3.5" drive (IWM/SmartPort, Sony GCR) is its own spec later (T89.2).
