**Status:** spec 2026-10-07 (Alex), built the same day on `t25-resid8` (hardware, this repo, `run_all.sh` PASS) and
`t25-resid8-app` (app, Gitea; host tests green, u64ii container build, app space PASS). **Cut the same day (Alex, §9 decision 3):
Filter Curve = Dag's values 0-7 only, no loadable curve table in the reSID8 hardware; built on `t25-resid8-dag` / `t25-resid8-dag-app`.**
Not on the board. Task: TODO.md T25. Engine: [T25.4-redip-ultisid.md](T25.4-redip-ultisid.md).
Overview: [T25-cleanroom-multisid.md](T25-cleanroom-multisid.md).

**One sentence:** on our bitstream the app calls the two SID engines **reSID8 1 / 2** (Dag Lem's reDIP,
extended to 8 SIDs, T25.4) and offers the filter and model choices that reDIP/reSID has (chip model, cutoff
curve of the 6581 with its two parameters, the 8580 curve, resonance and digi level that follow the chip);
on Gideon's own bitstream the same app still shows **UltiSID** and his menus, exactly as today.

## 0. Rules

- **A core of ours never shows Gideon's SID menus (Alex, 2026-10-14).** "reSID == Dag's curves,
  because that is the only thing they are good for. Gideon's setting == Gideon's SID, which we have
  not even read. So, in our app and our cores, the matching things please" (translated). His curve
  names and values describe his filter; ours describe Dag's. A build of ours that cannot offer Dag's
  curves at run time is therefore not a build we ship: the reference core carries no `TRX_SID`
  switch any more and comes up as reSID. `TRX_SID=redip2` and `TRX_SID=1` stay in the recipe as
  comparison builds for a bench, never for a core in a release. A two-SID build that wants the menus
  takes `sid_multi` with `NS = 2` (same registers, same curves; T25.4's smallest row), not Dag's
  fixed-configuration two-SID top.

- Clean room as T25.4 §0: nothing here read from Gideon's UltiSID/lp_filter/Copper VHDL. The app side
  (`software/u64/u64_config.cc`, its tables) is allowed and is the source of the old names and values.
- **Default sound = Dag's original reDIP** (Alex: "lass den Klang von reSID gleich zum Original"): with all
  reSID8 settings at their defaults the engine is bit exact with the original reDIP for both chip models
  (bench, §7). Every reDIP-derived default is the value that reDIP computes itself.
- **Filter interface open for C64RE's parameters** (Alex 2026-10-07: the filter of C64RE/TRX64 "klingt am
  besten für mich", its exact parametrisation is being asked for and will be forwarded): the interface is
  not tied to fixed presets (Dag's curve choice, base and offset plus Filter On/Off are the whole interface, §3, §6). Saving/loading **named filter profiles**
  (beside the settings, or files on USB/SD) is **M2, TODO T69, not built here**; §6 says what is kept ready.

## 1. What decides "reSID8" or "UltiSID": the bitstream tells

The app must show UltiSID on Gideon's core (his firmware on his bitstream, and the same app image on a
bitstream without our engine). The only authority is the hardware: the TRX IO block
(`designs/c64_basic/trx_io.v`, app `software/io/c64/trx_io.{h,cc}`), the same detection that trxmon, the
cartridge and the video layer already use. CAPS (0x004) and CAPS2 (0x005) have no free bit that older apps
ignore safely (CAPS2 b3 is the "session" bit of an old bitstream, read 0 on the slim core), so:

- new byte **CAPS3 at 0x006** (read only; bitstreams without it read 0, the block answers 0 for every offset it does not
  decode; Gideon's bitstreams read 0 for the whole block):
  - **b0 = RESID8**: the SID is the reDIP engine with the filter control registers of §3.2 (the
    `SID_MULTI` build, T25.4 §3.3; the number of SIDs is a parameter of it and does not matter here).
    A `TRX_SID=redip2` or `TRX_SID=1` build leaves it 0 - those are Dag's fixed-configuration two-SID
    top and the T25.1 engine, neither has runtime filter control, and the app then falls back to the
    UltiSID menus. Per §0 that fallback is for Gideon's bitstreams only: a core of ours is built so
    that the bit is set.
- app: `trx_io_caps3()` (cached like `trx_io_caps()`), `trx_io_resid8()` = ID present and CAPS3 b0. In the
  RISC-V image that serves both boards the call exists only under `U64 == 2` (trx_io.cc is not part of the
  Nios build); elsewhere `resid8` is a constant false.
- the choice is made **once, at construction of the configuration** (`U64Config`): the menu strings and
  the store are picked then; there is no switching at run time.

## 3. The filter model

### 3.1 Items of `reSID8 Configuration` (per engine u = 1, 2)

| Item (new) | Old item (UltiSID) | id | Values | Default |
|---|---|---|---|---|
| `reSID8 u Chip Model` | `UltiSID u Combined Waveforms` | 0x16/0x17 (**kept**) | `6581`, `8580` | `6581` (as before) |
| `reSID8 u Filter` | (none) | **0x9A/0x9B** (new) | `On`, `Off` | `On` |
| `reSID8 u Filter Curve` | `UltiSID u Filter Curve` | **0x90/0x91** (new) | see below | `Chip Model` |
| `reSID8 u Filter Resonance` | `UltiSID u Filter Resonance` | **0x92/0x93** | `Auto`, `Low`, `High` | `Auto` |
| `reSID8 u Digis Level` | `UltiSID u Digis Level` | **0x94/0x95** | `Auto`, `Off`, `Low`, `Medium`, `High` | `Auto` |
| `reSID8 u 6581 Base` | (none) | **0x96/0x97** | integer 0 .. 511 | 245 |
| `reSID8 u 6581 Offset` | (none) | **0x98/0x99** | integer -1024 .. 1023 | -780 |

Chip Model decides what reDIP decides per model: waveform DAC and combined-waveform tables, noise and
waveform-0 fade times, bus value lifetime, mixer DC, envelope DAC (T25.4 §2). Unchanged.

**Filter Curve** (values, in this order; index 0 is the default):

| # | Value | What the hardware does |
|---|---|---|
| 0 | `Chip Model` | reDIP's own filter of the chip model: 6581 = cutoff DAC + offset + tanh curve (`6581 Base`/`6581 Offset` at their reDIP defaults 245 / -780), 8580 = w0 = 5 fc. **Bit exact with the original reDIP.** |
| 1 | `6581 Follin` | own 6581 curve, base 245, offset -780 (= reDIP's default: the curve Dag fits "Follin-style", 240/-785 for the second chip of a pair) |
| 2 | `6581 Galway` | own 6581 curve, base 280, offset -405 |
| 3 | `6581 Average` | base 250, offset 0 |
| 4 | `6581 Strong` | base 260, offset +400 |
| 5 | `6581 Extreme` | base 200, offset +760 |
| 6 | `6581 Custom` | own 6581 curve with the items `6581 Base` / `6581 Offset` |
| 7 | `8580` | own 8580 filter (5 fc), whatever the chip model |

The presets 1-5 are the fits that Dag Lem documents for the 6581 curve formula in `sid_filter.sv`
(`fc_curve(fc, b, d)` = the code's `fc_base` and `fc_offset`). The presets write `6581 Base`/`6581 Offset`
too (`Custom` uses the two items as they stand, a preset does not touch them). The odd SIDs of an engine
(parts B and D of the split) are the second chip of reDIP's pair: hardware adds **-5 to base and offset**
(reDIP's own difference between its two chips, 240/-785 against 245/-780), always, at every setting; the
parts A and C and all of 1-5 above take the value as given. With the defaults the engine is exactly reDIP's pair.
Only these eight values exist (Alex 2026-10-07, "Wir nehmen Dags, und nur diese"); Gideon's seven tables (`8580 Lo`, `8580 Hi`, `6581`, `6581 Alt`, `U2 Low/Mid/High`) are not in the reSID8 menu, and the hardware has no table to load them into.

**Filter Resonance** `Auto` = reDIP's own: 1/Q table of the chip model (6581: reSID 0.16 formula, 8580:
2^((4-res)/8)). `Low`/`High` force the 6581 / 8580 table independent of the chip model (as the UltiSID
menu does).

**Digis Level** `Auto` = reDIP's own: voice DC full for the 6581, none for the 8580 (T25.4 §2: the table of
`0x800*0xff >> {inf, 2, 1, 0}` is `Off, Low, Medium, High`).

**Filter On/Off** (Alex 2026-10-07; per **engine**, like every other reSID8 item and like the hardware's per-UltiSID configuration; a
per-SID switch would need eight items for four parts nobody sets apart): `Off` = reSID's `enable_filter(false)`. Read from
`filter8580new.cc` `set_sum_mix`: with the filter disabled `sum = 0` (nothing enters the filter) and
`mix = 0x0f & voice_mask` (v1, v2, v3 and EXT IN go straight to the mixer; the LP/BP/HP bits `mode & 0x70` and 3 OFF
(`mode & 0x80`) are dropped, so $D415-$D417 and the filter bits of $D418 have no audible effect); the volume
(`mode_vol & 0x0f`) is not part of it and still scales the output. Hardware: `sid_filter` input `bypass` per SID, three gates
(FILT routing nibble at stage 1, mode nibble at stage 4, the 3 OFF test). It is exactly the state "nothing routed, no filter
output, 3 OFF ignored" that the unmodified reDIP computes for FILT = 0 and mode bits = 0. Default `On` (bypass 0) is the original
reDIP. The curve, resonance and digi choices stay as they are while Off.

### 3.2 Hardware interface (registers, app clock)

`trx_io.v` page 0, offsets 0x040 .. 0x04F (little endian; reset values = Auto = the original reDIP; read back is
the value written; the engine takes them through a two-flop synchroniser per bit like the other
`cfg_*`, a changing value is audible at most as one-pass glitch):

| Offset | Name | Bits |
|---|---|---|
| 0x040 / 0x041 | `RS8_FCSEL` engine 1 / 2 | b1:0: 0 Auto (the chip model's own filter), 1 own 6581 curve, 2 own 8580, **3 reserved** (acts as 2; the loadable table that used it is gone, decision 3) |
| 0x042 / 0x043 | `RS8_AUTO` | b0 resonance Auto (1/Q table follows the chip model), b1 digis Auto (voice DC follows the chip model); reset 3 |
| 0x044 / 0x045 | `RS8_BASE` engine 1, 9 bits | reset 245 |
| 0x046 / 0x047 | `RS8_OFFSET` engine 1, 11 bits signed | reset -780 |
| 0x048 .. 0x04B | `RS8_BASE` / `RS8_OFFSET` engine 2 | same |
| 0x04C / 0x04D | `RS8_BYPASS` engine 1 / 2 | b0: 1 = filter Off (bypass); reset 0 |
| 0x006 | `CAPS3` | read only, §1 |

The existing registers stay: WAVES (0x20/0x21 of the C64 IO page = chip model), RES (0x22/0x23), DIGI
(0x27/0x28): they carry `Low`/`High` and the digi level
when Auto is off. The curve table window at `C64_SID_BASE + 0x1000/0x1800` (`sidcv_*`) is **no longer connected to the 8-SID engine** (§3.3). Within the engine: `res_hi[s] = auto ? model[s] : RES`, `digi[s] = auto ? (model ? 0 : 3) : DIGI`.

`sid_filter` (reDIP's file, parameter `LEGACY_FC`): 1 = reDIP's own model only (the bench against the original), **2 = the same
model, per SID selected by `fc_sel`** (the 6581/8580 choice taken from `fc_sel`, Auto: from the chip model, instead of the model).
The default build uses 2. There is no table path any more: `LEGACY_FC = 0`, the `curve_addr` / `curve_data` ports of `sid_filter`,
`sid_core` and `sid_multi`, the 2 x 1024 x 16 RAM and `fc_sel` = 3 are removed. Cost: yosys (§8), see there.

### 3.3 The curve table is gone (Alex 2026-10-07: "Tabelle raus, wir brauchen nur das 'filter off'")

What was removed from the reSID8 hardware: filter source 3, the table RAM (`cv` in `sid_multi`), its read path (`w0_tab`,
the `curve_*` ports) and the connection of the `cv_*` write port from `trx_sid` to `sid_multi`. What stays and why:
the curve write window (`sidcv_*`, `ultimate_sys.vhd` region `r_sidcv` at `0x185000`, `top.v`, `c64_core.v`, `trx_sid` ports `cv_*`)
is **still used by the T25.1 engine** (`TRX_SID=1`, `trx_sid_engine`: its table RAM is that window) and is the target of
the app's UltiSID path on every bitstream without RESID8 (`TRX_SID=1`, `TRX_SID=redip2`: `sid_api` has no table either, so there
the app's writes land in the window and nothing reads them; behaviour unchanged). In the default 8-SID build the window outputs go nowhere
(Vivado removes the unloaded logic). It is therefore **not dead and not removed**; the 8-SID engine just does not look at it.
The only users of the 8-SID engine's table path were the benches `tb_new` / `tb_sym` (rewritten: no table writes) and `build_new.sh`
(the `LEGACY_FC = 0` builds). Nothing else (Gideon-compat paths, `redip2`) used `sid_multi`'s table.
`Custom` curves from C64RE's parametrisation come in as base/offset of the own 6581 curve (Dag's two parameters) and Filter On/Off;
a curve that needs more than that is outside this hardware (open, §9).

## 4. Compatibility

- **Saved settings** are stored by item id (`STORE_PAGE_ID` page, id, value): nothing is looked up by name.
  - Chip Model, Address, Range Split, Vol, Pan: same ids, saved values carry over.
  - Filter Curve, Resonance, Digis use **new ids** (0x90 .. 0x95) because their value lists changed and their
    defaults changed to Auto (the sound of the original reDIP); a value saved under the old ids (0x14, 0x15,
    0x18, 0x19, 0x1E, 0x1F) is **not** migrated to the reSID8 items: no firmware with reSID8 has been in the field,
    and the old default (`8580 Lo` on a 6581 chip) is exactly what the original-sound default replaces. The old ids
    are not registered on a RESID8 bitstream, so the next write of the flash page drops their stored values; a
    Gideon-core boot (or a bitstream without RESID8) uses them as before and starts from their defaults then. An
    app image runs on one machine with one bitstream, so this only matters when the bitstream is swapped.
- **REST / scripts:** the old keys keep working. The config store gets (a) the old category name as alternative
  name (`ConfigStore::set_alt_name`, already used for `C64U Specific Settings`) and (b) a **legacy item name** per
  item (`ConfigItem::set_legacy_name`, new, 2 lines), and the REST handlers (`route_configs.cc`) match a request
  against the item text **or** the legacy name, the category against the name **or** the alt name. The responses
  carry the new names. Example: `PUT /v1/configs/UltiSID Configuration/UltiSID 1 Filter Curve?value=8580` sets
  `reSID8 1 Filter Curve`; `Vol UltiSid 1` in `Audio Mixer` sets `Vol reSID8 1`. `Low`/`High` of resonance
  are in the new list; `Combined Waveforms` values `6581`/`8580` are unchanged; Digis `Off .. High` are in the new list.
  **A legacy value that named a curve table (`8580 Lo`, `8580 Hi`, `6581`, `6581 Alt`, `U2 Low`, `U2 Mid`, `U2 High`; e.g.
  `UltiSID 1 Filter Curve?value=6581`) is not in the reSID8 list any more and gets the normal unknown-value error
  (`Value '6581' is not a valid choice for item reSID8 1 Filter Curve`, the REST handler's own check). The value `8580` is valid but
  now means Dag's own 8580 filter.** A stored index above 7 (a flash page of the interim build with the fifteen values) is
  clamped to 7 (`8580`) by the config store when it loads.
- Gideon's core and bitstreams without RESID8: nothing changes (names, store, ids, behaviour). The new ids are
  not registered there.
- The C64 side (the SID address range split, mirroring, `C64_EMUSID*` registers, the player autoconfig) is unchanged.

## 5. Where the app programs the hardware

`U64Config::U64UltiSids` (class name kept; it is code, not UI): `effectuate_settings()` applies, per engine:

1. `C64_EMUSID{u}_WAVES` = chip model, as today;
2. the filter selection (§3.1) as `RS8_FCSEL`, `RS8_BASE`, `RS8_OFFSET` (and `RS8_BYPASS` from Filter On/Off); no table is written;
3. `RS8_AUTO` b0 / b1 from Resonance and Digis, and `C64_EMUSID{u}_RES` / `_DIGI` for the explicit values.

All of it is one pure function `resid8_plan(filter, res, digi, custom_base, custom_offset)` in
`software/u64/resid8_filter.h` (source, base, offset, the Auto bits, the explicit
RES/DIGI register values, bypass) and one writer `resid8_set_filter(u, plan)`; the menu items go through
them. This is the seam for T69 (§6) and what the host test runs (§7).

## 10. Evaluation: table-only hardware (all curves computed by the app), 2026-10-07

*Historical: Alex chose the other way the same day (decision 9, then decision 3: no table at all). Numbers refer to the table build of that time.*

Question (Alex): drop reDIP's own cutoff model from the hardware, keep only the table; the app computes every curve.

1. **Is w0 a pure function of FC?** Yes. `sid_filter.sv`: w0 is taken at stage 2/3 from `fc_8580 = {fc_hi, fc_lo[2:0]}` of the registers,
   8580: `5 * fc`; 6581: `fc_x = clamp(dac11(fc) - (offset + 0x600), +-1023)`, `w0 = base[8:3] + Y0 + sign(fc_x) * tanh_tab[|fc_x|]` with
   `dac11` a sum of 11 constant bit values (`dac_6581_cutoff.mem`) and `tanh_tab[i] = int(1.048576/8*2*pi*12000*tanh(i/350) + 0.5)`. No
   signal, state, resonance or time. Per-chip constants: model, base, offset, and for the odd SIDs -5 on base and offset. reSID's own
   code agrees in kind (`filter.cc`/`filter8580new.cc`: `set_w0` from `f0_dac[fc]`, a table of fc); reDIP's formula is its own
   approximation of it, so the table the app computes is reDIP's, not reSID's.
2. **Exactness.** 1024 entries (`FC >> 1`, value `<< 1`) are not exact: 1,543 of 2,048 values of the 6581 curve differ (max error 58 =
   1.5 %, 26 cents) and 1,024 of the 8580 (error 5 in w0 = 5 fc), because the odd FC changes the DAC output and w0 is odd. **Exact needs
   2048 entries x 15 bit per table** (w0 <= 19,739). Verified: a 2048 x 15 bit table computed by a short Python model of the formula
   (scratch, not committed) loaded into a table-only `sid_multi` (scratch copy: 12-bit curve address, `w0 = table[14:0]`) is **bit exact** with the
   original reDIP, 4 model pairs x 300 k cycles x 8 SIDs (2.4 M sample compares each, 0 errors), with the reference's second chip set to
   the same constants (see 4).
3. **BRAM.** 2 engines x 2048 x 15 bit = 61 Kbit = 2 RAMB36 (today 1 RAMB36 for 2 x 1024 x 16). yosys: 4.0 -> **5.0 tiles** table-only, against
   **4.5** for `LEGACY_FC = 2` (tanh table 0.5). LUT: **1,467** (scratch, no readmemh init) against 1,509 table-only today and **1,855**
   for `LEGACY_FC = 2`: -388 LUT, +0.5 tile against what is built now. LUT-RAM cannot hold it (61 Kbit = about 3,800 LUT). Writing 8 KB of curves
   needs the table window (`0x185000`, 4 KB, `ultimate_sys.vhd` region `r_sidcv`, `sidcv_addr` 12 bit) widened to 13 bit / 8 KB
   (0x186000-0x187FFF looks free, to be checked in the map) and the entry format changed to "w0 itself" (15 bit) on our bitstream.
4. **The odd-SID -5 rule does not fit a table per engine.** The four parts of an engine share the table; reDIP's second chip (240/-785) differs from
   the first (245/-780) by up to 142 (2.85 %, 49 cents) of w0. Bit exactness for all eight SIDs needs one table per parity (4 tables,
   4 RAMB36, +3 tiles over today) or the rule is dropped (all SIDs of an engine get the curve of the first chip: not the original sound
   for the odd SIDs, 49 cents at worst). Alex confirmed the rule (decision 6); table-only therefore needs +3 tiles or a deliberate deviation.
5. **App cost.** 2048 entries per curve: 11 adds for the DAC, one lookup in a 1024 x 16 bit tanh constant table (2 KB rodata, generated by
   Python's `math.tanh`, the libm of the Verilator bench; `tanh()` on the target risks a rounding difference at the +0.5), a few
   hundred instructions: about 1-2 ms per curve at 100 MHz (estimate, not measured on the target), 4 KB of byte writes over the IO bus (about 0.4 ms).
   Code about 1 KB, rodata 2 KB plus the 11 DAC constants. The seven UltiSID tables stay as data. A change of curve rewrites the table
   while the engine runs (a transient of w0, as with the UltiSID tables today).
6. **Recommendation, decided (Alex 2026-10-07, "Formel in Hardware lassen").** Keep `LEGACY_FC = 2` (decision 9 as built) unless BRAM is scarcer than LUT: table-only saves 388 LUT (yosys) but costs
   +0.5 tile with the -5 rule dropped, +3.5 tiles with it kept, plus a changed table window and format. At 69/75 tiles the +0.5 is affordable, the +3.5 is
   not. If the -5 rule may go (a deliberate deviation from the original reDIP for the odd SIDs, 49 cents at worst), table-only is
   the cleaner interface and makes profiles trivial (T69); with the rule it is not worth it. The Filter On/Off switch (§3.1) is independent of this choice.
