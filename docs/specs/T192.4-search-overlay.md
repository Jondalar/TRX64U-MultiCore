## §1 The problem

Alex wants one gesture that reaches any setting, page or action in both apps without walking menus. Reading of 2026-11-07
(epic §1 P4, analyses of the same day; file:line from them, not re-measured here):

- **What exists (core app):** `MenuTree` (`menutree.h:84-91`: areas -> tabs -> entries, plus contributed nodes with op/state/attr/
  group/owner), built every start by `menu_build`, with a dump (`menu_dump`, `menutree.h:112`); `Setting.key` (stable) + `label` +
  `group` + `show_state` (`desc.h:77-100`); `OpRegistry::op_at/nops` (`ops.h:177-180`); `goto_spec("Fn/tab")`; `LineEdit`
  (`app/edit/lineedit.h`).
- **What exists (host app):** nothing indexable. Pages, settings and actions are code in `hostui.cc` (`on_key` `6162`, footers as
  literals `1114-1146`); the index source appears only with the declarative host menu (T192.2, D12).
- **What is missing:** a flat index over these sources; visibility and a "disabled because X" reason; ranking; a way to select a row
  by id (`sel_` is private); activation by id through the confirm/dirty rules (running an op directly bypasses `ui.confirm`, which
  lives on the `MenuNode` and runs in `begin_confirm`); an overlay that owns the keys. Most ops have no label (only ops bound to a
  node/task have one); `settings.noop` settings cannot be told apart.
- **Why it matters:** letters are context functions (#34, R5, C1), so type-to-find cannot be a mode; it needs a chord and an overlay
  that cannot leak a key into the page below (D3). A search that runs actions around the confirm rules would be a hole next to R24.

**Parts (MECE):**
- **P1 Index** — what is searchable and from where, per app; built once on the shared core; no files (D8).
- **P2 Visibility** — which entries appear, which are shown disabled with a reason, which never appear.
- **P3 Query and ranking** — matching, order, result limits, empty and no-hit states, cost per keystroke.
- **P4 Open, own, close** — the chord, the overlay owning every key, where focus returns.
- **P5 Activation** — what RETURN does per type, through the same confirm/dirty/lock rules as the page; by id.
- **P6 Form** — the 960x540 graphic layout and the text-UI form of the same overlay.

## §3 Decision

Epic decisions that apply (quoted):

- **D3 (Alex, 2026-11-07, translated: "A yes, and when the search is in the overlay over the screen, the keys go into the search -
  NEVER into the UI below"):** only the chord C= SPACE opens the search; letters stay context functions everywhere, no type-to-find.
  While the search overlay is open it owns every key; nothing reaches the page underneath.
- **D8 (Alex, 2026-11-07: "C"; options A current folder, B all media with an index, C no files):** the search indexes settings, pages
  and actions only; no files.
- **D14 (Alex, 2026-11-07: "A"):** one shared core framework for host app and core app; the text UI, the search, the terminal
  client and the bundles are built once on it and serve both apps.
- Also bound by D4/D11 (a token holder activating by id gets the same question and may answer it) and R24 (confirmations gate every
  route).

### Design

**Where it lives.** The search is a framework feature (T192.1), not view code and not app code. It consists of (1) an `IndexSource`
interface each app implements, (2) the index builder and matcher in the shared core, (3) overlay state in the framework snapshot
(open/closed, query, results, focus, `n of m`), (4) intents `search.open`, `search.query(text)`, `search.move`, `search.activate`,
`search.close`, (5) a view per UI that only draws that state (LVGL overlay now; character grid in T192.5). A view keeps no query of its
own (T192.4-S23).

**Index entry.** `{id, type, label, path, value?, state: ok|disabled, reason?, target}`. `id` is the framework's stable item id
(T192.1; the same id the page rows carry and the intent `activate` takes). `type` is `SET`, `PG` or `ACT` (no `FILE`, D8). `path` is
the breadcrumb ("Settings > Video"). `value` is the current value for settings (read at open, display only). `target` is what the app
needs to jump or run; the search never interprets it.

**Sources, core app (built by T192.3's adapter, read at overlay open):**
- Pages: every `MenuTree` area and tab (`id`, `name`) that is not hidden (`tab_is_hidden`); type PG.
- Settings: every `Setting` with `key`, `label`, `group` that is visible (`show_state`), type SET, value from `values[]`
  (`setting_label`). Matching uses the label the user sees, i.e. after `rename`/`hide` of `menu.toml`; the stable `key` is a second
  match field, never shown.
- Actions: every `OpRegistry` op that is bound to a node/task or carries a label (type ACT) plus contributed nodes of kind op. An op
  with no label and no node is not searchable: it is not given an invented name (see §6 Q2 for how labels get added). A setting that is
  `noop` is not listed as an action.
- Path and focus come from the tree position; `target` is the item id for select-by-id.

**Sources, host app:** only the declarative menu description of T192.2 (pages F1/F3/F5/F7/F8 and their rows, settings, actions such as
core start of an entry, update, restore, convert, format, network join, picture change). No second list, no search-specific table: an
entry that is on a screen and not in the description is not findable (T192.4-S7), which also makes the description the single place to
fix. Dynamic entries (boot menu entries, cores found on SD) are boot-menu content, i.e. files/media in the sense of D8, and are not
indexed; their pages are.

**Visibility and disabled reasons.** Hidden = not indexed (same predicate the menu uses; the index calls the app's own visibility
function, it does not copy the rules). Visible but unusable now = indexed with `state: disabled` and the reason string the page shows
(`Item::dim`/`hint()` in the core app; the producing module's refuse text in the host, R23). The reason is read when the overlay
opens and refreshed on the event stream while it is open. RETURN on a disabled entry shows the reason and does nothing.

**Query and ranking.** Case-insensitive; tokens split on space, all tokens must match (AND). Per entry the best of: label prefix (rank 0),
word prefix in label or path (1), substring of label (2), match of the stable key only (3, ties shown after label hits). Ties: entries
under the page the chord was pressed on first, then area order, then label. At most 8 rows shown plus a count; cursor up/down moves
through all hits and scrolls. The index is built once at open (no I/O per keystroke); a query is a pass over the in-RAM entries; one
redraw per key. The size budget for the index (entries x bytes) and the open-time budget are set at build from a measurement on the
A1200 core app (T192.4-S16); stack use is measured against the 8x-minimal UI stack (epic risks 13, 19) before the shape is fixed.

**Empty and no-hit states.** Empty query: "type to search" and the 5 most recent activations of this session (RAM only, lost at restart;
persisting them is §6 Q3). No hit: "No match. Try fewer letters." plus the page names (areas) as fallback.

**Open, own, close (D3).** The chord C= SPACE is a key-map entry "key -> intent search.open" (T192.6 will make the key map a bundle;
until then it is a fixed entry of the default TRX64 set, D2). It is the only entry; no letter, no `/`. Chord detection happens in the
same layer that produces intents from keys, on the host side where the matrix is read (the host already masks key combos in hardware,
`hotkeys.h:1-4`), and for USB keyboards on the key the host maps to C=. When the overlay is open the router sends every key to the
overlay and none to the page: ownership is a router state, not a check in the overlay (a new page can never forget it). Text typed
goes into the query (letters only reach the overlay because it is open). Close: RUN/STOP or left arrow (the cursor-left key of the
C64 keyboard; the overlay has no other use for it) returns to the exact focus (page, tab, row, scroll); an activation that jumps does
not return. The chord is not taken while a modal owns the keys (app dialog, picture confirm, monitor, locked job); inside a text-entry
field it is suspended, as the concept says (§6 Q1 asks whether Alex wants an exception). Opening is only possible when the menu is
open; it does not hijack a running core (R3 stays separate).

**Activation by id, same gates.** `search.activate(id)` is an intent to the app's controller, not an op call. Per type:
- SET: select the row by id (new controller capability, replaces the private `sel_`/`goto_spec` string walk), open its group if
  collapsed, focus without editing. Switch settings may be toggled with RIGHT in place; that goes through the setting's normal change
  path, so the live-vs-at-reset marking and the held-until-Save rule apply (T192.4-S19).
- PG: go to the page by id.
- ACT: run through the node's own path, i.e. `begin_confirm` / `ui.confirm` when the node has a confirm, the write-back question, the
  flash-lock refusal, the armed-delete rule, the update/format ask pages (host, as jobs in state `asking`). The confirm appears on top
  of the result list; "no" returns to the list; "yes" runs and closes. A non-confirming action runs at once and the overlay closes.
  Because the intent is the same one the page's key produces, the search has no confirm logic of its own; there is nothing in the
  search that can be wrong about it, and a remote token holder gets the same question (D4, D11).
- Any `ACT` whose job is long keeps the normal job/progress page; the overlay is closed by then.

**Form.** Graphic (LVGL, 960x540 canvas or the mode's size below 960 wide; kept at one fixed size, D10): the page behind is dimmed,
one centred panel, query line "FIND > text", up to 8 rows `[tag] label  path  value/marker`, the focus row highlighted, a footer
"RET open  CRSR move  <- close  n of m". Disabled rows are dimmed with the reason in the value column; rows that confirm carry the
marker "confirms". Pad: stick/D-pad and A/B; typing needs an on-screen entry (§6 Q4). Text UI (T192.5): the same state drawn as a
character grid, tags `[SET]`, `[PG ]`, `[ACT]`, query line and footer on the cells of the grid, so the overlay is identical over
`ws://`.

**Files touched at build (names, to be fixed in T192.1/.2/.3):** shared `search` module in the T192.1 framework (index, matcher,
overlay state, intents); core-app adapter `IndexSource` in T192.3's controller layer; host adapter reading the T192.2 menu
description; overlay widget in `app/view/` (draws framework state only; no LVGL types in the API); render bench and apptests under
`tests/`.

**Weighed and lost.** Type-to-find on letters (refused by D3, C1). Indexing files (D8). An op call straight from the search
(bypasses `ui.confirm`; R24). A search index built from a second list kept beside the menu (drifts; T192.4-S7). Guessing labels for
ops that have none (invented names).

## §4 Out

- Files, folders, recents of files, library items, favourites paths in the search (D8). A "second chord for files" of the UX draft is
  not built.
- Type-to-find on letters or any other entry gesture than C= SPACE (D3); `/` as a key.
- Searching inside a running core or while the menu is closed (R3 stays separate).
- Persisted recents across restarts and fuzzy/typo matching and aliases beyond `rename` labels and the stable key (unless decided in
  §6).
- Searching the contents of values (a setting's value list) or the help text.
- Searching `.u2a` application screens inside their own session (an app is a second `MenuCtl`; its tab is a page, its rows are not
  indexed in this child).
- Bundles and key-map editing (T192.6); the text UI itself (T192.5); the framework (T192.1).
- Any gateware change.

## §6 Open questions

One at a time, most blocking first.

1. **Chord inside a text-entry field.** The concept suspends the search while a text field has focus (file name, Wi-Fi password).
   Keep it so, or allow C= SPACE to open the search even there (the field's draft is kept)? Proposed: keep suspended.
2. **Labels for ops that have none.** Most ops have no label today, so they would not be searchable. Add a label (and optional
   search words) per op in the descriptor/`menu.toml` and the host description, or list only ops that sit on a page? Proposed: only
   what sits on a page now; labels are added where a tester asks.
3. **Recents** (the empty-query list): RAM only per session, or kept in `host.cfg` / the core's settings across restarts?
4. **Pad (no keyboard).** The UX draft proposes Select long-press as the entry and an on-screen letter ring for typing. In this child
   or deferred to the pad wizard?
5. **USB keyboard key for C=.** Which physical key stands for C= on a PC keyboard in the host's key map (the one used for C=+F3/F5)?
   Taken over unchanged; confirm only if the existing map is not authoritative.
   **Answered from the code (coordinator, 2026-11-07):** The Windows/GUI key, left and right, stands for C=. In the USB keyboard driver the modifier byte is mapped through `modifier_locations[] = { 0x72, 0x00, 0x00, 0x75, 0x72, 0x00, 0x00, 0x75 }` (`host-app/software/io/usb/keyboard_usb.cc:409`), indexed by the HID modifier bit (bit 3 = left GUI, bit 7 = right GUI, comment at 401-404): `0x75` is row 7, column 5 = matrix key 61 = `K_CBM` (`coreapp/src/hotkeys.cc:24`); `0x72` (left and right Ctrl) is row 7, column 2 = CTRL; Shift is handled separately (456-459), Alt maps to nothing. No HID usage maps to 61 in `keymap_usb2matrix` (`keyboard_usb.cc:111-123`), so `usb_usage_matrix_index` (218) and `hk_usb_set_usage_map` (`hotkeys.cc:222`, set in `run.cc:484`) can never return C=; the C= chord is built from the modifier bits and reaches the hotkey code through the matrix filter (`keyboard_usb_matrix_filter`, `keyboard_usb.cc:236-237`, `run.cc:483`). The existing map is authoritative: C= = GUI/Windows/Cmd.
