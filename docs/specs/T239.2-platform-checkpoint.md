## §1 The problem

- **Who:** a developer outside this repository who wants a DFX (partial) core for the C64U / U64 Elite II. Also our CI, which today is the only place such a core can be built.
- **What they try to do:** write `layer2_<id>.v`, build it into the host's partition with Vivado 2024.1, pack a `.cor`, put it on the board.
- **What happens today:** it cannot be done without this repository and its private builder cache.
  - A DFX core is built by `host/core.tcl`. It needs `TRX_HOST_DCP`, `TRX_CORE`, `TRX_L2_KEY` (`host/core.tcl:1-12`, `:19-22`). It stops with an error when the checkpoint file does not exist (`:23`).
  - `TRX_HOST_DCP` is `static_routed.dcp` of the host entry in the content-keyed cache (`ci/bitstream_layers.sh:102`, `:139`). The cache root is `/cache/multicore` on the builder. It is not in git and not in a release. Its size was not measured in this session: the cache is not reachable from this machine. The 2026-10-12 measurement in T87 (§1, 2.1 GB cache total) predates the layered flow and names no size for it.
  - The core's recipe is `cores/<id>/core_sources.tcl`, sourced by `host/core.tcl:33`. It must set `l2_dcp` (`host/core.tcl:11`; template `cores/null/core_sources.tcl`: reads the Verilog, `synth_design -mode out_of_context`, `write_checkpoint`).
  - `host/core.tcl` sources two more files of this tree: `../tools/vivado_lib.tcl` (`:25`, in section `shared:` of `host/layers.txt`) and `check/trx_constraints.tcl` (`:26`, `host/check` is in `ignore:` of `host/layers.txt`). An outside build needs both next to the checkpoint.
  - `host/core.tcl:49-57` hard-codes a T29 multicycle path on the net `l2/c64/c64/cpu_rdy`. It applies only when that net exists, so it is inert for a core without a `c64` cell (the script prints a warning, `:60`).
  - The core stage ends with `pr_verify -initial $host_dcp -additional core_routed.dcp` (`host/core.tcl`, after route) and writes `<core>_partial.bit` only when WNS is not negative.
  - The host key is the first 8 hex of `host_key()` (`ci/lib.sh:271`), a hash of the host files, the reference core's key, the shared files, part, Vivado version and build options. It is written into the full bitstream's AXSS register by `trx_axss` (`tools/vivado_lib.tcl:174`, from `TRX_HOST_KEY8`). An outside builder cannot recompute the hash without this tree. It can read the key back from a full image of the same host with `tools/cor_pack.py hostkey` (`ci/bitstream_layers.sh:125`, `host_axss`). `ci/bitstream_layers.sh:136-137` says the property is in the checkpoint already.
  - The `.cor` carries `host_key` in its manifest (`tools/cor_pack.py:410-431`). The host app reads its own key from the BUILD register (`host-app/software/hostapp/hostapp.cc:34-41`, `:84`) and refuses another one: `cor.cc:285-287` returns `COR_ERR_HOST`. The contract is checked first (`cor.cc:281`, `COR_HOST_CONTRACT`, `contract/VERSION` = 2, 247 ports in `contract/layer2_ports.txt`).
  - `contract/host_pin.txt` pins the git object id of every file of the host, the shared files and the reference core; `tools/host_pin.sh --check` runs in lint (T94 D13). So a host change is visible and approved, and `--update` goes into the same commit.
  - The row of a core for another host shows: "Routed against host %08x; this host is %08x. Cannot be added." as a warning cell (`host_core_rows.cc:728-730`), and the row state text "other host" (`:121`). Whether the row is red in the list was not checked.
  - The packer and the schema are in this tree: `tools/cor_pack.py` (`pack`, `hostkey`, `check`), `tools/core_toml.py` (`SCHEMA`: `id`, `name`, `version`, `contract`, `app`, `order`, `experimental`, `sources`, ...). A `.cor` also carries an app image; `app` is `"blueprint"`, `"ultimate"` or `"none"`. The generic app is T239 B.
- **Licence facts of the checkpoint (reported, not decided).** `static_routed.dcp` is the routed host with the reference core `c64ref` in layer 2 (`ci/bitstream_layers.sh:5`, `reference_core`). Its content, by `PROVENANCE.md`:
  - our host gateware, GPL-3.0-or-later (`PROVENANCE.md` §3);
  - Gideon's VHDL from `vendor/gideon` (rvlite, buses, UART, SPI, Ethernet MAC, USB host, UCI, 1541 drive), GPL-3 (§3, §5, `LICENSING.md`);
  - the c64ref core: icepi-zero C64 core (GPL-3.0-or-later), reDIP SID/CIA (CERN-OHL-S-2.0), VIC-II Kawari (GPL-3.0), usb_hid_host (Apache-2.0), HDMI encoder (MIT or Apache-2.0) (`LICENSING.md`);
  - the boot ROM, derived from a GPL-3 loader (`PROVENANCE.md` §3);
  - AMD/Xilinx: the GT wizard IP generated at build time, and primitives (`PROVENANCE.md` §9: "AMD/Xilinx IP terms; no licence text in the repo"). A routed checkpoint holds the generated IP netlist, which the repository never stores (`PROVENANCE.md` §12: "no generated AMD/Xilinx source is in the repository").
  - `PROVENANCE.md` §12 says the `.cfw` (the host with the null core) is already published as a built bitstream with the source. Whether a `.dcp` falls under the same statement, and what AMD's terms say about a netlist checkpoint, is not answered in any document read. ADR 0029 covers only our own code (GPL-3.0-or-later). The Vivado image itself is not published (`PROVENANCE.md` §12).
- **Why it matters:** T239 D2 makes the host gateware a platform. Without a published checkpoint nobody outside can build a DFX core, and D4 (the maintainer builds his core again for a new platform) cannot be carried out by the maintainer.

**Parts (MECE):**

- **P1 The checkpoint as a release artifact.** What is published (`static_routed.dcp`, its SHA-256, the host key, the Vivado version, the part), where, and how CI produces it from the host cache entry.
- **P2 The SDK content for an outside DFX build.** `host/core.tcl`, `tools/vivado_lib.tcl`, `host/check/trx_constraints.tcl`, `contract/`, a template core, the packer and the TOML schema, and how they are versioned together with the checkpoint.
- **P3 The template core.** A minimal `layer2_<id>.v` and `core_sources.tcl` that builds out of the box against the published checkpoint.
- **P4 Outside build to board.** An outside container with Vivado 2024.1 builds a partial from P1-P3, packs a `.cor`, and the host of that release accepts and starts it.
- **P5 Refusal of a core for another platform.** A `.cor` built against an older checkpoint is refused by key and shown (D3).
- **P6 Platform identity and versioning.** What makes a new host key, what does not, and how the SemVer of the host gateware names the platform release.
- **P7 Licence position of the published checkpoint.** The facts, and the decision that is Alex's.

## §3 Decision

By reference to the epic. Nothing is decided here beyond it.

- **T239 D2:** "the SDK ships, per release of the host gateware, exactly that checkpoint ... with `host/core.tcl`, the contract (`contract/`) and a `core_sources.tcl` template; Vivado 2024.1 as the checkpoint's." A partial fits one host build only; "the host gateware changes rarely, and every change means all DFX cores are built again"; the registry records the host key per DFX core.
- **T239 D3:** a DFX core that does not fit the installed host stays visible, marked red.
- **T239 D4:** the maintainer of a core builds it again for a new platform; no central rebuild of other people's cores.
- **T239 D11:** GitHub is the development home; the release and its assets live there.
- **T239 D13:** order A, D, B, C; this spec is D.
- **T221 D5, D7, D12 (existing):** the host gateware has its own SemVer in `contract/version.toml`, outside `host/` so a bump does not move the host key; the contract folds into the MAJOR.

- **T239.2 D1 (Alex, 2026-11-19): the checkpoint is published as it is, AMD's GT wizard netlist included, under the take-down
  model of 2026-10-24** ("If someone has a problem and gets in touch, we react"); whoever uses it needs Vivado and AMD's licence
  anyway. Asked against "replace the GT wizard by our own GTPE2 instance first" and "clear the licence first"; Alex: "1 ja".
  The fallback, should AMD object: our own wrapper around the primitives `GTPE2_COMMON` and `GTPE2_CHANNEL` with the wizard's
  attribute values (they are unisim primitives, no IP licence). An open-source reference exists: LiteICLink (EnjoyDigital,
  BSD-2-Clause, `liteiclink/serdes/gtp_7series.py` and `gtp_7series_init.py`, read 2026-11-19). It would change the static
  design, so it would start a new platform.

- **T239.2 D2 (Alex, 2026-11-19): the checkpoint gets its own release tag `platform-<SemVer>`.** A platform changes far more rarely
  than the host app, so many host releases share one checkpoint and an outside builder sees at a glance which platform he builds
  against. Asked against "a plain asset of the normal host release"; Alex: "2".

- **T239.2 D3 (Alex, 2026-11-19): the host key comes from `platform.toml` and is checked three times.** (1) The SDK script compares
  the SHA-256 of the downloaded `static_routed.dcp` with `platform.toml`. (2) The platform build sets the key before it writes the
  checkpoint (today `host/build.tcl` writes `routed.dcp` at line 393 before `trx_axss` at 394, so the checkpoint carries only the
  TIMESTAMP of `host/pins.xdc`); `host/core.tcl` reads the key from the opened checkpoint (`get_property
  BITSTREAM.CONFIG.USR_ACCESS`) instead of the environment (`TRX_HOST_KEY8`) and stops on a difference to `platform.toml`.
  (3) `cor_pack.py hostkey` reads the AXSS word of the built `<core>_full.bit` and compares it with `platform.toml` before it
  writes the manifest's `host_key`. On the board the host refuses another key (`cor.cc:285`) and shows the core red (T239 D3).
  Asked with this design; Alex: "Ja". Swapping the two lines changes a host file and so the host key: the first platform
  release starts a new platform anyway.

- **T239.2 D4 (Alex, 2026-11-19): the template core gets its own folder `sdk/template-core/`.** A minimal `layer2_template.v` that
  serves the contract's ports and shows a test picture, its `core_sources.tcl` and `core.toml`, no third-party sources. Not
  `cores/null/`: the null core is the flash filler, part of every host update, and takes the TRNG (T239 D7), so it is part of the
  platform. Not `cores/vc20/`: it needs `gideon_vhdl.tcl` and vendor trees. Alex: "4:2".
- **T239.2 D5 (Alex, 2026-11-19): the checkpoint is a separate download.** `static_routed.dcp` and `platform.toml` are assets of the
  release `platform-<SemVer>`; the SDK (template, scripts, packer) has its own version, and its script fetches the checkpoint of the
  chosen platform with the SHA-256 check of D3. One SDK serves several platforms. Alex: "5:2". The checkpoint's size is still to be
  measured on the builder (GitHub takes up to 2 GB per asset).
