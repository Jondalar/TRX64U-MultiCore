# T192.5 — The text UI of both apps runs locally on the HDMI picture and remotely over ws://, from one cell model

**Status:** PROPOSED (2026-11-07).
**Repo:** TRX64U-MultiCore — view layer on the T192.1 framework (`app/view/` and the shared framework), per-app adapters in the host app
(`host-app/software/hostapp/`) and the core app (`coreapp/`); the terminal client is NOT here (T192 D16).
**Number:** T192.5 (child of epic T192, `TODO.md` row T192.5).
**Origin:** asked by Alex, 2026-11-07 (child of T192; D6, D16, D17 of the epic).
**Depends on:** T192.1 (state snapshot, intents with stable ids, event stream, token, WebSocket); per app on T192.2 (host) and T192.3 (core

**Milestone:** M3.

## §1 The problem

Alex wants a real text UI instead of the graphical one (epic §1 question 5), usable on the board without any other machine and from a
terminal on another machine. Epic D6: both in the first build; the remote path is `ws://` with the D4 token, no telnet, no SSH. Epic D17:
start from the TRX64-Ultimate monitor's cell model and draw it with a software glyph blitter into the pixel layer, no LVGL, no gateware.

What exists today (read from the code, not from comments):
- Cell model: `ui_screen_t` in TRX64-Ultimate `apps/trxmon/src/ui.h`: `char row[50][81]`, ONE attribute per row (`uint8_t attr[50]`, nine values
  `UA_NORMAL..UA_HINT`), `cols/rows`, `cursor_x/cursor_y`, `blank_rows`; 80x40 wide, 40x23 narrow. `ui_render(const ui_t*, ui_screen_t*)`
  builds the rows, `ui_key(ui_t*, int)` takes one key, `ui_map_key` maps firmware key codes to `UI_K_*`. The command line (`cmd[120]`,
  `cpos`, insert/delete, left/right/home/end, completion key) and its history (`chist[32]`, `ci`) are in `ui_t`/`ui.c` (900 lines). There
  is no drawing in it: "No drawing and no firmware calls here" (header); there `main.c` puts the rows on Gideon's character overlay, which
  the MultiCore host does not have (epic D17).
- The core app already draws such a grid, with LVGL: `build_terminal` (`coreapp/src/screens.cc:~790`) makes one `lv_label` per row (UNSCII
  8x8, `letter_space 4`), cell 12x13 px, 80 columns, rows up to `MON_ROWS_MAX 50`, grid origin y=10, so 40 rows end at y=530 of 540; row
  colour from `mon_color(attr)` (the C64 palette); a reversed box is the cursor. The layout `terminal` (80x40) and the app widget
  (`MON_COLS 80`, `screens.cc:~1337`) are the same grid. It redraws changed rows through `lv_label_set_text`.
- Menu content is plain text already: `MenuCtl::row(i, left, right, sub)`, `Item.title/sub/chip/value`, `BrowseRow`, `footer_legend`,
  `view_line` (epic §1, `coreapp.md` §6); colours are tone integers, not RGB. `/v1/ui/state` carries nearly all a text client needs
  (items, rows, dialog, footer, status, top bar) but is a pull snapshot, has no input route (`rpccontract.cc:26-28,128`) and no events.
- Host app: no cell view, no remote UI; its screens are LVGL code in `hostui.cc` until T192.2.
- Client candidate (separate project, D16): `TRX64/crates/trx64-cli/src/tui.rs` (2349 lines, ratatui 0.29 + crossterm 0.28, a `Cockpit` struct
  and `run_loop`) on an in-process `Engine` (`engine.rs`, 718 lines: `rpc`, `exec_line`, `key_down/up`, `snapshot`). It would swap `Engine`
  for a WS client; the cockpit panels are its own and would be replaced by one grid widget.

Why it matters: epic R7 (text UI first class, locally), R1/R6 (remote use without a graphical machine), and the proof that "a second UI" is
an official concept (epic Q4): a UI that only draws state and sends intents.

Estimate from the analyses (not measured): ~1000-1500 lines C++ for a cell view of the core app's items, browser, sheet, dialog, footer and
viewer; the real cost is in text entry and keys (`MenuCtl::key`, 271 lines of raw `KEY_*`), not in drawing.

**Parts (MECE):**
- **P1 Cell model:** one grid type, taken from `ui_screen_t`, that both apps fill from the T192.1 state and that the local blitter and the
  `ws://` stream both consume. Only the grid and the blitter are reused; the `ui.c` command line and history are not (epic D19c).
- **P2 Local drawing:** software glyph blitter into the pixel layer, dirty cells only, 80x40 at 960x540, font, cursor, colours; timed against
  LVGL for the same page (D17).
- **P3 Local input:** the board keyboard (USB and the C64 matrix) to the text UI, as intents on the T192.1 contract; unknown keys do nothing.
- **P4 Remote stream:** the same grid and the keys back over `ws://` with the D4 token; the wire protocol the separate client has to speak
  (D16), versioned by T192.1.
- **P5 Fallbacks:** text pages for screens that are graphic today (timeline, memory map, medium panel, live box, pad wizard, picture list),
  and "[picture not available in text mode]" where a picture cannot be text.
- **P6 Selection and cost:** how the text UI is switched on (text mode of the interface choice, D5/D7/D10), coexistence with the LVGL view,
  and the RAM, DDR2 and time it costs (cuts across P2-P4).

## §3 Decision

Epic decisions that apply, quoted:
- **D6 (Alex, 2026-11-07, translated: "A, that is then simply WS://"):** the text UI comes in the first build both locally (the menu as a
  character grid on the HDMI picture, board keyboard) and remotely in a terminal on another machine; the remote path is a WebSocket
  (`ws://`, token per D4) carrying the same text screen and the keys, no telnet, no SSH.
- **D17 (Alex, 2026-11-07: "yes"):** T192.5 starts from the TRX64-Ultimate monitor: its cell model `ui_screen_t`, `ui_render()`, the command
  line with editing and history (`ui.c`) [command line and history dropped by epic D19c]; the grid is drawn by a glyph blitter into the pixel layer and sent over ws://. Blitter (Alex,
  translated: "LVGL is really slow .. but yes, let us start like that"): software on the RISC-V, writing glyphs straight into the pixel
  layer without LVGL (dirty cells only), no gateware (the host's gateware is immutable). Its draw time is measured against LVGL's for the same
  page; if it is still too slow, gateware is a new question.
- **D16 (Alex, 2026-11-07, translated):** the terminal client for macOS/Linux is a separate project beside this repository; it binds to the
  board only through the T192.1 contract (ws://, token). This spec therefore defines the protocol and a test client, not the product client.
- **D14 (Alex, 2026-11-07: "A"):** one shared core for both apps; the text UI is built once on it and serves both apps.
- Also bound here: D4 (token), D11 (remote answers confirmations), D5/D7/D10 (text mode is part of the interface choice; no density choice).

### Design

Proposals marked (proposal) are not yet decided with Alex; they are listed in §6 as far as they need him.

**D1 Cell model (P1).** One `cell_grid` type in the shared framework, derived from `ui_screen_t`: up to 80x50 cells, `cols/rows`, cursor.
Difference from the template: the template has ONE attribute per row (`attr[50]`), which cannot mark a focus row inside a list with a tag
column or an inverse segment. The grid therefore carries one attribute byte per CELL (colour index of the nine tones plus bit for inverse and
bit for bold/dim). Memory: 80x50x2 = 8 KB per grid; a second copy for dirty tracking = 16 KB (to be measured, S20). The command line and
history of `ui_t` (`cmd`, `cpos`, `chist[32]`, completion hook) are not ported (epic D19c); the monitor's own verbs and
`status_text`/`regs_rows` stay in the monitor, they are not part of the grid code.
The grid is not stored by hand: a `view_text` renders the T192.1 state snapshot (items with stable ids, rows, dialog, footer, status, top
bar) into the grid with page layouts per screen kind: list/sheet, browser, dialog/confirm, viewer, footer legend, progress bar, job page.
Colours are tone integers mapped to the nine attribute tones; colour is only redundancy (ux.md §5): focus is inverse video, state is a text
tag, nothing depends on colour.

**D2 Local blitter (P2).** `textblit.c` in the view layer: a RAM copy of the previous grid; per frame it compares cell by cell and writes
only changed cells and the old and new cursor cell. Glyph = the 8x8 UNSCII font the core app already links (the template of
`build_terminal`: cell 12x13 px, origin y=10, 80x40 = 960x520 px, ends at y=530 of 540; letters 8 px wide with 4 px gap, glyph in the cell
rows 2..9). A cell is blitted by a fixed 12x13 loop from a font row table: foreground/background from the attribute via a 9-entry (plus
inverse) palette, the pixel format being the pixel layer's own. The layer's pixel format, stride and who owns the DDR2 frame are read from
`trxview`/the host's pixel-layer interface when building (not assumed here; see §6 Q1). The blitter writes the layer only while the text UI
is the active view; LVGL is not initialised for the page then or is not asked to draw (proposal: the LVGL display is parked, §6 Q2).
Wide-only: the 40x23 narrow window of the template does not exist here; the HDMI picture modes in use are 960x540 canvas (epic R31), so the
grid is 80x40 everywhere (D5); a smaller canvas than 960x520+10 px is an open point (§6 Q3).

**D3 Timing against LVGL (P2).** The same page (the core F5 Settings page of the mock-up) is drawn once by the existing LVGL `terminal`
layout and once by the blitter on the same board; measured are full redraw, one changed row, cursor step, N=20, RISC-V cycle counter, in
the same build; report lines go to §5. The harness is checked on a build where the blitter is slowed (S6, S7 controls).

**D4 Bound for "fast enough" (P2, proposal).** Not decided by Alex; proposed: the blitter passes when a key-to-changed-picture time of one
cell row change plus cursor stays inside one frame time of the active picture mode (20 ms at 50 Hz) at the core menu task's priority, and the
full redraw stays below the LVGL figure of the same page. If not met: spec section for gateware (a text overlay), as D17 says; not built here.

**D5 Wire protocol over ws:// (P4).** Based on the T192.1 WebSocket and token; the text UI adds a channel `text` with versioned messages (JSON
text frames for the first version, because the client is a separate project and a browser or a script must be able to read it; a binary form
is a later option):
- `hello` (server): `{proto: N, app: "host"|"core", cols, rows, tones: 9, attr: "cell-v1"}`; client answers `{proto, cols_max, rows_max}`; if
  the client cannot hold 80x40 the server sends a clipped window by scroll of rows (the client is told its `rows_max`; 80x24 minimum, ux.md §5),
  never reflows. ASCII only on the wire in v1 (glyphs outside 0x20..0x7e are replaced by the server).
- `full` (server): all rows as strings, plus a run-length attribute line per row, cursor position, a monotonic `seq`.
- `delta` (server): `seq` and a list of `{row, col, text, attr_runs}` for the changed cells only; the client applies in `seq` order; a gap
  in `seq` makes the client send `resync`, the server answers `full`.
- `key` (client): `{seq, k: "up"|"down"|"left"|"right"|"ret"|"back"|"stop"|"f1".."f8"|"del"|"home"|"end"|"tab"|"c=space"|"char", c: "x"}`; the
  server maps it to the same intent as the local key (T192.1 key->intent table, T192.6 bundle); the answer is `ack{seq}` and the following
  `delta`. A key unknown to the server returns `err{seq, "unknown key"}` and changes nothing.
- `ping/pong` for a dead peer; slow or dead clients are dropped by the server after a bounded queue (S15).
The server holds a bounded delta queue per client (proposal: 16 messages or 8 KB); a client that falls behind gets one `full` instead of a
queue (coalescing, not buffering without bound). The text channel is on the same TCP port and token as the T192.1 WebSocket (no second port,
no second auth). This protocol, with a reference test client (a small script, in `tools/`, not the product client), is the contract D16 binds
the separate terminal project to; its version is carried by `hello.proto` and by the T192.1 schema version.

**D6 Keys and input (P3).** The text UI takes intents, not raw codes: the local keyboard goes through the same "key -> intent" table as the
graphical UI (T192.1; T192.6 makes it a bundle), so the text UI never has a private key map. Text entry (rename, number) has no exception:
it uses the shared text-entry input of T192.1, as in the graphical UI (epic D19c), including its volatile entry history (epic D19d). C= SPACE opens the
search (T192.4) as an overlay; while it is open it owns every key (epic D3), in the text UI too.

**D7 Fallback pages (P5).** A registry of screen ids (one per graphic-only screen in the epic's list) with a mandatory text renderer; a screen
without one fails the build (S16). Shapes: Timewarp timeline = list of snapshots with frame numbers and step keys; memory map = hex rows with
the legend; medium panel = a table of drive/disk state; core live box = one status line (no core picture); pad wizard = prompt line plus
current mapping table; picture-mode list = list with the 8 s confirm countdown as text; pictures = placeholder line. The existing
`terminal` layout and the monitor (already text) are reused as they are.

**D8 Selection and coexistence (P6).** Text mode is a value of the interface choice (epic D5/D10): the host sets the default, a core may
override; safe mode C=+S forces the graphical TRX interface. Both views read the same state and send the same intents (T192.1); switching is
a view swap on a settled page, no state is lost. A `ws://` text client works whether the local view is LVGL or text: the text grid is
rendered for remote clients even while the HDMI shows LVGL (proposal: the grid is rendered only while at least one client is connected or
the local view is text, to save time, §6 Q4).

**D9 App adapters.** The host app uses the text UI after T192.2 (declarative host menu as client of `host_core`); the core app after T192.3
(A1200 first, epic D15). Until then the core app has `/v1/ui/state` and `terminal`; the grid code is written against the T192.1 snapshot and
tested with fixtures, so its bench does not wait for the apps (the apps' rows come from the fixtures of the mock-ups in S1).

**D10 Test client.** A ws test client for emu proofs lives in `tools/` (script, no new dependency on a language runtime beyond what the
tools already use); it holds a client-side grid, applies `full`/`delta`, sends keys, and is what S10-S15 use.

## §4 Out

- The product terminal client for macOS/Linux (separate project, D16); this spec delivers only the protocol (D5) and a test client (D10).
  The ratatui candidate of D16 (`trx64-cli`) is not touched.
- Telnet, SSH, serial text UI, VT100 escape sequences from the board (D6).
- Encryption (D4).
- Gateware: a hardware character overlay or any text hardware (D17: no gateware; if the blitter is too slow that is a new question, S7).
- A density choice or a larger text size (D10); a second grid size other than 80x40 locally.
- A pixel stream, the menu picture or core picture over `ws://` (a picture is a placeholder in text mode, S17).
- Colour as the carrier of meaning (colour is redundancy only).
- Non-ASCII glyphs and PETSCII graphics on the wire (v1 is ASCII).
- Search overlay content (T192.4), key bundles and safe mode logic (T192.6), the state/intent/event contract itself (T192.1).
- Using the TRX64-Ultimate monitor's verbs inside the host or core app's text UI as a new feature: the monitor stays what it is
  (`coreapp/src/trxmon`); only its cell model and line editor are taken over.

## §6 Open questions

1. (Q1, blocks D2) What is the pixel layer's format, stride and owner (DDR2 frame buffer, in the host and in the core app), and which
   hook lets the blitter write it without LVGL? To be read from `trxview` and the layer interface, not from comments.
   **Answered from the code (coordinator, 2026-11-07):** The format is RGB565 (2 bytes per pixel), the stride is `cv_w * 2` bytes (960 canvas: 1920 bytes; `PX_STRIDE` written at `host-app/software/lvgl_port/trx_lv_port.cc:88`, and the flush addresses `fb + y * cv_w + x`, line 107), the canvas is 960x540 by default and smaller per video mode (`trx_lv_set_canvas`, `trx_lv_port.h`), shown at scale 2 into 1920x1080 (`TRX_LV_SCALE`, `PX_POS`/`PX_OSIZE`). The owner is the LVGL port: two full frame buffers `malloc`ed from the application's heap, 16-byte aligned, `BUF_BYTES = 960*2*540` each (`trx_lv_port.cc:30,38-39,140-146`), in LVGL direct render mode (`:163`); the hardware shows `PX_FRONT` and takes `PX_BACK` at the next frame start, the flush writes `PX_BACK` and waits for the flip IRQ (`:104-122`). Host app and core app use the same file (`host-app/software/lvgl_port/`, compiled into both: `target/u64ii/riscv/coreapp/Makefile:120,284`; opened in `coreapp/src/ui.cc:77` and `hostapp/hostui.cc:6768`). Hooks that exist: `trx_lv_buffers(&a,&b)` returns both buffers (`trx_lv_port.h`, used by the menu picture in `hostui.cc:6631`), `trx_lv_show_picture(fb)` shows a caller-filled buffer as the first picture, `trx_lv_yield_layer()` gives the layer to someone else, `trx_lv_suspend()/trx_lv_resume()` switch the layer off/on. What does not exist: a call that presents a caller-filled buffer once the layer is on and LVGL is running (the flip is private in `flush_cb`; `trx_lv_show_picture` refuses when `layer_on`, `:200`). So the blitter needs one new function in the port, `trx_lv_present(fb)`: the `flush_cb` tail (clear flip sem, `ioWrite8(TRX_IRQ_CAUSE, TRX_IRQ_FLIP)`, write `PX_BACK`, wait on `flip_sem`) under the port lock, with LVGL not rendering into that buffer (suspend alone is not enough: it also switches the layer off, so a "park" state that keeps the layer on is also new).
2. (Q2, D2/D8) With the text UI active: is LVGL parked (display not flushed, no draw tasks) or does it keep running hidden? Affects RAM
   and the 25 MHz host time budget.
3. (Q3, D2) A canvas smaller than 960x540 (a compact mode): is text mode unavailable there, or is it clipped by rows?
4. (Q4, D8) Render the grid for `ws://` clients only while one is connected (saves time, delays the first `full`), or always?
   **Recommendation, Alex may override:** Render the grid only while the text UI is the active local view or a `ws://` client is connected; build the first `full` from the snapshot on connect. The model state is cheap to produce (`uistate_json` into 11000 bytes on request, `coreapp/src/uistate.cc:262-277`), and a client that connects asks anyway; keeping the grid always up would cost a menu-loop pass per change on the 25 MHz host for nobody. Delay of the first `full` is bounded by the request poll of 10 ms (`uistate.cc:283`) plus one build.

6. (Q6, D5) JSON text frames for v1 (readable by any client, bigger) or a binary delta from the start?
   **Answered from the code (coordinator, 2026-11-07):** `wsproto.cc` supports text frames only on the receive side: `ws_decode` closes the connection with 1003 for binary, continuation and fragmented frames and for any opcode other than text, close, ping, pong (`coreapp/src/wsproto.cc:78-120`, enum in `wsproto.h`), inbound payload is capped at `WS_PAYLOAD_MAX` 1024 (`wsproto.h`, 1009 above it) and must be masked. The send side, `ws_encode(op, payload, len, ...)` (`wsproto.cc:124-141`), takes any opcode and writes a single unfragmented frame up to 65535 bytes, so a server-to-client `WS_BINARY` frame would encode today; `ws_loop` only ever sends `WS_TEXT`, `WS_PONG` and `WS_CLOSE` (`restsrv.cc:52-125`), with `WS_MSG_MAX` 12288 per message (`restsrv.cc:15`). Client commands (keys) are JSON-RPC text, which fits the 1024 limit. So JSON text for v1 needs no protocol change; binary deltas to the client need only a `ws_loop` branch (and a flag from the client in the handshake or an RPC); binary from the client would need `ws_decode` to change.
