## §1 The problem

Alex wants a Commodore PET (the 1977-1981 family: 2001, 3000, 4000, 8000 series) as a core of the multi-core line, like the VIC-20 and the C128: a core file
on the SD, ROMs the user supplies, programs started from the core app, a picture on the host's pixel layer, the keyboard of the C64U. Nothing PET-shaped exists
in the tree. `docs/todo/T134.md` names one candidate, Thomas Skibo's `Pet2001_Arty`; this spec measures it against what the host offers, and says what is missing.

**What the candidate is** (read from the source, `git clone --depth 1` of `skibo/Pet2001_Arty`, 6,896 lines of Verilog including the benches):
`cpu6502.v` (1,091 lines, own 6502, 2022-23, with `RDY`), `pia6520.v` (240), `via6522.v` (548), `pet2001hw.v` (268, the bus: 32 KiB RAM `$0000-$7FFF`, 1 KiB video RAM
`$8000` (mirrored), one 16 KiB ROM array for `$C000-$FFFF` that also holds the 2 KiB character set at array offset `$2800`, I/O `$E800`), `pet2001io.v` (PIA1 `$E810`, PIA2 `$E820`, VIA `$E840`),
`pet2001vid.v` + `pet2001vga.v` (40 x 25 text, 640 x 480 VGA at clk/2), `pet2001ps2_key.v` / `pet2001uart_keys.v`, and `pet2001ieee.v`.
The clock is a ready strobe: `rdy <= !rdy && slow_clock` with `CLKDIV = 50` at 50 MHz, i.e. a 1 MHz CPU as a clock enable. **What it does not have:** no NMI
(`assign nmi = 0`), no CRTC (the 8032), no 80 columns, no BASIC 4 ROM window (`$B000-$BFFF` is not decoded, so only ROM sets that start at `$C000` fit), no RAM above 32 KiB.
`pet2001ieee.v` is **not a drive**: it answers device 8 from a 32 KiB block RAM holding one fixed program (`program.prg`, 2,971 bytes), ignores file names and supports LOAD only.
There is no disk, no tape-file layer (the cassette pins are free), no sound beyond the 1-bit CB2 line out.

**What a second source adds** (`MiSTer-devel/PET2001_MiSTer`, a port of Skibo's design; read, not run): 3032/4032 (non-CRTC) by Ruben Aparicio, the 28 KiB ROM map
(`$9000-$FFFF`), a tape module, CPU speed x1/x2/x4/x8, PRG/TAP injection, and `rtl/ieee_drive/` (Erik Scheffers, 2024: 4040/8250 dual-drive IEEE drives, about 2,200 lines of SystemVerilog, two T65 per unit, an M6532 RIOT, a sector-to-track generator that serves D64/D80/D82 images from SD blocks).
The MegaPET merge (`Rhialto/MegaPET`) is said to add the 8032 and CRTC; not read.

Why it matters: the PET is the only machine of the family that the multi-core line does not have; Alex's list of missing cores (2026-11-05): "PET, BBC Micro, GameBoy".

**Break the problem into parts (MECE):**

- **P1 Source and licence.** What is vendored, under which terms, and what never enters the repository (the ROMs).
- **P2 Machine core.** CPU, bus, memory map, clock, interrupts, the I/O chips, for the chosen models (2001 / 3032 / 4032 / 8032, 32 KiB or more).
- **P3 Video.** The PET picture (40 or 80 columns) to the host's pixel layer, geometry, colour of the phosphor.
- **P4 Keys.** The PET keyboard matrix from the C64U keyboard.
- **P5 Disks.** IEEE-488 and a drive (none exists in the candidate).
- **P6 Tape and sound.** Cassette 1 and 2, the CB2 speaker.
- **P7 Core application.** ROM files the user supplies, settings, programs (PRG), media, status.
- **P8 Fit.** Area, block RAM and timing in the DFX partition; core as DFX or large.
- **P9 Proof infrastructure.** Benches that need no Commodore ROM, and the board steps that do.

## §2 Scenarios — what proves it is solved

Benches run in the sim image (`trx64-sim-env`: GHDL and iverilog, as `cores/vc20/sim/run_hdmigeom.sh`). **No Commodore ROM is in the repository (P1)**, so every bench boots
a hand-written test ROM (generated by a script in `cores/pet/sim/`, like `cores/vc20/sim/gen_testrom.py`); a scenario that needs the real ROM is a board step with the person's files.

```gherkin
Scenario: S1 The vendored CPU, VIA and PIA pass the upstream benches
  Given Skibo's own testbenches test_cpu6502.v, test_via6522.v, test_pia6520.v (they ship in sim_1/)
  When  they run in iverilog on the copies under cores/pet/rtl
  Then  each prints its PASS line and the process exit code is 0
  And   a copy with one flag changed (a mutant: ADC carry, VIA T1 reload) FAILS the same bench

Scenario: S2 The test ROM runs a full memory and I/O walk
  Given a test ROM at $F000-$FFFF that writes a pattern through $0000-$7FFF, reads it back, and signs the result into $8000-$807F
  When  the core runs 100 ms of PET time in GHDL/iverilog
  Then  video RAM holds the expected 128 bytes (checksum compared in the testbench)
  And   with RAM size set to 16 KiB the sign differs (a write above $3FFF does not read back), so the control can fail

Scenario: S3 One CPU cycle is one microsecond, and RDY gates the bus
  Given the clock enable at its PET setting (1 MHz from the core clock) and a test ROM that counts cycles with a VIA timer
  When  the timer is read after 1,000 cycles of a known loop
  Then  the count equals the 6502 cycle count of that loop exactly (not "about")
  And   with the speed register at x2 the count is halved; a control with the enable stuck at 0 never advances (the bench fails by timeout)

Scenario: S4 The 60 Hz interrupt and the PIA/VIA registers behave as the PET ROM expects
  Given a test ROM that enables IRQ, counts the vertical-blank interrupt (the video retrace line into PIA1 CB1) and writes the count to $8000
  When  1 s of PET time has run
  Then  the count is 60 +- 1 for the 60 Hz setting and 50 +- 1 for the 50 Hz setting
  And   with PIA1 CRB bit 0 clear (IRQ disabled) the count stays 0

Scenario: S5 The picture reaches the host's pixel layer at the right geometry
  Given the frame writer fed from the core's video RAM and character ROM (the test ROM brings its own 2 KiB character set)
  When  the test ROM prints a fixed screen, in 40 columns and then in 80 columns (if Q3 chooses it)
  Then  the frame buffer of the newest complete frame has the expected size and a hash that equals the golden hash computed from the character set by the script
  And   the hash changes when one character code changes (the control proves the hash is not dead), and the host scaler locks to the idle raster (the hdmigeom bench with the PET stream: same numbers as the VC-20's contract)

Scenario: S6 Keys reach the PET matrix
  Given the keyboard path of the host (c64_keys) and the layout of Q5
  When  the bench presses each of the C64U keys that the layout maps, one at a time, and the test ROM scans PIA1 port A (row select) and port B (column read)
  Then  exactly the cell of the layout table is low for that key and no other cell
  And   a table with one entry moved FAILS (the control) and two keys held give two cells (no ghost cell in the matrix)

Scenario: S7 The core application loads the ROM set the user supplies and refuses a wrong one

  When  files of the right size are offered, then files of a wrong size, then a missing file
  Then  the right ones are written to the ROM aperture and read back identical; the wrong ones are refused with the size in the message; the gate keeps the core in reset while a ROM is missing
  And   the negative control (one byte flipped in the read-back) makes the test fail

Scenario: S8 A PRG is run
  Given the PRG loader (cbm_run.cc) with the PET's BASIC pointers (start $0401, end pointers $2A/$2C/$2E, keyboard buffer $026F, count $9E)
  When  a one-line BASIC PRG is queued for a booted test image and the core is released
  Then  the pointers in RAM are the ones the loader computes (compared with a golden list) and the keyboard buffer holds RUN
  And   a PRG whose load address is not $0401 is refused (control)

Scenario: S9 A disk is read over IEEE-488 (depends on Q4)
  Given the drive of Q4 with a D64 (and D80/D82 if Q4 lists them) from the test media folder, and a test program that LOADs "$" and one file
  When  the directory and the file arrive on the PET
  Then  the bytes equal the file in the image (sha256 of the received bytes)
  And   a bus with ATN held low from the PET side to the drive times out the way the PET ROM expects ("DEVICE NOT PRESENT" path: status byte $90), and a drive disabled in settings answers nothing

Scenario: S10 Tape and sound (depend on Q7, Q8)
  Given a cassette image written by the bench and read through c2n_read, and the CB2 line driven by the shift register in free-run mode
  When  the test ROM loads the tape block and plays a note
  Then  the received bytes equal the tape block; the audio output toggles at the programmed frequency within 1 %
  And   with the motor line off no byte arrives

Scenario: S11 The core fits the partition and closes timing
  Given the core stage of the pipeline (`core_sources.tcl`, `host/core.tcl`)
  When  it is synthesised out of context and routed against the cached host
  Then  LUT <= 13,600 (pb_l2) and block RAM <= 40 tiles in the report line of the core stage, WNS >= 0 on the routed partial; the numbers are written into §5
  And   the estimate of §3 D9 is replaced by the measured one

Scenario: S12 A real PET works on the board
  Given the person's ROMs on the SD (`/SD/cores/pet/roms/`), the .cor from the Gitea package, the C64U keyboard and a screen
  When  the core boots, BASIC prints its banner, a program is typed and run, a PRG is run from the menu
  Then  the banner matches the ROM's own, the typed program prints, the PRG runs; photos
  And   by hand because the real ROM cannot be checked in; run once as one batched session after S1-S11 are green

Scenario: S13 No ROM enters the repository
  Given the lint line of D1
  When  a file of 16 KiB named pet_rom.mem is planted under cores/pet/rtl
  Then  ci/lint.sh fails naming the file
  And   the clean tree passes (the control: a lint that never fails proves nothing)
```

## §3 Decision

Everything in this section is **proposed, coordinator** (2026-11-05). None of it is a decision of Alex's until it is recorded under §3a with his words. D-numbers are the proposal's.

**D1 Source and licence (P1).** Vendor Skibo's `Pet2001_Arty` sources (`source_1/cpu6502`, `pet2001hw`, `pia6520`, `via6522`, `pet2001vid` family) into `cores/pet/rtl/` with a `NOTICE`
like `cores/vc20/rtl/NOTICE`. **Verdict on the licence:** the files carry per-file headers, "Copyright (C) 2011, Thomas Skibo" (2015, 2020, 2022-23 on later files) with the BSD
3-clause text ("redistributions of source code must retain the above copyright notice ... binary forms must reproduce ... the names of contributors may not be used to endorse"; `cpu6502.v`
and `pet2001ieee.v` carry the 2-clause form). The repository has **no licence file**, but the headers are complete and permissive; redistribution in source and binary form is allowed
with the notices kept. That is enough to vendor; the `NOTICE` lists every file's copyright line verbatim. **Never vendored:** `roms/pet2001_rom1.mem`, `pet2001_rom2.mem` (PET ROM contents
under Commodore's copyright) and `charrom.mem` / the character set in them: the clean-room rule of the repository names only the exceptions Alex granted (Atari OS, SPC700 boot ROM), the PET is not one.
The core's ROM arrays are filled by the application from the user's files (as the VC-20's `put_basic`); the sim uses a generated test ROM and a generated character set. A lint line fails a push that
adds a `.rom`/`.mem`/`.bin` over 1 KiB under `cores/pet/` outside `sim/media/`. The MiSTer port is BSD for Skibo's part and **GPL-2** for `ieee_drive/` (Scheffers), 3-clause BSD plus GPL for the
rest; `T65` is the same family as the VC-20's; whether GPL parts may go in is Q1.

**D2 Machine (P2).** Keep Skibo's structure: one CPU clock enable (`rdy`) from the core clock, the CPU in `cpu6502.v` (an own 6502, no T65) or the repository's `vendor/icepi/cpu6510.v` — decided by the
S3 bench (cycle exactness, the PET needs the NMI that Skibo left out; the 6502 has the line, `nmi = 0` is the hardware's tie). Map: RAM `$0000-$7FFF` (8, 16 or 32 KiB by a register in reset), video RAM `$8000-$83FF`
(2 KiB for 8032), ROM `$9000-$FFFF` as a 28 KiB array of the MiSTer shape (`$9000-$AFFF` editor/extension, `$B000-$DFFF` BASIC 4, `$E000-$E7FF` editor, `$E800` I/O hole, `$F000-$FFFF` kernal) — the 16 KiB of Skibo is a subset.
The character set is a separate 2 KiB array (not inside the ROM array: one ROM image of the person's set is `kernal`, `basic`, `editor`, `chargen` files, Q12).

**D3 Models (P2).** Proposed first set: **4032** (BASIC 4, 40 columns, 32 KiB) as the default, **3032** (BASIC 2, same board) and **2001** (BASIC 1, original keyboard, 8-32 KiB) as ROM choices of the same hardware; **8032** (CRTC 6545, 80 columns, business keyboard)
as a second step with its own video block (Q2, Q3). 8096 (bank-switching RAM above 32 KiB, `$FFF0`) and SuperPET (6809) are Q-candidates for §4, not part of the first set.

**D4 Video (P3).** A frame writer of the VC-20 shape (`vc20_pixw`, T119): the core renders into DDR2 frame buffers; the host shows them on the pixel layer, integer scaled; the host's scaler only gets the idle raster it locks to (S5).
40 x 25 characters of 8 x 8 pixels = 320 x 200, 8032: 640 x 200. Skibo's VGA module (640 x 480, clk/2) is **not** used; the PET's own timing (the video-retrace line to PIA1 CB1 at 60 Hz, 50 Hz by setting) is what the ROM needs and S4 measures it. Phosphor: green / white / amber as a setting (the MiSTer port has green/white), Q6.

**D5 Keys (P4).** The host's `c64_keys` is a 64-bit C64 matrix; the PET's graphics keyboard has 73 keys (8 x 10 matrix) and the business keyboard about 80, so a **positional** table (the letter keys where the letters are, the PET-only keys on the
C64's free positions or on modifier combinations) goes in the core as a 64 -> 80 map, the table is in `cores/pet/rtl/` and the same file generates `coreapp/cores/pet_keys.h` for the app. Not a symbolic remap: the PET's shifted symbols and its graphic keys differ from the C64's. Layout choice is Q5; keys that do not fit in 64 bits (the PET-only ones) need either the extra-key route of the C128 (`c128_keys.h`, a hook that delivers raw USB codes — which the app does not have yet: "No hook in the application delivers raw USB keys to a descriptor today") or a table on modifier combinations.

**D6 Disk (P5).** Three routes, each a Q4 answer, none chosen: (a) **MiSTer's `ieee_drive`** (4040/8250, D64/D80/D82, GPL-2; area unmeasured, two T65 CPUs per unit, sector-based track generator fed from SD blocks, so it needs a block path to the app that the 1541 library does not have);
(b) a **2031** from `cores/c1541` (the 1541's mechanics and 6502 with VIA1 wired to IEEE-488 instead of IEC and the 2031 ROM; a 2031 is a 1541 with a different bus board, the GCR path and the cbm1541 library (D64/G64 images, write-back) are in the tree; area: the 1541 costs 1,820 LUT, run 275); the contract has one `drv_io` / `gcr_io` window and one drive, which is what a single 2031 needs; (c) a **file-level emulation in the app** that answers device 8 on the IEEE bus itself (the app plays the drive from files of the SD folder, the bus protocol in gateware as in Skibo's `pet2001ieee.v` but reading a file chosen by name; compatible for LOAD/SAVE only, not for copy protection, direct-access commands or DOS-wedge programs; the 4040's `#` buffers and `U1/U2` are out). Skibo's stub is a start for (c) only.

**D7 Tape and sound (P6).** The contract has the `c2n_*` pins (version 2), so cassette 1 (the PIA/VIA lines) is a wiring task plus an app side that plays/records `.tap`/`.p00`-style files; cassette 2 is a second PIA line. Sound is CB2 of the VIA into the shift register's free-run mode, 1 bit, to `audio_l/r` as a square wave through the host's audio path (S10).

**D8 Core application (P7).** A descriptor `coreapp/cores/pet.cc` (the generic core app, T104) with the ROM list (editor, kernal, basic, chargen — file names in Q12), settings: model (ROM set), RAM 8/16/32 KiB, 50/60 Hz, phosphor colour, CPU speed x1/x2/x4, Diag; tasks Reset and Reload ROMs; the PRG loader (`cbm_run.cc`) with the PET's numbers (`BASIC` at `$0401`, pointers `$2A-$2E`, keyboard buffer `$026F`/`$9E`), media slots for tape and (Q4) disks. Region map `MK_RAM 0..0x7FFF`.

**D9 Fit (P8).** DFX, in the partition `pb_l2` (budget 13,600 LUT, 40 BRAM tiles, 40 DSP since T164, `host/build.tcl`; about 78 % (10,600 LUT) is the highest that ever routed; corrected by the coordinator 2026-11-05, the first draft named the older 18,000 / 50). **Estimate, by source, not measured:**
Skibo's machine: CPU ~700 LUT, VIA ~300, 2 x PIA ~200, video and glue ~400, frame writer ~600 (the VC-20's `vc20_pixw`), registers and ROM loader ~300: **about 2,500 LUT** and **12-14 BRAM tiles** (32 KiB RAM = 8, 16 KiB ROM = 4, 2 KiB chargen 0.5-1, video RAM 0.5; the ROM window of D2 grows ROM to 28 KiB, +3 tiles). 8032 CRTC and 2 KiB video RAM +600 LUT, +1 tile.
A drive: route (b) +1,800 LUT as the 1541 measured; route (a) is the expensive one, about 2 x (T65 ~900 + RIOT/VIA ~500) + track generator ~1,500 for one dual unit = **about 4,500-6,000 LUT and 8-12 tiles**, to be measured; route (c) about +300 LUT. **Order of magnitude, whole core: 3,000-4,000 LUT with route (c)/none, 5,000-6,500 with route (b), 8,000-10,000 with route (a): at most about 74 % of `pb_l2` (13,600), 14-30 of 40 tiles.** It fits, route (a) near the limit, so there is no reason for a large core; S11 replaces the estimate by the report line. Risk: not area but the frame writer's DDR2 port (shared with the other cores' pattern) and the 28 KiB ROM array's reload path.

**D10 Proof infrastructure (P9).** `cores/pet/sim/`: a script `gen_testrom.py` writes the test ROM and a 2 KiB character set (a pseudo-random but fixed one, so S5's hash has content); the testbenches are in Verilog/VHDL as the vendored sources are Verilog (iverilog, as `tb_hdmigeom.v`); nothing third-party is checked in (D1).
