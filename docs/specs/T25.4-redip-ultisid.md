**Why the table is the cutoff (from the app's data):** the scaled "8580 Lo" table ends at 5118 for
FC = 2046/2047 (T25.1 §1.3); reDIP's 8580 formula gives `w0_T_lsl17 = 5 fc` = 10235 there; and
`2 x 5118 = 10236`, the table is linear (5.03 per entry, `table[i] << 1 = 10.06 i = 5 x 2i`). So the app's
value is `w0 T` in Q0.16 and reDIP's input is the same quantity in Q0.17: **"8580 Lo" in the menu
reproduces reDIP's own 8580 filter**, the other six curves move the cutoff as the menu says. The
resonance tables agree with T25.1 D6 (1448, 1324, 1219 ... and 1448, 1328, 1218 ...). Still to measure
on a C64U (T25.1 Q3): whether the hardware interpolates the odd FC values. A curve whose table x 2 does
not fit 16 bit signed ("U2 High" ends at 23577) is clamped to 32767 (`w0 T` = 0.25).
reDIP's own 6581 cutoff model (11 bit cutoff DAC, tanh table, `fc_base`/`fc_offset`) is not in the
hardware build any more ("Gideon measured wins": the app's 6581 curves are measured); it stays behind
the parameter `LEGACY_FC` for the bit-exact bench.

## 3. Architecture

### 3.1 Clock and pass

One pass per executed C64 cycle on `clk2x` (2 x dot4x, 64 clocks), started by `start` as in T25.1 D1/D2:
the op latched at `phi2_n` is applied by the pass that follows, the read-back is final before the CPU
samples in the next cycle. A pass always runs to its end (the rings must make complete rotations): a
`start` while one runs is ignored, `/RES` is sampled at the start. Length: `max(6 NS + 5, 5 NS + 12)`
clocks: **53 of 64 for NS = 8** (22 for NS = 2). OSC3/ENV3 of SID s are final from clock 9 + 3 s (30 for
SID 7), the bus values from clock 9, the NS outputs from clock 5 NS + 12 (52).

### 3.2 What changes in the reDIP files

reDIP keeps the state of its voices in rings of six registers (`o5..o0`, `n5..n0`, `e5..e0`, `v5..v0`,
...) that rotate in windows of six cycles; consumers tap fixed positions of the ring. With N = 3 NS
voices the ring is N positions long, the explicit positions stay (the taps do not move), the positions
in between only delay (shift register: SRL in the FPGA). Every window of six cycles becomes N cycles, the
second rotation (the 8580 final mix-in of sawtooth/triangle) 2N, everything relative to the voice index
j = cycle - window start; the SID of a cycle is `(cycle - window start) / 3` (`sid::sid_at`).

- `sid_control`: the CPU access arrives decoded (SID, register, data, op valid, all-SIDs flag). The write
  goes to the voice that is on its way into the head of the ring at cycle j + 1 (j = 3 s + reg / 7). The
  filter registers are a RAM word per SID instead of a two-entry ring. The bus value and its age are
  updated one SID per clock (one adder).
- `sid_waveform`, `sid_envelope`, `sid_voice`: the same code with the windows of §3.4; `model`, `variant`,
  `digi` are per SID.
- `sid_filter`: the five-cycle schedule per SID stays, SID k is shifted by 5k cycles (phase counters
  instead of cycle numbers); the state ring (vlp, vbp, vhp) is 3 NS long; the voices' DCA outputs go into
  a 24 x 22 bit RAM and are read at stages 2-4, because the filter takes 3 voices per 5 cycles while the
  voice pipeline makes 3 per 3 (reDIP stalls the voice pipeline once for two SIDs; that does not scale).
- `sid_core` (new): the part of `sid_api` that does not depend on the bus: counters, tick, the modules,
  OSC3/ENV3, the envelope levels, the NS filter outputs (captured at filter cycle 9 + 5k).
- `sid_api` (icepi bus wrapper): same ports as before, two SIDs in `sid_core`, the pass starts one clock
  later.

### 3.3 Adapter and integration

`cores/icepi/c64_redip_sid/sid_multi.sv` has the interface of `trx_sid_engine` (`op_*`, `cfg_*`, `cv_*`,
`rb_all`, `lv_*`, `smp_*`, `sum_*`; the state port `st_*` of T25.1 is not implemented). `trx_sid.v`
instantiates it under `` `ifdef SID_MULTI `` (`SID_MULTI_EQUIV` = reDIP's own cutoff, variant B and pulse
behaviour for the bench, never in a build), so the decode, split, POT, op latch, read-back copy and
`trx_audio` are unchanged. **Build switch (Alex, 2026-10-07, "ohne Build kein Hörtest"):** `designs/c64_basic/build.tcl` builds the
8-SID reDIP **by default** (defines `SID_MULTI`; `TRX_SID=redip8` is the same); `TRX_SID=redip2` builds reDIP's two
SIDs as before (`SID_REDIP`; `sid_api` on the generalised modules, bit exact in simulation), `TRX_SID=1` the T25.1
engine. `c64_core` elaborates with `-DSID_MULTI` (Verilator lint of the `dma_io` file list plus
`sid_multi.sv`); the Vivado build is the next step.

### 3.4 Cycle arithmetic (N = 3 NS, six-voice value in brackets)

| Unit | Window (cycles) | Meaning |
|---|---|---|
| control ring | 1 .. 2N (1..18 before, three rotations of six) | write head; taps v0 (osc: cycle j+2), v0-v2 (test/sync), v3 (waveform: j+5), v4 (envelope: j+6) |
| oscillator ring | 2 .. 2N+1 (2..13); update 2 .. N+1 (2..7) | taps o0-o4, update from o[N-1]; sync resets at cycles 4, 7, ... = 4 + 3k; MSB write-back 6 .. N+5 |
| noise ring | 5 .. 2N+4 (5..16); update 5 .. N+4; write-back 6 .. N+5 | n[0] output, n[1] write-back, n[N-1] read |
| sawtooth/triangle latch ring | 5 .. 2N+4 | st[0] written 5 .. N+4, st[N-1] read |
| previous-waveform rings | 6 .. 2N+5 (6..17) | 6581 update 6 .. N+5, 8580 update N+6 .. 2N+5 (final mix-in) |
| envelope ring | 6 .. N+5 (6..11) | e[N-1] read/updated |
| voice DCA | setup 7 .. N+6, DAC inputs 6 .. N+5 | model and digi of SID `(cycle-7)/3` |
| filter | cycle 1 = voice cycle 8; SID k stages at 5k + (1..9) | output of SID k captured at 9 + 5k; end 5 NS + 5 |

Taps that are positions of the ring relative to "previous pass" are at N-1 where reDIP has 5. The
second rotation takes its waveform selector from the previous-waveform ring (position N-2: the value
inserted N-1 cycles earlier), so the control ring needs two rotations (48 cycles for N = 24) and not
three (72, which does not fit the 64 clocks).

### 3.5 A reDIP behaviour that does not scale: the pulse bit of the 8580 final mix-in

In reDIP the pulse ring rotates for cycles 2..13 but the final mix-in of the 8580 (second rotation, cycles
12..17) reads it until cycle 17: for the last three voices (SID 2's voices) the ring has stopped and they
mix their waveform with the pulse bit of the third voice instead of their own. It matters only for the
8580 waveform-0 (floating) value and the noise write-back after pulse combinations on the second SID.
`PULSE_FIX = 0` reproduces it for every pair of SIDs (SIDs 2p, 2p+1: bit exact, bench), `PULSE_FIX = 1` gives every
voice its own pulse bit. **Decision (Alex, 2026-10-07): "lass doch den Klang von reSID gleich zum Original, egal welche
Anzahl SIDs" - `PULSE_FIX = 0` everywhere** (`sid_api`, `sid_multi` default, the `trx_sid.v` hardware instance), so
the sound is the original reDIP's for any number of SIDs. Consequence: even SIDs of a UltiSID (A, C) are equal to each
other and odd SIDs (B, D) are equal to each other, the two places differ in the 8580 corner case (`tb_sym` mode 2
checks both). `PULSE_FIX = 1` stays as a parameter (`tb_sym` mode 0 checks that all eight SIDs are then equal).

## 4. Filter detail

- `w0`: stage 3 reads `{u, FC[10:1]}` from the curve RAM (2 x 1024 x 16 bit, port B = the app's byte
  writes through `cv_*`, power-up content = the app's "8580 Lo" `sid_curve_init.mem`; one RAMB36), stage 4
  uses it: `a = min(table << 1, 32767)`.
- Filter state, saturating 17 bit sums, one shared 16x16 multiply-add as reDIP.
- 1/Q: constants (reSID 0.16 and `2^((4-res)/8)` times 1024, identical to T25.1's tables).

## 7b. Board result of run 481: digital silence (2026-10-07), cause: the mixer byte is 0

Test: SID 1 programmed from a 6502 loop, Vol UltiSid 1/2 = -12 dB, Vol Master = -30 dB, UDP stream peak 0 / rms 0;
integ-m1 (2-SID reDIP) under the same settings: peak 3856.

- **Cause (from the app's code, confirmed in simulation):** the app writes the UltiSID mixer bytes
  `vol = (source * master + 0x40) >> 7` and then `(pan_ctrl[pan] * vol) >> 8` per side
  (`u64_config.cc:310-320, 1376-1384`). -12 dB = `0x20`, -30 dB = `0x04`: `vol = (0x80 + 0x40) >> 7 = 1`; with the
  centre pan (`pan_ctrl[5] = 181`) `(181 * 1) >> 8 = 0`, and for every other pan `pan_ctrl[p] * 1 >> 8 = 0` (the table
  ends at 256). **Bytes 0-3 are all 0: the UltiSID channels are muted by the app's own arithmetic**, `trx_audio`
  multiplies by 0 and the output is exactly 0. The old build was audible because `ultimate_sys.vhd:1391-1392` feeds its
  mixer with the *larger* of the UltiSID byte (0/1) and the socket-1 byte (4/5; default socket volume 0 dB:
  `(0x80 * 4 + 0x40) >> 7 = 4`, `(181 * 4) >> 8 = 2`): gain 2 although the UltiSID channel was 0.
- **Evidence:** `designs/c64_basic/sim/redip/tb_audio_top.cpp` (`build_core.sh`; the whole `c64_core` with `-DSID_MULTI`, the
  app's register defaults of `ultimate_sys.vhd`, KERNAL boot, the 6502 program of the board test typed in with
  `SYS49152`, the core's audio output sampled once per I2S frame). Peak (24 bit) per gain byte of all four UltiSID bytes:
  `00` -> 0 (rms 0); `01` -> 16,614; `02` -> 27,350; `04` -> 51,611; `20` -> 482,499; `80` -> 1,830,173. So the whole
  path (decode, engine, `trx_audio`, output wiring, clocks, resets) works in simulation; the output is zero exactly
  when the byte is 0.
- Not a wiring or clock defect, so nothing was changed in the RTL. To hear the 8-SID build set Vol Master to 0 dB or
  Vol UltiSid to a value whose product with the master stays >= 3 (the stream then carries the SID). Whether the
  per-side gain should also take the socket bytes into account (as the old build accidentally did) is a question for
  the mixer, not for the SID (T25.3). The bench takes about 35 minutes (the KERNAL boot is 14 of them), so it is not in
  `run_all.sh` / CI.
