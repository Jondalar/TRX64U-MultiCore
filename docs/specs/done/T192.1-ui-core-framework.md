## §1 The problem

Alex wants a second UI (text, remote, web) to drive the host app and the core app without reimplementing their menus (T192 §1). Today
neither app offers a contract a client could bind to. Read from the code, 2026-11-07:

- Core app: `GET /v1/ui/state` is a pull snapshot built by the menu task on request (`coreapp/src/uistate.h:3-5,20-24`, 3 s wait, buffer
  `SNAP_MAX` 11000, `uistate.cc:13`), `"v":1` and a counter `seq` (`uistate.cc:15,60,67`). Items have no id: `MenuCtl::Item`
  (`menuctl.h:91-103`) carries slot/group/title/kind/flags only; the selection `sel_` is private. No input route (`rpccontract.cc` refuses
  `key_down/up`). `/v1/events` lists registry events only. WS exists (`/v1/ws`, `rest.cc:596`, `wsproto.cc`, `restsrv.cc:52 ws_loop`) but
  speaks JSON-RPC for ops and state, not the screen. REST ops bypass `ui.confirm` (`rest.cc`).
- Host app: `webui.cc` is Gideon's `HTTPServer` on port 80 (`webui.cc:518-541`), six routes (`webui.cc:231-310`), a one-slot command
  mailbox (`webui.cc:13`), the whole state as `WebSnapshot` (`web_json`), no version field, no WebSocket, no auth, no jobs; every
  confirmation is a blocking on-screen page (`hostui.cc`, ~25 `host_getch` waits), and `web_pump` starts entries with `ask=false`.
- Neither app has a token (T192 C3): the REST/WS surface is open and a remote key route, as D4/D11 want it, cannot be added safely.

Parts (MECE; the steps of "a remote client drives the app", plus what cuts across):

- **P1 Auth:** a token handed out at first login, kept as a file, shown in the menu, required afterwards (D4).
- **P2 State:** one versioned snapshot schema, with stable item ids, that both apps fill.
- **P3 Intents:** one input vocabulary (select/activate/set/key/back/open, plus answer/cancel) that goes through the app's own
  confirm/dirty/lock rules, not around them.
- **P4 Events:** a change/progress stream instead of polling.
- **P5 Jobs and questions:** long work with progress and cancel; every confirmation as a question that screen and remote client can answer.
- **P6 Transport:** one WebSocket framing and one set of HTTP routes in both apps, single-writer safe.
- **P7 Placement and mapping:** where the shared code lives and how today's `uistate.cc`, `rest.cc`, `wsproto.cc` and `webui.cc` map onto it
  without breaking what exists (the ops/state routes, T106 page, tests).

## §3 Decisions

Applying decisions of the epic (quoted from it, none added):

- **D4 (Alex, 2026-11-07):** "WebUI at the first login WITHOUT, then with." One token per app, shown in the menu, kept as a plain file; first
  WebUI login hands it out; afterwards every request needs it; accepted as URL parameter, header optional; plain HTTP, no encryption.
- **D11 (Alex, 2026-11-07, translated):** "A, updates too!" A remote client with the token may answer every confirmation, destructive ones and
  firmware updates included; the remote client is asked the same question the screen asks.
- **D14 (Alex, 2026-11-07):** "A". T192.1 is ONE shared core framework for both apps: state snapshot, intents with stable ids, event stream,
  jobs, token, WebSocket, written once; domain logic stays per app.
- **D16 (Alex, 2026-11-07, translated):** the terminal client is a separate project beside this repository and binds only through the T192.1
  contract (ws://, token); its language is open.

### Design (proposal; line numbers are `main` at 2026-11-07)

**D-A Where it lives.** New tree `app/ui/` (beside `app/view/`, which holds the LVGL layer; `app/` is already read by both apps and by
`ci/apptests.sh`, `common=` list line 27). Files:

| File | Content | Moves from |
|---|---|---|
| `uischema.h` | contract version, id rules, message/field names, size limits | new |
| `uiwrite.h/.cc` | the JSON writer both snapshots use | `coreapp/src/svcjson.*`, `uistate.cc` writer `w.ki/...` |
| `uistate.h/.cc` | `UiModel` interface (see D-B), rev counter, event ring, snapshot cache | `coreapp/src/uistate.*` (generic half) |
| `uiintent.h/.cc` | intent parser, queue, dispatcher to the app adapter | new |
| `uijob.h/.cc` | job table, question objects, answer/cancel | new; host flows and core `begin_confirm`/jobs adapt |
| `uitoken.h/.cc` | token make/verify/file, route classes | new |
| `uiws.h/.cc` | WebSocket framing | `coreapp/src/wsproto.*` verbatim (pure, benched) |
| `uihttp.h/.cc` | HTTP request parser + route table + WS upgrade | `coreapp/src/rest.cc` parser half (`HttpReq`, `http_feed`) and `restsrv.cc` accept loop |
| `port.h` | the only place that names FreeRTOS/lwIP/FatFs: mutex, clock ms, random bytes, file read/write, socket ops | new, two implementations (board, bench) |

Each app implements a small adapter (`UiApp`, D-B). Domain logic stays where it is (D14): `MenuCtl`/`OpRegistry` in the core app,
`host_core` (T192.2) in the host. The framework never reads an app's statics; it asks the adapter on the UI task.

**D-B The adapter.** The one interface an app implements, called only on the UI task (host: `hostui_run` loop, core app: the menu loop,
`run.cc:837-850`; the single-writer rule R30 stays as it is today):

```
struct UiApp {
  void snapshot(UiWriter &w);                  // the screen now: fills the schema of D-C
  UiReply intent(const UiIntent &in);          // taken / refused / asked(job) / held / blocked / gone / busy
  void tick(uint32_t ms);                      // jobs advance, timeouts, relist; may post events
};
```

The core app's `snapshot` is today's `uistate_json` body (`uistate.cc:62`) with ids added; `intent` calls new `MenuCtl` entry points that
T192.3 splits out (`select_id`, `activate_id`, `key`); the host's adapter wraps `host_core` (T192.2). Until T192.2/.3 exist, the first
adapters are thin: the core app's over today's `MenuCtl`, the host's over a read-only `WebSnapshot` plus the existing six commands.

**D-C State snapshot (contract v2; v1 = today's `/v1/ui/state`).** JSON, UTF-8, one object. Top level:

```
{"ui":2,"app":"core"|"host","rev":<u32>,"menu_open":bool,"screen":"<screen id>","title":..,"crumb":..,
 "focus":"<item id>","unsaved":bool,"keys_owner":"menu"|"monitor"|"dialog"|"picture"|"search"|"job",
 "areas":[{"id","title","active"}],"tabs":[{"id","title","active"}],
 "items":[{"id","kind","title","sub","chip","value","tone","enabled","dim","toggle","on","hidden","primary",
           "key"? ,"bkey"?,"live"? }],
 "rows":{"first","total"},"dialog":null|{...question...},"jobs":[{...}],"footer":[...],"status":{...}}
```

- `ui` is the contract major version. Minor additions are new optional fields; a client ignores unknown fields and refuses an unknown major
  (`hello` carries `ui_min`,`ui`). `rev` replaces `seq`: increases on every key taken, open/close, state change and job step (S10).
- Item `id` is a string, 1-48 chars `[a-z0-9._:-]`, derived from content, never from a position: core app menu nodes use the menu.toml node
  path as `goto_spec` already addresses it (areas/tabs/node names, `menutree.h:55-91`), settings `set:<Setting.key>`, ops `op:<name>`,
  browser entries `fs:<name>` inside the browser screen (the screen id carries the folder); host: pages `page:<name>`, boot entries
  `entry:<8 hex of the path's hash>`, settings `cfg:<key>`. Uniqueness is per screen (S4); an id that disappears answers `gone` (S5).
- `keys_owner` states who takes keys now (monitor, app dialog, picture confirm, lock: `run.cc:839-847`, `menuctl.cc:2303`), so a client knows
  why an intent answers `blocked` (S8).
- Size: the core app's cap stays one snapshot (`SNAP_MAX` 11000 today) with `rows.first/total` windowing; a larger list is windowed by the
  adapter, never truncated silently (`"more":true` when cut).

**D-D Intents.** Client to board, one JSON per WS text message or one POST body, each with a client `id` echoed in the reply:

| `do` | fields | Meaning (same path as the board key) |
|---|---|---|
| `select` | `item` | move focus to the item (no action) |
| `activate` | `item` | RETURN on that item: runs through `ui.confirm`, dirty and lock rules, may answer `asked` with a job id |
| `set` | `item` or `key`, `value` | settings write; reply `held` when it waits for Save |
| `key` | `key` (named: `up down left right ret back f1..f8 runstop space del home pgup pgdn`, `c=+<key>`, a one-char string) | a key as the board keyboard would deliver it; `any` for "any key" (picture confirm, boot countdown) |
| `history` | `dir` (`prev`/`next`) | recall in a text field from the entry history: RAM only, 20-50 entries, cleared by reboot or core change (epic D19d) |
| `back` | none | the back/close action of the current screen (R27 lock rules apply) |
| `open` | `target` (`goto_spec` string or screen id), optional `menu:true` | open a screen/tab, or the menu itself; the remote way to the hotkey that opens the core menu (R1/R2) |
| `answer` | `q`, `choice` | answer an open question (D-F) |
| `cancel` | `job` | cancel a job (D-F) |

Reply: `{"t":"ack","id":..,"rev":..,"r":"taken|refused|asked|held|blocked|gone|busy|bad","job":..,"why":..}`. `why` is the producing
module's text (R23), never composed by the framework. No intent bypasses a confirmation: the dispatcher has no "run op" verb (S6). The ops
routes (`POST /v1/ops/{name}`) are not intents, but a destructive op goes through the same confirmation gate (a D-F question, reply
`asked`) as an intent: one safety model (epic D18, D19a; Q1).

**D-E Event stream.** After the WS upgrade: `hello` (`ui`,`ui_min`,`app`,`core`,`rev`), then the snapshot, then events. Client messages
can set `{"t":"sub","push":"snap"|"note"}`. Event messages, board to client:

| `t` | Content |
|---|---|
| `snap` | full snapshot (default; pushed after a `rev` change, coalesced to the UI task's pass, at most one in flight per client) |
| `note` | `{rev}` only, client then sends `{"t":"get"}` (for clients that want to pull) |
| `job` | `{job, phase, step, done, total, cancelable, rev}`: small, sent per step without a snapshot |
| `ask` / `closed` | question opened / closed (answered where, by whom: `screen`\|`remote`\|`timeout`) |
| `toast` | the line the screen flashes (footer/status/toast are three channels today: F6) |
| `resync` | the client's queue overflowed; connection closes after it, the client reconnects (S11) |

Per-client queue is small and fixed (`RPC_QUEUE` 4 today, `rpc.h:22`); the UI task never blocks on a client. The registry events of
`service.subscribe` (`rpc.cc:122-171`) stay on their own channel; the new messages use `t` and never collide with JSON-RPC (`jsonrpc` key).

**D-F Jobs and questions.** One table, `UIJOBS_MAX` 4 (as the app jobs, R29), plus at most one open question per app (the screen shows one
dialog). Job: `{id:"j<n>", kind, title, phase: queued|running|asking|done|failed|cancelled, step, done, total (0 = unknown), cancelable,
result:{ok,text}}`. Producers: host flows (`start_sequence`, update, restore, convert, format, file ops; T192.2) and core-app jobs
(`busy()/progress()`, `menuctl.h`; T192.3) post steps; cancel is a flag the producer polls at its existing check points (the host's
`abort_key` at `hostui.cc:3690-3695` becomes `job.cancel_requested`; `fw_write` says `cancelable:false`).
Question: `{q:"q<n>", job, text, choices:[{id,label,key}], destructive, default, timeout_ms}`. Choice ids `yes`/`no` map to RETURN and Left
(`ui.confirm`, spec D2); the file-delete confirm (`confirm_task_`), the write-back question (`wb_ask_`, `menuctl.cc:1391-1405`), the full-firmware
confirm and the picture confirm are all questions. Rules: the question is created by the producer, shown by every view (screen, WS), answered
by the first answer from any source (S13), unanswered = nothing runs (D11 control), `timeout_ms` with a `default` only where today's flow
has a timer (picture confirm 8 s, S14). A remote `answer` needs the token like everything else; no extra gate (D11).

**D-G Token.** Per app one token: 16 random bytes, 32 hex characters (width is a build choice; arc42 §8 says 128 bit), from a real entropy
source via `port.h` (Q3). Files, plain text, one line: host `/Flash/trx/ui.token` (beside `host.cfg`, `picture.cc:406`); core app: the same
folder, name `ui.token` (the host and the core app are never both serving, one app owns port 80 at a time) (Q2). Routes by class (S2):
`public` = `GET /` page, `GET /v1/ui/hello` (versions, `grant:true|false`), `POST /v1/ui/grant`; everything else `token`. **Grant:** if no
token file exists the grant route creates it, writes it, answers it once; with a file present it answers 403 (S1, S14). The T106 page and
the web client call grant on load, keep the token in the page URL (`?t=<token>`). Presented as URL parameter `t=` (query, WS upgrade too:
`ws://host/v1/ws?t=...`) or `Authorization: Bearer <token>` / `X-Trx-Token` header (the core app's `HttpReq` parses only the WS headers
today, `rest.h:28-41`; `uihttp` adds these two). Compare in constant time. The menu shows the token on the network/info page (S17). A deleted
file means a new grant to the next fresh login and the old token is dead (S17 control). Regenerate = delete the file (menu action
"New token" does the same). Plain HTTP, no encryption (D4); FTP stays open (arc42 §8).

**D-H WebSocket framing.** `wsproto.cc` is already RFC 6455 text framing, pure and benched (client frames masked, server unmasked, close
codes 1002/1003/1009, no fragments, no binary, `WS_PAYLOAD_MAX` 1024 in, up to 65535 out, `wsproto.cc:122-141`). It moves to `app/ui/uiws.*`
unchanged. One message = one JSON object = one text frame. Incoming size limit 1024 is enough for intents; outgoing buffer on the board is
`WS_MSG_MAX` 12288 (`restsrv.cc:15`), above `SNAP_MAX`. Ping/pong and close as today (`restsrv.cc:114-120`). One path `/v1/ui/ws` for the
UI contract; `/v1/ws` stays the JSON-RPC adapter (T104.1) and gets the same token rule. Both can share the accept loop (`ws_loop`,
`restsrv.cc:52`).

**D-I Mapping of today's code.**

| Today | Becomes |
|---|---|
| `coreapp/src/uistate.cc` `uistate_json` / `uistate_request` handshake | adapter `snapshot()` body in the core app; the 3 s request handshake (`uistate.h:20-24`) is replaced by the event ring: the menu task renders when `rev` changed and a client wants it; `GET /v1/ui/state` serves the cached last snapshot (v2) |
| `/v1/ui/state` v1 | kept for one release with v1 output beside v2 (`?v=1`), golden-tested (S18); removed by a later spec |
| `coreapp/src/rest.cc` (alias table, `/v1/info /report /ops /state /events`) | stays; routes get a class from `uitoken` (D-G); `rest_serve` calls `uitoken_check` first; ops routes unchanged otherwise |
| `coreapp/src/rpc.cc` / `rpccontract.cc` (`service.*`, TRX64 aliases) | stay; `/v1/ws` upgrade checks the token; the contract's refused `key_down/up` stay refused |
| `coreapp/src/wsproto.cc` | moves to `app/ui/uiws.cc` |
| `coreapp/src/restsrv.cc` accept loop, `HttpReq` parser | moves to `app/ui/uihttp.cc` (generic: route table callback, upgrade hook) |

**D-J Threading.** Network tasks (HTTP accept, one task per WS client as `restsrv.cc` does today) only parse, check the token, and enqueue
intents into a fixed ring (8 entries); the UI task drains it once per pass, applies, and writes replies and events into per-client queues.
Snapshots are rendered on the UI task and handed over as a copy; no other task reads `MenuCtl` or host statics (S17). Max 3 clients as
`RESTSRV_CLIENTS_MAX`.

**D-K Build and tests.** New suite `tests/uicore` in `ci/apptests.sh` (pure C++, `port.h` bench implementation with fake clock/file/random).
`ci/lint.sh` gets the grep gate of S20. The RISC-V build of both apps is the agent's done criterion (CLAUDE.md "An app agent is done only
when the RISC-V build passes"). ue2emu runs: phase A (core app as any core) for S6, S7, S14-S16, S18; host flow run for the host adapter.

## §4 Out

- The domain split of either app: `MenuCtl` leaks (T192.3), `host_core` and the declarative host menu (T192.2). T192.1 ships thin adapters only.
- The search overlay (T192.4), the text UI and the terminal client (T192.5, D16), bundles and safe mode (T192.6). The framework only carries
  `keys_owner:"search"` and the `key` verb they will use.
- Encryption of HTTP/WS and a password for FTP (D4).
- Per-user tokens, token expiry, roles. One token per app (D4).
- Binary WebSocket frames, fragmented messages, compression (`wsproto` limits stay).
- Patch/diff snapshots; a full snapshot per `rev` is the first contract (Q4).
- Removing `/v1/ui/state` v1 and the old host JSON routes (kept this release, S18, S19).
- Camera/keyboard-less access beyond the intent set: no raw framebuffer or pixel route.

MVP (epic D20, branch `t192-mvp-core`). Written in the same commits as the code; the list below is what is true of the code now.

- **Placement:** `uicore/` at the top of the repository (not `app/ui/`): C++11, no `lv_`, no FreeRTOS, no lwIP, no include from an app or from Gideon's
  tree. Public header `uicore/uic.h` only; `uic_priv.h` is private. Files: `uic_json.cc` (writer, flat reader, ids), `uic_sha.cc` (SHA-256, constant

- **Q3 (decided: recommendation):** the token is 16 bytes of SHA-256 over the port's raw material (`UicPort::entropy`) || ms timer at grant || a grant
  counter || the ms timer of the requesting connection; stored as 32 hex characters + newline. Strength as stated in Q3: no true randomness.
- **Q1 / D19a:** destructive ops over REST answer `asked` and run only after an `answer` (the app marks which ops are destructive, see T192.3 §5).
- **Token lifecycle:** the grant is applied on the UI task (it writes the file), the network task waits for the reply. The UI task looks at the token
  file every two seconds: a deleted file ends the old token within two seconds, the next fresh login gets a new one (S17). `file_save == null` in the
  port turns auth off (benches of other parts).
- **Events:** one ring of 16 events shared by all clients (`rev` strictly increasing, not contiguous: plain state changes bump `rev` without an event);

  ring under a short critical section: it never waits for a client.
- **Snapshots:** rendered on the UI task into one cache buffer, only while a WebSocket client is connected or a REST reader asked; readers get a copy
  of the current `rev` (REST waits at most 3 s). Full snapshot per `rev` (Q4 recommendation).
- **Intents:** the network side queues into 8 slots and waits (3 s) for the UI task's reply; the board's own input goes through `uic_local()`, which
  applies at once and therefore always ahead of queued remote intents (T192.3-S10).
- **Public API of `uicore/uic.h` (what the host side adopts):** `UicPort` (target: clock, lock, sleep, UI-task test, entropy, token file), `UicDomain`

- **Rev follows state:** a render at the same `rev` that differs from the last one (a REST call changed a setting, a media poll) raises `rev` itself, so a
  state change that reached no `uic_note` is still seen; REST readers always get a fresh render, WS clients a re-check every 500 ms.

## §6 Open questions

- Q1: Do `POST /v1/ops/{name}` with the token stay a direct path that bypasses `ui.confirm` (as today), or must destructive ops answer `asked` too?
  Decided (Alex, 2026-11-07): epic D18 - destructive ops ask over REST too; no path bypasses a confirmation.
- Q2: Same token file name `/Flash/trx/ui.token` for host and core app, or one per core app per core?
- Q3: Which entropy source does the RISC-V application have for 16 token bytes (no `rand` use found in `coreapp/src` or `hostapp`)?
  **Answered from the code (coordinator, 2026-11-07):** No hardware RNG exists in the tree and nothing in `coreapp/src` or `hostapp` calls `rand`/`srand` (grep empty); lwIP's `LWIP_RAND()` is plain `rand()` (`vendor/gideon/software/network/config/arch/cc.h:105`), never seeded, so it is the same sequence every boot and must not be used. Sources that do exist: (a) the SPI flash unique ID, `W25Q_Flash::read_serial` (`vendor/gideon/software/io/flash/w25q_flash.cc:236`), 8 bytes, per-device constant, already exposed through the MAC (`io/network/rmii_interface.cc:121-130`) and `getProductUniqueId` (`system/product.cc:253`), so it is identity, not secret; (b) the ms timer `getMsTimer` (`system/itu.c:84`, 16 bit, counts since boot; the host app widens it in `core_cycles`, `hostapp/coreboot.cc:47`); (c) the ESP32 supply voltages, `wifi_get_voltages` (`io/wifi/wifi_cmd.h:50`, `voltages_t` has `v10`, `vusb`, ... as 16 bit ADC counts): noisy low bits; (d) the AP scan with RSSI (`wifi_scan`, `wifi_cmd.h:39`, used in `hostapp/wifinet.cc:126`) and the ESP32 MAC (`wifi_getmac`, `wifi_cmd.h:38`); (e) the arrival times of the first HTTP/WS requests and key presses, measured with the ms timer (the token is created on first use, not at boot, so these differ per run). SHA-256 exists in both apps (`coreapp/src/corefolder.cc`, `partial.cc`). Proposed mix (recommendation, Alex may override): token = first 16 bytes of SHA-256 over flash unique ID || ESP MAC || 8 samples of `wifi_get_voltages` (low bytes, 10 ms apart) || RSSI list || `getMsTimer` at creation and at the requesting connection's first byte || a persisted counter, written to `/Flash/trx/ui.token` once and then reused. Honest strength: no true randomness, about the entropy of the voltage noise and timing jitter; adequate for a LAN token that is only a gate against stray requests, not against an attacker on the same network who can also read the unique ID from the MAC. If that is not enough, the ESP32 firmware would need a `get_random` RPC (`esp_random()`), which is outside this repository.
- Q4: Full snapshot per `rev` (this spec) or patches from the start, given `SNAP_MAX` 11000 and the 4-entry client queue?
  **Recommendation, Alex may override:** Full snapshot per `rev` for the contract, but not as a notification. `RPC_QUEUE` is 4 entries of `RPC_NOTE_MAX` 320 bytes (`coreapp/src/rpc.h:22-23,40`), so a snapshot can never travel through the notification queue; it travels as a request/reply (`WS_MSG_MAX` 12288 holds it, `restsrv.cc:15`) or as `GET /v1/ui/state`, and the notification carries only `rev` (and `resync` on overflow). Today's `/v1/ui/state` is one JSON document written by `uistate_json` into a static `g_snap[SNAP_MAX]` of 11000 bytes (`uistate.cc:13-17`), hard limit: over it the answer is `{"v":1,"error":"the state does not fit"}` (`uistate.cc:272-274`). The size is bounded by the content, not measured here on a board: at most 24 browser rows (`first + 24`, `uistate.cc:172`) plus roots, items, footer and job lines; the cap is the number to design for. At 11 KB per change a patch format would only pay on a slow link; the producer builds the snapshot on request in the menu loop (`uistate_service`, `uistate.cc:262-277`, 10 ms polling in `uistate_request` at `uistate.cc:283`). Patches can be added later as an optional `since` parameter without breaking the full form.
- Q5: May the host's `webui.cc` leave Gideon's `HTTPServer` for `uihttp` (needed for WS; port 80 and anything else using that server)?
  **Decided (coordinator, 2026-11-08):** yes; nothing else in the host used it. Built, see §5.
- Q6: Contract major starts at 2 (v1 = today's `/v1/ui/state`); is that numbering fine?
  **Recommendation, Alex may override:** Yes, start at 2. Today's snapshot hard-codes `"v":1` (`coreapp/src/uistate.cc:66`) and no client of it checks the number as a contract; the new snapshot changes shape (ids, `rev`), so the major must differ from 1 for a client to tell them apart, which `ui` major (this spec, line 135) requires.
