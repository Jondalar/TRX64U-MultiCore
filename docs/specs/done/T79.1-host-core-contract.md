# T79.1: the host-core contract (draft, decisions taken)

Part of T79 (partial reconfiguration). Status: **draft 2026-10-11 (Claude), asked for by Alex**: "design the host-core contract as a spec, that makes total sense, above all because we want to hang N more cores behind it."

## 1. Why

Layer 1 (the host) stays loaded; layer 2 (a core: TRX64, later VC20, Minimig, ...) is swapped by partial reconfiguration; layer 3 is the core's software in DDR2 (T79 decisions). Every core plugs into the same socket, so the boundary between layer 1 and layer 2 is a contract: fixed for the host, the same for every core.

Today's boundary is not designed, it is where `top.v` happened to be cut (trial B, `tools/t79/extract_layer2.py`): **348 ports, 3,027 bits**. Measured cost (runs 700-706):

- **LUT:** an out-of-context partition cannot be optimised across its edge: every port and the logic behind it stays. Layer 2 measured 17,460 LUT against about 15,800 for the same blocks in the unsplit design (difference about 1,700, includes placement noise).
- **Routing:** run 706 placed, but the router did not converge (8,250 overlapping nodes after three iterations), with about 2,500 signals crossing the edge.
- **Portability:** a VC20 core would have to answer a C64-shaped socket (C64 RAM windows, drive debug bus, REU command port, freeze menu text layer).

Today's 3,027 bits by function (`layer2.v`, rough grouping):

| Group | Ports | Bits | Examples |
|---|---:|---:|---|
| App I/O windows into individual blocks | 86 | 689 | `ai2c_*`, `ap_*`, `cram_*`, `cw_*`, `ovl_*`, `pal_*`, `drv_io_*`, `gcr_io_*` |
| DDR2 client ports (one per block) | 43 | 590 | `drv_*`, `reu_cmd_*`, `v_*` (pixel layer), `vs_*`, `st_*` |
| Pins (slot, IEC, keyboards, LEDs, audio, RMII) | 60 | 261 | `SLOT_*`, `IEC_*`, `BLING_LED`, `RMII_*` |
| Debug and trace | 4 | 259 | `drive_dbg` (256 bits), `dbg_*` |
| Video and audio to layer 1 | 19 | 242 | `pix_color`, `pix_x`, `audio_l/r`, `hdmi_*` |
| Clocks and resets | 15 | 15 | `c64_gclk`, `sid2x_clk`, `sys_clk`, `cpu_clk`, `pix_clk`, `mclk` |
| Other (control, keys, joysticks, status) | 121 | 971 | `app_keys`, `app_joy1/2`, `app_freeze`, `app_cart_*_tgl`, `ai2c_scl_lo` |

## 2. Principles

1. **Narrow and generic.** A small set of channels, each a bus with its own protocol, not one wire per register. Target: **under 400 bits** across the edge (today 3,027).
2. **Core-agnostic.** Nothing in the contract names a C64 part. What is C64-specific is decoded inside the core.
3. **The host owns what every core needs.** Layer 1 rule (Alex, 2026-10-11): minimal for softboot plus what other cores can use (Ethernet and UDP streams included). The contract is the API of those services.
4. **Self-describing core.** The core answers an identity block (core ID, contract version, capabilities); the host's software (layer 3 loader) checks it before handing over.
5. **Every channel has a defined idle.** An empty partition (grey box) or a core that does not use a channel leaves it at its idle value; the host never hangs on it (DFX: during reconfiguration the outputs of layer 2 are undefined, the host gates them).
6. **Versioned.** `contract_version` in the identity block; additions are new channels or new capability bits, never changed meanings.

## 2a. Decisions

- **Board peripherals belong to the host** (Alex, 2026-10-11: "The peripherals should go into the host system too, so layer 1"). Line drawn (Claude): the host owns the electrics and the drivers, the core the meaning and the timing. Host: keyboard scan (I²C) and restore key, joysticks, LEDs (case, WS2812/APA102 bling), audio out (I²S, speaker, HDMI audio) and mixing, the app's I²C, IEC line levels (open collector). Core: what the C64 makes of them (CIA reads the matrix, the IEC protocol of C64 and 1541). Exception: the cartridge port stays the core's (bus timing in ns, synchronous to the core's PHI2); the host only holds its pins in a safe idle while no core runs. Answers open decisions 2 and, except for the cartridge port, 5. About 750 LUT move from layer 2 to layer 1 (keyboards, bling, LEDs, I²C, I²S, app input, IEC levels).

- **Video: the core delivers its native picture, the host makes every output** (Alex, 2026-10-11, decision 1 = V1a, after "we still have the S-Video/RGB out .. and different resolutions"). The core sends pixels with line and frame sync in its machine timing and states geometry and frame rate in its identity block; the host scales (generic, frame-locked to the core like `vic_scaler` to the VIC today), composites overlay and pixel layer, encodes HDMI in a selectable resolution, and later drives the analog AV connector (composite/S-Video/RGB, 4 `AVID` pins, not built today: gap G11, T40 non-goal) and the UDP video stream. The scaler and its 4 BRAM tiles move to layer 1 (layer 1 then needs about 22.5 tiles, layer 2 about 7.5 fewer). The C64 text layer (freeze menu from C64 RAM) stays in the core and draws into the native picture.

- **Clocks: a programmable MMCM in the host** (Alex, 2026-10-11, decision 3). The core names the frequencies it needs in its identity block (for TRX64 two: the C64 clock in PAL or NTSC and `sid2x`); the app programs a host MMCM over DRP before it releases the core's reset. Exact frequencies for every core (frame rate for the host scaler's lock, later the analog colour carrier). Costs one of the 50T's five MMCMs and the DRP sequencer in the host.

- **Memory: two ports, both limited to the core's window** (Alex, 2026-10-11, decision 4). A real-time port (highest priority, bounded latency: a Minimig's chip RAM, the C64 REU's DMA) and a general port (drive, cartridge, traces); the core arbitrates its own masters onto them. The host checks every address against the core's window in DDR2, so a core cannot overwrite the app or the host. About 160 bits across the edge (C3 shrinks from 240).

- **IEC: levels only** (Alex, 2026-10-11, decision 5). The host drives the open-collector lines (ATN, CLK, DATA, SRQ, RESET) and hands the inputs over synchronised and filtered; the wired-AND of C64, internal 1541 and the port and the whole protocol stay in the core, so fast loaders keep their bit-exact timing. About 10 bits across the edge.

- **Register bus: 8 bits, Gideon's I/O bus as it is** (Alex, 2026-10-11, decision 6, checked against a Minimig: "does that still work with a Minimig then?"): 24-bit address, 8-bit data, read/write/ack, the bus the app's drivers use today. Bulk data goes through the memory ports: a Minimig's floppy (ADF) and hard disk images lie in DDR2 and the core reads them itself, so the register bus carries only control, OSD and keys (on the MiST that path is SPI, slower still). About 45 bits across the edge.
- **To check before a Minimig port:** the real-time memory port must answer within the Amiga's chip bus cycle (about 280 ns at 7 MHz) even with a DDR2 refresh or an app access in between; our DDR2 controller's worst-case latency is not measured.

- **Several C64 cores, at least one floppy** (Alex, 2026-10-11 late): "the drop-in goal of M1 we reached with the M1 RC ... I am quite open to the multi-core architecture with several C64 cores .. one as C64RE companion, one as U64 replacement, etc. But yes, at least one floppy should be in it." So a core need not be a drop-in for Gideon's; every C64 core keeps one hardware 1541 (fast loaders need the cycle-exact drive; SoftIEC alone is not enough). The GCR codec (the app's image conversion, no deadline) may move to software.

All six decisions of section 5 are taken; sections 3 and 4 are the proposal they refine.

## 2b. The socket as a hardware interface

Alex, 2026-10-11: "and design it like a real BUS? So a hardware interface? That would need a controller on the host side and a client on the guest side?" Yes: the contract is a socket in the sense of a PC slot (mainboard and card), not a cut through one design. Not one shared bus but a few standard interfaces, each with a fixed master, like PCIe keeps register access, DMA and interrupts apart:

| Interface | Master | Host side | Core side | Like |
|---|---|---|---|---|
| C2 register bus | host | the app CPU's I/O bus master (exists), timeout for a missing `ack` | address decoder that spreads the window onto its registers (Gideon's `io_bus_splitter`, exists) | AXI-Lite |
| C3 memory ports | core | DDR2 arbiter (exists, `mig_arb`) plus the window check | arbiter of its own masters onto the two ports | AXI master into the host's memory |
| C4/C5 video, audio | core | scaler, mixer: a sink that takes the stream | the source (VIC, SID) | AXI-Stream |
| C1, C6, C7, C8 sideband | fixed per line | clocks, reset, key matrix, IEC levels, cartridge pins | the lines' C64 meaning | |

Rules that follow:

- **Real time never goes over the register bus.** A register access takes a few cycles and waits for `ack`; fine for control, wrong for pixels, IEC levels, audio samples or the cartridge bus. Those keep their own channels.
- **Neither side needs a new controller.** The host's ends exist today (I/O bus master, `mig_arb`, scaler); they move to the edge instead of being wired to single blocks. The core gets a decoder and a port arbiter: the TRX64 adapter of section 8.
- **Decoupling during a swap.** While layer 2 is being reconfigured its outputs are undefined. The host holds every channel at its idle (principle 5): the register bus answers with a timeout, the memory ports refuse requests, the video sink shows black, the cartridge pins stay released. With defined interfaces this is one gate per channel (Xilinx's DFX Decoupler does the same).
- **Register stages at the edge.** Every channel except the cartridge pins (ns timing) and the IEC levels may carry a flip-flop on each side of the edge. That costs one cycle of latency and gives the router and timing slack where the partition boundary is, which is the current bottleneck (section 7).

## 3. Channels (proposal)

| # | Channel | Direction | Width (about) | Replaces today |
|---|---|---|---:|---|
| C1 | Clocks and reset | host → core | 6 | the 15 clock/reset ports |
| C2 | Register bus (app ↔ core) | host ↔ core | 60 | the 86 app windows (689 bits) |
| C3 | Memory ports (DDR2) | core ↔ host | 2 × 80 = 160 | the 43 DDR2 client ports (590 bits) |
| C4 | Video out | core → host | 30 | `pix_*`, scaler output |
| C5 | Audio out | core → host | 50 | `audio_*`, `hdmi_snd` |
| C6 | Input (keyboard matrix, joysticks, buttons) | host → core | 80 | `app_keys`, `app_joy*`, keyboard pins |
| C7 | Connector pins (raw) | core ↔ host | per connector | `SLOT_*`, `IEC_*`, LEDs |
| C8 | Control and events | both | 16 | `app_freeze`, `app_pause`, `core_reset_req`, IRQs |
| C9 | Identity | core → host | over C2 | (new) |
| C10 | Debug tunnel | host → core | over C2 | `drive_dbg`, `dbg_*` |

### C1 Clocks and reset

The host owns every MMCM/PLL and BUFG (7-series DFX rule: clocking stays static). It offers a fixed set: `sys_clk` (100 MHz, the register bus), `mem_clk` (DDR2 user clock, the memory ports), and **two core clocks from a programmable MMCM** that the core asks for through the identity block (frequency table entry) and the app programs over DRP before the core is started. TRX64 uses them for the C64 clock (31.5 MHz family) and `sid2x`. Reset: `core_rst` (held during and after reconfiguration until the app releases it).

### C2 Register bus

One window of the app CPU's I/O space goes to the core as Gideon's I/O bus (decided, 2a): `address[23:0]`, `data[7:0]` both ways, `read`, `write`, `ack`, in `cpu_clk`. The core decodes its own registers (TRX64: the C64 windows, drive registers, GCR codec, palette, I²C, cart control, ...). One timeout in the host so a missing `ack` (grey box) never stalls the CPU. Interrupts: `irq[3:0]` core → host.

### C3 Memory ports

Two DDR2 client ports (decided, 2a) with one protocol (today's mig_arb toggle handshake, 32-bit write, 128-bit read, 26-bit address): **real-time** (highest priority, bounded latency: a Minimig's chip RAM, the REU's DMA) and **general** (drive, cartridge memory, traces, captures). The core arbitrates its own masters onto them. Each port is limited to the core's address range in DDR2 (host-side window, so a core cannot overwrite the app).

### C4 Video out — decision V1 below

The core delivers its picture as a pixel stream. Two possible cuts:

- **V1a, native video:** the core sends its native picture (C64: VIC colour index or RGB, raster x/y, a pixel enable in its own clock); the host scales it to 1080p. Then the scaler must know every core's raster: generic only as a "frame buffer in line RAM" scaler with parameters (source width/height, scale factor).
- **V1b, final video:** the core sends 1080p RGB with `hs`, `vs`, `de` on the host's `pix_clk` (the core scales itself, frame-locked as `vic_scaler` does today); the host composites its layers on top and encodes HDMI.

In both cases the host owns overlay (app menu text), pixel layer (RGB565 from DDR2, LVGL), HDMI encoder and the UDP video stream tap (overlay 401, pixel layer 548, encoder 621 LUT, 5.5 BRAM tiles: these move to layer 1). The C64 text layer (freeze menu from C64 RAM) stays in the core and is drawn into the core's picture.

### C5 Audio out

Stereo samples, 24 bits each, with a sample strobe at a fixed rate (48 kHz) in `sys_clk`; the host feeds HDMI audio, I²S and the UDP audio stream. (Today `audio_l/r` already have this shape.)

### C6 Input

The C64U's physical keyboard and joysticks are board hardware, so the host scans them (keyboard over I²C, joystick pins, restore key) and offers a generic state: `keys[63:0]` (the matrix as the keyboard wires it), `joy1[4:0]`, `joy2[4:0]`, `restore`, plus the app's injected keys merged in by the host. A VC20 core reads the same matrix.

### C7 Connector pins

The I/O buffers stay in the host (DFX rule); the core gets each connector as raw lines `i`, `o`, `oe` per pin: cartridge slot (address, data, control, transceiver direction/enable), IEC (ATN, CLK, DATA, SRQ, RESET), user-facing LEDs. The host's only job is a safe default (all `oe` off, transceivers disabled) while no core is running. About 60 pins × 3 = 180 bits: the largest channel, and core-specific by nature (a Minimig core would leave the slot idle).

### C8 Control and events

`core_run` (host → core: start after load), `pause`, `freeze`, `core_reset_req` (core → host, the C64's reset button), `busy`, and the event lines the app waits on. A few bits.

### C9 Identity and C10 debug tunnel

Fixed registers at the start of the C2 window: `core_id` (4 characters), `contract_version`, `capabilities` (which channels it uses, which clock table entry), build hash. The JTAG debug (`jtag_dbg`, host) reaches into the core through C2 as a second master, so the core's debug state (drive debug bus, engine, monitor) is read as registers, not as 256 parallel wires.

**Order changed (Alex, 2026-10-11 late, after runs 708/709):** "then like that and only the host first; when it builds, hold the core against it and the wiring step by step". H1: layer 1 alone with a grey box in layer 2 (`T79_HOST_ONLY=1`, today's edge), to see whether the host and the edge route without the core. H2: the edge as the contract's channels, grouped by function and speed (quasi-static settings as registers over C2, slow control over C2 or a few sideband lines, bulk over C3, real time on its own narrow lines), partition pins placed per group next to their partner in the host (`HD.PARTPIN_RANGE`), still with the grey box. H3: the TRX64 core against that host, one channel at a time (P3, P4, ... above). Partition pins are not flip-flops: a fixed routing point at the edge, the same for every core; register stages are an extra (2b).

What the phases do not change: the C64 blocks themselves (CPU, VIC, CIAs, SID, cartridge, 1541, ring engine, monitor); they get adapters at the edge.

Known risk: moving blocks between layers does not lower the total. On the 50T the design is about 25,000 LUT with the partition; the contract's gain is the edge (fewer partition pins, less DFX overhead, less congestion), measured after each phase.

- **ICAP loader in layer 1 (Claude, 2026-10-12, built, not yet run on the board):** the RISC-V loads layer 2's partial itself. `ultimate_sys.vhd` decodes `0x100606xx` as `r_icap` (was `r_none`), `top.v` instantiates `ICAPE2` (X32, `cpu_clk`, `CSIB = ~icap_we`, `RDWRB = 0`, every byte bit-reversed per UG470), static, outside `pb_l2`. Register map (byte accesses, acked at once like the other host regions):

  | Offset | Access | Meaning |
  |---|---|---|
  | +0x00 | R | ID byte `0x7A` (Gideon's FPGA-type byte on a Spartan; nothing in the app reads it) |
  | +0x04, +0x08 | W ignored, R 0 | Gideon's pulse/write: `W25Q_Flash::reboot` / `AT45_Flash::reboot` write a Spartan warm-boot sequence there; they stay inert, so the app cannot reconfigure this FPGA by that path |
  | +0x10 | W | one bitstream byte in file order, ignored while the enable is 0; every 4th byte completes a word (first byte = bits 31:24) and pulses it to the ICAP for one clock |
  | +0x14 | W / R | bit 0 = enable; writing it also clears the byte counter (0 to 1 also clears the word counter); read: bit 0 = enable |
  | +0x18..+0x1B | R | words pulsed since the enable went up, 32 bit, little-endian bytes |
  | +0x20 | W / R | app decouple request (cpu_clk): write bit 0; read: bit 0 = the app's request, bit 1 = the effective `core_decouple` (fed back from top.v). Cleared by the host reset |
