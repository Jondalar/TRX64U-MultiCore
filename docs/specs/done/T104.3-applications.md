## Current Contract and Status (2026-10-25)

**What holds.**
- An application is a `.u2a` of format 3 with `kind = app` and an `app_main` entry; a library is the same file with
  `kind = lib` and `lib_register`. One file may have both entries (a resident app that also contributes). (T104.1 D10)
- Residence: `transient` (loaded when opened, freed with everything it made when it returns) or `resident` (stays; may
  register menu nodes, file actions, settings, a poll). (T104.1 D10.3, Alex 2026-10-18)
- **New (Alex, 2026-10-25):** an application brings its own UI. The base gives it a container on the pixel layer; the
  app builds its LVGL widgets inside. The cartridge tools get a modern UI this way. The monitor (`trxmon`) keeps the
  80-column `terminal` widget.
- **New (Alex, 2026-10-25):** applications hook into the declarative menus like libraries (file actions, tasks, nodes),
  but are self-contained.

**What is built (step 1 of §4, 2026-10-25):** `LibLoader::run` calls `app_main(api, ctx)` with the action, the file and a reply
line; `LibApi` carries `sys`, `mem`, `ops` and `fs` (`libapi.h`). Every block of `mem` and every file of `fs` belongs to the app
that runs; a transient app is freed with all of it when it returns (S1, `tests/loader`). `fs` applies the `/flash` rule of
`fsif.h` itself; `CoreFs` gained `mkdir` and `rename` (board: `fm_fs.cc`). The board host runs `app_main` (`libboard.cc`);
nothing in the menu opens an app yet (D6, step 4).

**What is built (step 2 of §4, container and dialogs, 2026-10-25):** `api->ui` (`appui.cc`): `open` / `run` / `close` / `theme`
and the six dialogs of D4, on the real `ui.cc`, `trxview.cc` and LVGL; `LibLoader::set_ui` closes a window an app leaves open before
its image goes. S2 green in `tests/coreapp/render` (`appui_bench.cc`). Not yet: the board's `AppUiPort` in `run.cc` (it comes with
the menu hooks of step 4, which open the first app), the LVGL import path of D8 (waits for Q2).

**What is built (step 3 of §4, jobs, 2026-10-25):** `api->job` and `ui->post` (`appjob.cc`, on `OsPort`): a task per job (4 slots),
progress drawn by the base as a strip above the footer, `cancelled`, `join` (on the menu task it keeps posts and the strip running).
An accepted close and the end of an app stop every job and wait for it before the window or the image goes. S3 and S4 green in
`tests/coreapp/render/appjob_bench.cc` (threads).

**Not proven yet:** none of steps 1-3 has been compiled for RISC-V or run in ue2emu; so far only the native benches (§4, first
paragraph).

**What is open:** Q1 (the overlay over the running core), the monitor's screen on a breakpoint stop, the native benches (S6, S9), the
board (S8); see the log of 2026-10-28.

Open (one line, as in the TODO table): Done 11-15 (Alex: in builds for weeks)

## 1. The problem

**Who:** Alex at the machine; the people who write applications (today TRX64-FW, later others); the MultiCore session
that owns the base.

**What happens today.** Gideon's applications (format 2, ABI 2.1, `apps/ultimate/software/app_loader/app_api.h`) get a
set of tables (`sys`, `mem`, `ui`, `fs`, `c64`, `media`, `config`, `diag`, `net`, `trx`, `ring`) and draw on his
character screen (`ui->screen_open`, `win_puts`, 40 or 80 columns of text). The generic core application cannot run
them: its loader reads only format 3 / ABI 3 (`libload.cc:123-140`) and never calls `app_main`. The four applications
of TRX64 Ultimate (`trxmon`, `trex_crt`, `softboot`, `unzip`) therefore have no home in the generic application, and
the monitor is on the day-1 list (ADR-0057 point 7).

**Why not port the character screen.** The generic application draws with LVGL on the pixel layer; there is no
character screen. Emulating Gideon's `win_*` calls on LVGL would carry his 40-column text design into the new UI, which
is what ADR-0057 point 3 rules out, and Alex wants the cartridge tools modern.

## 2. Design

### D1 One container format, two roles (as T104.1, no change)

`kind`, `residence`, `register_offset`, `main_offset` of `U2a3Header` stay. The manifest (format 2 JSON, carried
unchanged) keeps the application's id, name, version, file types and tasks; the loader turns them into menu entries
(D6).

### D2 The service table `svc` (ABI 3.0)

`app_main(const Svc *svc, AppCtx *ctx)` and `lib_register(const Svc *svc, LibRecord *out)` both get the same table
(`LibApi` grows into it; `struct_size` and `abi_major/minor` stay its first fields, so the check of T104.1 D11 holds).
Groups, each a sub-table with its own `size` (the `U2P_HAS` rule of format 2: a field is there when the size covers it):

| Group | Contents | Source of the idea |
|---|---|---|
| `sys` | log, `ms()`, `sleep_ms()`, version, the core's name and capabilities | ABI 2 `sys` |
| `mem` | `malloc`, `free`, `realloc` from the app's own heap account (freed when a transient app ends) | ABI 2 `mem` |
| `ops` | `call(name, args, result)`, `state(name)`, `subscribe(event, fn, user)` on the registry (`ops.h`) | T104.1 D1 |
| `fs` | open/read/write (at a 64-bit offset, no seek)/size/sync/close, `list`, `stat`, `load`, `save`, `mkdir`, `remove`, `rename` on `CoreFs` (T104.1 D16); the `/flash` rule of `fsif.h` applies; files a transient app leaves open are closed | ABI 2 `fs` |
| `ui` | the container (D3), dialogs (D4), the terminal widget (D5), `post(fn, user)` to run code on the UI task (D7) | new |
| `job` | `start(fn, user)`, `progress(h, value, total, text)`, `cancelled(h)`, `join(h)` (D7) | new |
| `machine` | the core's register window (`CoreIo` page reads/writes), RAM window reads/writes while frozen, `reset`, `freeze` state | ABI 2 `c64`, `CoreIo` |
| `net` | listen/accept/recv/send/close/wait/peer | ABI 2 `net` (trxmon) |
| `trx` | the TRX debug block: acquire/release, announce RPC port, `detach` (keep running with the menu closed), `stop_requested`, `ui_request` | ABI 2 `trx` |
| `ring` | Timewarp ring and trace | ABI 2 `ring` |

A group the core does not have is a null pointer (the `trx` and `ring` groups exist only on a core whose ID block
says so); the app checks before use, as with `U2P_HAS`.

### D0 Declarative app UI (Alex, 2026-10-26) - supersedes D3 and D8

Alex, 2026-10-26, when asked how apps reach LVGL: "wait ... I assumed the app brings its UI declaratively and the core
generic app part renders it" - and to the summary below: "Yes, let us try that, that would be a very clean architecture"
(both translated). Read back against his origin quote ("cope well with the declarative UI approach"), D3 and D8 as written
on 2026-10-25 (the app gets an LVGL root and calls LVGL directly) were a misreading.

- An app brings a **UI description** (TOML compiled at pack time into a record, the same way as a core's or library's menu
  description, T104.1 D9/D12), never UI code. The generic core application renders it with its own widgets (lists, settings,
  dialogs, progress, the `terminal` character grid, ...).
- The app's behaviour is **operations, state values and events** in the registry (T104.1 D1), as for libraries; widgets bind
  to them by name.
- **No app calls LVGL**; the app format carries no LVGL headers or import table. A widget the application lacks is added to
  the application, not to an app.
- Q1 holds: a description may mark a container as an overlay that stays open over the running core (first case: the monitor
  as a `terminal` overlay on the TRX64 core, its content written through an operation).
- **To rework:** `ui->open` / the LVGL root of D3, D8's LVGL import path, and what steps 1-3 built on them; the rest of the
  runner and `svc` (sys, mem, ops, fs, job) stays.

### D3 The container: the app's own UI (superseded by D0, 2026-10-26)

- `ui->open(const AppWinSpec *spec)` returns an `lv_obj_t *` root that the base created on the pixel layer: the content pane of
  the application's frame (top bar with the spec's title, footer "R/S CLOSE"). The menu view is hidden while the container is up.
  One window at a time. `ui->run()` takes the keys and renders until the window closes (1: the person closed it, 0: the app did).
- The app builds any LVGL widgets under the root. **LVGL is called directly** (D8): the app is compiled against the
  base's LVGL headers and `lv_conf.h`.
- **Keys:** the base keeps RUN/STOP, the menu button, F10/SCROLL LOCK (they ask the app to close: `on_close` callback;
  the app may refuse, each time, with a reason the base shows, e.g. during a flash write); every other key, ESC and DEL
  included, goes to the app: to `on_key` when the spec has one, else to the root as `LV_EVENT_KEY` with the key as parameter.
- **Theme:** `ui->theme()` returns the skin's fonts and colours (`TrxTheme`, `app/view/trxview.h`), so an app looks like
  part of the application without copying its constants.
- **Speed rules (T93):** no D-cache; build pages once, change only what changed, drain keys before one render. The
  base renders (`ui_render_now`) after the app's key handler returned; an app never calls `lv_refr_now` itself.
- **Close:** when `app_main` returns, or after `ui->close()` (from a key handler: after the handler returned), the base deletes
  the root (and with it every child), then frees a transient image. Objects an app made outside the root are its own fault:
  counted, named in the log and removed with the screen.

### D4 Dialogs the base provides

`confirm(title, text)`, `choose(title, items, n, sel)` (-1: cancelled), `text(title, buf, max)`, `pick_file(start, ext, out,
outlen)`, `pick_folder(start, out, outlen)`, `message(title, text, bad)`. Modal on top of the container (the top layer), drawn by
the base in the current skin, with a key legend; RUN/STOP and ESC cancel. A list moves its selection by restyling two rows and
builds its rows again only when the window scrolls (T104). The pickers list `..`, the folders, then the files whose name ends in
`ext` (any case); `pick_folder` has "[ use this folder ]" first.
They replace ABI 2's `popup`, `confirm`, `menu`, `string_input`, `path_input`.

### D5 The terminal widget (for the monitor)

`ui->term_open(cols, rows)` gives a character grid widget (`terminal`, T104.1 D7) with `puts(x, y, s, colour)`,
`clear`, `cursor`, `scroll`, reverse cells, and the C64 character set or a monospace font by skin. `trxmon` keeps its
80 x 40 layout and its key handling (`getch_monitor` becomes the key events of D3).

### D6 Hooking into the menus

From the manifest (`filetypes`, `tasks`) and, for resident apps, from `LibRecord` nodes/file actions:
- a file type entry ("Write to Cartridge" on `.crt`) opens the app with `ctx->action` and `ctx->file`;
- a task ("Dump Cartridge" in the core's actions area) opens it with `ctx->action`;
- placement follows T104.1 D8 (area / tab / group keys, order key, then load order) and T104 point 3 (stable numbers
  independent of load order).

### D7 Long work and the UI task

LVGL runs on the menu task only. An app's handlers run there. Work that takes longer than one frame (a 30 s flash
write, a dump) runs as a **job** on a worker task: `job->start(fn, user)`; the job reports `progress`; it touches LVGL
only through `ui->post(fn, user)`, which the menu task runs before its next render. `cancelled()` tells a job that the
person asked to stop; the job decides whether it can (a flash write may not). The machine lock (`core_lock`) is taken
by the job for its register traffic, as an operation does.

### D8 How an app reaches LVGL (superseded by D0, 2026-10-26)

**Proposed: an import table in format 3.** The base exports a fixed list of LVGL functions (and the `svc` entry) by
name; the packer writes every undefined symbol of the app as an import (name, word offset); the loader resolves each
against the base's export list and refuses the file when one is missing, naming it. The export list is part of the
ABI (`base >= 3.x`), LVGL's version is part of the dependency (`needs lvgl >= 9.6`). Alternative: a table of function
pointers in `svc->lv` plus a header that maps `lv_*` to it (no format change, but every LVGL call an app wants must be
added to the table by hand). See §6 Q2.

### D9 What each of the four applications becomes

| App | Role | UI | Needs |
|---|---|---|---|
| `trex_crt` | transient app | own LVGL UI in the container: bank map, progress, results | `machine` (cartridge registers, RAM window), `fs`, `job`, dialogs; the TRX slot block |
| `trxmon` | resident app | `terminal` 80 x 40 | `net`, `trx`, `ring`, `machine`, `job` (the RPC server task) |
| `unzip` | transient app without a window | dialogs, progress | `fs`, `job` |
| `softboot` | transient app without a window | confirm, progress | `fs`, `sys` boot request (the boot ROM's request block) |

**trxmon is static, not an app (Alex, 2026-10-29: "a"):** of the two monitors built on 2026-10-28 (linked into the TRX64U
application, full layer 80 columns as today; and the loadable `trxmon.u2a` in the menu frame on branch `t104-3-loader`),
the linked one stays, reached by F8 Expert / hotkey M, with the RPC on TCP 4312. The `trxmon` row above no longer
applies; `trxmon.u2a` is dropped and its RPC server moves into the linked monitor when the branches merge.

### D9.1 TREX CRT screen contract (Alex, 2026-10-28)

Alex asked for new TREX CRT screens which match the established LVGL UX. The executable XML prototypes are
`docs/lvgl_ui_project/screens/crt_*.xml`; the full interaction and binding contract is
`docs/lvgl_ui_project/TREX-CRT-UI.md`. TREX CRT is not implemented in the separate terminal-theme prototype.

The application opens in a full-screen **app mode**. It does not show the global F-key area rail because the existing
tool operations already own F1/F3/F5/F7. Four visible number tabs remain stable: Home, Dump, Flash and Inspector. Cursor
and Return are a complete route, C64 left-arrow goes back, and R/S closes unless the current hardware step cannot safely
stop. A refused close is visible as `R/S LOCKED` with the reason.

Eight visual states cover the current implementation without changing its behavior: chooser, dump, flash, destructive
write confirmation, whole-EF3 erase confirmation, progress, result and Inspector. Whole-cart erase remains a secondary
Flash/F7 menu action rather than a tab, retains the implementation's two-confirmation boundary, and names the system area,
directory, every slot and type 90 recovery requirement. Source file, physical cartridge, EF3 slot and erase scope are
visible together before a write. Bank cells bind to the existing per-bank states; progress binds to the job
phase/value/total and cancellable state. The app remains declarative under D0 and calls no LVGL API.

## 4. Order of building

**How every step is proven (Alex, 2026-10-25: "Du solltest es lokal compilen, mit dem Emulator testen, bis eine vollwertige App da
ist, wie fürs board und als letzter Schritt geht es aufs Board"; translated: compile it locally, test it with the emulator until a
complete app is there, as for the board, and the board is the last step):** the RISC-V image is built locally in the build container
(`tools/build_coreapp.sh`, image `u64-build-env`), booted in ue2emu (`run --firmware <coreapp.elf> --board c64u --caps 25E40202`,
monolith profile of T104.2) and driven there until the app works end to end as it would on the board. The native benches stay as
gates; they are not the proof. Nothing is pushed to find compile errors (the MultiCore CI has one builder). The board comes last,
with Alex's OK (S8).

1. Runner and `svc` v0 (`sys`, `mem`, `ops`, `fs`), S1.
2. Container, dialogs, theme, S2; the LVGL import path (D8), S5.
3. Jobs and `post`, S3, S4.
4. Manifest -> menu, S6.
5. `unzip` and `softboot` on ABI 3 (small), then `trex_crt` with its new UI, then `trxmon` with `terminal`, `net`,
   `trx`, `ring`; S7 in the emulator.
6. Hand-over to the MultiCore session; S8 when Alex opens a board session.
