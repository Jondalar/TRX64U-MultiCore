## §1 The problem

- **Who:** Alex at the board, and the next change to the c64scpu core.
- **What happens today:**
  - Master's Boom in play stutters and then freezes on the c64scpu (T241 §5, board 2026-11-19 and 2026-11-21). The S2
    change (interrupt decision, RTI) did not change the symptom.
  - After a reset the c64scpu leaves `$02a6` = 0 (NTSC) on a PAL machine. CIA1 timer A then has the NTSC latch
    `$4295` (period 17046 instead of 16422), and the jiffy clock runs 3.7 % slow.
  - The causes were looked for one guess at a time (Alex: "poking around").
- **What is known (T241 §5, read from code and measured):**
  - Boom plays at 1 MHz, emulation mode, SuperCPU registers off, mirror everything (`$d077`). Raster interrupts at
    lines 87, 145 and 217. Its dispatcher reads `$d012` 62 cycles after the interrupt sequence starts and needs line
    146: no margin on a stock C64.
  - The CMD ROM's reset writes `$d07b` (20 MHz) before CINT. CINT's PAL test needs its screen clear to end at line
    256 or later.
- **The parts:**
  - **P1** PAL or NTSC: what the VIC is, what the reset decided, and the KERNAL's PAL test at 1 and 20 MHz.
  - **P2** The cycles of every opcode at 1 MHz.
  - **P3** Code at 1 MHz with cache hits and misses, with and without sprite DMA, against a C64.
  - **P4** The point where the CPU takes an interrupt, per interrupted instruction.
  - **P5** Boom's raster chain: the line-145/146 edge in four conditions, and the chain over 500 frames.
  - **P6** 20 MHz: speed, I/O reads, writes to the C64 bus, writes held by badlines, cache misses; the VICE programs.
  - **P7** Which writes reach the C64 RAM, per mirror mode and speed; bursts, RMW, 16-bit stores, MVN; the REU programs.
  - **P8** The ROM shadow and the `$01` banking at 1 and 20 MHz.
  - **P9** One permanent board-test page for the results.

## §3 Decision

- **D1:** our own programs, 64tass, in `tests/c64scpu/`, with the `.prg` files committed (the board needs no assembler).
  The shared code is `lib.inc`. Each program checks its own values and prints `n checks, m failed`.
- **D2:** time is measured in PHI2 cycles by CIA2 timers A and B chained (32 bit). The same count works at 1 and 20 MHz.
  Where both ends of a measurement can use the same instruction (`sty $dd0e`), they do, and no calibration is needed.
- **D3:** the C64 RAM is read through the VIC (scpu7): sprite 0 shows the test byte's block, sprite 1 has `$ff` at the
  test byte's place; `$d01e` bit 1 tells whether the byte in the C64 RAM is not 0. The CPU itself only sees its own RAM.
- **D4:** expected values: the board's C64 core trx64g (S0, 2026-11-21). The c64re runtime gave the first values; it
  differs from trx64g in two places. scpu4: one cycle more in every row, because its CIA is a 6526; trx64g and the
  c64scpu use the 8521, whose interrupt comes one cycle earlier (`cia_interrupt.sv`, `ir_set_prev` against
  `ir_set_phi2`). scpu5 condition d: one cycle less (the sprite DMA). Measured on the board wins (Alex's rule), and the
  c64scpu has the same CIA as trx64g. For 20 MHz and the mirror there is no C64: real SuperCPU values from
  VICE-testprogs, a model checked against them (the badline writes), and the mirror windows of VICE's `scpu64mem.c`
  (lines 81-86) as `scpu_mem.v` has them.
- **D5:** VICE-testprogs is not copied into the repository. `vice.sh` fetches its SCPU programs at a pinned commit
  (4049366d) into `~/.cache/trx64-vice-scpu/`; `put.sh` copies them to the board with ours.
- **D6:** `put.sh` takes the board's address from `BOARD`; no address is in the repository.
- **D7 (P9):** the page is the existing artifact "Board Test", recycled: the old results are cleared, the cards are this
  suite's. Alex: "one permanent page that is recycled again and again". The other board-test pages are deleted, each
  with Alex's go.
- **D8 (P5): the phases of the main loop in scpu5.** Between two interrupts the main loop runs one frame minus the
  handler, so its phase at the next interrupt moves by that difference (mod 7 for the 7-cycle spin). The first version
  added 0 to 7 cycles per interrupt: the phases then follow a quadratic series that meets only some of the 7 phases,
  and which ones depended on the start (2026-11-21: condition c gave 79/82 with one build, 78/80 with the next, on
  trx64g and on c64re alike), and the handler's length depended on the read (145 or 146). Now the handler takes the
  same time for both reads; 14 interrupts per K: the first 8 move by one constant step, the last 6 by a step one cycle
  shorter. Unless a step is 0 mod 7, a series of 7 meets every phase, and the two steps cannot both be 0. The soak does
  the same in blocks of 7 frames. Three code layouts gave the same values on c64re after the change.
- **D9:** the check counters are 16 bit: scpu2 makes 402 checks, and an 8-bit counter showed 146 (2026-11-21).
- **D10:** `rest.py` runs the programs over REST from the Mac and prints their screens. A memory read is a DMA on the
  board's C64 cores: it holds the CPU, so `rest.py` reads only after a program's run time (2026-11-21: reading scpu5's
  screen every 2 s gave other edges).

## §5 Built

- **2026-11-21, branch `t241.1-scpu-suite`:** `tests/c64scpu/` with `lib.inc`, `scpu1_env` to `scpu8_shadow`

- **S0, c64re part:** every program run in a c64re sandbox, model c64-pal: 0 failed in all eight (scpu6: "no
  supercpu"). scpu1 also on c64-ntsc: 0 failed (VIC 17095 cycles and 263 lines, `$02a6` = 0, timer A 17045). The
  screens are in `ref/stock_pal.txt`.
- **Measured on c64re while building (the values in the programs):**
  - scpu4: the lowest latency is 12 for every sled but `bne taken`, which has 13.
  - scpu5: edge `all` at K = 62 (a), 62 (b), 82 (c), 43 (d); the soak at K = 43 gives 0 early and 0 out of order.
  - scpu1: `$e518` lasts 40550 cycles at 1 MHz (more than two frames), so at 1 MHz every start line gives PAL.
- **The PAL value of test_badline (scpu6):** one write per PHI2 cycle and none in a badline's 40 DMA cycles, from line
  255, gives 69536 for NTSC; the real NTSC SuperCPU gives 69538 (`$10fa2`, VICE-testprogs readme). The same model
  gives 68776 for PAL; scpu6 expects 68778 within 30.
- **Timed loops:** in scpu3 and scpu6 the loads sit in one page (`.align 256`), in scpu5 the spin is aligned, so no
  branch crosses a page and the cycles do not depend on where the code lands.
- **Review (agent, 2026-11-21) and the fixes:** scpu2 waits for line 250 after the screen goes off (no badlines in the
  first cases); scpu2, scpu4 and scpu5 measure in mirror mode `$c7` and `$c0` (Boom's); scpu3's memory load uses
  `$cb00` (it shared a cache index with the code), and scpu3 calibrates before every load; `head` sets `mstyle`; a
  20 MHz part that ran at 1 MHz (speed switch) prints a line and counts one failed check (`slow20`); `build.sh` and
  `vice.sh` write through a temporary file; `put.sh` skips an empty glob; four comments corrected.
