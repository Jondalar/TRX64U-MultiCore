## §1 The problem

- P1 **Sublines.** Two-line rows (name over a small grey line) halve what fits at 480p and mostly repeat the same text. Inventory
  2026-11-11 (row counts at 480p from the code's row heights, with / without): core F3 Library 5/8 (size, "Folder", "Medium"),
  core F5-F8 media slots 7/10 (mounted file or "No image"), core settings with a reason 6/8 ("Not available now", a path), core flat
  lists 9/15 (key hint, the same on every row), host F1 boot menu 3 at 480p (path + version), host config overlay (media + " - all settings").
- P2 **Row gap.** Even one-line rows are spaced too far apart (Alex, mock-up at pitch 29 px at 480p).
- P3 **Scrolling.** The list scrolls only when the selection reaches the first or last visible row; the next rows are not seen ahead.
- P4 **Paging keys.** Lists page with +/- (PAGEUP/PAGEDOWN, `menuctl.cc:1374`, `:1407`), but the foot never names them.

## §2 Scenarios

Proof = the real app in ue2emu (`tests/ui` features, `I save the picture`) at 480p and 1080p, ux-review PASS (skill R5), plus
the R1/R2 geometry asserts.

- S1 Library: one line per entry, the size right-aligned as the value, no "Folder"/"Parent folder"/"Medium" text; a 31+ character
  name is cut with an ellipsis and never covers the size.
- S2 Media slots: the mounted file is the row's value, cut in the middle when long; "No image" is the value of an empty slot.
- S3 Settings and flat lists: no subline; a reason ("Not available now", why) or a key hint shows in the foot for the selected row only.
- S4 Host F1 boot menu and config overlay: name only; version / "all settings" as a badge; the selected entry's path in the foot.
- S5 Row pitch reduced on every list (value chosen with Alex from emulator pictures); at 480p the Library shows more than 8 entries.
- S6 Scroll margin: moving down, the list scrolls while 2 rows are still below the selection (and up likewise), except at the list's
  ends; the selection is never on the first/last visible row unless the list ends there.
- S7 Every list longer than one screen names its paging keys in the foot (e.g. "+/- PAGE"), in the same words in host and core app (the host writes its foot words in lowercase, "+/- page", since 2026-11-16; the core app keeps capitals).
- S8 Board: Alex looks at F3, F5 and the host menu at 480p and 1080p.

### File Browser, n entries (2026-11-16, GitHub #93, branch browser-n)
No spec owns the host F3 browser's listing as such (T192.2 moved it to `host_core_nav` and is done; T209 D7 owns its paging keys), so the fix sits here, next to the paging fix above. Report, Jondalar/TRX64U-MultiCore #93, a tester, 2026-11-16 (translated quote): "I have an USB folder with 784 snes games, all zipped. If I browse with the host f3 file browser and use +/- to page through the list I can only page to about 200 files. It just stops scrolling." Expected: works with n files.

**Cause.** `host_core_nav.h` `HC_BR_MAX 200` sized a fixed `HostDirEntry bl[201]` in `HcNav`; `hc_browse_load` asked `hostfs_list` for `HC_BR_MAX - bn` entries and `hostfs_list` stopped at `max` without saying so (folders first, then files in directory order, so the cut fell on the files). `hostui.cc` `BR_MAX 200` was a dead define (no use) and is removed.

**Decision (built).** The browser's list is heap, not a fixed array: `HcNav.bl` is a pointer, 256 rows first (`HC_BR_START`, kept between loads), and `hc_browse_load` grows it when the folder is longer: `hostfs_list_n` reports `*total`, the core then sizes the buffer to the whole folder, bounded by a quarter of the free heap (`HcNavPlatform.free_heap` = `media_free_heap()`, `sizeof(HostDirEntry)` = 72 bytes a row) and `HC_BR_HARD` 32768 rows, and reads again (a long folder's buffer is freed at the next load first, so the budget is measured against what is free then). Sorting is unchanged and stays whole: the lister reads the entire directory, folders first, then the files in the order the medium gives; the buffer takes all of it. What still does not fit: `HcNav.bmore` = the entries not held, shown as one more, last row `... The parent row stays row 0. The core application's own file browser (coreapp, Library) was read for the same cut: see the report below.

*Decision: a list that grows from the heap, like the host's, not a windowed read.* `FsEntry` is 272 bytes (T180 #38), so 512 rows are 139 KB, held inline twice (Library and pick) whether used or not. The core application's heap is `configTOTAL_HEAP_SIZE 0x7A0000` = 7,995,392 bytes (`ucHeap` in `coreapp.elf`; `xPortGetFreeHeapSize`, shown on F4 as "Heap free"); free at the Library: not measured (the emulator script has no shifted key for the F4 "Heap free" line); the budget is read live (`xPortGetFreeHeapSize`), so with the whole heap free it is a quarter of 7.6 MiB = about 7,300 entries, never the 512 of the array. A windowed read needs an offset (and a total) in `CoreFs::list`, and every lister behind it (FAT directory through `FmFs`, disk images, FTP, Online) would have to honour it; the FAT lister reads the whole directory into a `FileInfo` list on every call anyway (`FmFs::list_t`), so a window costs one full directory read per page or key, and the Library re-reads its folder every 2 s (`relist`). The growing list reads the folder once per growth and keeps its buffer. Smaller change, no lister touched.
*Built:* `coreapp/src/listgrow.h` `ListGrow::read`: 512 entries first (`START`), and while the folder fills the buffer a new buffer of twice the size is taken and the folder read again, as long as the added size is at most a quarter of the free heap (`xPortGetFreeHeapSize`, wired in `run.cc`) and at most `HARD` 32768 entries; what the budget refuses sets `more`. `CoreFs::list` has no total (the listers cannot all give one), so the core app's line has no count: `... more not shown`. Library: `FileMgr::list` / `marked` are heap (`ensure_list`), `more` shows as the last row (`MenuCtl::rows`, `browse_row`, `row`), `move()` keeps the cursor on the last entry (R10). Folder pick: `pick_list_` is taken while the pick is open and given back when it ends (`pick_release`); when the budget cut it, the pick's status line says "- more entries are not shown" (no extra row: the pick's rows are actions). Search: reads each folder with the same growing buffer; a cut folder makes the answer say "(stopped: refine the name)". A folder with exactly as many entries as the budget allows is shown as cut (a full buffer is the only sign).
