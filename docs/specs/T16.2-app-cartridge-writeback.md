# T16.2 — Writable cartridges: hardware interface and the app's write-back

**Status:** draft spec, 2026-10-01. Nothing built. Depends on T06 (CRT into DDR2, done),
T12 B (machine pause, simulated). Touches T20 (snapshots) and T21 (monitor). TODO.md
row T16.2 is the task; this document is the design.

**Revision 2026-10-01 (hardware cut to the minimum).** Two decisions change the hardware
part of this spec: (1) the cartridge model becomes icepi's own (`cores/icepi/
c64_cartridge.v` with `c64_flash_amd.v` and `c64_eeprom_93c86.v`) in place of
`cart_slot`/`cart_logic` (patch 0030); the swap is its own task; (2) write-back is driven by
the app through interrupt and timer, and the hardware gives only what software cannot do.
The resulting hardware, its registers and its cost are in
`docs/specs/ARCH-lean-state-access.md` §7.4, §10 (page 0x4xxx) and §11. In this document
the parts that are gone are marked **(see ARCH)**; the app side (§7-§8), the per-type data
(§6) and the behaviour list (§9) stay.

**One sentence:** our cartridge emulation (icepi's own model, swapped in) has one flash command responder and a
93C86 EEPROM, both reporting every change as an event to the
Ultimate app (trex/main), which applies flash commands to the image in DDR2 with its own
CPU stores, keeps a dirty map, and writes the changed packets back to the CRT file
the cartridge came from — the contract of CWBI (TREX-PROP-001 Rev D), with the flash part
and chip layout taken from the mapping descriptor record (TREX-PROP-002 Rev A).

**Sources and marking.** Proposals: `docs/specs/PROP-001-cartridge-writeback-interface.md`
(**[CWBI §n]**) and `docs/specs/PROP-002-cartridge-mapping-descriptor.md` (**[PROP-002 §n]**).
Copied or adapted code/concepts are marked **[IcePi: file]** (`icepi-zero-c64`, branch
`easyflash-writable`), **[TRX64: file]** (`/path/to/Development/C64/Tools/TRX64/`) or
**[trex/main: file]** (`1541ultimate`, branch `trex/main` = 90f301ce). Hardware facts are
from this repo's code, paths relative to its root.

## 2. Goals and non-goals

### Goals

1. A C64 program that writes its cartridge's flash with **its own** code (stock EAPI, a
   game's own AMD routine, the Protovision TwoMegabyter API) sees a real flash part:
   autoselect ID, DQ7/DQ6/DQ3 status, program, sector and chip erase with the datasheet
   sector map. Same for the GMod2 93C86 EEPROM.
2. Every change reaches the CRT file it was loaded from without the menu, atomically,
   within `T_QUIET` (2 s) of the last write; before a cartridge change, reset, power-off.
3. The image is never changed behind the firmware's back: one writer path, so dirty
   tracking is exact and no hash is needed (CWBI §4.7).
4. Types: EasyFlash (32), GMod2 (60, flash and EEPROM), MegaByter (86), TwoMegabyter (87),
   C64MegaCart (61/88, §6.5); EasyFlash XL (232) only if open question 5 says yes.
5. Consistent with T20: the responder FSM and EEPROM state are part of the machine state;
   `.c64re` `cartFlash` / `cartState` are filled faithfully.

### Non-goals (T16.2)

- Physical cartridges on the port (T16), shadow mode + journal for real carts (T20 §1).
- The generic bank/mode decode of PROP-002 §3-§7 in hardware. T16.2 uses PROP-002's
  record format and its `layout` and `flash` fields; banking stays per type in
  `cart_logic.v`. The generic decode is its own task (open question 13).
- SPI-flash carts (GMod3/GMod4), freezer RAM persistence (volatile on the real thing).
- The UCI (T28). With CWBI the original EAPI runs; nothing needs `$DE1C`.

## 3. Design overview

```
 C64 bus ─► icepi c64_cartridge (banking per type) ─► c64_flash_amd (one pending op, BUSY until ACK)
                     │                                        │ evt cmd/chip/addr/data
                     │ c64_eeprom_93c86 + RAMB18 ── written ──┤
                     ▼                                        ▼
           image in DDR2 (T60 §7: 0x1000000)         IRQ cause + WR_COUNT (ARCH §7.4)
                     ▲                                        │
                     └── CPU stores (AND / $FF), CART_INVAL ◄─ app ISR: apply, ACK, dirty map,
                                                               LOG_PUT for T20 ─► write-back to the CRT file
```

| # | Decision | Why |
|---|---|---|
| D1 | Responder = **icepi's own** `c64_flash_amd` inside icepi's `c64_cartridge` (swap of patch 0030), not a responder behind `cart_logic` | User decision 2026-10-01; the model is the one verified on IcePi hardware (CWBI §2.7) and already carries the per-type address case. |
| D2 | CWBI `EXECUTE` semantics kept: the chip stays `BUSY` until the app acknowledges | Contract identical to IcePi and to the CWBI acceptance tests (§9.1 there). Sector geometry stays data in firmware (CWBI §4.3). |
| D3 | The app applies program/erase itself with **CPU stores** into the image (AND for program, `$FF` for erase), then ACKs; then one `CART_INVAL` strobe (the swap keeps `cart_fill`'s line cache). No hardware executor, no hardware dirty map. | User decision: hardware only for what software cannot do (ARCH §7.4). The ISR performs every flash change, so its dirty map is exact; T20 gets the change through `LOG_PUT` (ARCH §7.4). |
| D4 | EEPROM in its own RAMB18, exposed at Gideon's window 0x1004C000 with his semantics, `CAPAB_EEPROM` set | trex/main's GMod2 code (`get_eeprom_*`, `find_eeprom`, `eeprom_chunk`, autosave) runs unchanged. CWBI §6.5.3: EEPROM write data never comes from the C64 data bus. |
| D5 | Write-back unit = one CRT CHIP packet; dirty granularity = 8 KiB of image, kept in software | Every listed type stores 8 KiB packets except TwoMegabyter (16 KiB = two bits). Sector erase marks the packets it covers. |
| D6 | File update = journaled in-place patch when every dirty block has a packet in the file; full rewrite (`.tmp` + rename) otherwise | In-place is fast for 2-4 MiB images; the journal makes it atomic (§7.4). Full rewrite is today's proven path. |
| D7 | The legacy `$DE09 := $65` path is off when CW is present; the EAPI swap is skipped | CWBI §7.4. The image's own EAPI runs; `write_image` no longer has to restore it. |

## 4. What the hardware must expose to the app

### 4.1 Functions (revised: minimum, see ARCH §7.4)

1. **Flash part configuration** (unlock addresses, mask, IDs, enable): write-only registers,
   written at CRT load (the ID must be answered inside the bus cycle right after `90`,
   CWBI §7.1.4).
2. **The pending operation** (`evt_cmd`, chip, image address, data) of `c64_flash_amd`:
   one at a time, the chip stays `BUSY` until **ACK**.
3. **EEPROM** in a RAMB18 behind Gideon's window, with his dirty byte.
4. **`WR_COUNT`**: +1 per flash operation and per EEPROM write; it is also the EEPROM
   seqlock.
5. **Interrupt** with two causes: flash operation pending, EEPROM written (one ITU line
   shared with the rest of the TRX block, ARCH §7.7).
6. **`CART_INVAL`** (all lines of `cart_fill`'s line cache, which the swap keeps).
7. Mapper, responder and 93C86 state for snapshots and the monitor: state-bus chip "cart"
   (ARCH §5.4), not CW registers.

Removed **(see ARCH §7.4)**: chip records ×4 with address modes, event queue (16) with
OBSERVE/NOTIFY, executor (`PROGRAM_AND`/`FILL`/`INVAL`), dirty bitmaps with latch-and-clear,
`GEN`/`QUIET_MS`/`QUIET_THRESH`/`CNT_*`, `HOLD`, readback registers
`CART_TYPE`/`BANK`/`MODE`/`FSM`.

### 4.2 Register map

Page 0x4xxx of the one TRX IO block at 0x101A0000 **(see ARCH §10)**. The EEPROM window
0x1004C000 stays Gideon's (D4). The block "CW" at 0x101B0000 is dropped.

### 4.3 FPGA cost

**(see ARCH §11)**.

## 5. Responder integration (now inside icepi's `c64_cartridge`)

The responder sits where icepi put it (D1), so §5.1-§5.4 of the first draft (inputs from
`cart_logic`, chip-address modes HALF/LINEAR, read override in `cart_slot`) are replaced by
the swapped model **(see ARCH §7.4)**. Requirements that stay and that the swap has to
meet:

- `strobe` in the CPU half only: VIC (phi1) fetches read array data, never status
  [TRX64: `cart.rs` `vic_romh`].
- Bus-DMA cycles of the app (`ext_dma_busy`, patch 0050) do not change the responder: no
  state change, no DQ6 toggle (§9 item 7).
- A read in a non-`READ` state is answered inside the bus cycle (CWBI §6.5.1).
- Writes in `READ` state change nothing (CWBI §6.3.5); `cs` only where the board's flash
  mode maps the chip (CWBI §4.4).
- The image is read through `cart_fill`'s line cache with a fixed answer time; a miss never
  stalls the machine on DDR2 (decision 2026-10-01, ARCH §14 item 6; done by the swap).

### 5.5 EEPROM (`c64_eeprom_93c86`)

Vendored `c64_eeprom_93c86` [IcePi: `gateware/c64_eeprom_93c86.v`] with its `mem_*` port on
port A of a RAMB18 (one-clock ack) instead of SDRAM cycles. CS/CLK/DI from the GMod2
register (`$DE00` bits 6/5/4), DO read at `$DE00` bit 7 — the bits of PROP-002 §6.3. It
applies writes itself and keeps its own ready/busy (CWBI §6.4.1); per completed write it sets
the Gideon dirty byte, increments `WR_COUNT` and raises the "EEPROM written" interrupt
cause (no event queue, ARCH §7.4).

### 5.6 Executor

Removed **(see ARCH §7.4)**: the ISR applies program and erase with CPU stores (D3).

## 6. Per cart type: layout, part, sectors, write-back unit

With icepi's model (D1) the "Chip record" rows below no longer configure address modes:
the model has its own per-type address case, and the rows only give the part data the
firmware writes into the flash configuration (unlock addresses, mask, IDs) **(see ARCH
§7.4)**. Image layout, sectors and file units are unchanged.

Image = DDR2 0x1000000 (T60 §7; 0x3C00000 in Gideon's layout) + `bank * 0x4000` (+ 0x2000 for the upper half). File = CRT: 0x40
header (or `CRTHDR_HDRSIZE`), then CHIP packets `{"CHIP", u32 BE length, u16 type (0 ROM,
1 RAM, 2 flash), u16 bank, u16 load, u16 size, data}` [trex/main: `c64_crt.cc`
`read_chip_packet`].

Flash part data: CWBI §7.1.1 table and [IcePi: `firmware/c64_cart.c` `flash_profiles`];
TRX64 values where they differ are listed in §6.7.

## 7. App side: the CWBI service and write-back (trex/main)

### 7.1 Service (`software/io/c64/cart_writeback.{cc,h}`, new, ours)

- **Detection** at boot: the TRX IO block (ARCH §10) reads `ID` = 'TRX2' and its `CAPS`
  has the cartridge page. Absent → today's hash-based path stays exactly as it is (Gideon's
  bitstreams, ue2emu without a CW model).
- **Attach** after `read_crt` (§8.1 hook): look up the profile record for the CRT type
  (§7.2), write the flash configuration (page 0x4xxx), clear the software dirty map,
  record the file's packet table (§7.4), enable the two interrupt causes.
- **ISR** (the shared TRX interrupt line, `irq_high(2)` since T28, ARCH §14 item 1), short and
  allocation-free, like [IcePi: `firmware/c64_cart.c` `c64_cart_isr`]:

| Cause / pending operation | ISR action |
|---|---|
| PROGRAM (a, d) | CPU store `image[a] &= d` (flash only clears bits); dirty bit of a's 8 KiB block; `LOG_PUT` one record if T20 is armed; `CART_INVAL`; ACK |
| SECTOR_ERASE (a) | sector of a from the profile (boot-block table, CWBI §7.1.2) → image ranges (8 KiB pieces at 16 KiB stride for split layouts); if T20 is armed, engine `COPY` of the old sector into the ring and one range record by `LOG_PUT`; fill `$FF` with CPU stores; dirty bits; `CART_INVAL`; ACK |
| CHIP_ERASE | as sector erase over the whole chip |
| EEPROM written | nothing to apply (the 93C86 did it); remember "EEPROM dirty" (Gideon's byte is also set) |

  An erase of 64 KiB by CPU stores takes on the order of a millisecond; the chip shows BUSY
  meanwhile, as a real erase does (far longer).
- **Polling fallback** (no interrupt line): a task at the FreeRTOS tick checks the pending
  operation. Each program then costs up to one tick (5 ms at 200 Hz): an 8 KiB EAPI save
  ≈ 40 s. Not acceptable for EasyFlash; acceptable only as a bring-up mode.
- **Dirty map in firmware**: kept by the ISR itself (it applies every flash change), so it
  is exact without a hardware map **(see ARCH §7.4)**.

### 7.2 Profile = PROP-002 record

- One record per CRT type in the format of PROP-002 §9.2 (JSON), keys `crt_type`,
  `layout`, `flash {part, magic1, magic2, mask, id, id_ofs, size, sectors}`, plus
  `eeprom: "93c86"` where present. The banking fields (`regs`, `rules`, `bank`, `mode`,
  `table`) are carried and ignored until the hardware has the generic decode.
- Source of truth: `tools/cart_descriptors/*.json` (one per type, shared with IcePi and
  TRX64), converted at build time into a C table in `cart_writeback.cc`
  (`tools/gen_cart_profiles.py`). No JSON parser in the firmware.
- Override per image: the existing associated `.cfg` next to the CRT
  (`ConfigIO::S_load_associated_config`, CWBI §7.1.3) gets a category "Cartridge Flash"
  with part name (from the table) or explicit magic/mask/ID. Only the `.u2a` editor (§8.4)
  writes it.
- `layout` → chip records: `SPLIT` → two HALF records with half select 2/3; `L8` /
  `L8_MIRROR` → one HALF record; `L16` → one LINEAR record (§5.3).

### 7.3 Triggers

| Trigger | Mode Off | Ask | Auto |
|---|---|---|---|
| Quiet: no change for `T_QUIET` (default 2000 ms; software timer on the last ISR action and `WR_COUNT`) | — | remembered for the menu | write back |
| Max age: changes pending for `T_MAX` (30 s) without a quiet period | — | — | write back, copying between two operations (a game that writes continuously) |
| Menu open (`crt_autosave_menu_hook`) | — | dirty → popup as today | write back first, then show the menu |
| CRT load / unmount / `start_cartridge(NULL)` / Clear Mem | — | popup "Cartridge changed. Save?" | write back, then proceed |

### 7.4 Writing the file atomically

Which file: `C64_CRT::get_source()`. Refused (notice once per change, as today): not
writable (`crt_source_is_writable`), Temp RAM disk (REST upload), network paths, `/flash`.

At attach the service reads the file's packet table once (header length, then every CHIP
header: file offset, bank, load, size) and its size and FAT date/time. Each image 8 KiB
block maps to (packet, offset in packet) by (bank, load half); TwoMegabyter 16 KiB packets
take two blocks.

Write-back of a pending map:

1. Copy each dirty block from the image (8 KiB, CPU reads of the image at 0x01000000+ (T60 §7); see open
   question 11 on the D-cache) into a buffer, inside the ISR's lock so no operation is
   applied meanwhile (a C64 operation that arrives waits BUSY until the ACK); EEPROM by
   `get_eeprom_data` with `WR_COUNT` as the seqlock. Pending map → "in flight".
2. **Conflict check**: file size and date/time equal to what we loaded or last wrote?
   Otherwise §7.5.
3. If every in-flight block has a packet in the file: **journaled in-place patch**:
   write `NAME.wbj` = `{"CWBJ", u32 count, then per block: u32 file offset, u16 length,
   data, u32 CRC32}`, close (FatFS `f_sync`), patch each block in `NAME` at its offset,
   close, delete `NAME.wbj`. At every CRT load, a leftover `NAME.wbj` with valid CRCs is
   replayed into `NAME` first, then deleted; one with a bad CRC is deleted (the patch never
   started).
4. Else (a block with no packet: an EasyFlash bank that was empty in the file, a packet
   that `write_image` skipped as all `$FF`): **full rewrite** by today's
   `crt_save_in_place` (`.tmp`, `.bak` once, rename), from the image (operations held off
   during the copy only, not during the file write: the rewrite takes the copied blocks).
5. Success: "in flight" cleared, file date/time recorded. Failure: "in flight" ORed back
   into pending, error logged; the menu shows it at the next open (as today).

The original EAPI no longer needs restoring (D7). `.bak` policy unchanged (first original
kept once).

### 7.6 Power-off via the ESP32 rocker

Today the app gets no warning (§1.2). With `T_QUIET` = 2 s and a 4 s hold, a write
finished before the user starts holding is on the card before the regulators go off, as
long as the write-back takes < 2 s (true for a few 8 KiB blocks; not guaranteed for a full
4 MiB rewrite). To close the gap:

- ESP32 (`software/u64ctrl/main/button_handler.c`, or T26's new ESP32 firmware): at 1 s
  held, send `EVENT_POWER_PENDING` (new, 0x84); at 4 s send `EVENT_POWER_OFF` and wait up
  to 3 s for an RPC `POWER_READY` from the app before `regulator_enable(0, 0)`.
- App (`software/io/wifi/wifi.cc`, one `case` in the event dispatch): `EVENT_POWER_PENDING`
  → write back now (no quiet wait); `EVENT_POWER_OFF` → finish, `POWER_READY`.
- Menu "Power OFF" (`MENU_C64_POWEROFF`) and REST `machine:poweroff`: write back first.

### 7.7 Interplay with the machine pause (T12 B)

- Paused: the C64 issues no commands; a pending `BUSY` stays; the app may still apply and
  ACK (the ACK and `CART_INVAL` take effect at the first edge after the resume, ARCH §7.4).
- Freeze-mode menu = pause: the menu-open write-back happens on a still image.
- `.u2a` apps run only paused (`app_loader.cc`): the inspector (§8.4) always sees a still
  image and a stable dirty map.
- Bus DMA while paused (the app's freeze reads `$8000`): ignored by the responder (§5.1).
- Resume: no CW action. The cache line state is derived and rebuilt on demand.

### 7.8 Interplay with T20 snapshots and `.c64re`

> The `.c64re` side of this section is not in M1 (A13, no `.c64re` at all; rebuilt with T66 in M2). The ring side stays.

| Item | Rule |
|---|---|
| Machine state | Responder per-chip state, pending cmd/chip/address/data, toggle bit; 93C86 shift state; mapper registers. All in state-bus chip 7 "cartridge" (ARCH §5.4). |
| Snap with an operation pending | Captured as is. On restore the FSM is `BUSY` again and the event is re-queued by the restore; the app re-executes it. PROGRAM (AND) and erase (fill) are idempotent. |
| Cart flash bytes | T20 stream B by `LOG_PUT` from the ISR (one record per program, a range record plus the old sector per erase; ARCH §7.4, open question 12 answered). |
| EEPROM array | Not in DDR2: the 2 KiB go into the keyframe like cart RAM, and EEPROM writes into stream B (space "EEPROM", word address). Needs T20's keyframe layout to grow by 2 KiB. |
| Restore / seek changes the image | The timewarp app tells the CW service which blocks the restore changed (software call; there is no hardware map), so the app writes the restored state back after the next quiet period. Whether a rewind should roll the CRT file back is a decision (open question 7). |
| `.c64re` `cartBytes` | the CRT as loaded (unchanged) |
| `.c64re` `cartFlash` | EasyFlash: chip 0 then chip 1 (de-interleaved from DDR2); GMod2: flash ‖ EEPROM; MegaByter / C64MegaCart: the 8 KiB halves concatenated; TwoMegabyter: 2 MiB linear [TRX64: `cart.rs` `writable_image`]. T20 §9.3 says "EasyFlash lo‖hi layout, same as save_crt": correct for TRX64's `cartFlash`, but `save_crt` writes CRT packets and DDR2 is interleaved per bank; the app converts. |
| `.c64re` `cartState` | `currentBank`, `controlRegister` from BANK/MODE; `easyflashJumper` from the CRT header; `easyflashRam` from DDR2 0xEF1F00; `flashLoState` / `flashHiState` mapped onto TRX64's `Flash040StateSnapshot` [TRX64: `flash040.rs` `FlashState`, `c64re_snapshot.rs`]: READ→0, UNLOCK1→1, UNLOCK2→2, AUTOSEL*→3, PROGRAM armed→4, ERASE→6, ERASE1→7, BUSY program→4 with `programByte`, BUSY sector erase→10, BUSY chip erase→9; `eraseMask` from the pending sector; `eraseAlarmClk` 0; `eepromState` from the 93C86 registers + array. |
| Load of a `.c64re` | Reverse mapping; `FSM` register written while paused; TRX64's intermediate states (5, 8, 11, 12) map to READ with a log line (partial fidelity, T20 §9.3 class "partial"). |

## 9. Behaviour details that are easy to get wrong

1. The byte after `A0` is program data even if it is `$F0` (CWBI §6.3.6).
2. EAPIInit interleaves the unlock cycles of both EasyFlash chips: state per chip
   (CWBI §6.3.2; [IcePi: `c64_flash_amd.v`]).
3. Program ANDs, erase sets `$FF`; a 0→1 program leaves the byte unchanged
   [TRX64 803 §5.1, same rule for SPI flash].
4. MegaByter and C64MegaCart device ID is at byte address 2 in byte mode (CWBI §7.1.1).
5. TwoMegabyter polls status in 16K mode, not in Ultimax (CWBI §6.3.1).
6. VIC fetches never see status (§5.1).
7. Bus DMA reads must not toggle DQ6 (§5.1).
8. Dirty map kept by the ISR; EEPROM copy under the `WR_COUNT` seqlock.
9. A C64 reset aborts sequences but not a pending operation; the app still executes it.
10. (First draft: event-queue overflow.) Gone with the queue **(see ARCH §7.4)**.
