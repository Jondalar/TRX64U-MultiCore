## §1 The problem

Evidence is code on `main` (line numbers from the T192 analysis of the same day; T187 moves them, so every number is re-read at build time).

`MenuCtl` (`menuctl.cc`, 3918 lines, 113 methods, no `lv_` call) is the view-model of the core app. The views (`ui.cc`, `screens.cc`) call no
op; the ops (`OpRegistry`, `ops.h:30`) are the functional layer REST already uses. What sits between them is not only navigation: the
controller also holds domain logic and the raw C64 keyboard model. A second UI (text UI, search, remote client) would have to copy that
logic or drive `MenuCtl` through a key route that does not exist (`rpccontract.cc:26-28,128` refuse key input).

- **P1 Domain logic inside the controller.** Ten leaks, all in `menuctl.cc`:
  1. gamepad remap wizard `begin_map/map_key/map_ask/map_finish/map_tick` (3800-3918) calling `pad_state`, `pad_capture_*`,
     `pad_set_custom`, `pad_save_map`;
  2. monitor keys `mon_key/mon_wants_stop/mon_diag_requested/mon_leave_requested/mon_release` inside `key()` (3037-3043), `monitor_open()` (3767);
  3. timewarp keys: key to op translation `tw.step`/`tw.seconds` hard-coded (3775-3779), `timeline_key`;
  4. write-back question: `wb_menu_open`/`wb_answer` called from the controller, own state `wb_ask_` threaded through key handling
     (85-97, 618, 1391-1405, 2149);
  5. WiFi: `ops_state("wifi.onoff")`, `ops_call("wifi.toggle")` (764-765, 2007), a fixed entry `EK_WIFI` owned by the controller;
  6. T64 tape directory: `t64_list` and a static `t64_acts[]` file-action table (1669-1677, 1863-1876);
  7. volume: `change_volume` knows `VOLUME_KEY`, `volume_is_generic` and the C64 characters `{`/`}` for SHIFT+/- (1742-1760, 3081-3084);
  8. a file manager: `FsEntry list_[512]`, `load_dir` (347), `run_search` (3367, 85 lines), viewer/hex (`view_data_`, `view_line`),
     marks/copy/move state;
  9. startup/home: `home_dir`, `home_enter` (300-302), `refresh_roots` media chips; the 2 s relist is driven from `run.cc:902-904` and
     half-owned by the controller (hot-plug split between two files);
  10. input model: `key()` is 271 lines of raw `KEY_*` codes (2988-3258) with magic `0x60` (left arrow -> ESC, 3000); `text_key` 206 lines,
      `pick_key` 129 lines, `footer_legend` 142 lines (key legend text built from key names).
- **P2 No stable item identity and no intent entry.** `Item` (`menuctl.h` `struct Item`) carries slot/group/title/kind but no id and no op;
  the selection `sel_[][]` is private; only `goto_spec("F5/drives")` exists. A client cannot say "activate this row" and get the
  confirm/dirty rules of the key (`begin_confirm`, `unsaved()`); running the op directly bypasses `ui.confirm` (REST does).
- **P3 State and events are a pull snapshot** (`/v1/ui/state` `"v":1`, `uistate.cc`): the snapshot is built through `ui_shell_info_now(&si, m)`
  (`uistate.cc:125`), i.e. top bar and footer come from the view layer; progress and job state arrive only inside the snapshot;
  `/v1/events` lists registry events only (`rest.cc:643`).
- **P4 Proof on a whole core.** Moving the code is only worth it if one core runs complete on the new path. Alex chose the Amiga 1200 as the
  first core (D15: "there is really a lot in it"): RAM/ROM/hard file media, floppy, pad wizard, write-back, hotkeys, picture, volume. The proof
  must be a running core in ue2emu (S44 phase A), at the three HDMI modes the board shows, not only a unit test.
- **P5 The other cores follow** the same path (C64/trx64u, C128, Apple II, Atari, VC-20, ZX, CPC, NES/SNES, Neo Geo and the rest of
  `cores/`) without a per-core rewrite; where a core carries own menu code (trx64u `trx64u_ops.cc`, `menu_rec.inc`), it is listed, not hidden.

## §3 Decisions

### §3.1 From the epic (only those that apply)

- **D1 (Alex, 2026-11-07, translated: "C++ is the core then, kick Rust out of the design"):** the functional layer stays C++ on the board's RISC-V
  application; no Rust backend, no rewrite.
- **D3 (Alex, 2026-11-07, translated: "A yes, and when the search is in the overlay over the screen, the keys go into the search - NEVER into
  the UI below"):** only the chord C= SPACE opens the search; this spec supplies the intent table the overlay will use, it adds no search.
- **D11 (Alex, 2026-11-07, translated: "A, updates too!"):** a remote client with the token may answer every confirmation; the question stays
  (S9 here keeps the question on every route).
- **D14 (Alex, 2026-11-07: "A"):** ONE shared core framework for both apps; the domain logic stays per app. Core app domain: ops, settings, media.
- **D15 (Alex, 2026-11-07, translated: "192.2 first candidate A1200, because there is really a lot in it"; confirmed: meant the core app on the
  shared core):** the first core moved fully onto the shared core, proven in ue2emu, is the Amiga 1200.
- **D16 (Alex, 2026-11-07):** the terminal client is a separate project bound only by the T192.1 contract; nothing in this spec is shaped for it.
- **D9 (Alex, 2026-11-07):** bundles are data; this spec builds the "key -> intent" table that D9/T192.6 needs, with the TRX64 key grammar as the
  default (D2).
- **D2 (Alex, 2026-11-07, translated: "Mine, TRX."):** the default key set is the TRX64 grammar; the table built here is that set, unchanged in behaviour.

### §3.2 Design (proposal; names are suggestions, T192.1 fixes the framework's own names)

- **D-A Rule: the controller keeps navigation, dialogs and rows, and nothing else.** A `MenuCtl` method may read a model and call `intent`;
  it may not call a domain function. The gate of S1 enforces it (grep over includes and call names, plus a list of forbidden literal op names).
- **D-B One module per leak, behind ops and state names** (the same registry REST uses, `ops_register_base`, `ops_glue.cc:32-47`):
  | Leak | New home | Ops / state (names proposed) |
  |---|---|---|
  | 1 pad wizard | `padwiz.cc` (state machine, step table, texts) | `pad.map.begin(player)`, `pad.map.cancel`, `pad.map.save`; state `pad.map` (step, prompt, current map) |
  | 2 monitor | `monitor` owns its key handling: `monitor.key(code)` | `monitor.open/close`; state `monitor.owns_keys`, `monitor.wants_stop` |
  | 3 timewarp | `ringops.cc` gets `tw.key`-free ops | `tw.step(n)`, `tw.seconds(n)` as ops; the table row maps the key to the op with its argument |
  | 4 write-back | `writeback.cc` already holds the logic; add the flow | state `wb.ask` (question, note), op `wb.answer(yes)`; `wb_ask_` leaves the controller |
  | 5 WiFi | entry `EK_WIFI` becomes a descriptor node (op + state), not a controller case | existing `wifi.onoff`, `wifi.toggle` |
  | 6 T64 | `t64.cc` exposes `t64.list` and its action table as file actions in `desc.h` terms (`FileAction`, `desc.h:105-139`) | file-action registration |
  | 7 volume | `volume` owns the key map (`VOLUME_KEY`, generic vs core) and the C64 characters | `volume.change(delta)`; the table maps the keys |
  | 8 file manager | `filemgr.cc`: entries, marks, search, viewer, copy/move/delete jobs on the framework's job type | `fm.open(path)`, `fm.mark`, `fm.copy/move/delete`, `fm.search`, `fm.view`; model read through a window (`first`, `rows`) |
  | 9 startup/home | `home.cc` (exists as `home.h`) takes `home_dir/home_enter`; media chips and the 2 s relist become a poll task of the module, driven by the framework's tick, not by `run.cc:902-904` | state `media.roots`, event `media.changed` |
  | 10 input | `keymap` table `key -> intent` (data: `{code, modifiers, context, intent, arg}`), contexts: `menu`, `list`, `browser`, `text`, `picker`, `monitor`, `wizard`, `question` | `KEY_*` stays in the table and in the text/picker handlers only |
- **D-C Intent set of the core app** (all take an id from D-D unless noted; all pass the same gate as the key): `open`, `close`, `goto(spec)`,
  `select(id)`, `activate(id)`, `back`, `set(setting_key, value)`, `answer(choice)`, `cancel_job`, `page(delta)`, `text(utf8)` /
  `text_edit(op)`, `volume(delta)`. The controller owns the one queue (R30); the local keyboard enters it as a producer, as does the remote
  route of T192.1; the local producer has priority (S10). The key table translates a key into exactly these intents. `key()` stays as a
  compatibility shim that looks up the table and calls `intent`; REST/WS `ui/key` (T192.1) feeds the same shim.
- **D-D Stable ids.** `MenuNode`/`Setting` already carry stable keys (`Setting.key`, node `id`, `desc.h:77-100`); the id is built from them in
  `menu_build` and stored in `Item::id[40]` (new field beside `slot`, `menuctl.h` `struct Item`). Library rows: id from mount + path of the
  entry; the id is valid while the folder content is; `focus_id` is kept per page next to `sel_`. The row index stays for drawing only.
  The golden dump (`menu_dump`, `menutree.h:112`) gains the id column so a rename of a key is a visible diff.
- **D-E Confirm and dirty rules live in the controller, not the key.** `begin_confirm`/`wb` questions/file delete become a model state
  `asking {text, choices, default}`; `answer` is the only way out; the text still comes from the producing module (R23). The existing
  unsaved/Discard behaviour (`dirty_`, bug B1 "dirty not cleared after Discard") is carried over unchanged; B1 is not fixed here unless T187
  already fixes it (decided there, not by this spec).
- **D-F State and events.** `uistate.cc` is rewritten as a view of the controller state over the T192.1 schema; it no longer calls
  `ui_shell_info_now`. Top bar and footer strings are produced by the controller (`footer_legend` splits: key legend from the table, texts
  from the controller). `ui.cc` keeps calling the same getters; only the source of top bar/footer text moves. No view change on screen (S13).
- **D-G Order of work (proposal).**
  1. Read the T187 result (merged `t187-ux` or its branch head) and re-measure the line numbers in §1; update this spec's §1 where they moved.
  2. Gate script and ids first (S1 as a warning list, S7), no behaviour change.
  3. Leaks in this order: 7 volume, 5 WiFi, 3 timewarp, 2 monitor, 6 T64, 4 write-back, 1 pad wizard, 9 startup/home, 8 file manager, 10 key
     table last (it depends on the others' ops). Each step is a commit with its bench green.
  4. Intents + queue + `focus_id` + `asking` (S8-S10), then state/events (S11, S12).
  5. A1200 in phase A (S13, S14); the S1 gate turns from warning to error when the A1200 is green.
  6. Other cores (S15), one table row per core in §5.
- **D-H Per-core code.** Cores that carry their own menu code (`trx64u_ops.cc`, `menu_rec.inc`, `extend` functions such as `hk_extend`,
  `home_extend`) keep their ops; what they do through the controller moves with it. A core whose extend function reaches into `MenuCtl`
  internals is listed in §5 and fixed in S15, not special-cased.
- **D-I What is not decided here:** the framework's own names, the id syntax in the wire format, the WS routes (T192.1); the layout of the
  search results (T192.4); the TOML of key bundles (T192.6).

## §4 Out

- The search overlay, the text UI, the terminal client and the bundles (T192.4-.6, D16); this spec only builds the intent table and the ids they use.

- A fix of T187 findings that are not leaks (P4b value column, trx64u quarter-screen P6, 192.0.2.18 vs .189 address finding).

- The 2 s relist interval and the 3 s hot-plug poll values: unchanged, moved only.
- Making REST confirm: whether REST ops pass `ui.confirm` is decided in T192.1 (D11); here S16 only requires both routes to agree where the framework says so.

## §5 Build

MVP (epic D20, branch `t192-mvp-core`): only what the MVP needs; the ten leaks of §1 are NOT moved. What exists:

- **Adapter** `coreapp/src/uiapp.{h,cc}` (pure, benched natively) is the core app's `UicDomain` over `MenuCtl` (uicore, T192.1 §5); board glue in
  `uiapp_board.cc`; the run loop (`run.cc`) lends the key path (`give_key`), open/close and the dialog owners through `UiAppEnv`.
- **`MenuCtl` additions:** `Item::ident` (what an item IS: `set:<Setting.key>`, `task:<label>`, `media:<state>`, `node:<op>:<binds>`, `info:`, `fixed:`),
  `select_index(i)` (the cursor to row i by the steps of the cursor keys), `browsing()`, a remote confirmation (`remote_ask/take_remote_answer/remote_close`,
  shown as dialog `confirm`), `replace_text` and `entry_hook` (entry history), and the write-back question reports dialog `confirm`.
- **Ids (S7 here):** `uic_id_make(prefix, ident)`: lower case, `[a-z0-9._:-]`, a changed or cut name gets `-<4 hex>`; rows of one tab that share an identity get
  `.2`, `.3`. Browser rows `fs:<shortened name>` (folder names are unique, so no ordinal), sheet rows `act:<label>`. Position is never in an id.
- **Intents in the core app:** `select/activate` resolve the id to a row, move the cursor with `select_index` and press RETURN through the loop's key path
  (so `ui.confirm`, dirty and lock rules apply: S6); `key` names map to `KEY_*`; the board keyboard enters through the same `key` intent
  (`uiapp_local_key`: S7); `set` is `settings.set` (the menu's own call) and answers `held` while Save is pending (S9); `open` opens the menu or a `goto_spec`.
- **Destructive ops over REST (S16, D18, D19a):** the set is the ops of nodes whose ui says `confirm` plus `files.delete_job`, `settings.reset_to_host`,
  `settings.reset_defaults`, `settings.clear`, `machine.restart`, `update.run_record`; `POST /v1/ops/<op>` answers 202 `asked` and the screen shows the same
  question; the op runs when the question is answered yes (on screen or by `answer`). Aliases and WS JSON-RPC calls of such an op are refused with the
  reason (their arguments cannot wait for an answer).
- **Which cores (H3, widened by D24 below, by Alex on 2026-11-09 and by D31):** the service is on for every core that runs the generic application (`service_core`, D31); Gideon's application (`trx64g`) is untouched.
- **Alt ID before the init functions (board unproven):** the core's ID is taken as the pixel layer's alt ID before the init functions run (the RTC asked `trx_io_caps()` first and cached "no block",
  so no pixel layer in ue2emu for every non-TRX2 core). Proven in ue2emu only; the board has not seen the new order.
- **One gate for every network call (M1):** `svc_call_net`; `machine.cold_reset` / `machine.warm_reset` are destructive operations now.
- **Left as they are in the MVP, moved by the parity cut below:** the ten leaks, the gate script, `focus_id` per page, the intent queue with local priority, the picture-confirm
  question (still the loop's: keys_owner `picture` is reported), the top bar and footer text in the v2 snapshot, the parity pictures and the other cores. `uistate.cc` v1

### The left arrow in the Library (D27)

**Replaced (Alex, 2026-11-12):** "CRSR LINKS = eine ebene Hoch, LARROW = ESC" (cursor left = one level up; left arrow = ESC). In the
Library cursor-left (`MI_LEFT`) goes up a folder; the left arrow and ESC (`MI_BACK`) leave the area as everywhere else, they no longer go
up a folder. The D27 fix below in `MI_BACK` is to be taken back. Not built yet.
Cursor keys in every file browser and in the select popup with a file tree (Alex, 2026-11-12): up = one entry up, down = one entry
down, right = into a folder or ZIP, left = one folder up / out of the folder or ZIP.

Cause: `MenuCtl::key` maps the C64 left arrow (0x60) to ESC through `KS_ALIAS` and ESC is `MI_BACK`. `MI_BACK` goes up a folder only `if (is_browser() && screen())`, and `screen()` is true
when the tab has a `layout`. The TRX64U's Library tabs carry `layout = "library"` in `menu.toml`; the browser tab a generic core builds has none, so `screen()` was false and BACK took the
next branch (tab 0, then Home, then close). Cursor-left (`MI_LEFT`) has no `screen()` condition, which is why it went up. Not a core record or a per-core key row: the key table is the
same for all cores, one condition differed. Fix in the generic default (`menuctl.cc`, `MI_BACK`): a browser tab goes up a folder when it is a screen or when nothing holds the keys
(`!busy_ && !pick_ && !entry_`). `coreapp/cores/trx64u` and the C64 cores' files are untouched; at the media level ("/") the key leaves the Library as on the TRX64U.
Keywalk golden: only the F3/browse starts s1, s2, s5, s6 of the cores whose Library tab has no layout moved (listed in the commit). Tests: A1200 `library`, `media_level` and
`steps._up` use the left arrow (the third press "nowhere above" is the next scenario's "leaves the Library").
