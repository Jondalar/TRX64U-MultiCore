## §1 The problem

**Who:** the TRX64-FW session, which replaces Gideon's application on TRX64 Ultimate (D9.6); this repository's
coordinator, who adds cores; Alex, who drives the menu, the web page and the tests.

**What they are trying to do:** write a function once - "mount a disk in drive A", "reset", "open the
monitor" - and have it appear in the menu, in REST and in WS JSON-RPC, on every core that has the hardware
for it, without the generic application naming the core or the function.

**What happens today.** Read from the code on 2026-10-18 (branch `t104-generic-app`, `ccd58253`):

- **P1 No named operations.** A function is a C function pointer inside a descriptor struct: `Setting.apply`
  (`coreapp/src/desc.h:41`), `Task.run` (`:47`), `FileAction.run` (`:53`), `MediaSlot.what`/`eject`
  (`:66-67`), `RomSpec.put` (`:28`). The menu calls them directly (`coreapp/src/menuctl.cc:329, 352, 400,
  413`). Nothing outside the menu can reach them by name.
- **P2 Every transport has its own dispatch.** The host's web page has a hand-made command enum,
  `WEB_VIDEO .. WEB_DEFAULT` (`host-app/software/hostapp/webui.h:39-45`), applied by the UI task. ADR-0002 wants
  WS JSON-RPC for every new function; T24-ui-wiring §8 lists the `ult/*` methods as a third table. Each new
  function would be written into the menu, the enum and the method table: three times.
- **P3 One source for menus, fixed in code.** `menu_build()` writes five areas and their tabs by hand
  (`coreapp/src/menutree.cc:65-115`) from one descriptor plus two fixed entries. A library or an application
  cannot add a node, a file action or a setting. The only contribution path that exists - the `.u2a` manifest
  with file types, tasks and REST actions (`apps/ultimate/software/app_loader/app_manifest.h:20-49`) - lives in
  Gideon's application, which D9.1 removes.
- **P4 The description is code.** The descriptor is a compiled C table (`coreapp/src/table.cc:5-9`). The `.cor`
  has four records - manifest, partial, app, icon - and accepts each once, in order
  (`tools/cor_pack.py:40, 187-192`). There is no record for a description or a library.
- **P5 No door for libraries.** The `.u2a` door has one fixed load address, `U2A_LOAD_ADDR 0x03A00000`, and a
  2 MB area (`app_format.h:32-33`); the loader refuses any other address (`app_loader.cc:226`). There is no
  relocation. One application is resident at a time (`app_loader.cc:376-389`). Everything it allocated is freed
  when it returns (`app_loader.cc:513-519`). The firmware calls in only through `app_main`
  (`app_api.h:578`), `detach` (`:526`) and `ui_request` (`:547`). And our applications do not link the loader at
  all: `host-app/` vendors only `app_api.h` and `app_api_net.h` (`host-app/vendor.list:4-5`).
- **P6 Lifecycle is tied to the menu.** The core's `service` hook runs only while the menu is closed
  (`coreapp/src/run.cc:299-306`). (The Overlay mode that made this a stall is out since 2026-10-20: an open core menu is
  Freeze, Alex. Original wording in the Implementation Log.)
- **P7 Day 1 has no address.** D9.7 lists six things TRX64 Ultimate needs before Gideon's application goes.
  None of them has a named owner in the new structure: base, library, application or widget.

**Why it matters:** without one service layer, every function is written once per transport and once per
core, which is exactly the duplication T104 P2 exists to remove. Without a contribution model, "the menus
result" (D9.3) has nothing to result from, and the 1541 library (T104 §5.4) has nowhere to put its menus.

**Worked example.** The VC-20 descriptor of T104 §5.9 has the action `{ label = "Mount Disk", op = "mount",
slot = "iec:drive_a", mode = "rw" }`. Today nothing can execute `op = "mount"`: the structure it would land in
needs `FileAction.run`, a function pointer, and `desc_check` rejects an action without one
(`coreapp/src/desc_check.cc:58`). The same mount from a test needs a fourth path that does not exist.

### A. The service layer

**D1 — Three kinds of thing, all registered by name.**

| kind | shape | example |
|---|---|---|
| operation | `domain.verb(args) -> result`; args and result typed | `machine.reset(kind: enum cold|warm)`, `drive.mount(slot, path, mode)` |
| state value | `domain.name`, typed, readable, with a revision counter | `drive.iec:drive_a.image`, `net.ip`, `machine.state` |
| event | `domain.name` + one typed payload, emitted on change | `media.changed`, `job.progress`, `dialog.open` |

The types are few and fixed: `int` (with range), `bool`, `enum` (labels), `string` (max length), `path`,
`slot` (a media-slot id), `blob` (a handle, never bytes over a transport). The result is the `u2p_err_e` code
set the app ABI already has (`app_api.h:42-51`) plus one typed result object. Reusing those codes means an
application sees the same errors through the ABI that a REST client sees.

**D2 — One writer.** Every operation runs on one executor task, in the order it was queued. The UI, the REST
adapter, the WS adapter and the service polls put requests in its queue; none of them touches state directly.
This is T106 D2 - the web task fills a mailbox (`web_take`, `host-app/software/hostapp/webui.cc:20`) that only
the UI task empties (`hostui.cc:1497`), and reads a snapshot (`web_publish`, `webui.cc:14`) - made general, and T24-ui-wiring §10 Q6 ("one at a time, keep it simple", Alex 2026-10-03). Reads come from the state
values - **and those reads are not guarded** (see §5.2, Poll): `OpRegistry::state()` runs on the reader's own task (the menu loop, a transport) with
no lock, calls the getter, which reads what an operation or a poll is writing at that moment, and updates the value's hash and revision with no lock
either. The core lock covers handlers only. "Only the executor writes" is therefore true of the operations and false of the polls, and a reader can see
a half-written text or lose a revision count; whether that shows on the board is untested. A long operation reports `job.progress` events and does not block
reads. **Polls are the exception (Q9, Alex 2026-10-18: "Ja 3"):** each contributor's `poll` runs on a task of
its own at a priority above the UI's, and only the access to the core is locked between a poll and the
executor. This keeps what Gideon's application measurably does - each 1541/1581 has its own FreeRTOS task
(`c1541.cc:234`, `c1581.cc:138`; `PRIO_FLOPPY` 1 above `PRIO_USERIFACE` 0, `FreeRTOSConfig.h:6-13`), so a
drive never stalls behind the menu - and replaces his per-subsystem mutexes (commands run in the calling task
under a 5 s lock that answers `HTTP_LOCKED`, `infra/subsys.h:53,75,203`) with the one executor.

**D3 — Transports are thin adapters with no per-operation code.**

- **In-process (the menu, widgets):** call the registry directly, on the executor.
- **REST:** `POST /v1/ops/<name>` with a JSON object of args; `GET /v1/state/<name>`; `GET /v1/ops` lists the
  registry with its types. The adapter turns JSON into typed args from the registered schema and back.
- **WS JSON-RPC (ADR-0002):** the method name is the operation name; params are the same object; events are
  notifications with the event name. Existing contract methods (`session/reset`, `media/mount`, T24-ui-wiring
  §8) are aliases in the adapter's alias table, not separate code.
- **App ABI:** a new table `svc` with `call(name, json_args, json_out, len)`, `get(name, ...)` and
  `subscribe(name, fn)`. T24-ui-wiring §10 Q1 asked for exactly this: "the command table the LVGL UI uses in
  process is exposed to apps through the app ABI (one table, two consumers)".

S2 proves the adapters carry no operation names.

### B. The contribution model

**D4 — A contribution is one registration record.** A library or an application hands the base one record:
its identity and version, what it needs (D12), and six lists:

1. **operations, state values, events** (D1), each with its handler;
2. **menu nodes**: kind (`op` button, `setting`, `state` line, `widget`, `group`), label, an **anchor** (area
   key + tab id + group, D8), an order key, and conditions (`when_state`, `capability`);
3. **file actions**: match by extension list, and optionally by magic (offset + bytes), size set
   (`size_in`, T104 §5.2) and parent extension (`parent_ext`); the action is an operation name with argument
   bindings (`path = $file`, constants), a label and `closes_menu`;
4. **settings**: items for the config store (D5);
5. **lifecycle callbacks** (D6);
6. **widgets** it provides, by name (D7).

The `.u2a` manifest's three lists (`filetypes`, `tasks`, `rest`, `app_manifest.h:24-49`) map onto 3, 2 and 1;
an application keeps declaring them in the manifest, and the base turns them into the same record.

**D5 — Settings go into the store; the menu shows them through source (a).** A contributed setting becomes an
item of `Settings` (`coreapp/src/settings.h:25-71`) under the contributor's store section, with the three
layers that class already has: `.cfg`, host, default. Its menu row is not a separate node: every setting whose
`group` matches a tab's group appears in that tab, which is how T104 §5.9 already ties settings to tabs. The
setting's effect is an operation (`apply = "drive.set_bus_id"`), not a function pointer. `SETTINGS_MAX 16`
(`settings.h:23`) and `MENU_MAX_ENTRIES 48` (`menutree.h:27`) are too small for a C64 with the 1541 library
and become sized from the records at start.

**D6 — Lifecycle callbacks, and the service runs on its own task.** The callbacks are `on_core_start`,
`on_core_stop`, `on_freeze`, `on_thaw`, `on_mount(slot)`, `on_eject(slot)` and `poll` with a period. The
executor calls all of them but `poll`. `poll` runs whenever the core is started - **with the menu open or
closed** - on the contributor's own task above the UI's priority, and only its access to the core is locked
against the executor (D2, Q9), not the menu loop. This removes the limit of
`run.cc:299-306` and matches what the Amiga fork did with its own task (T104 §5.3). Whether a contributor's
poll also runs while the machine is frozen is declared per contributor (`poll_when_frozen`). **DECIDED (Alex, 2026-10-20: "Yes", to dropping it):** the
flag goes; while the machine is frozen no poll runs. Its only reason (an Amiga in Overlay mode) went with the Overlay mode, a frozen core
requests nothing, and a mount or eject from the open menu is done by its operation, not by the poll. To build: remove the field from
`coreapp/src/desc.h` and the gate in the service. Original wording in the Implementation Log.

**D7 — Widgets stay code, and are referenced by name.** The file browser (`browser`), the settings list
(`settings`), the terminal for 80-column applications (`terminal`, T24-ui-wiring §4.2), the hex view (`hex`) and
the Timewarp timeline (`timeline`) are C++ in the base or in a library, drawn with the speed rules of T93: no
D-cache, so pages are built once, only changed rows are redrawn, keys are drained before one `lv_refr_now`
(T93 §5.14), and media are listed every 2 s, never per render (`run.cc:137-156`). A description or a menu
node names a widget and passes it arguments (`group = "drive_a"`, `filter = "file_actions"`); it never
describes the widget's pixels.

### C. The declarative description

**D8 — The description gives the skeleton; everything else attaches to it.** The description (source b)
names the areas, their tabs, the tab numbers and the groups, and which widget each tab shows. It is the
route of T104 §5.8 and §5.9 (`[[area]]` with `tabs`). An anchor is `area key / tab id / group`; tab ids
are names, the numbers are only printed. Without a description the base uses its default route, which is
today's `menu_build()` (`menutree.cc:65-115`).

**The merge, in order:**

1. Areas and tabs from the description, numbered as it numbers them.
2. Settings (a): every store item lands in the tab whose group it names.
3. Library nodes (c): placed at their anchor, in order key, then load order.
4. Application nodes (d): placed the same way, after library nodes at the same anchor.
5. An empty tab is dropped, and an area without a tab with it (`menutree.cc:47-63` does this today).

**Precedence and conflicts:**

- An operation, state or event name has one owner: the first registration wins, a second is refused with
  both names in the log and on the System page (S4).
- A route number is never reused or reordered: a contributed tab appends after the description's
  (NAVIGATION.md: "new tabs append to an area and do not silently reorder existing sequences").
- The description may rename or hide a contributed node by its id; a library may not rename the
  description's nodes.
- A node whose anchor does not exist is refused by name (S3), never silently dropped.
- Two file actions with the same label for the same extension: both are shown, the description's order
  decides. Whether the description may restrict which contributions appear at all is Q3.

**D9 — Format: TOML compiled at pack time into a binary record (Alex, 2026-10-18: "1", Q1).** The three
candidates as they were weighed:

| candidate | for | against |
|---|---|---|
| LVGL XML as is (`docs/lvgl_ui_project/`) | the prototype exists; 30 screens | the vendored LVGL 9.6.0 has no XML loader (no `LV_USE_XML` in `host-app/software/lvgl/lv_conf_template.h`); the project is authored for 9.5.0 (T24-ui-project-review.md:79); XML describes look, not the binding of a node to an operation; parsing on a CPU without D-cache |
| TOML or JSON source, compiled at pack time into a flat binary record (string table + fixed-size entries, offsets, no pointers) | no parsing on the board; `cor_pack.py` validates it, as T104 D3 asks; the record is loaded by pointer arithmetic; the same record format serves `.cor`, libraries and applications | a second tool step; the record format needs a version and a checker on both sides |
| JSON loaded and parsed at run time | the `.u2a` manifest is already JSON parsed on the device (`app_manifest.h:51-58`, `host-app/software/api/jsmn.h`); editable on a stick | parse cost and memory at start; errors found only at run time; the manifest's limits (4 KB, `app_format.h:20`; 8 file types, `app_manifest.h:20`) are far below a C64's menu |

**Recommendation:** the second. Author in TOML, as T104 §5.9 already does; `cor_pack.py` (and a sibling for
libraries) checks it and writes the binary record; the base reads it without parsing and checks it again
with `desc_check`. The prototype's XML stays the visual reference for the widgets, not a runtime input.

### D. The loader

**D10 — Libraries come through the `.u2a` door, extended.** D9.4 decides the door. What the door has today
does not carry a library (P5), so it grows four things, each as a new field or record in the `.u2a` format
(`U2A_FORMAT_VERSION 2`, `app_format.h:18`, becomes 3):

1. **Relocation.** A library is linked position-independent (`-static-pie`) and carries a table of
   `R_RISCV_RELATIVE` entries; the loader puts it at an address of its choosing in a library arena and
   applies the table before the first instruction. Alternatives in Q4.
2. **A second entry point.** `lib_register(api, out_record)` returns the registration record (D4). The base
   then calls the record's handlers; this is the inversion T104 D6 named ("who calls whom").
3. **Residence.** A library is never unloaded and its allocations are not freed on return, unlike an
   application (`app_loader.cc:513-519`). A library that fails `lib_register` leaves nothing behind.
   **An application declares its residence in its record (Alex, 2026-10-18, relayed by TRX64-FW: "Apps
   sollten auch A) nur wenn offen laufen B) dauerhaft laufen. Je nach use case."** - apps should also A) run
   only while open, B) run permanently, depending on the use case): `transient` is today's `.u2a` - loaded
   when opened, unloaded and its allocations freed when closed; `resident` stays loaded like a library, and
   its poll and lifecycle callbacks (D6) keep running with the menu closed. Both count against the Q7 budget.
4. **The registration record** in the image, in the format of D9.

**D11 — Version checks, two of them.** The ABI check stays as it is: `api_version_min/max` against the
base's major (`app_loader.cc:192-195`), fields by `U2P_HAS` (`app_api.h:54-55`). The new check is
dependencies: a record names what it needs as `name >= version` (`base >= 3.1`, `cbm1541 >= 1`), and a core's
description names the libraries it needs the same way. The loader resolves in order, refuses a missing or
too-old one by name and version (S6), and the core stays held with that message (T104 S2's shape). **DECIDED (point 1, Alex 2026-10-20):** "Do not start. Error and back to the host." (translated): a missing or too old required library means the core does not start, the error names library and version, and the application returns to the host. The loader as built still carries on (5.5: "A refusal does not stop the core"); that is the open build item.

**D12 — Where libraries come from.**

- **MultiCore:** from the `.cor`. `cor_pack.py` accepts each record type once and in order
  (`tools/cor_pack.py:187-192`), so two new record types are needed: one description, and zero or more
  libraries. Whether a library is copied into every bundle that needs it or lives once in the flash next to
  the host is Q5.
- **TRX64 Ultimate** (no `.cor`): from the flash or the file system, from a fixed folder, with the same
  dependency check. The base library set is linked in; libraries are files.

**D13 — Memory.** Measured numbers, and what they are doing:

- The core application's image region is `0x00030000 + 0xE60000` (`host-app/target/u64ii/riscv/coreapp/linker.x:7`).
  Its FreeRTOS heap is `0x7A0000` = 7.625 MB (`host-app/target/u64ii/riscv/coreapp/Makefile:154`).
- The two LVGL frame buffers take 2 x 1,036,800 B from that heap (`trx_lv_port.cc:125`, 960 x 540 RGB565).
- The "237 KB + 384 KB" of the brief is one number, not two: T24 lowered the heap by 384 KB to make room for
  LVGL's 237 KB of code and data in Gideon's image (T24-lvgl-ui.md:257-266). LVGL's objects come from the C
  library's malloc (`host-app/software/hostapp/lv_conf.h:24`, which the core application's build includes,
  `host-app/target/u64ii/riscv/coreapp/Makefile:152`), so they come out of the same 7.625 MB.
- Free heap in the core application with a menu open is **not measured**. The log line exists
  (`trx_lv_port.cc:158`); S7 reads it.
- The `.u2a` area at `0x03A00000` (2 MB) lies outside the image region. Whether that address is backed and
  unused by every core's DDR2 use is **not checked**: on TRX64 Ultimate `0x03000000-0x03C00000` is the
  updater area (`T60-reu-16mb.md:95`) and `0x02000000` is used by the ICAP test (T79.1). The library arena's address and size
  are Q7.

### 5.1 The DDR2 survey for Q7 (TRX64-FW, read from code, 2026-10-18)

The DDR2 is 128 MB (MT47H64M16), but the RISC-V reaches only the bottom 64 MB: `ddr2_port.v:274`
`a_addr <= {1'b0, address[25:1]}` (both repositories), `bootrom.c:76` `DDR_SIZE 0x04000000`. Above 64 MB only
the trx_engine COPY, the pixel layer and JTAG reach.

| range | use |
|---|---|
| `0x00030000-0x00E8FFFF` | application image and heap (heap `0x7A0000`) |
| `0x00E90000-0x00EA7FFF` | **unused in both configurations: 96 KB, the only hole** |
| `0x00EA8000-0x00FFFFFF` | KERNAL, drive, cartridge |
| `0x01000000-0x01FFFFFF` | REU / the core's window |
| `0x02000000-0x02FFFFFF` | RAM disk |
| `0x03000000-0x03BFFFFF` | updater and staging; the `.u2a` area `0x03A00000` is borrowed from it |
| `0x03C00000-0x03FFFFFF` | cartridge ROM, hand-over, trampoline |

**Consequence:** there is no free address range for a library arena. With static-pie relocation (Q4) none is
needed: libraries and resident applications go into memory allocated from the application's heap, so Q7 is a
heap budget, not an address. `0x03A00000` is borrowed space on both lines, not free.

**A collision to check, on the MultiCore side:** T93 §5 already found the fourth frame buffer
(FB_BASE `0x01D00000` + 3 x 1 MiB) outside the application's window. The survey adds where it lands: past
`0x02000000`, in the RAM disk area - the NES to `0x0201C000` (`nes.cc:136`), the Atari to `0x02036000`
(`atari800.cc:163`); the C264 (`c264_pixw.v:110`) and the Amiga (`amiga_fb.v:16-17`, up to about `0x020BDD80`)
are not resolved. Whether the core application uses a RAM disk at all is open; so are the Amiga's `wb_idx`
and whether a core other than trx64 writes `0x03C00000` through its cart fill.

### 5.2 D14 items 1, 2 and 4 built (TRX64-FW, branch `t104-generic-app`, 2026-10-18)

What was decided while building, and where the code differs from the text above.

**Registry (`coreapp/src/ops.h/.cc`).**
- A handler is `int fn(CoreCtx *, const OpArgs &, OpOut &)`; the result is an `OpErr` with the values of `u2p_err_e`
  (`OPE_ARG -1 .. OPE_FAILED -7`). The old hooks keep their `(c, msg, msglen)` shape: `op_hook<H>` wraps one as an operation
  without arguments, and **any nonzero return becomes `OPE_FAILED`** - the finer codes (`OPE_FORMAT` for a bad `.nes`, `OPE_NOT_FOUND`
  for a missing file) are not mapped yet; the reason is in the message.
- Types as in D1 (`int` with range, `bool`, `enum`, `string`, `path`, `slot`, `blob`). A caller hands untyped `OpIn` values: a transport
  gives text, the menu gives integers and a file, the ROM manager gives bytes. An enum takes its label (case-insensitive) or its
  index; an int takes a number or decimal text. A `slot` is checked as `[a-z0-9_:]+`, at most 31 characters; the set of declared slot
  ids is not checked yet (there is no declaration to check against before D14 item 3).
- A `blob` carries a pointer and a length, valid for the call; it never leaves the process. D1 says "never bytes over a transport"; the
  ROM `put` is the only user and is in-process.
- A state value is text (null: nothing). Its revision counts the changes **seen by `state()`** (a hash of the text at each read), not
  changes as they happen; the executor does not publish them. Typed state values (int, enum) are not built: no consumer.
- Events: registered with one typed payload, subscribers called by `emit` on the emitting task. The two built-in contributors register
  none and emit none; the mechanism is benched only (`test_ops`).
- Names: `domain.verb`, lower case, one owner each; the first registration wins and `error()` names both owners (D8, S4's second line).
- Names chosen: the shared resets are the base's `machine.warm_reset`, `machine.cold_reset`, `machine.reload_roms` (D1's example
  `machine.reset(kind: enum cold|warm)` is not used: two of the three resets are tasks of every core with ROMs and need no argument);
  the Picture item is `picture.apply`; the Atari's are `atari800.{set_ram,set_flags,set_speed,put_os,put_basic,remove_cart,eject,mount,
  run_xex,insert_cart,service}`, the NES's `nes.{set_system,run}`; media slots are the state values `atari800.d1.image` ..
  `atari800.d4.image`, `atari800.cartridge.image`, `nes.cartridge.image`.
- A setting's `apply` is an operation with **one int or enum argument named `value`**; `desc_check` demands its range covers
  `0 .. nvalues-1`. The Atari's two flag items share `atari800.set_flags` (it rereads both settings, as the old hook did).
- A task, a file action or a slot's eject binds **every** argument of its operation (`OpBind`: `$file`, an integer or a text constant); the
  Atari's `Mount D1: and cold start`, `Mount D1:` .. `D4:` are five bindings of one `atari800.mount(path, drive, boot)` (the boot flag is an argument, not a rule on the drive number; Alex 2026-10-20, T108 D6). This is D4's `bind` for what the descriptor needs
  today; the TOML form is the compiler's, not built.

**`desc_check`.** It builds a registry of the base plus the descriptor's `register_ops` and checks against it; `desc_check_with(d, reg)`
takes a registry the caller filled. Refusals name the entry and the operation ("tasks: \"Ghost\" calls operation \"test.ghost\", which no
contributor registered"). It also refuses: a binding to an argument the operation does not have, bound twice, of the wrong type or out
of range; an argument left unbound; a file bound in a task; a setting whose operation takes fewer values than the item has; a ROM put
that does not take exactly one blob; a media state nobody registered; a service operation with arguments; a core whose contributor
takes a name of the base. "A setting needs at least two values" stays. The result is a static buffer (valid until the next check).

**Executor (`exec.h/.cc`).**
- Arguments are checked **in the calling task** before anything is queued, so a refused call never touches the queue or the handler. The
  queue holds 8 requests (`EXEC_SLOTS`, each with its own completion semaphore); a ninth gets `OPE_BUSY`. FIFO is a ring of slot numbers.
- `Executor::start` returns only when the task has said who it is (`task_`): before, a call between `task_new` and the task's first instruction ran on
  its caller, against the one-task rule (and made the order check in `test_ops` fail under load). Bench: an os that starts its thread 80 ms late.
- A call from the executor's own task (an operation that calls an operation) runs at once and does not queue; before `start()` it runs on
  the caller under the core lock. The menu, the boot code and the autorun all go through `ops_call`, which uses the executor when
  `ctx.exec` is set and the caller otherwise (every bench, and the start sequence).
- The build has no counting semaphores (`configUSE_COUNTING_SEMAPHORES 0`, `FreeRTOSConfig.h:33`), so `OsPort` is binary and the executor
  drains its queue after each wake-up; `HostOs` in the benches is binary on purpose.
- Priorities: the executor runs at the menu task's priority, a poll one above it (`configMAX_PRIORITIES 5`). Stacks 6 x
  `configMINIMAL_STACK_SIZE` each (38 KB), a guess: a handler that opens files and sectors (FatFS) runs there now. **Not measured.**

**Poll (`service.h/.cc`), D6/Q9.**
- The whole handler runs under the core lock, executor operations and polls alike: "only the access to the core is locked" is
  implemented as "an operation is the access". The menu loop takes no lock. The UI's own reads (state values, the settings) are not under
  the lock; they read what an operation or a poll wrote and were never serialised against a second task before - **a data-race question
  for the board**, not tested.
- Reads of state values are **not guarded** against polls: `OpRegistry::state()` takes no lock (the getter, the hash and the revision are
  touched on the reader's task while a poll or the executor may be in the core). Not tested; if the board shows torn texts, the fix is a lock
  around the getter, which costs the menu loop a wait for a running handler.
- `poll_allowed` is `started && (!frozen || poll_when_frozen)`, checked **twice**: before the poll takes the core lock and again after it holds
  it (review fix, 5.5): `open_menu` sets `frozen` and then waits for the lock, so a poll that was past the first check and queued on the lock
  used to run into the frozen machine. Bench `test_service.cc` freezes between the two (control `svc_relock`). `ctx.frozen` is set by the menu **before** the Freeze starts, followed
  by a lock/unlock of the core lock so a poll that is inside the core has finished; `ctx.menu_open` is a fact the poll never reads.
- Tick: the build runs at 200 Hz (`configTICK_RATE_HZ`), so `BoardOs` counts time in ticks (5 ms) and the Atari's 5 ms period is one tick.
  A poll that keeps having work asks for the processor back at once, as the old loop did, but for at most `BURST_MAX_MS` = 20 ms in
  a row, then sleeps one period: the poll is above the menu task, which flips the picture. **That cap is new; the old loop had none** and
  it costs a SIO burst a 5 ms gap every 20 ms. Whether the Atari's SIO engine minds is a board question.
- The Atari declares `poll_when_frozen = false`: with the menu open (always frozen today) nothing is served, as before. The NES has no
  service. So on screen and on the SIO wire nothing changes until a core declares otherwise or an Overlay mode exists.
- No other lifecycle callback of D6 (`on_core_start`, `on_freeze`, `on_mount` ...) exists; only `poll`.

**Where text and code disagreed.**

### 5.3 D10-D12 built: the loader (TRX64-FW, branch `t104-generic-app`, 2026-10-18)

**Where.** `coreapp/src/libfmt.h` (the .u2a format 3), `libapi.h` (what a library sees and returns), `libload.h/.cc` (the loader);
`app/lib/` (linker script `lib.ld`, make fragment `lib.mk`, `testlib/`); `tools/u2a_pack.py`; `tests/loader/`. Reason for `coreapp/src`: the
loader registers into the `OpRegistry` and hands `CoreCtx` to handlers, both of which live there; it names no core. Gideon's submodule is not
touched; format 2's `app_format.h` stays his. The core application's Makefile compiles `libload.cc`; when this section was written nothing
referenced it (the board `LibHost` and the call at core start are §5.5).

**Format 3 (`libfmt.h`).** Header of 104 bytes, then the needs (name + `major << 16 | minor`, at most 4), the payload, the relocation table,
the app's JSON manifest. Fields: kind (library | app), residence (transient | resident), arch, the ABI majors the file knows, what it
provides (name, version), the capability, payload / bss size, alignment (4 .. 4096), **two entry offsets** (`lib_register`, `app_main`; one
or both), table offset and count. There is no variant table: ABI 3 is only for our RISC-V cores (Q6). The image is linked at 0; the table
lists the offset of every 32-bit address word; the loader does `word += base`. An R_RISCV_RELATIVE addend is written into the word by the
packer, so the loader never sees a RELA entry.

**Decisions taken while building.**
- **A library is always resident**; a transient app may not register (nothing to take back when it returns, since the registry is a stack
  with a mark); a resident app may. An app declares `app_main`, a library `lib_register`.
- **Checks before the first instruction, all on data** (the file, not the record): magic, format, names, ABI majors, residence shape, every
  range inside the file, alignment, both entry offsets inside the payload and even, the needs, the capability, the name not yet loaded; then,
  after the copy, each relocation word aligned, inside the payload and **strictly ascending** (a repeated word would be added to twice).
  The handlers a library registers are **not** checked to lie in its image: once `lib_register` ran, the library is native code with no
  sandbox, and a handler in the base is legitimate.
- `needs` is `name >= version` on `major << 16 | minor`. `base` is the loader's own `3.U2A_BASE_MINOR` (0 now); any other name must be loaded
  already, so **load order is dependency order** (the `.cor` lists them in it). Missing, or too old: the sentence names library, dependency
  and both numbers.
- **Capability (Q10)**: the sentence is `Library "x" needs the capability "c", which the core "Name" does not have.` and no memory has been
  allocated by then. The predicate is `LibHost::has_capability`; the list is `CoreDesc::caps` (§5.5).
- **Failure leaves nothing**: `OpRegistry::mark()/rollback()` (new) take back the operations, states and events registered since; the image
  is released. Benched with a failing `lib_register` and with a name taken by an earlier library (its first name is rolled back too).
- Contributions registered today: operations, state values, events, under the library's name. Nodes, file actions, settings and the poll
  are in `LibRecord` and kept in `LibInfo::record`; **merging them is D8 and the poll task is D6**, neither built.
- Limits: 12 images, 1 MiB each (payload + bss), 15-character names `[a-z0-9_]`. The image is `alloc(size + align)` from the heap and aligned
  inside; the payload is read in 256-byte blocks (the reason Gideon's loader gives for FatFS), which the host model cannot confirm.

**Toolchain finding.** The installed bare-metal binutils (`riscv64-elf-ld` 2.47, Homebrew) refuses `-pie` and `--shared`. A real
`-static-pie` therefore cannot be produced here, and whether the build image's `riscv32-unknown-elf-ld` can is **not checked**. The build
path uses what works: `-fPIE -mcmodel=medany -mno-relax`, `ld --emit-relocs` at link base 0, and the packer turns every R_RISCV_32 of an
allocated section into a table entry (the word must point into the image) and refuses absolute HI20/LO12, GOT, PLT, TLS and a non-empty
`.got`. The packer also reads ET_DYN with R_RISCV_RELATIVE (Q4's wording); that path is tested only on ELF files the test writes itself.

**Verified.** `tools/test_u2a_pack.py` (43 checks): the same objects of `testlib` linked by a real riscv64 `ld` at 0 and at 0x1000 pack to the
same bytes, and the image of the first relocated by 0x1000 equals the second **byte for byte**; dropping a table entry or relocating by
another base does not. `tests/loader/run.sh` (179 checks, 21 controls when this was written - the text said 178 and 20 - and 208 checks, 27 controls after the 5.5 additions): the real packed testlib is loaded into a modelled address space and
compared with that second link; two libraries and a resident app at different aligned addresses, each answering from where it was put through
a relocated pointer, no byte outside the three images written, a transient app freed; every refusal above with the heap, the registry and
the entry-call count unchanged. **Not verified:** that RISC-V code of a library runs (the model calls a host-compiled twin of
`lib_register`; the real `testlib.cc` is the twin of the real image); `fence.i`; the call through the board's function pointer; any
build with the build image's toolchain; the heap on the board (S7's number).

**Size.** Not in the image yet (unreferenced, `--gc-sections`). `libload.cc` alone compiles to 4.5 KB text, no data, with riscv64-elf-g++ 16.2
`-Os` against stub headers (not the build image); a `LibLoader` instance adds roughly 1.7 KB bss. The registry's `mark/rollback` is part of
`ops.o`.

**Text and code disagree.**
- D10 and Q4 say "library arena"; §5.1 already replaced it with the heap, and the loader has none. D10.1 "format 3 ... becomes 3" keeps
  magic and the `U2AP` name but not format 2's variant table or fixed load address.
- D10.2 "lib_register returns the registration record": it fills `out_record` and returns a code, so a failure has a code to name.
- D1 names a state `drive.$slot.image`; `name_ok` refuses `$`. The `$slot` expansion belongs to the compiler and is not built.
- D12: `.cor` records are **not** added (`cor_pack.py` untouched). Needed: a `library` record, repeatable, each holding one .u2a in
  dependency order, and a `description` record; the check "needs satisfied inside the bundle" can reuse `u2a_pack.parse_need`.

### 5.5 The loader at the board's start (TRX64-FW, branch `t104-generic-app`, 2026-10-18)

**Where.** `coreapp/src/libscan.{h,cc}` (pure: folder, order, log), `libboard.{h,cc}` (board: `LibHost`, cache, call), `run.cc` (one call, one
screen message, one info line), `desc.h` / `desc_check.cc` (capabilities). Benches: `tests/coreapp/test_libscan.cc` (97 checks, 10 controls), `test_libwait.cc` (22 checks, 4), `test_libguard.cc` (98 checks, 6),
`test_desc.cc` (capability cases, 4 controls), `tests/loader/` (the registry holds no error after a rolled-back library).

**Decisions taken while building (Alex's list: the proposals are mine until he says otherwise).**
- **The folder** is one constant, `LIB_FOLDER "trx/lib"` in `libscan.h`, looked for on `/usb0 .. /usb3` (`lib_roots`, the same sticks and the same
  lower-case spelling `romfind.cc` uses; the file manager is case-insensitive): `/usb1/trx/lib/<name>.u2a`. Every root that has it is read, so two
  sticks add up; the same library on both is the loader's "loaded already" for the second. A missing folder is one log line and no error. The flash
  is not read (T93 S14 stays a rule about writing; a library in the flash would be a release item, D12 first bullet, Q5).
- **When:** in `coreapp_run`, after the descriptor and `ui_open`, **before `boot_start`**: the core is still held, the registry exists, and what a
  library registers is there for the executor, the poll and the menu. A refusal does not stop the core.
- **Order:** read the header and needs of every file, then take the first library (by path) whose providers are all in front of it. `base` is no
  edge; a name no file provides is the loader's `not loaded` sentence; a cycle, or a library that needs its own name, is **refused and named**
  (`Library "pp" is part of a dependency cycle (pp, qq) and is not loaded.`) before any memory is spent, and what lies behind a cycle gets the
  loader's `not loaded`. Not a library (an application) in the folder: refused, not loaded (a transient app would leak, a resident app is not
  asked for yet). More than 24 files: the rest is named in the log and left alone; the loader's own 12-image limit shows as refusals.
- **Log**, one line per file: `[lib] testlib v1.0 at 0x00a31230 : ok` or `[lib] cbm1541 v1.0 : refused: <the loader's sentence>` (a refused line has
  no address: nothing was placed; a file that is not a library is named by its file name), and one summary line with the resident bytes and the heap
  before and after (the number S7 and Q7 want). `api->log` of a library prints as `[lib] <text>`.
- **The user sees it** (Q10): a refusal gives the message "Library not loaded" with the first sentence (library, capability, core) and "(more in the
  log)" when there are more, on the same screen the ROM messages use, until a key or 6 s; and the Home page has an information line **Libraries**
  (`none`, `2 loaded`, `1 loaded, 1 refused: cbm1541`). The F8 System area holds only the two fixed buttons and no information lines, so the line is on
  Home beside Core / Application / ROMs; if Alex wants it on System it is a one-line move in `menu_build`.
- **The wait for the stick** (`lib_wait_for_stick`, `libscan.cc`; first version waited `LIB_MOUNT_WAIT_MS` = 4000 at every start, so a start without a
  stick was 4 s slower). Decided before it waits, logged as `[lib] stick wait: <reason>`: (1) a root `/usb0..3` lists already: no wait; (2) a root's
  name is in the listing of `/` (the USB stack installed the device, `UsbScsiDriver::install` adds the root entry, the medium attaches later): wait;
  (3) the core's ROMs were found in `/flash` and no stick is installed: no wait; (4) the USB stack has no mass-storage device: no wait; (5) a
  mass-storage device is enumerating: wait. A wait ends when a root lists or after 4000 ms. **The USB signal** is `usb2.rootDevice` and the tree
  below it (hubs through `UsbHubDriver::getChild`, three levels): any interface of class 8 (`libboard.cc`, `usb_has_storage`); read only, nothing
  of the fork is changed. A stick that is plugged in while the core starts, after the tree was read, is not waited for (its libraries load at the
  next start). Bench: `tests/coreapp/test_libwait.cc` (no USB: 0 ms and no delay call; flash ROMs; a root already listing; install at 700 ms and
  mount at 1900 ms: waits 1900; a medium that never comes: 4000), 4 controls. Not verified on the board (the tree walk).
- **Capabilities:** `CoreDesc::caps/ncaps` (trailing fields). Atari 800 XL: `sio`, `cartridge`; NES: `cartridge`. No `drive_a` and no `iec` anywhere
  yet: the Commodore drive library is refused on both, which is the case Q10 describes. Names are `[a-z0-9_]{1,15}` like the field in the file;
  `desc_check` refuses the rest and duplicates. The set is mine; each future core states what it has.
- **Cache:** NEORV32 has a 2 KB direct-mapped instruction cache and `fence.i` only with Zifencei (the cpu_unit wrapper has it only with the JTAG
  debugger), so `sync_code` executes 512 NOPs from firmware text, as `app_icache_sweep` in Gideon's `app_loader.cc` does. There is no data cache in
  that wrapper (only `ICACHE_EN`), so nothing is written back.
- **The CPU has no C extension** (`CPU_EXTENSION_RISCV_C => false`; the core application is `-march=rv32im -mno-div`). `lib.mk` built `rv32imac`: an
  image of that would trap on its first compressed instruction. Now `rv32im -mno-div`; the fixtures and the packer test's offsets follow. The
  loader refuses an entry that is not 4-aligned (`entries[i] & 3`, was `& 1`): a 2-aligned entry is legal with the C extension and a trap on this
  CPU; `u2a_pack.py` refuses it too. Header `flags` and `reserved` must be 0 (format 3 defines none); any other value is refused as a feature this
  base does not have.

**Verified (Mac).** The benches above, `tests/loader/run.sh`, `tests/hostapp/run.sh`, the render bench (`tests/coreapp/render/run.sh`),
`tools/test_u2a_pack.py`; goldens of the menu dump gained `info Libraries`. testlib builds and packs here with `riscv64-elf-`.
**Not verified.** Everything RISC-V at run time: `run.cc` and `libboard.cc` were not built (no build image here; `libboard.cc` was syntax-checked
against a stub `FreeRTOS.h`); the build image's `riscv32-unknown-elf-g++` / `ld` with `lib.mk`'s flags; the cache sweep; the call through the
relocated entry; heap alignment of `pvPortMalloc` (the loader aligns inside anyway); FatFS reads in 256-byte blocks through `FmFile::read`; the screen
message and its 6 s; the heap numbers.

   (c) `u2a_pack.py ... --capability drive_a` copy: `[lib] ... : refused: Library "..." needs the capability "drive_a", which the core "Atari 800 XL" does not

### 5.4 D16 built: sizes and offsets of 64 bit (TRX64-FW, branches `t104-fs64` of the fork and `t104-generic-app`, 2026-10-18)

**Why.** Amiga WHDLoad / HDF images can be larger than 4 GiB (Alex, 2026-10-18). FatFS in the fork is exFAT with `FSIZE_t` = 64 bit
(`ff.h:114`, `ffconf.h:233`), but `FileInfo.size`, `File::seek` and `File::get_size` and `CoreFs`/`CoreFile` cut everything at 32 bit.

**The fork** (`apps/ultimate`, branch `t104-fs64` from `1791f3c5`, three commits). `FileInfo.size`, `File::seek`, `File::get_size` are `uint64_t`,
`FileFAT` hands them to FatFS as `FSIZE_t`. `seek64` / `get_size64` stay as aliases with the signatures of `619e040b`, so the Amiga application
compiles unchanged (they are non-virtual there, not virtual as in `619e040b`: nothing overrides them; if that branch is merged, its FAT
overrides go). Every file system overrides the 64 bit signatures - a 32 bit `seek` in a subclass would silently stop overriding and return
`FR_NO_FILESYSTEM`; D64, T64, ISO 9660 and the RAM file keep 32 bit contents and refuse a seek beyond them. `BlockDevice_File` seeks with a 64
bit byte offset. FTP (`SIZE`, `LIST`, `MLSD`, `MLST`, the 150 of `RETR`, the FTP file system's own `LIST` parser) and `GET /v1/files/.../info`
report the real size; the file browser shows `5120M` / `  20G`.

**Decision: a saturating 32 bit view for the 32 bit holders.** `File::get_size32`, `FileInfo::size32` and `fs_size32` (CoreFs) return
`0xFFFFFFFF` for 4 GiB and more. The alternative, `(uint32_t)` at every holder, lets a file of 4 GiB + 184320 bytes pass as an XFD of 184320 and a
file of 4 GiB + 16384 as a 16 KiB ROM. Where a size is compared or counted (IEC directory blocks, the app registry's file compare) it stays 64 bit.
**The firmware's printf has no 64 bit conversion** (`small_printf.cc`: `%llu` prints the letters; a `uint64_t` for `%d` shifts every later
argument), so numbers go through `u64_dec` / `u64_dec_pad` and `%s`. The `SIZE` reply buffer was 20 bytes for a line of up to 25.

**Not changed, and why.** The application ABI (`app_api.h`): the `dir` callback's `uint32_t size` and the stdio `long fseek/ftell` stay (an ABI
change is Alex's call; the callback now gets the saturated value). `ult_syscalls.cc` (newlib `off_t` is 32 bit) and the DOS command interface
(`dos_info.size` is 32 bit on the wire) get the saturated value. **`host-app/` is not touched**: it is a byte-for-byte vendored copy of the
fork at `1791f3c5` (its own `ftpd.cc`, `vfs.h` with `int st_size`, `File` with 32 bit `seek`), and `hostapp/hostfs.cc` (own code) keeps a
`uint32_t` size. They follow when the submodule pointer is bumped and `tools/hostapp_vendor.py copy` is run; **the pointer was not bumped at that time** (since done: see the Implementation Log).

**B.** `CoreFs`/`CoreFile`: `FsEntry.size`, `size()`, `read/write(uint64_t off, ...)`, `stat(..., uint64_t *size, ...)`; `fs_size32` in the ROM manager and the
ATR / XEX / cartridge / iNES openers. `settings.cc` takes the `.cfg` size as 64 bit.

**Verified.** In the fork `software/filesystem/tests/run.sh`: an exFAT volume of 6 GiB (sparse image, `FM_EXFAT`, because `FM_ANY` makes FAT32 there and
FAT32 stops at 4 GiB - 1), the fork's stack from `BlockDevice` to `FileManager` and the VFS of the FTP server; a file of 5 GiB + 16 with markers at

### 5.6 The USB mouse through a library (branch `t104-mouse`, 2026-10-20)

**Decision (Alex, 2026-10-20):** the USB mouse reaches every core that has a mouse through a library (C64 as a 1351, Amiga); our application's
UI stays keys only. "No mouse control in our app! Only keys." / "That has to go into a library. The C64 etc. have a mouse too." (translated).

**Cause.** The only place that sees the HID reports is `UsbHidDriver::process_mouse_report()` (vendored `usb_hid.cc`). It drove the 1351 pots and
joystick port 1 itself and, with `CFG_MENU_MOUSE_NAV` on (default 1) and a menu open, turned the mouse into menu keys. The Amiga sink
(`mousesink`, 5.2) was built but nothing fed it (T104-amiga-build-notes "Not done").

**Built.**
- Hook, one change to the vendored driver: `usb_hid_set_mouse_sink(fn)`; `process_mouse_report` calls `fn(dx, dy, hid_buttons)` once per
  report (motion after sensitivity and acceleration, HID order 1/2/4) before any menu or port-1 handling; `true` consumes the report.
  Null (the lean host app, the default): the old path, unchanged. Recorded as `MODIFIED` in `tools/hostapp_vendor.py`, `host-app/PROVENANCE.md`
  and `host-app/patches/io_usb_usb_hid.{cc,h}.patch` (the patches reproduce the files byte for byte from the original).
- Library `coreapp/src/mousesink.{h,cc}`: `mouse_sink_usb_report()` is the sink. The descriptor's `MouseSinkSpec::kind` names the backend:

### 5.7 D15 built: the `cbm1541` drive library (branch `t104-cbm1541`, Claude, 2026-10-22; not merged)

Alex, 2026-10-22: "build the 1541 please" (translated), so that the VC-20, the C264 and the C64 descriptor get drive A through it. The same day, for the 1581:
"and .d81 right away too!" (translated). The library therefore serves **both drive types**; the C128 (T113, CP/M on the 1581) will use it later.

**Where it lives.** `app/lib/cbm1541/` is the portable library, pure (`CoreIo` and `CoreFs` only): `d1541_gcr` (the disk in memory: GCR code, track layout,
decoder, `.g64` file, blank `.d64` / `.d81`), `d1541_wd` (the 1581's WD177x controller and its MFM layout, in software) and `d1541_drive` (`CbmDrive`: the
register sequences, the track parameter RAM, the dirty flags and the write-back, the drive ROM, the settings, mount / eject / save / create).
`coreapp/cores/cbm1541.cc` is the contributor (`r.contributor("cbm1541")`, registered from the core's `register_ops` like the PRG operations), and
`coreapp/cores/cbm1541_desc.h` holds the descriptor pieces. Because the menu merge of D8 is not built, a core splices those pieces into its own tables
(settings, tasks, file actions, the media slot, the ROM); the library is compiled into the application, not loaded (`libload` is not wired to the board
for any library). The names, arguments and state of D15 stand where listed below.

**Source.** Gideon's `c1541.cc`, `disk_image.cc`, `wd177x.cc` and `mfmdisk.cc`, read from the code. Kept: the register sequences of an insert and a remove
(the drive is not stopped by the menu while the disk changes; the sensor is covered 150 ms; the swap delay), the parameter RAM layout (two words per half
track: DDR2 address; `length - 1 | bit time << 16`), the dirty-flag protocol (`DR_DIRTY`: read b7 any, b0 this track; write b7 clears "any", otherwise this
track; a track still being written is skipped), the GCR track layout (5 sync bytes, header, 9 gap bytes, data block, zone gap, the track twist 2700, the
error bytes 2, 3, 4, 5, 9, 11), the decoder's walk over a track and its status codes, the `.g64` format, the WD177x command handling with its DMA
buffer. Changed: the 4-to-5 byte code is software (a 16 entry table), so **no GCR_CODER page is needed** (deviation from T104.2 D9.1, which listed it);
`CoreFile` for `File`; no popups, a call returns a sentence; the bounded waits; no drive sounds (`drive_l2` leaves `audio_sample` open); the interrupt of
the WD177x became a poll of the FIFO flag (`irq_ack` b7, the same flag that drives `io_irq`, `cores/c64u/gideon/wd177x.vhd`).

**Operations** (all under the contributor `cbm1541`; `slot` is `iec:drive_a` or `drive_a`, anything else is refused with the slot the core has):

| Operation | Arguments | What it does |
|---|---|---|
| `drive.mount` | slot, path, mode `rw` / `ro` / `unlinked` | `.d64` / `.g64` (1541) or `.d81` (1581, no `unlinked`). Opens the file (a read-only medium or `ro`: write protected, sensor covered), switches the drive type and its ROM when the image needs another, unfreezes the drive, takes the old disk out, converts the image to GCR (a `.d64`) or reads it (a `.g64`), points the head at the tracks, announces the change. A disk that holds changes no file has is not left silently (see eject) |
| `drive.eject` | slot | writes pending tracks, then removes the disk. **Ask twice**: a disk with changes that are in no file (an unlinked disk written to, a write that failed) is refused once with a sentence; the next `eject` or `mount` throws the changes away. This replaces Gideon's "Save?" popup |
| `drive.save` | slot, path, format `d64` / `g64` | `.d64` decodes the GCR (error bytes kept when a sector does not decode), `.g64` aligns every track to sector 0. Never over an existing file; a bare name goes to the usual folder. Empty path or a folder: a free name `<disk>_saved.d64` in the folder of the last disk, then the media in the order `/usb0 .. /usb3 /sd`. Not for a `.d81` (the 1581's sectors are written to its file as they come) |
| `drive.create` | path, format `d64` / `g64` / `d81`, name | a blank formatted image (`NAME,ID`, 35 tracks / 80 tracks), never over an existing file; empty path or folder: `blank.d64`, `blank2.d64` ... as `save` |
| `drive.reset` | slot | device number, power cycle |
| `drive.set_rom` | slot, path | a 16 or 32 KB file as the ROM of the drive type now in the drive, for this session (the ROM manager's `put_rom` replaces it at the next boot or Reload) |
| `drive.mount_run_file` | slot, path inside an image, how `dma` / `load` | **Mount & Run** / **Real Run** of one PRG inside a `.d64` / `.d81` (5.7.1) |
| `drive.mount_run` | slot, path | **Run Disk** (the menu's name): mount read-write, then the core's `type_op` (`CoreDesc::type_op`, new): reset the machine and, at READY, type `LOAD"*",<id>,1` and `RUN` into the keyboard buffer in pieces of at most ten keys, each only after the machine took the one before. Refused (machine not touched) when the drive is off or has no ROM |
| `drive.put_rom`, `drive.put_rom1581` | data | what the ROM manager gives (`RomSpec` `1541.rom`, `1581.rom`, optional): written to the drive's ROM area, the drive resets |
| `drive.set_power`, `drive.set_bus_id`, `drive.set_ram`, `drive.set_swap_delay` | value | the four settings of D15 (`Drive`, `Drive Bus ID`, `Extra RAM`, `Disk swap delay`), live |
| `drive.poll` | - | the drive's service: tracks the head wrote go back into the image file, the 1581's commands are answered. It rides on the core's own service operation (the descriptor has one), now every 20 ms |

States: `drive.drive_a.image` (the file name, empty when no disk) and `drive.drive_a.mode` (`rw` / `ro` / `unlinked` / `empty`); a name has no `:`, so
the `$slot` of D15 became `drive_a`. Write-back: `.d64` rewrites the track's sectors in the file (the error section is kept), `.g64` rewrites the track
with its length field, `.d81` is written sector by sector by the controller. A write that cannot reach the file (read-only medium, track not in the

### 5.9 The remaining parts built (branch `t104-1-rest`, Claude, 2026-10-26, after Alex's answers to the questions of 5.8)

Alex, 2026-10-26: contributed settings stay in the one `.cfg` section; hide and rename reach settings and file actions; every core registers its own memory
operations and the RPC door follows the TRX64 runtime contract; no authentication; "Yes do it, nothing out" for the `svc` table, the TOML sibling for a library's
own record, contributed tabs, `$slot` and the library poll. What is built, and where it differs from what was asked:

**A. hide / rename by id for settings and file actions.** The id of a setting is its key, of a file action its label (a node keeps `id`, else its operation or state).
`hide` removes it before it is checked; `rename` gives a setting another key (which is also its key in the `.cfg`, the one section) and a file action another label.
A renamed key that collides with a taken one is refused by name.

**B. The memory of every core: `machine.read_mem(address, length)` and `machine.write_mem(address, data)`** (`memops.h/.cc`). Each core's contributor registers the
pair with its own address width in the range of `address`; `MemMap` per core (a static of its `.cc`) lists regions of three kinds, taken from the windows the
core's own code already uses: the base RAM window (`ram_read` / `ram_write`, with `C64_DMA_MEMONLY` on for the C64 family and put back), the same window
through a page register that is put back to 0, and the DDR2 window at a base. A read comes back **with the result** (`OpResult::data`, at most 256 bytes; REST and
RPC show it as `"data"` base64), a write takes **hex text** (two digits a byte, 127 bytes at most): a blob is still never an argument. An access lies inside one
region and does not wrap. Where the application cannot reach the memory, the pair answers `OPE_UNSUPPORTED` and says why.

| Core | Address width | Memory the pair reaches | Source of the window |
|---|---|---|---|
| C64 (`TRX2`), VC-20, C264 | 16 bit | the 64 KB RAM window, RAM only (`C64_DMA_MEMONLY` on during the access) | `cold_ram_bytes 0x10000` of VC-20 / C264, T104.2 D6 |
| Atari 800 XL | 16 bit | the 64 KB the 6502 sees (extra RAM above 64 KB, `A8_W_RAM`, is not mapped: its layout is not stated in the code) | `atari800_regs.h` |
| Apple //e | 17 bit | main RAM 64 KB in the window; aux RAM 64 KB in the DDR2 window at `A2_W_AUX` | `apple2_regs.h` |
| ZX Spectrum, Amstrad CPC | 17 bit | 128 KB through the 64 KB window, `*_WIN_PAGE` b0 picks the half | `zx_regs.h`, `cpc_regs.h`: "b0: the 64 KB half of the RAM window" |
| ZX Spectrum Next | 21 bit | the machine's 2 MB at `ZXN_W_RAM` | `zxnext_regs.h` |
| NES | 16 bit | **not reachable**: the DDR2 window holds the cartridge image, not the CPU's RAM | `nes_regs.h` |
| Amiga 500, 1200 | 24 bit | **not reachable**: chip and slow RAM are the core's SDRAM | `amiga_regs.h` |

Not verified on a board or in the gateware: whether each window shows what the code assumes (the model in `test_memops` is the code's own assumption). The Atari's
extra RAM, the Amiga's and the NES's memory are the open reaches; they need a window in the gateware, not code here.

| Answered | How |
|---|---|
| `ping` | `{runtime_version:"trx64-runtime/2", version:"coreapp <v>", backend:"coreapp", core, project:null, idleExit:null}` |
| `daemon/keep_alive` | `{armed:false}` (a board has no idle exit) |

**The gap against C64RE**, written as the list a person acts on: (1) keys and joysticks have no operation on any core (the 9); (2) the debugger and trace are `trxmon`'s, not
this application's - C64RE reaches them on a core that runs `trxmon`; (3) the ring needs the T20 engine; (4) `session/state` has no cpu/vic/drive panels, `c64Cycles`, `pc` and
`rasterLine` are null; (5) `read_memory` has two lenses of the daemon's five (`ram|io|cpu|rom|cart`) and 6 KiB a call; (6) the A/V binary frames are not served;
(7) notifications `debug/*`, `audio/flush` are not sent (events here are the registry's, `service.subscribe`). Not verified against a running C64RE.

**D. Contributed tabs** (`LibTabDecl`, `LibRecord::tabs`; `[[tab]]` of the TOML): the route is copied into the merge's own storage and a tab is appended to an area
after its own, with the next free printed number (above every number and every place in the area, so published numbers never move); refused by name when the area is not
on the route, the id is taken, the number is taken, or the area has six tabs (the strip's room). Tabs are merged before nodes, settings groups and polls, so all of them can
use a contributed tab.

**E. `$slot` per media slot (D15).** A core's slots are its capabilities named `drive_<x>` (T104.2 D3 already lists `drive_a`); no descriptor field was added. A node, setting
or file action that has `$slot` in a label, anchor, key, group, operation, state, condition, id or text binding is made once for each slot with `$slot` replaced by its name;
a core with no slot gets none (not an error); a declaration without `$slot` is made once. Hide and rename act on the expanded ids.

**F. The poll of a contributor is served.** `LibPollDecl` of a library record, or `[poll]` of a description or menu record, becomes an entry of `MenuMerge::polls` (the operation
has to exist and take no argument; the period is 1 .. 60000 ms) and `run.cc` starts one `PollTask` for each (service.h: own task above the menu's, the core lock, none while
the machine is frozen: `poll_when_frozen` is gone, as decided on 2026-10-20).

**G. A library's own menu record (the TOML sibling of D9).** `tools/u2a_pack.py --menu menu.toml` carries the nodes, file actions, settings, tabs and poll of a file as the
record of `descrec.h`, behind the manifest: header flag bit 0 and the `reserved` word (its file offset). `libmenu.cc` reads it before anything is spent (a refusal by name
for a bad offset, a damaged record, or one that gives a route or hides or renames what others contribute), the slot keeps it, `bundle_merge` makes it a second contributor of
the same name and rank. What a file's operations, states and events are stays code (`lib_register`): they are handlers. **The record format changed in place (it was never
shipped):** header 136 bytes, a twelfth table (contributed tabs) and the poll words at offset 120.

**H. The `svc` table of ABI 3 is T104.3's** (`docs/specs/done/T104.3-applications.md` D2, branch `t104-3-app-ui`, `coreapp/src/libapi.h` there): `sys`, `mem`, `ops`, `fs`, `job`
(and `ui`, which T104.3 D0 reworks into a declarative description). This branch defines **no second layout**. What T104.1 D3 asked of the table and T104.3 has: `ops.call`
and `ops.state`. What it lacks: `ops.subscribe(event, fn, user)` (D2 of T104.3 lists it, the struct does not have it) - the registry's `subscribe` is there to wire it. The
changes of this branch are kept mergeable: `LibNodeDecl`/`LibRecord`/`LibInfo` grew at their tails, the new logic is in new files (`libmenu.*`, `contrib.*`), and `libload.cc`
has three small hunks (header flags, the menu record, `discard`). Merging `t104-3-app-ui` into this branch has not been done; it is the coordinator's call.
