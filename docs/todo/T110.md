Milestone M3, status 📅. Open (one line, as in the TODO table): bitstream.yml:92-95 decide it for host and cores (jtag_dbg out, was T46); the rebuild moves host_pin

Alex, 2026-10-16 (translated): "we have reSID 8". We decided it (ADR-0037, T25.4 §3.3, T25.5 §1) and
`cores/trx64/core.toml` even writes down that `TRX_SID` must stay unset for it — but no build has ever
been made that way. `.gitea/workflows/bitstream.yml` carries the T79 trial's environment, and nothing
reads `core.toml`'s `features`, so those lines are the whole truth about every bitstream in this
repository:

| line | value | consequence |
|---|---|---|
| `:87` | `TRX_SID: redip2` | `SID_REDIP` instead of `SID_MULTI`, so `sid_resid8 = 0` (`cores/trx64/c64_core.v:885-889`), `caps3` b0 clear (`layer2_trx64.v:483`) and the application offers Gideon's menus, not reSID8 with Dag's curves |
| `:88` | `TRX_FEATURES: jtag` | host: `NO_UCI`, `NO_STREAMS`; every core: `NO_REU`, `NO_SAMPLER`, `NO_TURBO` |
| `:89` | `T79_GREYBOX: "1"` | the trial's grey-box partial is written as well |
| `:90` | `T79_FLOOR: B` | the compact core region of the trial |

**Measured, not inferred.** The run that built the host image on the board (`0e8fb06e58872c33`, run 828
job 4839, 2026-10-14 21:11) printed `=== SID: reDIP` and `=== features off: reu sampler uci turbo
streams (TRX_FEATURES)`. The override entered with `dd15aaf5` ("T79 measurement: build integ-m1 with
the two-SID reDIP instead of reSID8") and was never removed.

**The monolithic line does not have this problem.** On `integ-m1` (`designs/c64_basic/build.tcl:79-82`)
`TRX_SID` is unset and its workflow sets nothing, so it builds `SID_MULTI` = reSID8, and Alex accepted
that on the board himself with Tuneful Eight and Sander's demos - all of it before MultiCore existed.
So this is a **regression MultiCore inherited**, not an open question about whether reSID8 works.
(Note for whoever checks: `TRX64-Ultimate`'s `main` is a documentation branch and still carries the
pre-T25.4 recipe. Reading it instead of `integ-m1` is what produced the wrong claim in the first
version of `docs/layering-map.md`.)

**There is nothing to port.** The reSID8 sources here and in the monolith's accepted build are the same
code: `vendor/icepi/c64_redip_sid/sid_multi.sv` against `cores/icepi/c64_redip_sid/sid_multi.sv` on
`integ-m1` differs in one comment line (a path), and `trx_sid.v`, `trx_audio.v` and `trx_sid_engine.v`
differ in comments only - 0 code lines across all four (diff, 2026-10-16). So the whole question is the
build line and the area it costs, not the engine.

**Area is exactly the obstacle, and that is why it went out.** Alex, 2026-10-16 (translated): "it was
out here because back then it needed MORE LUTs." Correct, and a claim in the first version of this file
said the opposite because it read only the *logic LUT* column of T25.4 §157-161 and ignored SRL and
LUT-as-RAM. The full rows, yosys, 15-25 % above Vivado:

| build | logic LUT | SRL | LUT as RAM | FF | BRAM |
|---|---:|---:|---:|---:|---:|
| original reDIP, 2 SIDs | 1,511 | 172 | 0 | 929 | 6.5 |
| `sid_api` NS=2 (what we build) | 1,557 | 172 | 24 | 907 | 6.5 |
| `sid_multi` NS=8 = reSID8 | 1,501 | 173 | 136 | 2,058 | **4.0** |

T25.4 §166-169 says it in words: "+127 LUT incl. SRL/RAM, +8 %; scaled to Vivado about +110 LUT over
today's 1,454", with 2.5 BRAM tiles freed and FF +1,130. The SID is in `core_synth`, so those LUTs land
in **layer 2**, which is the tightest partition we have: the reference core measures 14,103 of 18,000
(78.35 %, run 35) and 78.35 % is also the highest that has ever routed. +110 LUT puts it near 79 %.
BRAM goes the other way, 39 -> about 36.5 of 50.

UCI plus the streams are the host's side: about +740 LUT (211 `uci_unit`, yosys T28; 528 streams, run
275), never measured on the current host, which stands at 76.96 % LUT and 21 of 25 BRAM.

One more thing to fix with the build, not before: `cores/trx64/core.toml`'s note claims reSID8 "costs no
area" on the same logic-LUT-only reading. It is wrong and has to go in the same change - editing it
alone moves the core's cache key (`git ls-files -s` over `cores/trx64`, `ci/lib.sh:56-64`) and forces a
re-route of the core and, because it is the reference core, of the host.

What has to be decided, because it is not ours to decide: a rebuild makes a **new host image**, so it
moves `contract/host_pin.txt`, and Alex's rule is that no core work touches the host. This is the same
question as T103 Q1, and it is one question for all of it, not one per feature.
