## Next board session (the switch to the run-813 host)

Everything is in the generic package `trx64-ultimate/main-9eeedabb` and in `/USB1/cores-813/` on the
stick. The order below loads the new host into SRAM first, because the flash's app half is the open
question: the app at 0x220000 is the lean host app built by hand in T84 against the run-406 host, and
the CI does not build that app yet (P4). The boot ROM only starts the flash app when the flash
bitstream carries the running bitstream's stamp (T15), so a host written to 0x0 pairs the new host
with that old app, and nothing proves it fits.

1. **Host into SRAM, no flash write:** `tools/load.sh` / `openFPGALoader -c usb-blaster -m c64_basic.bit`.
   The boot ROM then waits for a JTAG app, so no flash content is touched and a power cycle with the
   Blaster unplugged brings back today's board.
2. **The host app over JTAG** (`tools/trxdbg.sh riscv <app> follow`) and watch its console: does the boot
   menu come up, does it find `/USB1/cores-813/*.cor`, does an ICAP start work? `host-app/` has the
   sources and `host-app/target/u64ii/riscv/hostapp/Makefile`, no binary is built here yet - building it
   is P4 and the first thing to do in that session if the old app does not run.
3. Only when 1 and 2 hold: `openFPGALoader -c usb-blaster --fpga-part xc7a50tfgg484 -f c64_basic.bit`
   (flash 0x0), then the matching app to 0x220000, then rename `/USB1/cores-813/` to `/USB1/cores/` and
   check `/Flash/boot.cfg` (`default=` is a 0-based index). Alex unplugs the Blaster and power-cycles.

Restore point if step 3 goes wrong: package `trx64-ultimate/t85-amiga-787d8efc` holds the run-406
`c64_basic.bit`; the old bundles are still in `/USB1/cores/`.

## Open points that are Alex's, not mine

- The key fix of D13 invalidates the host and every core once: Alex accepted that rebuild
  (2026-10-14, "as long as the host is immutable afterwards until we change it ourselves - fine!").
- Every later host change needs his explicit approval, then `tools/host_pin.sh --update`.
- **Does an update file carry a core?** The manifest of T49 has exactly two blobs, bitstream and app, and
  no core in the flash was Alex's decision of 2026-10-03. Today's bundle therefore installs the host with
  the TRX64 core inside its bitstream and ships the other cores as files for `/USB1/cores`. If a `.cor` is
  to live in the flash drive (so the menu has cores without a stick), the manifest needs a third blob and
  the updater code the matching case.
