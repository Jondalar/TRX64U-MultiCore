# T67: App registry keeps the old path when a .u2a file is replaced

Milestone M1, status ✅. Open (one line, as in the TODO table): –

## Description

App registry keeps the old path when an app's .u2a file is replaced (/Flash/config/apps.json; found 2026-10-06 by Alex): the entry is not updated, delete + reinstall needed. Fix in the app's registry (replace = update the path); not built.

- **2026-10-09, crash cause found by reading the code (app t67-refresh-app 5bce2a4c): stack overflow of the HTTP listener task (1600 words = 6.4 KB, `configCHECK_FOR_STACK_OVERFLOW` 0).** `PUT apps/{id}:run` -> `lookup_fresh()` -> `refresh(false)` kept a 1304-byte `AppManifest` on the stack in the route (`route_apps.cc` copy), `refresh()`, `lookup_fresh()` and `scan_flash()` (plus `app_read_manifest`/JSON parse), and only a changed manifest goes on to `save()` (JSON tree, render, FatFS open/create/write on /Flash) on top of that. The overrun corrupts the heap block below the stack (queue/TCB), so REST still answers and a task dies seconds later in `xTaskRemoveFromEventList` (tasks.c:3112, `configASSERT(pxUnblockedTCB)`) or jumps to 0. The boot refresh runs on the big init stack, hence fine. Not the suspects `update_tasks()` (returns early while the task menu was never opened) or freed strings (`AppManifest` is plain chars, no pointers). Fix: scratch manifests on the heap (`ManifestBuffer` in app_registry.cc, heap copy in the route); refresh itself unchanged. Spec 3.5 point 4. Not measured (no stack watermark in this build); board proof = `tests/t67_board.py` all cases incl. 4b.
- **2026-10-09, board test (autonomous, package main-acbd9c35 = CI run 589, app with fix 1bf7c968; script `tests/t67_board.py`, test apps built from the board's own restcheck.u2a with other manifests; /Flash/apps and apps.json saved first and put back afterwards, byte-identical; only FTP/REST, no raw flash, no configs:save_to_flash): spec 3.5 cases PASS, one case FAILS with a crash.** PASS: (1) /Flash/apps/restcheck.u2a replaced by a build with version 9.9 + another REST action, app restarted: entry keeps its path, registry shows 9.9 and the new action, `restcheck:run?action=echo` runs; (3) a new .u2a in /Flash/apps is registered at boot without popup; (2) a registered /Flash entry whose file was deleted is dropped at the next boot; (4a) entries on /Temp and on a medium that does not exist stay at boot; (4c) entry on a medium that is absent (`/USB9/...`): `PUT apps/{id}:run` answers 404 "medium not present", entry kept (the real USB stick was not touched or pulled; absent medium simulated with a path on an unmounted drive); (5) truncated .u2a of a registered app: 409 "app file incomplete or invalid", entry kept, the restored file runs again; (4b first half) an entry on /Temp with its file present runs. **FAIL (new bug):** any refresh at runtime that finds a changed manifest crashes the app a few seconds after the call. Reproduced three times, also without a launch: replace /Flash/apps/restcheck.u2a (version 1.0 -> 9.9, or back) over FTP and call `PUT apps/restcheck:run?action=echo` (REST answered 200, the registry line `AppRegistry: manifest of restcheck changed` and `6 app(s) after refresh, changed` were printed) or `PUT apps/nonexist:run` (404 "registry refreshed"): then `ASSERTION FAIL ... FreeRTOS/Source/tasks.c:3112` (twice) or a GURU MEDITATION at address 0 (once), network gone, board hung. The same manifest change handled by the boot refresh (`refresh(boot)`) is fine, as is a plain run without a changed manifest (3 runs in a row), so the fault is in the runtime path `refresh(false)` after the changed-manifest branch (`save()` / `update_tasks()` from the HTTP task; `update_tasks` returns early while the task menu was never opened, so `save()` or the context is the first suspect; not proven, no code read beyond app_registry.cc `refresh`). Hence the case "launch uses the new file" (4b) is unproven and the row stays open; the script runs it last. After each crash the bitstream has to be loaded again before the app starts (a second app start on the same bitstream asserts in heap_4.c during init); the script does that.
