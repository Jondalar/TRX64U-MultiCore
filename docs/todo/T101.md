- **2026-10-16, board: "Add core" says "cannot read the file".** Found in the code, not guessed.
  `cor_abort` is a file-scope flag that `cor_read_part` checks per chunk and answers with
  `COR_ERR_IO` (`cor.cc:252`), whose text is "cannot read the file" (`cor.cc:13`). Only
  `core_stage` clears it (`coreboot.cc:61`), and only `part_progress` sets it
  (`coreboot.cc:34-38`) when the caller's callback asks to stop. **So after one aborted core start
  the flag stays true**, and `add_bundle` - which never clears it and passes no progress callback
  (`hostui.cc:1352`) - fails on the first chunk of the first part with exactly that message, for
  every bundle, until the next core start resets it. Fix: clear `cor_abort` where a read begins
  instead of where a stage begins.
  Two other paths print the same text, and the message is wrong in both: `add_bundle`'s
  `malloc(big)` returning NULL is reported as `COR_ERR_IO` (`hostui.cc:1349`), and `big` is up to
  **1,519,496 bytes** (the trx64 bundle's partial; the seven range 1,319,164-1,519,496, measured
  from the manifests in `dist/trx64mc-main-0279c207`), which is a large single allocation for a
  verify pass that hashes chunk by chunk anyway and only needs `dst` to grow because
  `cor_read_part` writes at `dst + done`. And a genuinely unopenable path (the known USB1
  visibility delay) gives the same line.
