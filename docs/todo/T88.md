# T88: Atari 800 XL core

Milestone M3, status done. Open (one line, as in the TODO table): Done: the core runs; media (disk, .xex) continue in T108 (closed 2026-10-28, Alex)

## Description

An Atari 800 XL (PAL) core in layer 2 of the T79 host/core split, fourth in the order of the cores. Source: Mark Watson's
Atari800 core as in `MiSTer-devel/Atari800_MiSTer` (MiSTle-Dev has no Atari 800 core; the Tang Nano port by carlosbravoa is a
third-party reference). Non-commercial licence: TREX-internal only. 64 KB in block RAM, RAM above 64 KB and cartridges in DDR2,
picture through the host's pixel layer, ATR disks served by the app over the SIO bridge, Freeze like the C64. Spec:
[T88-atari800-core](../specs/done/T88-atari800-core.md).

## Board session 2026-10-16: the disk path is unproved, and it does not work

Alex put a real disk on the stick (`boulderdash.atr`, a valid ATR: magic 0x0296, 128-byte sectors, 184
of the 368 sectors its header declares - `atr_geometry` takes the smaller number, so it never reads past
the file). Mounted to D1:, **Cold start** pressed, and the screen showed `READY.` - Atari BASIC.

That word is the diagnosis: an XL asks D1: over SIO at a cold start and falls into BASIC when nothing
answers in time. So the boot request was never answered. The application's SIO handler has benches, but
they run our model against our model; between it and POKEY's serial port there is no test at all
(`sim/machine/run.sh` knows boot, cart8, cart16, cartmax - no disk mode).

Also found: there is no way to switch BASIC off. The settings are RAM, video, joystick ports and CPU
speed (`atari800.cc:36-41`); the console keys exist in the core (`a8_core.vhd:259,292`) but come from
the keyboard, so nothing can hold OPTION while the OS looks for it.

Alex asked for a spec: [T108](../specs/T108-atari800-media.md) - disk, .xex and cartridge, each with the
bench that proves it.

**The picture is not an open point.** Measured 2026-10-16: the core draws 384 x 288 at scale 3 = 1152 x
864 (`coreapp/cores/atari800.cc:161`), which is 60 % x 80 % of a 1080p frame, and scale 3 is the pixel
layer's ceiling (`host/pix_layer.v:63`). At 720p the picture would have to drop to scale 2, 768 x 576 -
the very same 60 % x 80 %, with fewer real pixels. So 1080p is already the right mode for this core,
unlike the NES, whose 224 lines at scale 3 fill only 62 % ([ADR-0057](../adr/0057-every-application-owns-the-video-mode.md),
[T107](T107.md)).
