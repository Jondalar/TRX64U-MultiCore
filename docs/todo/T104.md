# T104 — one generic application, described by each core's own bundle

Milestone M2, status done. Open (one line, as in the TODO table): Done: generic app on every DFX core; Reload core and fast seek seen on the board (Alex)

Decided with Alex on 2026-10-15, in one sitting, after the evening had shown what the fork costs: the five
machine applications (trx64, vc20, c264, amiga, amiga1200) are branches of Gideon's whole Ultimate
application, 283 commits above `trex/main` for the VC-20 line, built by hand on a Mac and uploaded into a
generic package. Moving that fork here was tried and abandoned the same night (spec D7).

The target, in his words: "Am ende eine generische App die nur mit einer Config läuft, alle Cores die
Selbe App Grunde." The spec is [T104](../specs/done/T104-generic-core-app.md).

## The decisions, short
- **Gideon's code is a library** - FreeRTOS, USB, SD/FatFS, file system, flash, lwIP/FTP, ITU. Not his UI,
  not his menus, not his machine classes. (D1)
- **Three layers; no per-core code without proven need, shared behaviour lives in libraries** (D2, D3; wording
  PROPOSED 2026-10-20, it replaces "the middle one is meant to be empty"): file formats are a library in the
  application (a `.hdf` loader serves the A500 and the A1200, `.d64` serves three machines), the
  description travels as a versioned record in the `.cor`, and a core module exists only for a live
  protocol that cannot be declared.
- **Two binaries on one base** (D4): the host rescues Alex from a broken core, so it does not move when a
  core application changes.
- **Every core, the C64 and TRX64 Ultimate too, leaves Gideon's application** (D9, 2026-10-18; it
  supersedes D5): menus result from settings, a declarative description, libraries and apps; libraries
  load dynamically; the application lives here; TRX64-FW builds it on its own branch, we review and merge.
- *Before D9:* **the C64 kept Gideon's application** (D5), with the application-loader ABI as the path that
  brings it over later (D6) - the same ABI the rare core module uses, with a different lifecycle: a module
  is a record in the `.cor`, loaded when the core is, registered with callbacks, never unloaded.

**Nothing is written from scratch (D8).** Two applications exist; T104 merges them. Reuse is the default,
and the two rebuilds have reasons: the descriptor becomes data, and the two view layers become one.

## What has to happen, in order
**Taken by the TRX64-FW session (2026-10-18, D9.6)**, clone `TRX64U-MultiCore-fw`, branch
`t104-generic-app`: the contribution-model spec T104.1 (registration by libraries and apps, the
declarative format, the service API, fit with the u2a ABI and D3), then step 2, then the 1541/IEC
library with GCR (§5.4). Nobody else picks these up; we review and merge.

1. The shared base as a library, the two main programs on top; the host application moves onto it
   unchanged in behaviour.
2. The descriptor format: written down, packed by `tools/cor_pack.py`, validated there, refused by the
   application when it cannot serve it. Bigger than it looked: `desc_check.cc` requires a C hook in
   every structure, so it is rewritten around named operations first (§5.3).
3. The loader library in the order of §5.6; the CBM PRG loader first, because it blocks two cores.
   The view layer is rebuilt against the LVGL prototype in `TRX64-Ultimate/docs/lvgl_ui_project/` and
   `lvgl_ui_terminal/` (§5.8): same canvas, 960 x 540, one navigation grammar, two skins.
4. The VC-20 first: its descriptor beside the old build, the menu walk of S7 compared on the board.
   It needs the 1541 library (§5.4) and a `CoreIo` port to the drive and GCR pages.
5. Then c264, amiga, amiga1200 - each one descriptor, each one board walk.
6. `ci/trxapps.sh` builds two binaries and no machine application any more; `trx64.app` is the only one
   left in the uploaded package.
7. The fork repository and its worktree go (D7). Done on 2026-10-15.

## Board session 2026-10-16

Alex, with the NES core: "App startet mit dem Core, super / Menü sieht erstmal gut aus / Bedienbarkeit
ist grottig, gefühlt 0.5-1 sek Verzögerung nach Tastendruck. Schau in die Host-App, da ist es nicht
perfekt aber besser." (translated: the application starts with the core, the menu looks good, but
operating it is dreadful - half a second to a second after a key; look at the host application, it is
not perfect there but better.)

Cause, read out of the code: the key loop is not at fault - it collects every queued key and draws once
(`run.cc:290-324`, 10 ms tick), the same shape as the host's. The drawing is. Every key goes through
`ui_menu_render()` -> `trx_shell()` -> `lv_obj_clean(g_content)` (`trxview.cc:183`) and builds every row
again as new LVGL objects, so the whole content pane is invalidated and pushed through the pixel layer.
The host application instead restyles two row objects on a selection move (`hostui.cc:1596-1604`) and
rebuilds only when the list itself changed. The comment at `run.cc:292` claims the two loops are built
the same way: true of the loop, false of the draw path.

**Built the same day.** `trx_row_at()` returns the row object and always builds the marker bar hidden,
`trx_row_select()` flips background, marker and value colour in place, and `trx_shell_same()` says
whether the frame would stand. `ui_menu_render()` keeps the window's rows with a signature over
everything in the pane that is not the selection (title, status, window, every row's text and active
flag); an equal signature plus a moved selection restyles two rows and returns. The rows are forgotten
wherever the screen is cleaned (`ui_menu_visible(false)`, `ui_message`, `ui_message_clear`).

Measured in `tests/coreapp/render` (the counter is the host's `inv_pixels()`, now in both benches):
**one key invalidates 52,768 px instead of 355,656** - two rows of ~36 x 864 instead of the whole pane -
the frame is not rebuilt (`trx_shell_frames()` unchanged) and `ui_cheap_moves()` counts the move. A row
whose text changes (a setting's value) still rebuilds, as it must. Control `UI_NO_CHEAP_PATH=1` compiles
the path out and fails 3 of the 5 checks.
