# T96 — SNES core in the host/core split

Milestone M3, status ✖. Open (one line, as in the TODO table): Dropped from the list (Alex, 2026-10-18)

Added to the core list by Alex on 2026-10-13: "SNES too if it works, though the buttons need looking at there, or USB
gamepads like 8BitDo's help then" (translated). The list and the reasoning are in [T79](T79.md).

## What has to be answered before it is built
- **Does it fit?** This is the first question, not an assumption. The partition is 18,000 LUT and 50 block RAM tiles,
  and the reference core already uses 14,103 LUT and 39 tiles. An SNES core with its coprocessors is well above the
  small 8-bit cores we have ported, so the spec starts with a measured estimate: out-of-context synthesis of the
  candidate core for the XC7A50T, then the decision whether its RAM can live in DDR2 (as T89 plans for the Apple's
  aux RAM) and what has to be left out. If it does not fit, that is the answer and it stays off the build list.
- Which core and its licence, file by file.
- Controllers: eight buttons plus the shoulder buttons do not fit the C64U's joystick ports; the way in is a USB pad
  through the host's `usb_hid_host` and the contract. Mapping open.
- ROMs and cartridge images never go into the repository, the CI or a `.cor`.

## Decided on 2026-10-15 (Alex): not as a layer-2 core

Alex, after seeing the numbers: "fine by me .. so SNES only as a single core with the full flash, if
at all" (translated). So the SNES is **off the partition**: it is not built as a `.cor` under the
host, and it is not part of the release set. If it is ever built it is a bitstream of its own that
owns the whole chip, written to flash 0x000000 in place of the host, with the updater or a USB
Blaster as the way back.

The numbers that decided it, taken on 2026-10-15:

| | Analogue Pocket | this board |
|---|---|---|
| FPGA | Cyclone V 5CEBA9, 301,000 LE | XC7A50T, 32,600 LUT6 |
| available to one core | ~49,000 LE (Analogue's openFPGA documentation) | **18,000 LUT** (`pb_l2`) |
| block RAM | ~14.25 Mbit = 1.7 MiB | 75 tiles on the chip, **50 for the core = 225 KiB** |
| memory beside it | the Pocket's own SDRAM | DDR2 through the host's window |

Block RAM is what kills it in the partition, not logic: the SNES needs 128 KiB WRAM + 64 KiB VRAM +
64 KiB ARAM + OAM/CGRAM, about **257 KiB against the partition's 225 KiB**, before a single line
buffer. VRAM cannot move to DDR2 (several accesses per pixel). Whole-chip it is a different sum: 75
tiles are 337 KiB, and 32,600 LUT6 is roughly the same league as the ~49,000 LE a Pocket core gets -
which is why it runs there and MiSTer (~110,000 LE) has no trouble at all.

The partition cannot grow: the host is pinned (`contract/host_pin.txt`) and the floorplan is fixed.
