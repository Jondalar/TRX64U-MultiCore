# T107 — every application chooses its own video mode

Spec: [T107-application-owns-the-picture](../specs/T107-application-owns-the-picture.md).

Milestone M1, status 🔨. Open (one line, as in the TODO table): D7/D8/D11 designed in T164 (host); Sony cause found (pixel repetition, §5); host app 720-wide UI open

Decided with Alex on 2026-10-16 while he tested the NES core on the board:
[ADR-0057](../adr/0057-every-application-owns-the-video-mode.md). T105 gave the mode to the host; this
gives it to whoever is running, as Gideon's base does (`u64_config.cc:391`, "HDMI Scan Resolution", a
setting of the running application).

## Why it came up

Zelda on the board, 2026-10-16: the picture sits in a wide black border. Measured, not guessed - the NES
core already draws at the pixel layer's **highest** scale (3, `pix_layer.v:63`, a two-bit field), so
256 x 224 becomes 768 x 672 and fills 40 % x 62 % of a 1080p frame. At 720p the same pixels fill
60 % x 93 %. The side border is 4:3 content on a 16:9 screen and stays.

## What has to happen

1. `videomode.{h,cc}` moves from `host-app/software/hostapp/` to the shared application library under
   `app/`; both binaries link it. Its EDID path and `VIDEOMODE_NO_BOARD` stay as they are.
2. The bundle says what a core draws (native width, height, preferred scale). Packed and checked by
   `tools/cor_pack.py`, declared in `core.toml`. No core code for the first choice.
3. The core application applies its own mode after the hand-over: the user's setting if there is one,
   else the mode its numbers ask for. A later change at run time is allowed (Amiga PAL/NTSC, interlace).
4. The core application gets the mode as a visible setting, like Gideon's, so a person can override it.
5. **The host re-asserts its own mode when a core returns.** Bench: after a core that changed the mode
   returns, the host's registers hold the host's mode. Negative control: a build without the re-assert
   has to fail it.
6. The NES descriptor asks for 720p; the C16 and the Amiga from their own numbers. **The Atari stays at
   1080p** - measured 2026-10-16: 384 x 288 at scale 3 is 1152 x 864, 60 % x 80 % of a 1080p frame, and
   at 720p it would have to drop to scale 2 (768 x 576) for exactly the same 60 % x 80 % with fewer real
   pixels. The rule derives the mode from the core's numbers for this reason: a mode written down per
   core by hand would have made this picture worse.

- **2026-10-20, correction:** the layout is the 1080p layout in every mode (the host's frame is fixed, spec 5.6; Alex: "No, simply 1080p always", translated). Picture/Auto no longer move a pixel; real mode switching is a host change, open with Alex.

## Built (2026-10-16)

- `videomode.{h,cc}` moved to `app/video/`; both binaries compile it from there (`VPATH` in the two
  Makefiles, and every bench's include path).
- `video_mode_fits(w, h, allow_pc_modes)` picks the mode that shows a picture largest: it skips any
  frame the picture would be cut by, then takes the one whose **height** the picture fills best, a tie
  going to the frame with more pixels. 10 checks in `tests/hostapp/test_videomode.cc`, among them the
  two Alex saw: 768 x 672 (NES) wants 720p, 1152 x 864 (Atari) wants 1080p. Control `vm_always1080`
  still fails 5.
- `Video::wanted_hdmi()` asks it with the core's own numbers (`d_.w * d_.scale`, `d_.h * d_.scale`), so
  nothing is written down per core. Checked in `tests/coreapp/test_video.cc` against both descriptors.
- `coreapp/src/run.cc` applies it once the descriptor is known, keeping the handed-over system (PAL or
  NTSC), and says in the log what it changed and why.
- The host re-asserts: `hostui_run()` now calls `video_start()` **always**, not only when boot.cfg names
  a mode. Before, a board with nothing stored left `vid_hdmi` at -1 and whatever the last core had set.
  Checked in the render bench.

## Built (2026-10-16, second half)

- The "Picture" setting every core application has (Auto + six modes, `WHEN_LIVE`, kept in the `.cfg`), added
  to the core's own list at start-up (`coreapp/src/picture.{h,cc}`); `run.cc` takes the stored choice through the
  same layout path as a change at run time, so the NES at 720p sits at 256 / 24 instead of the 1080p position.
  Spec: `docs/specs/T107-application-owns-the-picture.md`. Bench `tests/coreapp/test_picture.cc` (200 checks, 15 controls).

## Open

- The board step: the NES at 720p, a choice through the menu and after a restart, the host back in its own mode.
- No confirm-or-revert timer for a mode the screen refuses (spec §4, to decide with Alex).
- Applications that are not the generic one (the Amiga, T102) need the same item.
- The numbers still come from the `VideoDesc` in the core table, not from the bundle (T104).
