# T128 - A folder on the stick/SD as an Amiga hard disk

Milestone M3, status in progress (built; board steps open). Open (one line, as in the TODO table): Board B1 passed 11-04 (A1200 boots a folder as HD0); B2-B6 open: write, delete, power cut, A500 KS 2.05/3.x

## Origin
Alex, 2026-10-24, while fast seek for disk images was being built: "Folder als hdf wäre auch noch gut!" ("a folder as an HDF would be good too!") -
an ordinary directory on the medium presented to the A500/A1200 as a hard disk (as a directory filesystem does), instead of an .hdf image.

## History

- 2026-11-04, board B1 (Alex, main-91f629ce, A1200): the A600 tree (`DH0_A600`, 14,271 files, on the USB stick) mounted as HD0 boots
  ("I can easily boot Horst's HD0 from USB", translated). Alex's reading: the folder itself is fine, the trouble is the unmount/mount.
  Tracked as GitHub issues #36 (mount not stored after reboot) and #37 (from discussion #35).

- 2026-11-04, GitHub discussion #35 (testers, release c83a83c2, A1200 with a folder as HD0): (1) above 1 GB the disk cannot be formatted or
  accessed from Workbench (another tester: 2 GB works); (2) the mounted folder is not kept as a core option after a restart (it was in earlier
  releases; confirmed by a second tester); (3) after about three ADF mounts in a row the next "Mount DF0" locks the machine for ~10 s (installing
  Workbench 3.2 onto the folder; confirmed); ejecting DF0 before mounting the next one helps; (4) some copies onto the folder fail with write errors
  (LOCALE during the install), not reproduced by the second tester. Alex asked to prepare the folder disk for this. Analysis on branch t128-d35.
- 2026-11-04, causes for issues #36 (mount not stored) and #37 (the four points), spec 5.7: (3) fixed - a floppy mount/eject folded the folder back
  synchronously (`win_eject` -> `sec_sync_all`), bench S11 6400 ms -> 0 ms, control fh_swap_sync; (1) no defect in the synthesis up to 8 GB, the 4 GiB limit
  of the Kickstart is the open question; (2) the mount was never stored by this app (decision); (4) `FH_SRUNS_MAX` 8,192 / `FH_CREATED_MAX` 4,096 reached between fold-backs (decision).
  Also: the mount job said "Building the image" (menuctl.cc 1106/1115), now "Mounting the folder".

- 2026-10-24: put on the list. Nothing built; approach (a filesystem handler on the Amiga side vs. a block device synthesised by the app) open.
- 2026-10-24, decision: the app synthesises a block device. Alex: "Die App erzeugt ein Blockgerät. So wie IEC bei Gideon." ("The app
  creates a block device. Like IEC at Gideon's.") - the folder is turned into a filesystem image on the fly by the core app, the
  Amiga sees an ordinary hard disk; no handler on the Amiga side.
- 2026-10-26: spec written, PROPOSED ([T128](../specs/T128-folder-hdd.md)); nothing built. Read from the code first: the gateware needs an RDB (`nanomig.v` 664-765:
  `RDSK`, cylinders/sectors/heads from longwords 16-18, CHS only), the sector service takes any `CoreFile` (`sectors.cc`), so the folder is one new `CoreFile`
  (`FolderDisk`) and no gateware change; Gideon's IEC is a file level protocol, only its principle carries over. Proposed: RDB + one FFS (`DOS\3`) partition computed
  on demand, data writes straight to the files, metadata in an overlay folded back at idle sync, heap caps against the 5,921,792-byte ceiling. 10 open questions
  (Q1-Q10) and 14 exclusion candidates (C1-C14), all for Alex.
- 2026-10-26, Q3 decided (Alex): the folder disk goes into both Amiga cores, the A500 core and the A1200 (spec Q3).
- 2026-10-26, Q1 decided (Alex): an Amiga delete deletes the host file; the Workbench Trashcan is a normal drawer (spec Q1).
- 2026-10-26, Q2+Q6 decided (Alex): folder and size in GB per unit set in the core menu, bounded by the medium (spec Q2, Q6).
