# T105 — the picture a board comes up in is not ours to decide

Milestone M1, status closed. Open (one line, as in the TODO table): Overtaken by T107 (the host stays at 1080p, each core picks its mode); mode choice moves to F8 (T139)

Found by a tester outside this house on 2026-10-16: he installed `trx64mc-main-51e89821`, power-cycled,
and got a black screen with the ethernet lights on. Alex: "Wieso bootet unser Test Host nicht hoch bei
jemand anderem?" The host was running the whole time. Our applications forced 1920 x 1080 at 50 Hz and
offered no setting, no key and no file to change it, and his screen does not show that mode. Another
HDMI screen was the whole fix - which is also what closed the diagnosis.

Spec: [T105](../specs/done/T105-video-mode.md).

## What is built
- `host-app/software/hostapp/videomode.{h,cc}`: the chooser (EDID over the HDMI DDC lines, the CEA-861
  Video Data Block), the packing for the hand-over, and the board half behind `VIDEOMODE_NO_BOARD` so
  a bench without firmware links the pure part.
- `boot.cfg` carries `video=<system>,<hdmi>`; -1 or missing means "ask the screen".
- `Handover::video` (what was `reserved`): the core application comes up in the mode the user just saw.
- `V` in the host menu steps the resolution, applies it at once and saves it; it is in the footer.
- `INSTALL.md` names the HDMI-only limit, the EDID choice, the V key and the boot.cfg line.

## What is measured
- `tests/hostapp/test_videomode.cc` 26 checks, control `vm_always1080` red as it must be.
- `tests/hostapp/test_bootcfg.cc`: the round trip and the refusal of values that are not modes.
- `tests/hostapp/render/render.cc`: V applies and saves, and comes back round (48 checks).

## Open
- The board step (in [board-tests-mc](../archive/board-tests/board-tests-mc.md)): a screen that lists no 50 Hz mode, and the V key on real hardware.
- The tester's board said **"no network"** in the top bar while its ethernet lights were on, so the FTP
  path would not have helped him. Worth its own look: whether that is DHCP timing or something else.
- The browser page and the REST interface are decided and built: [T106](T106.md), on `main` since
  97db9f39.

## History
- 2026-11-13, status check: header said IN PROGRESS; row/todo overtaken by T107; header now says so.
- 2026-10-28, TODO review (Alex: "Ja 105 zu"): closed, overtaken by T107 5.6; the mode choice is the F8 settings page of T139 (board step there).

- **2026-10-23, board (Alex):** V shows the new resolution in the note, the screen does not change. Cause (code): `video_apply`
  (`app/video/videomode.cc:233`) writes Gideon's mode registers (`SetVideoMode1080p`), but our host gateware puts out
  1080p at a fixed timing (`host/top.v:1313`, MMCM 148.87 MHz); only the system mode (50/60 Hz, `vmode`) reaches it
  (`top.v:1390`). So the EDID choice and V change nothing on the HDMI output. Making them work is a host change (frozen).
- **2026-10-16:** found by a tester, cause named the same night (hard-coded 1080p50 plus no analog video
  in the bitstream at all), fix built and green on the benches. The tester's board came up on another
  HDMI screen, which confirmed the diagnosis.
